--memory e --cpus — limites de recursos

A Ana subiu três containers no servidor da Loja Aurora sem limitar nada: a API, o banco e um worker de relatórios. Numa terça-feira à noite, o worker disparou um relatório gigante, consumiu toda a memória RAM do servidor e o kernel matou processos às cegas — inclusive o banco de dados. O site inteiro caiu. Esse é o problema do "vizinho barulhento": sem limites, qualquer container pode comer todos os recursos da máquina e derrubar os outros. Com --memory, --cpus e --pids-limit você isola cada container como se fosse uma máquina pequena.

Você vai aprender
  • Por que limitar recursos em produção (OOM killer, previsibilidade, custo).
  • --memory 512m e as unidades b, k, m, g.
  • --memory-swap (RAM + swap) e --memory-reservation (limite "leve").
  • --cpus 1.5, --cpu-shares (peso relativo) e --pids-limit (contra fork bomb).
  • O que acontece quando o limite estoura: Exited (137) e OOMKilled: true.
  • Como acompanhar o uso real com docker stats e declarar limites no Compose.

A ideia: cada container vira uma máquina pequena

Sem limites, o container enxerga toda a máquina: todos os núcleos de CPU, toda a RAM. É como morar num prédio sem paredes: o vizinho barulhento (um processo descontrolado) ocupa o salón inteiro e ninguém mais usa. Os cgroups (o mecanismo do kernel que o Docker usa por baixo) permitem criar "paredes": você diz "esse apartamento usa no máximo 512MB e 1 núcleo de CPU", e o kernel faz valer.

--memory: o teto de memória RAM

Defina o máximo de memória que o container pode usar. Se passar disso, o kernel mata o processo dentro do container (OOM kill):

$ docker run -d --name api --memory 512m -p 3000:3000 node:22-alpine node server.js
f3a1b2c3d4e5f6a1b2c3d4e5f6a1b2c3d4e5f6a1b2c3d4e5f6a1b2c3d4e5

As unidades aceitas são b (bytes), k (KB), m (MB) e g (GB) — maiúsculas também valem: --memory 512m, --memory 1g, --memory 268435456 (tudo igual; 268435456 bytes = 256MB). O valor mínimo aceito pelo Docker é 4m (4MB).

--memory-swap e --memory-reservation

Se você define só --memory, o Docker assume --memory-swap = 2× a memória (o container pode usar até metade do total em swap). Para desativar a swap do container, iguale os dois valores:

$ docker run -d --name api --memory 512m --memory-swap 512m …   « sem swap
--memory 512m
Teto duro de RAM do container (passou disso, OOM kill).
--memory-swap 1g
Teto de RAM + swap. Se for igual ao --memory, a swap fica desligada para o container (útil para bancos de dados, que odeiam swap).
--memory-reservation 256m
Limite "leve" (soft limit): o container pode passar dele quando a máquina tem memória sobrando, mas é o primeiro a ceder quando faltar (o kernel aperta primeiro quem tem reservation menor).

--cpus: o teto de processador

Um container sem limite usa todos os núcleos disponíveis. Com --cpus, você diz quantos núcleos (ou frações) ele pode usar:

$ docker run -d --name worker --cpus 1.5 node:22-alpine node worker.js
b2c3d4e5f6a1…

--cpus 1.5 = um núcleo e meio. --cpus 0.5 = metade de um núcleo. Para peso relativo entre vários containers na mesma máquina, use --cpu-shares (ex.: --cpu-shares 512 — padrão é 1024; na disputa por CPU, quem tem mais shares leva mais tempo de processador) e --cpu-period/--cpu-quota (controle fino de quota dentro de um período de 100ms).

--pids-limit: proteção contra fork bomb

Um processo descontrolado (ou malicioso) pode criar milhares de processos e travar o kernel inteiro — o famoso fork bomb. O --pids-limit trava a quantidade de processos dentro do container:

$ docker run -d --name api --pids-limit 200 --memory 512m --cpus 1 -p 3000:3000 node:22-alpine node server.js
c3d4e5f6a1b2…

Passou de 200 processos? O próximo fork() recebe erro. Barato de ligar, protege o host.

Missão: suba um container com limites — docker run -d --name api --memory=512m --cpus=1 nginx:alpine (no simulador, use = nas flags) — e depois veja ele rodando com docker ps.

Missão extra: com o container api no ar, rode docker stats e veja as colunas de CPU % e MEM USAGE / LIMIT — é assim que você acompanha se o limite está perto de estourar.

O que acontece quando o limite estoura (OOM kill)

Se o container tenta usar mais memória do que o --memory permite, o kernel mata o processo e o container para com código 137 (128 + 9 = SIGKILL):

$ docker ps -a
CONTAINER ID   IMAGE            STATUS                          PORTS     NAMES
c3d4e5f6a1b2   node:22-alpine   Exited (137) 4 seconds ago              api

$ docker inspect api --format '{{.State.OOMKilled}}'
true

$ docker logs api | tail -3
Killed                                    « o kernel matou o processo: memória estourou

O OOMKilled: true no inspect confirma que foi falta de memória, não um erro da aplicação. Se tiver --restart unless-stopped (aula anterior), o container volta sozinho depois de morrer.

Sem limite, o OOM killer pode matar o processo errado. Num servidor sem --memory, quando a RAM acaba, o kernel escolhe uma vítima pela heurística dele — às vezes o banco de dados, não o culpado (exatamente o que aconteceu com o worker de relatórios da Ana). Limite sempre os containers em produção e acompanhe o uso com docker stats.
Cenário real: o relatório que matou o banco

O worker de relatórios da Loja Aurora rodava sem --memory. No relatório anual, ele carregou a planilha inteira na RAM (6GB) num servidor de 8GB — e o kernel, sem nada limitado, matou o PostgreSQL para liberar memória. Site fora do ar na segunda-feira de manhã. Depois de dar --memory 1g no worker (e --restart on-failure:3), o pior que acontece agora é o worker morrer com Exited (137) e voltar sozinho — o banco segue intacto. É isso que limite compra: previsibilidade.

Declarando limites no docker-compose.yml

Em produção a Ana não usa docker run solto: ela declara os limites no docker-compose.yml (aula compose), na seção deploy.resources — que também vale no Swarm, por réplica:

services:
  api:
    image: ana/minha-api:1.0
    deploy:
      resources:
        limits:
          cpus: "1.0"
          memory: 512M
        reservations:
          cpus: "0.25"
          memory: 128M
      restart_policy:
        condition: unless-stopped
  worker:
    image: ana/minha-api:1.0
    command: node worker.js
    deploy:
      resources:
        limits:
          cpus: "0.5"
          memory: 1G
          pids: 200
  db:
    image: postgres:16-alpine
    deploy:
      resources:
        limits:
          memory: 2G

Repare: limits é o teto duro (vale --memory/--cpus), reservations é o soft (vale --memory-reservation), e pids limita processos. O restart_policy.condition é o equivalente do --restart no Compose/Swarm.

Resumo das flags de recursos

FlagExemploO que limita
--memory / -m--memory 512mMemória RAM (OOM kill ao passar). Unidades: b, k, m, g.

--cpus--cpus 1.5Núcleos de CPU (frações valem).

Esses limites também aparecem no docker inspect (.HostConfig.Memory, .HostConfig.NanoCpus, .HostConfig.PidsLimit) — dá para auditar um container assim. E no Swarm, declared em deploy.resources.limits, valem por réplica do serviço.

Como escolher os limites certos (sem chute)

Chutar limite dá dois problemas: muito justo (OOM kill à toa) ou muito folgado (não protege nada). O jeito certo é medir:

  1. Suba o container sem limite em ambiente de teste com carga parecida com a de produção (faça o relatório, simule os acessos).
  2. Acompanhe com docker stats api por alguns minutos e anote o pico de MEM USAGE e de CPU %:
$ docker stats api
CONTAINER ID   NAME   CPU %   MEM USAGE / LIMIT   MEM %   NET I/O       BLOCK I/O   PIDS
c3d4e5f6a1b2   api    12.50%  380MiB / 7.79GiB    4.75%   1.2MB / 0B    2GB / 12MB  45

(Aqui sem limite: o "LIMIT" mostra a RAM total da máquina, 7.79GiB.)

  1. Defina o limite um pouco acima do pico observado: pico de 380MB → --memory 512m. CPU a 120% (1,2 núcleos) → --cpus 2.
  2. Deixe o --restart unless-stopped ligado: se um pico inesperado estourar o limite, o container morre e volta sozinho em vez de travar a máquina.
  3. Reavalie de tempos em tempos: docker stats no servidor mostra todos os containers e o quanto cada um está perto do teto.

Resumo

  • Sem limites, um container pode consumir toda a CPU/RAM da máquina e derrubar os outros (vizinho barulhento).
  • --memory 512m (unidades b/k/m/g) = teto de RAM; estourado, o kernel mata o processo: Exited (137) + OOMKilled: true.
  • --memory-swap controla RAM+swap (igual ao --memory desliga swap); --memory-reservation é o limite leve.
  • --cpus 1.5 limita núcleos (frações valem); --cpu-shares dá peso relativo na disputa por CPU.
  • --pids-limit 200 barra o fork bomb.
  • No Compose/Swarm, os limites vão em deploy.resources.limits e valem por réplica; acompanhe o uso com docker stats.
