Imagens, Containers, Registry e Docker Hub

Quatro palavras que aparecem o tempo todo no Docker. Entender a diferença entre elas é entender o Docker. A analogia que vamos usar: uma padaria.

Você vai aprender
  • Imagem = a receita escrita (somente leitura, em camadas).
  • Container = o bolo pronto, assado a partir da receita (instância viva, descartável).
  • Registry = o depósito de ingredientes/imagens (onde elas ficam guardadas e de onde são distribuídas).
  • Docker Hub = o supermercado público, o registry padrão (docker.io).
  • Como um nome de imagem é montado: registry/namespace/repositório:tag.
  • Por que apagar um container não apaga a imagem.

A padaria do Docker

Toda padaria tem: a receita (escrita num caderno, não muda), o bolo (feito na hora, vendido e descartado), o depósito (onde ficam os sacos de farinha e fermento) e o supermercado (onde a padaria compra os ingredientes prontos). No Docker:

Imagem = a receita

Arquivo somente leitura, em camadas, com o sistema base + tudo instalado. Você não altera a imagem depois de pronta — se precisar mudar, cria uma camada nova em cima (isso vira outra imagem, na aula de Dockerfile). A imagem fica guardada no disco da máquina e ocupa espaço (veja a coluna SIZE no docker images).

Somente leitura
Nenhum container consegue modificar a imagem original. O que o programa grava vai para uma camada gravável em cima, que pertence só ao container.
Em camadas (layers)
A imagem é uma pilha de camadas. A base é um mini sistema operacional (ex.: Alpine Linux, ~5MB); em cima vêm as bibliotecas, o programa, as configurações. Camadas iguais são reutilizadas entre imagens diferentes e não ocupam espaço duplicado — a aula docker pull mostra isso na prática.
Identificada por hash
Toda imagem tem um ID único (um hash sha256), além do nome. Duas tags podem apontar para o mesmo ID.

Container = o bolo

Uma instância viva da imagem, com uma camada gravável em cima. Vários containers podem vir da mesma imagem — como assar vários bolos da mesma receita. Você pode parar, apagar e recriar containers à vontade: apagar o bolo não rasga a receita.

$ docker run -d --name bolo1 nginx:alpine   « assou o bolo 1
$ docker run -d --name bolo2 nginx:alpine   « assou o bolo 2, da MESMA receita
$ docker ps
CONTAINER ID   IMAGE          STATUS         NAMES
aaa111bbb222   nginx:alpine   Up 3 seconds   bolo1
ccc333ddd444   nginx:alpine   Up 2 seconds   bolo2
$ docker rm -f bolo1 bolo2                  « jogou os bolos fora
$ docker images
…                  nginx:alpine   …          « a receita continua no caderno
Cuidado com a camada gravável

Os arquivos que um programa grava dentro do container ficam nessa camada gravável — e somem quando o container é apagado com docker rm. Se o container guardava dados importantes (um banco de dados, por exemplo), eles vão junto. A solução são volumes, a aula Volumes (-v).

Registry = o depósito

Um servidor que guarda e distribui imagens. O comando docker pull baixa de um registry; docker push envia para um. Pense no registry como o depósito da padaria: a receita pode estar no caderno local ou vir de fora, trazida pelo caminhão do depósito.

  • Quando a imagem não está na sua máquina, docker run faz pull automático do registry padrão.
  • Você pode indicar outro registry no próprio nome: registry.empresa.com/time/meuapp:1.0 (a aula Registry privado mostra isso).
  • Se nada for escrito, o Docker completa com docker.io — o Docker Hub.

Docker Hub = o supermercado público

O registry público oficial (hub.docker.com), mantido pela Docker Inc. Tem imagens oficiais (nginx, postgres, node…) e as da comunidade. O comando docker pull nginx baixa de lá por padrão — sem você escrever docker.io.

Anatomia completa de um nome de imagem

docker.io / library / nginx : alpine
   │          │         │       └── tag (versão/variante)
   │          │         └────────── repository (nome da imagem)
   │          └──────────────────── namespace (quem publica)
   └─────────────────────────────── registry (o depósito)
docker.io
O registry. Se omitir, o Docker assume docker.io (o Hub).
library
O namespace das imagens oficiais, mantidas pela equipe do próprio software ou pela Docker. docker pull nginx na verdade baixa docker.io/library/nginx:latest.
ana
Um namespace de usuário comum — ex.: docker.io/ana/meuapp:1.0 seria uma imagem publicada pela usuária ana.
nginx
O repository: o nome da imagem.
:alpine
A tag: a variante baseada no Alpine Linux. Sem tag, vale :latest (aula Tags).

Confusões comuns (e como não cair nelas)

"Apaguei o container, então perdi o programa"

Não. O programa está na imagem, que continua na máquina (docker images). O que se perde com docker rm são os arquivos gravados pelo programa durante a execução (a camada gravável) — para esses, use volumes. Pense de novo na padaria: jogar o bolo fora não rasga a receita.

"Baixar a imagem é a mesma coisa que rodar o programa"

Não. docker pull nginx só baixa a receita para o seu computador (fica visível no docker images, mas nada está rodando). Quem assa o bolo é o docker run — aí sim nasce um container, que aparece no docker ps. A aula docker pull e a docker run mostram a diferença na tela.

"Meu amigo mandou a imagem dele por email"

Imagens não são arquivos soltos para mandar por email — elas moram em um registry. O fluxo certo é: seu amigo dá docker push para o Hub (ou um registry privado) e você dá docker pull do mesmo endereço. Se a imagem for só local, dá para exportar com docker save (gera um arquivo .tar) e importar com docker load na outra máquina.

Resumo

  • Imagem = a receita (somente leitura, em camadas, com ID único). Container = o bolo pronto (instância viva + camada gravável).
  • Registry = o depósito de imagens; Docker Hub (docker.io) = o registro público padrão.
  • Nome completo: registry/namespace/repositório:tag — ex.: docker.io/library/nginx:alpine. Omitir o registry = usar o Hub; omitir a tag = :latest.
  • Apagar um container não apaga a imagem; vários containers podem vir da mesma imagem.
  • O que um container grava na camada própria some com docker rm — dados que devem durar precisam de volumes.
  • docker images lista as receitas; docker ps lista os bolos rodando; docker pull traz receita nova do depósito.
