O que é um Dockerfile

Até agora você usou imagens prontas, baixadas do Docker Hub — como comprar pão na padaria. Agora você vai criar a sua própria imagem, do zero. Para isso, o Docker usa um arquivo de texto chamado Dockerfile. Pense nele como a receita de um bolo: cada linha é um passo escrito em letras garrafais, e o resultado final, depois de "assar", é a imagem. Nesta aula a Ana, no notebook dela (ana@notebook), vai escrever a primeira receita: um "olá" empacotado em container.

Você vai aprender
  • A analogia da receita: ingrediente base, preparo e modo de servir.
  • O Dockerfile mínimo (FROM + CMD), comentado linha a linha.
  • Onde o arquivo fica: na raiz do contexto do build, com o D maiúsculo.
  • Quem lê o arquivo: o comando docker build, e por que o . no fim importa.
  • O caminho completo: Dockerfile → docker build → imagem → docker run → container.
  • A diferença entre Dockerfile, imagem e container (tabela comparativa).
  • Os erros reais de principiante: arquivo na pasta errada, nome com letra minúscula, build sem arquivo.

A história: a Ana quer empacotar o "olá" dela

A Ana escreveu um programazinho que imprime "Olá!" no terminal do notebook dela. Ela podia mandar o código por e-mail para a amiga, junto com um bilhete dizendo "instala o Node antes de rodar". Só que aí cada amiga teria que instalar a mesma coisa, na mesma versão, e torcer para dar certo. Em vez disso, ela vai empacotar o programa junto com o ambiente numa imagem Docker — aí a amiga só precisa rodar docker run e pronto.

O primeiro passo é criar uma pasta só para o projeto e escrever a receita dentro dela. No terminal do notebook da Ana:

$ mkdir ~/ola-docker
$ cd ~/ola-docker
$ cat > Dockerfile <<'EOF'
FROM alpine:3.20
CMD ["echo", "Olá! Eu fui assado por um Dockerfile."]
EOF
$ ls
Dockerfile

O comando cat > Dockerfile <<'EOF' … EOF é um heredoc do Bash: tudo que a Ana digita entre as duas linhas EOF vai para dentro do arquivo. Repare que o arquivo se chama exatamente Dockerfile — com D maiúsculo e sem extensão. Esse nome é uma convenção forte: é o arquivo que o docker build procura por padrão.

Por que o D maiúsculo?

Porque é a convenção oficial e porque o Linux liga para maiúsculas: dockerfile (minúsculo) não é encontrado pelo build padrão. Muita gente já perdeu dez minutos procurando o arquivo errado por causa disso.

A imagem como receita de bolo

Uma receita de bolo tem três partes — e o Dockerfile também. Toda instrução do arquivo cai em uma dessas partes:

Parte da receitaInstrução do DockerfileExemploQuando acontece
O ingrediente baseFROMFROM alpine:3.20Escolhida no build, uma vez
O preparo (misturar, assar)RUN, COPY, ENV…RUN apk add curlDurante o docker build
O modo de servirCMDCMD ["echo", "Olá!"]Toda vez que um container inicia

O bolo pronto é a imagem: um pacote fechado, só de leitura, com tudo dentro. Cada container que você cria a partir dela é uma fatia servida desse bolo — com uma camada gravável em cima, para não estragar o bolo original. Se a fatia sujar, o bolo continua limpo.

Ingrediente base (FROM)
de onde a imagem começa: outra imagem, como alpine:3.20 ou node:22-alpine.
Preparo (RUN, COPY…)
passos executados na hora do build para deixar a imagem pronta (instalar pacotes, copiar o código).
Modo de servir (CMD)
o comando padrão que roda quando o container inicia.

O Dockerfile mínimo, linha a linha

Com apenas duas instruções você já gera uma imagem funcional. Esse é o Dockerfile que a Ana escreveu:

# arquivo: Dockerfile
# Linha 1: de onde a imagem nasce (a base)
FROM alpine:3.20
# Linha 2: o que roda quando o container iniciar
CMD ["echo", "Olá! Eu fui assado por um Dockerfile."]
# comentário
Linhas que começam com # são comentários: o Docker as ignora. Use e abuse para explicar cada passo — o seu "eu do futuro" agradece.
FROM alpine:3.20
"A partir de alpine na versão 3.20". O alpine é uma distribuição Linux minúscula (uns 5MB); a tag :3.20 fixa a versão. Escolher a base tem aula própria: FROM: a imagem base.
CMD
"Quando este container iniciar, rode isto". É o comando padrão do container.
["echo", "Olá! …"]
A sintaxe entre colchetes é a forma exec (uma lista em JSON): cada elemento vira um argumento do comando, sem passar por shell. A aula RUN e CMD compara com a forma shell (CMD echo "Olá!").

Detalhes que fazem diferença:

  • Uma instrução por linha. O Dockerfile não usa ponto e vírgula no fim — cada linha já é um comando completo.
  • Ordem importa. O FROM tem que ser a primeira instrução (depois de comentários). Se você colocar um RUN antes do FROM, o build quebra na hora.
  • O arquivo é lido de cima para baixo, como uma receita mesmo: cada linha usa o resultado das anteriores.
Erro comum: texto grudado na instrução. Escrever FROMalpine:3.20 (sem espaço) dá erro de parse: docker: 'FROMalpine:3.20' is not a valid command-style — na verdade o build acusa unknown instruction: FROMALPINE:3.20. Sempre um espaço entre a instrução e o argumento.

Onde o arquivo fica: a raiz do contexto do build

Por padrão, o arquivo se chama Dockerfile e fica na raiz do projeto — a pasta que você manda para o Docker. Essa pasta tem nome chique: contexto do build (build context). Tudo que está nela pode ser copiado para dentro da imagem com COPY (aula COPY, ADD e WORKDIR), e tudo que está fora dela não pode entrar na imagem.

$ ls ~/ola-docker
Dockerfile
$ tree ~/ola-docker   « a pasta só tem a receita ainda
.
└── Dockerfile

O arquivo .dockerignore, quando existe nessa mesma raiz, funciona como uma lista de exclusão: o que está nele não é enviado no contexto (aula .dockerignore).

ConceitoO que éAnalogia
Contexto do buildA pasta que você passa no docker build . (o .)A cesta de ingredientes que você leva para a cozinha
DockerfileO arquivo de receita dentro do contextoO papel com o passo a passo
ImagemO resultado do build: camadas só de leitura empilhadasO bolo pronto, embalado a vácuo
ContainerUma imagem rodando, com uma camada gravável em cimaA fatia servida no prato

Quem lê o Dockerfile: o docker build

Ninguém lê o arquivo sozinho — quem transforma a receita em imagem é o comando docker build. Ele procura o arquivo Dockerfile dentro da pasta que você indicar e executa cada instrução, uma de cada vez:

docker build
o comando que lê o Dockerfile e monta a imagem passo a passo.
-t ola:1.0
dá um nome e uma tag à imagem resultante (formato nome:tag). Sem -t, a imagem fica sem nome ("<none>").
.
o contexto do build: "a pasta atual", onde está o Dockerfile. O ponto é um caminho relativo — poderia ser ~/ola-docker também.
$ docker build -t ola:1.0 .
Sending build context to Docker daemon  2.048kB
Step 1/2 : FROM alpine:3.20
 ---> e5f6a1b2c3d4
Step 2/2 : CMD ["echo", "Olá! Eu fui assado por um Dockerfile."]
 ---> Running in a1b2c3d4e5f6
Removing intermediate container a1b2c3d4e5f6
 ---> b2c3d4e5f6a1
Successfully built b2c3d4e5f6a1
Successfully tagged ola:1.0

Vamos ler essa saída, porque ela aparece em todo build:

  1. Sending build context to Docker daemon 2.048kB — a pasta do projeto foi compactada e enviada ao daemon (o processo do Docker que faz o trabalho pesado).
  2. Step 1/2 : FROM alpine:3.20 — a instrução 1 de 2 está sendo executada. A base foi baixada (ou reutilizada do cache) e recebeu o ID e5f6a1b2c3d4.
  3. Step 2/2 : CMD […] — a instrução 2 rodou num container temporário (Running in a1b2c3d4e5f6), que foi descartado (Removing intermediate container) e virou a camada b2c3d4e5f6a1.
  4. Successfully built + Successfully tagged ola:1.0 — a imagem final foi montada e etiquetada. É o "bolo pronto".

Do Dockerfile à imagem rodando: o caminho completo

Pronto: a imagem ola:1.0 agora existe na máquina da Ana. Ela confirma listando as imagens e depois roda a imagem — que é de onde vem o container:

$ docker images
REPOSITORY   TAG          IMAGE ID       CREATED          SIZE
ola          1.0          b2c3d4e5f6a1   20 seconds ago   7.85MB
alpine       3.20         e5f6a1b2c3d4   3 weeks ago      7.8MB
hello-world  latest       a1b2c3d4e5f6   2 weeks ago      18.2kB
$ docker run --rm ola:1.0
Olá! Eu fui assado por um Dockerfile.
$ docker ps -a
CONTAINER ID   IMAGE   COMMAND   CREATED   STATUS   PORTS   NAMES

O --rm faz o container se apagar sozinho quando termina (bom para testes). Como a saída mostra, o docker ps -a veio vazio: o container do "olá" já rodou, imprimiu e foi removido. Sem --rm, ele ficaria parado na lista até você dar docker rm.

2. Assar o bolodocker build -t ola:1.0 .Lê o Dockerfile e monta a imagem ola:1.0
3. Conferir o bolodocker imagesLista as imagens que existem na máquina

Quando dá errado

Erro comum nº 1: rodar o build numa pasta que não tem Dockerfile. A Ana esqueceu de dar cd e rodou o build na home:
$ docker build -t ola .
ERROR: failed to solve: failed to read dockerfile: open Dockerfile: no such file or directory
O daemon não acha o arquivo e responde no such file or directory. Como consertar: entre na pasta do projeto (cd ~/ola-docker) ou aponte o contexto: docker build -t ola ~/ola-docker. Se o arquivo tiver outro nome, use -f (aula docker build).
Erro comum nº 2: arquivo com nome minúsculo. Se a Ana tivesse salvo como dockerfile, o build padrão não encontraria e daria o mesmo erro acima. No Linux, Dockerfile e dockerfile são arquivos diferentes. Como consertar: renomeie com mv dockerfile Dockerfile — ou use docker build -f dockerfile . para indicar o nome na hora.
Erro comum nº 3: instrução antes do FROM. O Dockerfile precisa começar pela base:
# ERRADO: preparo antes do ingrediente base
RUN echo "ei"
FROM alpine:3.20
O build falha com Error response from daemon: Dockerfile parse error line 2: unknown instruction: RUN-style (a mensagem exata varia, mas o problema é o mesmo: não existe imagem ainda para rodar o RUN). Como consertar: FROM sempre primeiro.
Erro comum nº 4: esquecer as aspas no CMD em forma exec. CMD [echo, "Olá"] (sem aspas no primeiro elemento) não é JSON válido e o build acusa erro de parse na linha do CMD. Na forma exec, todos os elementos vão entre aspas: CMD ["echo", "Olá"].

Resumo

  • O Dockerfile é a receita da imagem: um arquivo de texto, com D maiúsculo, na raiz do contexto do build, uma instrução por linha, # para comentários.
  • Toda receita começa com FROM (a base), passa pelo preparo (RUN, COPY) e termina no CMD (o que roda quando o container inicia).
  • Quem lê a receita é o docker build -t nome:tag .: o . é o contexto (a pasta atual), enviado inteiro ao daemon.
  • O build imprime Step N/M por instrução e termina com Successfully built / Successfully tagged.
  • Imagem é o bolo pronto (só leitura); container é a fatia rodando, com uma camada gravável em cima — docker run --rm cria, roda e apaga.
  • Erros clássicaços: build na pasta errada, arquivo com nome minúsculo, instrução antes do FROM, aspas faltando no CMD em forma exec.
