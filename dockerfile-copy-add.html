COPY, ADD e WORKDIR

A imagem base vem vazia de código — é você que leva o seu projeto para dentro dela. Quem faz essa mudança de pasta e essa cópia de arquivos são três instruções: WORKDIR (arruma a casa), COPY (traz os arquivos do seu computador) e ADD (o irmão turbinado, que também descompacta e baixa da internet). Nesta aula a Ana vai empacotar a API dela inteira dentro da imagem.

Você vai aprender
  • WORKDIR: criar a pasta de trabalho, mudar para ela e por que caminhos relativos passam a valer a partir dela.
  • COPY: copiar arquivos e pastas do contexto do build para a imagem — com glob (package*.json) e vários destinos.
  • Por que a ordem dos COPY deixa o npm install em cache (ponte para a aula de camadas).
  • ADD: quando ele é útil (descompactar tar local, baixar URL) e quando evitar.
  • COPY --from: copiar de outra etapa do próprio build (multi-stage) ou de qualquer imagem.
  • Erros reais: copiar de fora do contexto, barra no fim do destino, arquivo que o .dockerignore excluiu.

A cena: a pasta da Ana antes do build

No notebook da Ana, o projeto ~/minha-api está assim:

$ cd ~/minha-api
$ ls -la
Dockerfile  package.json  package-lock.json  server.js  src/  test/

Ela quer que tudo isso vá para dentro da imagem, numa pasta /app. É exatamente o que WORKDIR + COPY fazem.

WORKDIR: a pasta de trabalho

O WORKDIR cria a pasta se ela não existir e muda para ela. Tudo que vem depois no Dockerfile (RUN, COPY, CMD…) acontece dentro dela, e caminhos relativos são resolvidos a partir dela:

FROM node:22-alpine
WORKDIR /app
# a partir daqui, tudo acontece em /app dentro da imagem:
# COPY . .  vai copiar para /app, e o CMD roda em /app

É o equivalente a dar um cd /app permanente no build. Sem WORKDIR, os arquivos cairiam na raiz / da imagem — uma bagunça (e o CMD teria que usar caminhos absolutos).

WORKDIR
"a partir de agora, trabalhe nesta pasta".
/app
caminho absoluto dentro da imagem. Se você usar um caminho relativo (WORKDIR app), ele é relativo ao WORKDIR anterior — evite, prefira sempre absoluto.
WORKDIR cria as pastas no meio do caminho: WORKDIR /app/src cria /app e /app/src se não existirem. E vários WORKDIR vão se acumulando: depois de WORKDIR /app, um WORKDIR src leva para /app/src.
Erro comum: WORKDIR relativo. WORKDIR app depois de WORKDIR /srv leva para /srv/app, não para /app. Muita gente acha que é absoluto. Regra: comece a pasta com / para deixar explícito que é absoluto.

COPY: trazer arquivos do seu computador para a imagem

O COPY copia arquivos do contexto do build (as pastas que você enviou com o . no docker build) para dentro da imagem. A forma mais comum é "copiar tudo para cá":

WORKDIR /app
COPY . .
COPY
a instrução de cópia.
. (origem)
tudo da pasta atual do seu computador (o contexto). Pode ser arquivo, pasta ou glob (*.json, src/).
. (destino)
a pasta /app dentro da imagem (o WORKDIR atual). O ponto como destino significa "o diretório de trabalho atual".

Você também pode ser específico e copiar só alguns arquivos:

COPY package.json package-lock.json server.js ./

E pode ter vários pares origem-destino, e o destino pode ser uma pasta explícita:

COPY package*.json ./          # glob: package.json, package-lock.json…
COPY src/ /app/src/            # copia o CONTEÚDO de src/ para /app/src/
COPY README.md /app/README.md  # arquivo único para caminho exato
EscritaO que copia
COPY . .Tudo do contexto para o WORKDIR
COPY package*.json ./Todos os arquivos que começam com package e terminam com .json
COPY src/ /app/src/O conteúdo da pasta src/ para /app/src/ na imagem
COPY a.txt b.txt /pasta/Vários arquivos de uma vez para a mesma pasta
COPY --chown=node:node . .Copia mudando o dono dos arquivos (útil quando a imagem roda como usuário não-root — nível 3)
Erro real: barra no fim faz diferença. COPY src /app (sem barra no destino) copia a pasta src como /app (o conteúdo de src vai parar dentro de /app, e se /app já existir como pasta, dá not a directory). Já COPY src/ /app/ copia o conteúdo de src para dentro de /app. A barra no fim do destino é o que manda: com barra = "dentro dessa pasta"; sem barra = "esse nome". Na dúvida, ponha barra nos dois lados quando copiar pastas.
Erro real: copiar de fora do contexto. Se a Ana roda docker build . dentro de ~/minha-api e escreve COPY ../outra-pasta/arquivo.txt ., o build falha: failed to compute cache key: … not found — tudo que o COPY usa tem que estar dentro do contexto. O daemon não vê nada fora da pasta enviada. Se precisar de um arquivo de fora, copie ele para dentro do projeto antes (ou mude o contexto do build).

A ordem dos COPY: cache amigo

O truque mais importante desta aula: copie os arquivos que mudam pouco antes, e o código por último. A Ana separa o COPY em dois:

WORKDIR /app
COPY package*.json ./     # muda só quando as dependências mudam
RUN npm install           # fica em cache na maioria dos builds
COPY . .                  # o código muda toda hora — mas está no fim

Assim, quando a Ana edita o server.js e rebuilda, só o último COPY é refeito — o npm install continua em cache e o build leva segundos. Se a ordem fosse invertida, cada mudança de código quebraria o cache do npm install e o build demoraria minutos. A aula Camadas e cache do build detalha por quê.

Por que não um COPY só? Dá para fazer COPY . . uma vez só — funciona. A divisão existe purely pelo cache: dependências mudam raramente, código muda toda hora.

ADD: COPY com superpoderes (use com moderação)

O ADD faz tudo o que o COPY faz mais duas coisas:

  • se a origem for um arquivo compactado local (.tar, .tar.gz, .tar.xz…), ele descompacta sozinho no destino;
  • se a origem for uma URL (https://…), ele baixa o arquivo da internet durante o build.
ADD https://github.com/meu-org/meu-app/archive/refs/tags/v1.2.3.tar.gz /tmp/app.tar.gz
ADD fontes.tar.gz /app/fontes/

O primeiro baixa o código da release direto do GitHub; o segundo descompacta o tar local na pasta de fontes.

Regra prática: use COPY para arquivos do seu projeto. Use ADD só quando precisar descompactar um tar local ou baixar uma URL — esses dois recursos invalidam o cache do build com frequência (aula Camadas e cache) e uma URL que muda de conteúdo pode quebrar builds antigos sem aviso. Se for baixar algo, prefira RUN curl -o … && … com a URL explícita no comando — aí o cache quebra de forma visível e controlável.

COPY --from: copiar de outra etapa (multi-stage)

Em builds com várias etapas (FROM … AS nome, aula FROM), o COPY --from copia arquivos de uma etapa anterior — ou de qualquer imagem — em vez do contexto:

FROM node:22-alpine AS build
WORKDIR /app
COPY . .
RUN npm run build        # gera /app/dist

FROM nginx:alpine
COPY --from=build /app/dist /usr/share/nginx/html

A imagem final recebe só o dist compilado — sem Node, sem dependências de build, bem menor. Também dá para copiar de uma imagem qualquer: COPY --from=nginx:alpine /etc/nginx/nginx.conf /etc/nginx/nginx.conf. É assim que se gera imagens enxutas (aula Multi-stage builds, nível 3).

Exemplo completo: copiando a app Node da Ana

# Dockerfile da ~/minha-api
FROM node:22-alpine
WORKDIR /app
COPY package*.json ./
RUN npm install
COPY . .
EXPOSE 3000
CMD ["node", "server.js"]

Quando dá errado

Arquivo ignorado pelo .dockerignore: se o .dockerignore exclui node_modules/ e o Dockerfile tem COPY node_modules /app/, o build falha com failed to compute cache key: node_modules: not found. O .dockerignore vale para o COPY também — o arquivo nem chega ao daemon (aula .dockerignore).
Permissão depois do COPY: arquivos copiados com COPY mantêm as permissões do host e pertencem ao root dentro da imagem. Se a sua app roda como usuário não-root (boa prática, nível 3) e precisa escrever numa pasta copiada, use COPY --chown=usuario:grupo … ou ajuste com RUN chown.
Symlinks que apontam para fora: se o contexto tem um link simbólico apontando para fora da pasta do projeto, o Docker segue o link e pode acabar enviando (ou quebrando) — o comportamento mudou ao longo das versões; o seguro é não ter symlinks apontando para fora no contexto.

Quiz rápido

1. Para que serve o WORKDIR /app?

2. O que COPY . . faz?

3. Por que a Ana separa COPY package*.json ./ + RUN npm install de COPY . ., nessa ordem?

4. Qual a diferença prática entre COPY e ADD?

Resumo

  • WORKDIR /app cria a pasta e muda para ela; todo RUN/COPY/CMD depois trabalha dali. Prefira caminho absoluto (começando com /).
  • COPY origem destino traz arquivos do contexto do build para a imagem; COPY . . copia tudo para o WORKDIR; glob (*.json) funciona na origem.
  • Ordem importa pelo cache: copie o que muda pouco (manifests) antes e o código por último — COPY package*.json ./ → RUN npm install → COPY . ..
  • ADD = COPY + descompactar tar local + baixar URL. Use só nesses dois casos; para o resto, COPY é mais previsível com o cache.
  • COPY --from=etapa copia de outra etapa do multi-stage ou de outra imagem — sem tocar no contexto.
  • Erros reais: copiar de fora do contexto (not found), barra no fim do destino mudando o sentido, arquivo excluído pelo .dockerignore, permissão de arquivos copiados (use --chown).
