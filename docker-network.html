docker network — criar, conectar e remover redes

Além das três redes de fábrica (bridge, host, none), você pode criar redes suas com docker network create. Uma rede própria traz duas vantagens grandes: isola um projeto do outro (o projeto A não enxerga o projeto B) e liga o DNS automático — dentro dela, um container alcança o outro pelo nome (assunto da próxima aula). A Ana vai criar a rede da aplicação dela agora.

Você vai aprender
  • docker network create e docker network ls — e as opções --driver, --subnet, --gateway.
  • Subir containers numa rede dedicada com --network.
  • docker network connect e disconnect em containers que já existem (um container pode estar em várias redes).
  • docker network inspect: o JSON da rede, com sub-rede, gateway e containers conectados.
  • docker network rm e os erros reais: rede predefinida e "active endpoints".
  • docker network prune para limpar redes não usadas.

Por que criar uma rede própria?

Na bridge padrão, todos os containers que você sobe sem --network ficam no mesmo quintal — e se alcançam pelo IP. Se a Ana tem dois projetos no notebook (o site dela e o sistema da empresa), os containers dos dois se misturam. Com uma rede por projeto:

  • Isolamento: o container do projeto A não alcança o do projeto B (nem por IP, nem por nome).
  • DNS automático: dentro da rede criada por você, o nome do container resolve para o IP (na bridge padrão isso não acontece — próxima aula).
  • Organização: docker network ls vira o mapa dos seus projetos; dá para apagar a rede inteira de um projeto antigo com um comando.

Criando uma rede

$ docker network create app-net
7d6e5f4a3b2c1d0e9f8a7b6c5d4e3f2a1b0c9d8e7f6a5b4c3d2e1f0a9b8c7d6e
$ docker network ls
NETWORK ID     NAME      DRIVER    SCOPE
a1b2c3d4e5f6   bridge    bridge    local
b2c3d4e5f6a1   host      host      local
c3d4e5f6a1b2   none      null      local
7d6e5f4a3b2c   app-net   bridge    local

O create devolve o ID completo (64 hex) da rede nova. Repare que a rede criada usa o driver bridge — ela é uma bridge nova, separada da padrão, com a própria faixa de IPs (172.18.x.x, 172.19.x.x… conforme as redes vão sendo criadas).

docker network
o subgrupo de comandos que gerencia redes.
create
cria uma rede nova (driver bridge por padrão).
app-net
o nome da rede — único na máquina; é esse nome que vai no --network.

Opções úteis do create

$ docker network create --driver bridge \
>     --subnet 192.168.50.0/24 --gateway 192.168.50.1 \
>     --label projeto=guia rede-customizada
$ docker network create --driver macvlan --subnet 192.168.1.0/24 \
>     --gateway 192.168.1.1 -o parent=eth0 rede-macvlan   « macvlan dá IP real da rede física ao container

Na maioria dos casos o padrão basta. O --subnet/--gateway servem para encaixar o Docker numa rede corporativa com faixa fixa; o driver macvlan/ipvlan é para o container aparecer como um dispositivo real na rede física (caso avançado).

Exemplo: rede dedicada para app + banco

O cenário clássico da Ana: uma API e um Postgres que precisam se falar, sem nada mais nessa rede:

$ docker network create app-net
7d6e5f4a3b2c1d0e9f8a7b6c5d4e3f2a1b0c9d8e7f6a5b4c3d2e1f0a9b8c7d6e
$ docker run -d --name meu-banco --network app-net \
>     -e POSTGRES_PASSWORD=segredo \
>     -v dados-postgres:/var/lib/postgresql/data \
>     postgres:16-alpine
a1b2c3d4e5f6a1b2c3d4e5f6a1b2c3d4e5f6a1b2c3d4e5f6a1b2c3d4e5f6a1b2c3d4e5f6a1b2c3d4e5f6a1b2c3d4e5
$ docker run -d --name minha-api --network app-net \
>     -p 3000:3000 \
>     -e DATABASE_URL=postgres://meu-banco:5432/guia \
>     node:22-alpine node server.js
b2c3d4e5f6a1b2c3d4e5f6a1b2c3d4e5f6a1b2c3d4e5f6a1b2c3d4e5f6a1b2c3d4e5f6a1b2c3d4e5f6a1b2c3d4e5
$ docker ps
CONTAINER ID   IMAGE              STATUS         PORTS                     NAMES
a1b2c3d4e5f6   postgres:16-alpine Up 8 seconds   5432/tcp                  meu-banco
b2c3d4e5f6a1   node:22-alpine     Up 5 seconds   0.0.0.0:3000->3000/tcp    minha-api

Repare na coluna PORTS: só a API tem porta publicada (3000:3000). O banco está 5432/tcp só — alcançável dentro da app-net, invisível para o mundo de fora. A variável DATABASE_URL já aponta para o banco pelo nome: postgres://meu-banco:5432/guia (próxima aula explica o DNS interno que faz isso funcionar).

Conectar um container que já existe

O container nasce na rede padrão, mas dá para ligá-lo a outra rede depois — sem recriar nada:

$ docker run -d --name web nginx:alpine   « nasceu na bridge padrão
$ docker network connect app-net web      « agora está nas duas redes
$ docker inspect web --format '{{range $k,$v := .NetworkSettings.Networks}}{{$k}} {{end}}'
bridge app-net
$ docker network disconnect bridge web     « opcional: tira da rede padrão

Um container pode estar em várias redes ao mesmo tempo — cada uma vira uma interface de rede dentro dele (visível com docker exec web ip addr: eth0, eth1…).

Erro real: conectar container que não existe. docker network connect app-net site (nome errado) dá Error response from daemon: No such container: site. E conectar duas vezes na mesma rede dá endpoint with name … already exists in network app-net. Confira o nome com docker ps antes.

Inspecionando a rede: quem está conectado

O docker network inspect mostra o JSON da rede — sub-rede, gateway e a lista de containers conectados com IP e MAC:

$ docker network inspect app-net
[
    {
        "Name": "app-net",
        "Id": "7d6e5f4a3b2c…",
        "Scope": "local",
        "Driver": "bridge",
        "IPAM": {
            "Config": [
                {
                    "Subnet": "172.18.0.0/16",
                    "Gateway": "172.18.0.1"
                }
            ]
        },
        "Containers": {
            "a1b2c3d4e5f6…": { "Name": "meu-banco", "IPv4Address": "172.18.0.2/16" },
            "b2c3d4e5f6a1…": { "Name": "minha-api", "IPv4Address": "172.18.0.3/16" }
        }
    }
]

Com --format dá para extrair só os nomes dos containers conectados — útil para scripts de "quem está na minha rede?":

$ docker network inspect app-net --format '{{range .Containers}}{{.Name}}{{"\n"}}{{end}}'
meu-banco
minha-api

Removendo uma rede

$ docker network rm app-net
app-net

Sem erro, o comando devolve o nome da rede removida. Mas há dois erros comuns:

$ docker network rm bridge
Error response from daemon: predefined network bridge cannot be removed
$ docker network rm app-net
Error response from daemon: network app-net has active endpoints
Dois erros na hora de remover rede: predefined network bridge cannot be removed — as redes bridge, host e none são de fábrica e não podem ser apagadas. E network app-net has active endpoints — ainda existe container conectado; rode docker network disconnect app-net <container> (ou remova o container) antes.

docker network prune

Com o tempo, redes de projetos antigos vão sobrando. O prune remove todas as redes que nenhum container está usando (as de fábrica nunca são removidas):

$ docker network prune
WARNING! This will remove all custom networks not used by at least one container.
Are you sure you want to continue? [y/N] y
Deleted Networks:
app-net-antiga
teste-net

O diagrama da rede app-net

A rede que a Ana criou funciona do mesmo jeito que a bridge padrão, só que separada — é uma "segunda ponte" só dela:

# diagrama da app-net (rede criada com docker network create app-net)

host (notebook da Ana)
  └── app-net (bridge própria) .. gateway 172.18.0.1, faixa 172.18.0.0/16
        ├── container "meu-banco" ... 172.18.0.2  (5432/tcp — sem -p, só interna)
        └── container "minha-api" ... 172.18.0.3  (3000 → publicada na 3000 do host)
              └── DNS interno em 127.0.0.11 resolve "meu-banco" → 172.18.0.2

  └── bridge (padrão) ........... outros containers que não usam --network ficam aqui

Isolamento na prática: da app-net, ninguém alcança os containers da bridge padrão pelo nome (nem pelo IP, se as faixas não se cruzam) — são prédios diferentes.

Resumo dos subcomandos

ComandoO que faz
docker network lsLista as redes (use --filter e -q para filtrar/ só nomes).
docker network create app-netCria uma rede bridge própria, com DNS automático por nome de container.
docker network connect app-net webLiga um container existente à rede (ele pode ficar em várias).
docker network disconnect app-net webDesliga o container da rede.
docker network inspect app-netMostra o JSON da rede: sub-rede, gateway e containers conectados (com IPs).
docker network rm app-netRemove a rede (só se não tiver container conectado e não for de fábrica).
docker network pruneRemove todas as redes personalizadas não usadas por nenhum container.
SintomaCausa
predefined network bridge cannot be removedTentou apagar bridge/host/none — não pode
network app-net has active endpointsTem container conectado: disconnect ou remova o container antes
No such container: site no connectNome do container errado — confira com docker ps
network … not found no rm/inspectNome da rede errado — confira com docker network ls

Missão: crie a sua primeira rede: rode docker network create app-net e depois confirme com docker network ls — o nome app-net deve aparecer na lista.

Missão extra: depois de criar a rede, rode docker network inspect app-net no terminal abaixo e veja o help do subgrupo (no simulador, o inspect cai no help que lista "one or more networks").

Resumo

  • Além de bridge/host/none, você cria redes próprias com docker network create NOME (driver bridge por padrão, com --subnet/--gateway/--label opcionais).
  • Rede própria = isolamento entre projetos + DNS automático por nome de container dentro dela.
  • Suba containers nela com --network app-net; um container pode estar em várias redes (docker network connect/disconnect depois do run).
  • docker network inspect app-net mostra sub-rede, gateway e os containers conectados com IPs — e com --format dá para extrair só os nomes.
  • docker network rm falha se a rede for de fábrica (predefined network … cannot be removed) ou tiver container conectado (has active endpoints).
  • docker network prune limpa as redes personalizadas não usadas.
