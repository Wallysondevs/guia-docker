FROM — a imagem base

Toda imagem nova nasce em cima de uma imagem existente. A instrução FROM é a primeira linha obrigatória de todo Dockerfile: ela escolhe o "ingrediente base" da sua receita — o sistema operacional e as ferramentas que já vêm de fábrica. A escolha certa deixa a imagem pequena, segura e rápida de baixar; a escolha errada deixa tudo isso ao contrário.

Você vai aprender
  • Como funciona o FROM: repositório, tag e o library/ do Docker Hub.
  • Como escolher a base: alpine, slim ou imagem completa — com tabela de tamanhos.
  • O que é a tag :latest e por que fixar a versão (pinagem): tag de versão maior, versão exata e digest @sha256:….
  • Por que o FROM tem que ser a primeira instrução e por que o último FROM vence.
  • A sintaxe FROM … AS nome (base do multi-stage) e o caso especial FROM scratch.
  • O erro real de uma tag que não existe e como descobrir as tags disponíveis.

A cena: a Ana escolhe a base do projeto dela

A Ana está criando a minha-api, uma API em Node.js. Ela abre o editor no notebook (ana@notebook) e precisa decidir: começa de que imagem? Ela testa as opções puxando cada uma e vendo o tamanho:

$ docker pull node:22-alpine
$ docker pull node:22-slim
$ docker pull node:22
$ docker images node
REPOSITORY   TAG       IMAGE ID       CREATED       SIZE
node         22-alpine c3d4e5f6a1b2   1 week ago    189MB
node         22-slim   f6a1b2c3d4e5   1 week ago    407MB
node         22        1a2b3c4d5e6f   1 week ago    1.09GB

Mesma versão do Node (22), três pacotes bem diferentes: 189MB, 407MB, 1GB. A diferença é o sistema operacional embaixo: Alpine (distro mínima, ~5MB) ou Debian completo. Para a API dela, que só precisa do Node para servir requisições, o alpine sobra. Ela escreve no Dockerfile:

FROM node:22-alpine

A anatomia do FROM

FROM
a instrução que declara a imagem base. Sem ela, o build nem começa — o Docker não sabe em cima do que empilhar as camadas.
node
o repositório: a imagem oficial node da biblioteca do Docker Hub. Quando você não põe usuário, o Docker completa com docker.io/library/node.
:22-alpine
a tag: a "versão" dentro do repositório — aqui, Node 22 na variante Alpine. Se você omitir a tag, o Docker assume :latest (a mais recente).
FROM node:22-alpine

Outras formas de escrever a mesma coisa:

FROM docker.io/library/node:22-alpine     # nome completo, com registry e library
FROM node@sha256:9f8e7d6c…                # pelo digest: o conteúdo exato, imutável
Parte do nomeExemploSignificado
Registrydocker.ioO "supermercado" de imagens. Se omitir, o Docker usa o Docker Hub.
Usuário/organizaçãolibrary ou anaImagens oficiais ficam em library/; as suas ficam em seu-usuario/.
RepositórionodeO nome da imagem em si.
Tag:22-alpineA versão/variante. Sem tag, vale :latest.
Digest@sha256:9f8e…O hash do conteúdo: aponta sempre para a mesma imagem, não importa a tag.

Escolhendo a base: alpine, slim ou completa

A mesma aplicação pode começar de bases bem diferentes. A regra geral: comece pequeno e só cresça se precisar — você sempre pode trocar depois.

VarianteTamanho típico da baseExemplosQuando usar
alpinebase ~5–8MB (com app, ~50–200MB)node:22-alpine, nginx:alpine, python:3.12-alpine, postgres:16-alpineQuase sempre: imagem enxuta, menos superfície de ataque, download rápido. Usa o gerenciador de pacotes apk e a biblioteca musl em vez da glibc.
slimbase ~45–80MBpython:3.12-slim, node:22-slim, debian:12-slimQuando você precisa do Debian (glibc) e não do Alpine — alguns binários compilados (ou pacotes como alguns de Python/C++) só funcionam no Debian.
completa (ex.: node:22)base ~350MB–1GBnode:22, ubuntu:24.04, debian:12Quando precisa de ferramentas de sistema completas (compiladores, git, vim, debug). Em produção, prefira slim/alpine.

Na dúvida, teste as duas e compare com docker images — como a Ana fez acima. E lembre: segurança também é tamanho: quanto menos coisa instalada na imagem, menos porta aberta para um ataque.

Cuidado com o Alpine: nem tudo roda lá. O Alpine usa a biblioteca musl em vez da glibc do Debian. A maioria das apps em Node/Python/Go funciona de boa, mas pacotes nativos compilados para glibc (certos drivers de banco, bibliotecas de machine learning) podem quebrar. Se algo misterioso acontece no Alpine, tente a variante slim antes de desistir.

Tags e pinagem: fuja do :latest em produção

A tag é a "versão" da imagem. Quando você escreve só FROM node, o Docker completa com node:latest — e o latest anda no tempo: hoje aponta para o Node 22, amanhã pode apontar para o 23. Dois builds com o mesmo Dockerfile, em meses diferentes, podem gerar imagens diferentes. Em produção e em CI, isso quebra a previsibilidade.

Para builds reproduzíveis, fixe a versão. Do mais frouxo para o mais travado:

node:22-alpine
fixa a versão maior (22) — recebe atualizações de segurança do 22.x automaticamente.
node:22.9.0-alpine
fixa a versão exata (22.9.0) — não muda nem com patch de segurança.
node@sha256:9f8e…
fixa pelo digest (hash do conteúdo) — a imagem nunca muda, nem se a tag for republicada. Máxima segurança e rastreabilidade.

Veja como o digest aparece no pull:

$ docker pull node:22-alpine
22-alpine: Pulling from library/node
a1b2c3d4e5f6: Pull complete
b2c3d4e5f6a1: Pull complete
c3d4e5f6a1b2: Pull complete
Digest: sha256:9f8e7d6c5b4a3f2e1d0c9b8a7f6e5d4c3b2a19f8e7d6c5b4a3f2e1d0c9b8a7f6
Status: Downloaded newer image for node:22-alpine
docker.io/library/node:22-alpine

A linha Digest: sha256:… é o que você pode copiar para o seu Dockerfile se quiser travar tudo: FROM node@sha256:9f8e7d6c….

Veja as tags disponíveis de uma imagem oficial na página dela no Docker Hub (ex.: hub.docker.com/_/node → aba "Tags"), como a Ana fez antes de escolher.

Imagens oficiais: de onde elas vêm

docker pull node na verdade baixa docker.io/library/node:latest: o library/ é o repositório das imagens oficiais, mantidas pela comunidade ou pela empresa junto com a Docker, e auditadas. Imagens de outros usuários ficam em docker.io/usuario/imagem — e aí a confiança muda de figura. A aula Imagens oficiais e verificadas detalha como confiar numa imagem (Docker Official Images, Verified Publisher,assinatura com cosign).

Vários FROM no mesmo arquivo: o último vence

Um Dockerfile pode ter mais de um FROM. Quando isso acontece, cada FROM começa uma etapa nova do build, e a imagem final é a da última etapa — as anteriores servem só para produire artefatos que você copia para a final (é o multi-stage). Sem AS, a última etapa é anônima:

FROM node:22-alpine
RUN echo "etapa 1: só para testar"

FROM alpine:3.20
CMD ["echo", "só a etapa final vira imagem"]

Nesse exemplo, o RUN echo acontece durante o build, mas o resultado não entra na imagem final — só a etapa do alpine:3.20 vira imagem.

FROM … AS nome: a porta do multi-stage

Você pode dar um nome para a etapa do build com AS. Isso permite usar várias etapas no mesmo Dockerfile e copiar o resultado de uma para a outra — a base dos multi-stage builds (nível 3, aula Multi-stage builds):

# etapa 1: compila a aplicação (nomeada "build")
FROM node:22-alpine AS build
WORKDIR /app
COPY . .
RUN npm run build

# etapa 2: imagem final só com o resultado (nomeada "final")
FROM nginx:alpine AS final
COPY --from=build /app/dist /usr/share/nginx/html

A imagem final carrega só o site compilado — sem Node, sem node_modules, bem menor. O COPY --from=build copia da etapa chamada build; é explicado na aula COPY, ADD e WORKDIR. Você também pode referenciar etapas por número: COPY --from=0 ….

O caso especial: FROM scratch

Existe uma imagem base vazia, chamada scratch: ela não tem sistema operacional nenhum, só o seu programa. É usada para binários estáticos (programas em Go, C, Rust compilados sem dependências) que não precisam de shell nem de bibliotecas:

FROM scratch
COPY ola-estatico /ola
CMD ["/ola"]

A imagem resultante tem só o seu binário — pode ter menos de 10MB. É o extremo oposto do node:22 de 1GB. Quando o seu app é um binário estático, scratch é a base perfeita (e a mais segura: não tem nada dentro para atacar).

Quando dá errado

Tag inexistente (já vimos acima): FROM node:99-naoexiste quebra o build com not found. Como consertar: confira as tags na página do Docker Hub e corrija a tag.
RUN antes do FROM: o Dockerfile precisa começar pela base: 
# ERRADO
RUN echo "oi"
FROM alpine:3.20
O build falha na hora com erro de parse (unknown instruction na linha 1, porque fora de uma etapa não existe instrução válida antes do FROM). Como consertar: FROM sempre primeiro; comentários com # são a única coisa permitida antes dele.
Esquecer os dois pontos da tag: FROM node 22-alpine (espaço no lugar de :) é lido como repositório node + argumento extra, e o build acusa erro de parse. A tag vai grudada no nome com :: node:22-alpine.
Registry privado sem login: se o seu FROM aponta para um registry da empresa (registry.empresa.com/minha-base:1.0) e você não fez docker login, o build falha com pull access denied. Como consertar: docker login registry.empresa.com antes do build (aula Registry privado e login).

Resumo

  • FROM é a primeira instrução obrigatória do Dockerfile e escolhe a imagem base: FROM repositorio:tag, com :latest implícito quando a tag falta.
  • O nome completo é registry/usuario/repositorio:tag; imagens oficiais ficam em docker.io/library/….
  • Escolha a base pelo tamanho e pela necessidade: alpine (~5MB, musl/apk) na maioria dos casos, slim (Debian enxuto, glibc) quando precisar de compatibilidade, completa só em dev, scratch para binários estáticos.
  • Em produção, fixe a versão: :22 (versão maior) ou, para travar tudo, o digest @sha256:…. Evite :latest.
  • Vários FROM no mesmo arquivo criam etapas; a imagem final é a da última etapa. FROM … AS nome nomeia a etapa para o COPY --from do multi-stage.
  • Erros reais: tag inexistente (not found), RUN antes do FROM, tag separada por espaço em vez de :, registry privado sem docker login.
