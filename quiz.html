Parte 1 — imagem, container e o comando run

As duas primeiras perguntas são o alicerce de tudo: a diferença entre imagem (o modelo, somente leitura, formado por camadas) e container (a instância criada a partir dessa imagem, com uma camada de escrita em cima), e o que as flags -d e -it fazem de verdade no docker run. Se você decorou só uma coisa deste guia, que seja a primeira pergunta. 2. Qual é a diferença entre -d e -it no docker run?

Lembrou a regra? -d = detach (segundo plano, terminal livre); -it = interactive + tty (você entra dentro do container). E para sair do modo interativo sem matar o container: Ctrl-P Ctrl-Q (aula Modo interativo).

Parte 2 — portas e persistência

Agora as duas pegadinhas que mais pegam quem está começando: o formato -p 8080:80 (quem é host, quem é container? dica: sempre HOST:CONTAINER, e a prova aparece na coluna PORTS do docker ps como 0.0.0.0:8080->80/tcp) e o que acontece com os arquivos gravados num container sem volume quando ele é apagado. 4. Você gravou arquivos dentro de um container sem volume e depois apagou o container. O que acontece com esses arquivos?

Exato: a escrita de um container vai para a camada de escrita dele, que morre com o docker rm. Para dados que precisam sobreviver (banco de dados, uploads), use -v com volume nomeado ou bind mount — é o papel dos volumes no projeto do WordPress.

Parte 3 — build, run e Compose

Chegamos ao fluxo do dia a dia: quem cria a imagem (docker build, a partir do Dockerfile) e quem cria o container (docker run, a partir da imagem) — e o que o docker compose up faz quando o projeto tem vários serviços de uma vez (cria rede, volumes e todos os containers). Aulas de revisão: docker build, compose up e down e os projetos 2 e 3, que usam exatamente esse fluxo.

5. Qual é a ordem correta para criar sua própria imagem e rodar um container dela?

6. O que o comando docker compose up faz?

7. Para que serve a flag --rm no docker run?

O trio build → run → compose é o esqueleto de todo o guia: build empacota, run executa um container, compose up executa vários. E o --rm é perfeito para testes e tarefas one-shot — o container some sozinho ao terminar, sem deixar lixo no docker ps -a.

Gabarito comentado

Depois de responder tudo, releia as respostas com calma — este é o resumo do guia em 10 linhas:

  1. Imagem × container: a imagem é o modelo somente leitura (camadas empilhadas); o container é a instância criada a partir dela, com uma camada de escrita em cima. (aula: Conceitos)
  2. -d × -it: -d roda em segundo plano e libera o terminal; -it abre um terminal interativo dentro do container (saia com Ctrl-P Ctrl-Q sem matar). (docker run, modo interativo)
  3. -p 8080:80: formato HOST:CONTAINER — a 8080 da sua máquina publica a 80 do container. (Portas)
  4. Sem volume, os dados somem: a escrita do container vai para a camada temporária, apagada com o docker rm. Para persistir, use -v. (Volumes)
  5. build → run: docker build cria a imagem a partir do Dockerfile; docker run cria o container a partir da imagem. (docker build)
  6. compose up: cria e inicia todos os serviços do docker-compose.yml — containers, rede e volumes. (compose up/down)
  7. --rm: apaga o container automaticamente ao terminar — ideal para testes e tarefas one-shot. (flags do run)
  8. multi-stage: vários FROM no mesmo Dockerfile; a imagem final recebe só o necessário, sem as ferramentas de build. (Multi-stage)
  9. --read-only: monta o sistema de arquivos do container como somente leitura (use --tmpfs para exceções). (--read-only)
  10. HEALTHCHECK: o Docker roda um comando de tempos em tempos dentro do container e marca o status como healthy/unhealthy. (HEALTHCHECK)
