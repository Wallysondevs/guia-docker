Imagens oficiais e verificadas

No Docker Hub qualquer um pode publicar uma imagem. Saber escolher a certa evita dor de cabeça — e brecha de segurança. Nesta aula a Ana aprende a ler os selos e os sinais de confiança antes de dar docker pull numa imagem desconhecida.

Você vai aprender
  • Os três selos do Hub: Official Image, Verified Publisher, Docker Sponsored OSS.
  • O que olhar numa página de imagem: pulls, atualização, descrição, Dockerfile público, tags.
  • A anatomia do endereço: docker.io/namespace/repo:tag — e o que é o library.
  • Os riscos de imagem aleatória: código malicioso, root por padrão, segredos embutidos.
  • Como escanear vulnerabilidades (docker scout) e inspecionar camadas.

Os selos

SeloSignificadoExemplo
🐳 Official ImageMantida pela equipe do próprio software (ou pela Docker Inc.). É a escolha padrão — auditada, atualizada, com Dockerfile público.nginx, postgres, node, python, redis, mysql
✔ Verified PublisherEmpresa verificada pela Docker Inc. — o nome da empresa foi confirmado.bitnami/*, grafana/*, mongo (MongoDB Inc.)
💙 Docker Sponsored OSSProjeto open source patrocinado pela Docker — comunidade, não a empresa do software.várias imagens de projetos open source
(sem selo)Publicado por um usuário comum. Pode ser ótimo ou perigoso — olhe os sinais abaixo.usuarioaleatorio/app

Regra prática: na dúvida, prefira oficial > verified >社区 com muitos pulls e atualização recente > aleatória.

A anatomia do endereço no Hub

hub.docker.com / _ / nginx        → oficial (o "_" é o apelido de "library")
hub.docker.com / bitnami / nginx  → editor verificado (Bitnami)
hub.docker.com / ana / meuapp     → usuário comum "ana"

No terminal, o mesmo endereço aparece completo: docker.io/library/nginx, docker.io/bitnami/nginx, docker.io/ana/meuapp. O library (mostrado como _ no site) é o namespace das oficiais.

O que olhar antes de usar

  1. O selo (tabela acima).
  2. Pulls e stars: quanto mais, mais popular (e mais testada pela comunidade). postgres tem bilhões de pulls; uma imagem com 12 pulls precisa de mais escrutínio.
  3. Última atualização: imagem parada há anos pode ter vulnerabilidades connues. Prefira "Updated X days ago".
  4. A descrição: boa imagem explica como usar, quais variáveis de ambiente aceita (POSTGRES_PASSWORD…), quais portas expõe e dá exemplo de docker run.
  5. O Dockerfile público: nas oficiais, o link leva ao repositório do Dockerfile — dá para auditar exatamente o que foi instalado.
  6. A aba Tags: escolha a tag certa (aula tags) — evite :latest em produção.
Sinal verde ✅Sinal vermelho 🚩
Selo oficial/verificadoSem selo e poucos pulls
Atualizada há dias/semanasParada há anos

Os riscos de uma imagem aleatória

Uma imagem é um sistema de arquivos inteiro rodando na sua máquina (e, se publishar portas, na rede). Uma imagem maliciosa pode:

  • roubar variáveis de ambiente (senhas que você passou com -e ficam legíveis dentro do container — e no docker inspect);
  • minerar criptomoeda às suas custas (CPU em 100% — dá para ver no docker stats);
  • abrir uma porta escondida e servir de ponte para a sua rede;
  • modificar os arquivos que você monta com -v (se não usar :ro).
Segurança: nunca rode uma imagem aleatória em produção sem inspecionar. Prefira oficiais ou verificadas, faça scan de vulnerabilidades e, quando montar pastas do host, use :ro (somente leitura). A aula Analisando camadas (dive) mostra como ver o que tem dentro de uma imagem, e usuário não-root endurece a execução.

Escaneando vulnerabilidades

O próprio Docker tem um scanner integrado (Docker Scout), grátis para uso pessoal no Hub:

$ docker scout quickview nginx:alpine
$ docker scout cves nginx:alpine        « lista as CVEs conhecidas dessa imagem
$ docker scout recommendations nginx:alpine   « sugere uma imagem base mais atualizada

Também dá para ativar o scan automático no Docker Desktop: toda imagem que você baixa aparece com o resumo de vulnerabilidades na aba Images.

As oficiais mais usadas (e suas variáveis)

Estas são as imagens oficiais que aparecem neste guia. Na página de cada uma no Hub está a lista de variáveis de ambiente que ela aceita — é lá que você descobre, por exemplo, a senha do banco:

nginxServidor web / proxy reverso— (config via volume)80
postgresBanco relacionalPOSTGRES_PASSWORD (obrigatória), POSTGRES_USER, POSTGRES_DB5432
mysqlBanco relacionalMYSQL_ROOT_PASSWORD, MYSQL_DATABASE, MYSQL_USER3306

Essas variáveis você passa com -e (aula variáveis de ambiente).

De oficial a sua própria imagem: o caminho

  1. Você cria a imagem com docker build (nível 2, aula Dockerfile).
  2. Dá um nome no formato do Hub: docker tag meuapp:latest ana/meuapp:1.0 (seu usuário do Hub + nome + tag).
  3. Faz login: docker login.
  4. Publica: docker push ana/meuapp:1.0 — aula docker tag e push.
Nunca publique segredos dentro de uma imagem

Uma imagem publicada no Hub é pública (a menos que você pague por repositório privado). Se você pôs uma senha no Dockerfile (ENV API_KEY=…) ou copiou um arquivo .env com COPY, qualquer um que baixar a imagem vê. Regra: segredos vão por variável de ambiente na hora do run (-e) ou por volume — nunca na imagem. E use .dockerignore (aula .dockerignore) para não mandar .env no build.

Alternativas modernas e endurecidas

Além das oficiais, existem opções focadas em segurança e tamanho (nível 3 aprofunda):

TipoExemploQuando usar
Distroless (Google)gcr.io/distroless/nodejs22Produção enxuta e segura: só o runtime, sem shell, sem gerenciador de pacotes — superfície de ataque mínima
Chainguard Imagescgr.dev/chainguard/nginxImagens sem vulnerabilidades conhecidas (zero CVE), assinadas
Bitnami (Verified Publisher)bitnami/postgresqlBanco pronto para produção, com helm charts e configs padrão

As imagens distroless não têm shell — ou seja, docker exec -it … sh não funciona dentro delas (debug fica mais difícil). É o trade-off: segurança × conveniência. A aula Imagens distroless e Alpine compara.

Conferindo a assinatura/integridade

Além do digest (hash do conteúdo), dá para exigir assinaturas criptográficas com DOCKER_CONTENT_TRUST=1 — o Docker só baixa/ roda imagens assinadas:

$ export DOCKER_CONTENT_TRUST=1
$ docker pull ana/meuapp:1.0     « se a imagem não for assinada por ana, o pull recusa

Procurando imagem pelo terminal: docker search

Além do site, dá para procurar no próprio terminal (comando real do Docker CLI):

$ docker search postgres --filter "is-official=true"
NAME      DESCRIPTION                    STARS   OFFICIAL
postgres  The PostgreSQL object-relational…  15000   [OK]
$ docker search nginx --filter "is-automated=true"   « builds automáticos (CI)
$ docker search redis --limit 10                     « só os 10 primeiros

Os filtros is-official=true, is-verified=true e stars=100 (mínimo de estrelas) ajudam a achar coisa confiável rápido.

Cuidado com "automated builds" antigos

Builds automáticos de usuários aleatórios podem estar desatualizados há anos e cheios de vulnerabilidades. Se for usar um sem selo, cheque a data do último push e o Dockerfile. Para produção, oficial/verificado ou a sua própria imagem.

Resumo

  • No Docker Hub qualquer um publica. Ordem de confiança: 🐳 Official Image (namespace library) > ✔ Verified Publisher > comunidade com muitos pulls e atualização recente > aleatória.
  • Conferir antes: selo, pulls/stars, última atualização, descrição com exemplos de uso, Dockerfile público, aba Tags.
  • Riscos de imagem aleatória: roubo de variáveis (-e), minerador, porta escondida, acesso a pastas montadas com -v (use :ro).
  • Scan de vulnerabilidades: docker scout cves IMAGEM (ou o scan automático do Desktop).
  • Endereço completo: docker.io/namespace/repo:tag; no site, oficiais aparecem como _/repo.
