Variáveis de ambiente (-e)

Muitas imagens precisam de configuração na hora de subir: a senha do banco, o modo de produção, a porta interna. Você passa isso com -e NOME=valor — sem trocar a imagem, só mudando o comportamento do container. Pense numa variável de ambiente como um "interruptor e mostrador" do programa dentro da caixa.

Você vai aprender
  • Para que servem variáveis de ambiente num container (config sem trocar imagem).
  • -e NOME=valor (uma ou várias vezes) e -e NOME (herda do seu shell).
  • --env-file .env: ler várias de um arquivo.
  • Exemplos reais: POSTGRES_PASSWORD, MYSQL_ROOT_PASSWORD, NODE_ENV.
  • Como ver as variáveis dentro do container (printenv) e no docker inspect.
  • Segurança: variáveis aparecem no docker inspect — não bote segredos nelas em máquina compartilhada.

A ideia: a mesma caixa, regulagens diferentes

A imagem postgres é sempre a mesma — mas cada uso precisa de uma senha diferente. Em vez de criar uma imagem por senha, você passa a senha como variável de ambiente na hora do run:

$ docker run -d --name banco \
    -e POSTGRES_PASSWORD=segredo123 \
    -e POSTGRES_USER=ana \
    -e POSTGRES_DB=minha_loja \
    -p 127.0.0.1:5432:5432 \
    postgres:16-alpine

A página da imagem no Docker Hub lista as variáveis que ela aceita (para o postgres: POSTGRES_PASSWORD é obrigatória — sem ela o container nem sobe).

ImagemVariáveis típicas
postgresPOSTGRES_PASSWORD*, POSTGRES_USER, POSTGRES_DB
mysqlMYSQL_ROOT_PASSWORD*, MYSQL_DATABASE, MYSQL_USER, MYSQL_PASSWORD
redissenha via config; REDIS_ARGS em imagens variantes
node (sua API)NODE_ENV=production, PORT=3000, DATABASE_URL=…
nginxNGINX_HOST, NGINX_PORT (imagens variantes)

* obrigatórias — se faltarem, o container inicia e cai na hora (veja o erro com docker logs).

Uma variável, várias, e herdar do seu shell

-e POSTGRES_PASSWORD=segredo
Define POSTGRES_PASSWORD com o valor segredo dentro do container. A flag pode repetir: -e A=1 -e B=2 -e C=3.
-e MINHA_VAR
Sem =: o Docker pega o valor da variável do seu shell e passa para dentro. Ex.: se no seu terminal export API_KEY=abc, então docker run -e API_KEY … leva abc para dentro.
espaços no valor
Se o valor tem espaço, ponha entre aspas: -e "MOTD=Bem vinda, Ana".
$ docker run -d --name api \
    -e NODE_ENV=production \
    -e PORT=3000 \
    -e DATABASE_URL \
    -p 3000:3000 \
    node:22-alpine node server.js     « DATABASE_URL veio do shell da Ana

--env-file: várias variáveis de um arquivo .env

Quando são muitas variáveis, junte num arquivo .env (um NOME=valor por linha):

$ cat .env
NODE_ENV=production
PORT=3000
DATABASE_URL=postgres://ana:segredo@banco:5432/loja
$ docker run -d --env-file .env -p 3000:3000 --name api node:22-alpine node server.js

O Compose (nível 2) também lê .env sozinho — aula docker-compose.yml.

Nunca commite o .env no Git

O .env tem senhas. Coloque .env no .gitignore e mantenha um .env.example só com os nomes (sem valores) para a equipe saber o que precisa preencher.

Vendo as variáveis dentro do container

Duas formas. A primeira, rodando printenv dentro do container com docker exec (aula exec):

Missão: suba um container com variável (docker run -d -e NODE_ENV=production --name api node:22-alpine) e rode docker exec api printenv NODE_ENV para ver a variável dentro dele.

$ docker run -d -e NODE_ENV=production --name api node:22-alpine
$ docker exec api printenv NODE_ENV
production
$ docker exec api printenv          « todas as variáveis do container
PATH=/usr/local/sbin:…
NODE_ENV=production
…

A segunda, sem entrar no container: o docker inspect mostra as variáveis na seção Env:

$ docker inspect api --format '{{range .Config.Env}}{{println .}}{{end}}'
PATH=/usr/local/sbin:…
NODE_ENV=production
Segurança: variáveis ficam visíveis no docker inspect

Qualquer pessoa com acesso ao Docker da máquina vê as variáveis de todos os containers pelo docker inspect. Em máquina compartilhada ou servidor de produção, prefira passar segredos por volumes (arquivo montado com permissão restrita) ou por sistemas de segredos (Docker Secrets no Swarm — nível 3). Nunca deixe senha hardcoded na imagem (via ENV no Dockerfile): qualquer um que baixa a imagem vê.

Regra prática: padrão público vai no Dockerfile (ENV); segredo e config de ambiente vão no -e/.env. A aula EXPOSE, ENV e ARG aprofunda a parte do Dockerfile.

Exemplo completo: API + banco com variáveis

Juntando o que a Ana aprendeu: um banco Postgres e uma API, conversando por variáveis de ambiente:

$ docker run -d --name banco \
    -e POSTGRES_PASSWORD=segredo123 \
    -e POSTGRES_USER=ana \
    -e POSTGRES_DB=loja \
    -p 127.0.0.1:5432:5432 \
    postgres:16-alpine
$ docker run -d --name api \
    -e NODE_ENV=production \
    -e DATABASE_URL=postgres://ana:segredo123@banco:5432/loja \
    -p 3000:3000 \
    --link banco \
    node:22-alpine node server.js
$ docker exec api printenv DATABASE_URL
postgres://ana:segredo123@banco:5432/loja
$ curl -s http://localhost:3000/produtos | head -c 120
[{"id":1,"nome":"Caderno","preco":19.9},…

Repare: a API reaches o banco pelo nome banco (o Docker resolve nomes de containers na mesma rede — aula containers se comunicando, nível 2).

Debugando: o container sobe e cai na hora

Sintoma clássico de variável obrigatória faltando:

$ docker run -d --name banco2 postgres:16-alpine    « esqueceu a POSTGRES_PASSWORD
$ docker ps -a
… Exited (1) 2 seconds ago   banco2
$ docker logs banco2
Error: Database is uninitialized and superuser password is not specified.
       You must specify POSTGRES_PASSWORD to a non-empty value for superuser…

O propio log diz o que faltou. Esse padrão — ps -a vê Exited (1), logs explica — é o fluxo de debug de qualquer container (aula erros comuns resume a tabela).

Debug: "a variável não chegou dentro do container"

Sintoma comum: você passou -e e o programa diz que a variável está vazia. Checklist:

  1. Nome certo? docker exec X printenv lista todas — procure a sua (Cuidado: maiúsculas importam: node_env ≠ NODE_ENV).
  2. Valor com espaço? Tem que ir entre aspas: -e "TITULO=Olá mundo" — sem aspas, o shell quebra em dois.
  3. Usa -e VAR (herda do shell) mas a variável não estava exportada? Faça export VAR=valor antes do run.
  4. Está no .env mas esqueceu o --env-file .env? Ou o arquivo não está na pasta atual?
  5. O programa lê a variável só na inicialização — se o container já estava rodando, recria: docker rm X + run de novo.
-e não persiste

As variáveis passadas com -e valem só para aquele container. Se você recriar sem o -e, elas somem (a menos que estejam no ENV da imagem). Para não esquecer: mantenha um .env ou um script/compose com os -e.

Boas práticas com variáveis

  • Um lugar só para a lista: mantenha um .env.example no projeto (só os nomes) e o .env real no .gitignore — a equipe toda sabe o que precisa preencher.
  • Nomeie com o padrão do programa: a imagem oficial diz quais variáveis aceita (ex.: POSTGRES_PASSWORD). Não invente nome — o programa não vai ler.
  • Valores com espaço ou caracteres especiais: sempre entre aspas: -e "MSG=olá, tudo bem?".
  • Não misture camadas: ENV no Dockerfile para o que é fixo e público; -e/.env para o que muda por ambiente ou é segredo.
  • Verifique depois: docker exec X printenv — ver com os olhos beats adivinhar.

Resumo

  • Variáveis de ambiente configuram o programa dentro do container sem trocar a imagem: -e NOME=valor (repita a flag para várias).
  • -e NOME (sem =) herda o valor do seu shell. --env-file .env lê várias de um arquivo (cuidado para não commitar o .env!).
  • Exemplos reais: POSTGRES_PASSWORD (obrigatória no postgres), MYSQL_ROOT_PASSWORD, NODE_ENV=production, PORT, DATABASE_URL.
  • Para ver dentro do container: docker exec X printenv. De fora: docker inspect X (seção Env) — e é por isso que segredo não vai em -e em máquina compartilhada.
  • ENV no Dockerfile = valor fixo e público gravado na imagem; -e no run = valor por container, pode sobrescrever o ENV.
