EXPOSE, ENV e ARG

Três instruções que configuram a imagem sem copiar nenhum arquivo: EXPOSE documenta qual porta a aplicação usa, ENV grava variáveis de ambiente permanentes na imagem e o ARG recebe valores na hora do build (via --build-arg), sumindo depois. Juntas elas respondem às três perguntas: "que porta minha app usa?", "quais variáveis ela precisa para funcionar?" e "qual versão estou buildando?".

Você vai aprender
  • EXPOSE 3000: documentação da porta — e por que ela não publica nada sozinha (só -p publica; -P publica todas as declaradas).
  • ENV: variáveis fixas na imagem, visíveis no build (nos RUN) e no runtime — e sobrescrevíveis com -e no docker run.
  • Os dois formatos do ENV: ENV chave=valor (recomendado) e o antigo ENV chave valor.
  • ARG: argumento de build com valor padrão, entregue por --build-arg — e o truque ENV X=$ARG para gravá-lo.
  • A diferença entre ENV, ARG e o -e do docker run (tabela comparativa).
  • Por que ARG não serve para senhas (docker history entrega o valor).

A cena: a API da Ana precisa de configuração

A API da Ana ouve na porta 3000, precisa saber que está em produção (NODE_ENV=production) e recebe a versão do app na hora do build (para logar "versão 2.3 no ar"). No Dockerfile dela, isso vira EXPOSE, ENV e ARG — três linhas que não copiam arquivo nenhum, mas mudam o comportamento da imagem.

EXPOSE: documentar a porta (não publicar!)

Dentro do container, a sua aplicação ouve numa porta (a API Node ouve na 3000, o Nginx na 80). O EXPOSE serve para documentar isso na imagem — quem lê o Dockerfile ou faz docker inspect vê a porta declarada:

EXPOSE 3000

Você pode declarar várias de uma vez: EXPOSE 3000 8080. E dá para informar o protocolo: EXPOSE 3000/tcp (tcp é o padrão; /udp existe para jogos e DNS).

Erro comum: achar que EXPOSE publica a porta para fora. Não publica. A porta só fica acessível de fora com -p no docker run (aula Publicando portas). A Ana já caiu nessa: 
$ docker run -d --name api api:1.0
$ curl http://localhost:3000
curl: (7) Failed to connect to localhost port 3000   « o EXPOSE não publicou nada
$ docker run -d -p 3000:3000 --name api2 api:1.0     « agora sim: host 3000 → container 3000
$ curl http://localhost:3000
{"mensagem":"olá do container!"}
A única exceção é docker run -P (P maiúsculo), que publica automaticamente todas as portas declaradas com EXPOSE em portas aleatórias do host — útil para testes rápidos: 
$ docker run -d -P --name api3 api:1.0
$ docker ps
…  0.0.0.0:32768->3000/tcp   api3   « o host escolheu a 32768 para a 3000 do container

ENV: variáveis de ambiente fixas na imagem

O ENV grava uma variável dentro da imagem. Ela fica disponível durante o build (os comandos RUN enxergam) e durante a execução (o CMD e qualquer docker exec enxergam):

FROM node:22-alpine
ENV NODE_ENV=production
ENV APP_NAME="minha-api"

Formatos aceitos: ENV chave=valor (recomendado, e permite várias na mesma linha: ENV A=1 B=2) e o formato antigo ENV chave valor (onde tudo depois do espaço vira o valor — por isso evite: ENV NOME Ana Beatriz vira valor "Ana Beatriz", com espaço).

A Ana confirma que a variável chegou dentro do container:

$ docker run --rm api:1.0 node -e "console.log(process.env.NODE_ENV)"
production

Variáveis do ENV podem ser sobrescritas na hora do docker run com -e (aula Variáveis de ambiente): docker run -e NODE_ENV=development api:1.0 — o valor do -e ganha do valor do ENV.

ENV
"grave esta variável na imagem".
NODE_ENV=production
formato chave=valor. Em Node, NODE_ENV=production ativa otimizações (menos logs, cache de views etc.).
APP_NAME="minha-api"
valores com espaço vão entre aspas duplas.
Erro comum: aspas no lugar errado. ENV NODE_ENV="production" (aspas só no valor) funciona, mas ENV "NODE_ENV=production" (aspas em volta de tudo) grava uma variável de nome estranho. A forma segura é sem aspas quando não tem espaço: ENV NODE_ENV=production.

ARG: argumento que só existe durante o build

O ARG declara um parâmetro do build. Ele recebe valor com --build-arg no docker build e não fica gravado como variável na imagem final — some depois do build. Perfeito para versões, flags de compilação e coisas que mudam entre builds mas não entre runs:

FROM node:22-alpine
ARG VERSAO=1.0
ENV APP_VERSION=$VERSAO
WORKDIR /app
COPY . .
CMD ["node", "server.js"]

A Ana builda passando a versão real do release:

$ docker build --build-arg VERSAO=2.3 -t api:2.3 .
…
Successfully tagged api:2.3
$ docker run --rm api:2.3 node -e "console.log(process.env.APP_VERSION)"
2.3
docker build
o comando de build.
--build-arg VERSAO=2.3
entrega o valor 2.3 para o ARG chamado VERSAO declarado no Dockerfile.
-t api:2.3
nome e tag da imagem gerada.
.
o contexto do build.

Se o --build-arg não for passado, vale o padrão declarado no Dockerfile (ARG VERSAO=1.0 → 1.0). Truque comum: ENV APP_VERSION=$VERSAO copia o valor do ARG para uma variável permanente da imagem, como no exemplo acima — o ARG em si some, o ENV fica.

ARG não é segredo: o valor passado com --build-arg fica registrado no histórico da imagem — docker history api:2.3 mostra a instrução com o valor. Nunca use ARG para senhas ou tokens: qualquer um que baixa a imagem vê o histórico. Para segredos de build existem os build secrets (RUN --mount=type=secret, nível 3); para segredos de runtime, use -e ou volumes de tmpfs.

As três formas de passar variáveis confundem porque todas parecem "colocar uma variável no container". A diferença é quando e onde cada uma existe:

Quando dá errado

Achar que EXPOSE publica a porta: rodar docker run -d api:1.0 sem -p e tentar acessar de fora dá curl: (7) Failed to connect. EXPOSE é só documentação (metadado da imagem). Como consertar: publique com -p 3000:3000 ou deixe todas pública com -P.
ARG sem valor e sem padrão: se o Dockerfile declara ARG VERSAO (sem =1.0) e o build não passa --build-arg, a variável fica vazia — e ENV APP_VERSION=$VERSAO grava string vazia, sem erro. A app pode quebrar só no runtime com "versão vazia". Como consertar: sempre dê um padrão (ARG VERSAO=1.0) ou valide no build.
Usar ARG para senha: ARG DB_PASSWORD + --build-arg DB_PASSWORD=123456 parece prático, mas o valor fica no docker history da imagem para sempre — e a imagem pode ser publicada no registry. Como consertar: senha nunca vai em ARG/ENV do Dockerfile: use -e no run, --env-file, ou build secrets (RUN --mount=type=secret).
ENV com espaço sem aspas: ENV MSG olá mundo (formato antigo) grava MSG com valor "olá mundo" — mas no formato ENV MSG=olá mundo (com igual), o Docker lê MSG=olá e trata mundo como outra instrução — erro de parse. Como consertar: valor com espaço vai entre aspas: ENV MSG="olá mundo".

Quiz rápido

1. A Ana pôs EXPOSE 3000 no Dockerfile e rodou docker run -d api:1.0, mas não conseguiu acessar localhost:3000. Por quê?

2. Qual a diferença entre ARG e ENV no Dockerfile?

3. A Ana quer que a imagem já nasça com NODE_ENV=production, mas que dê para trocar na hora do run. Como ela faz?

4. Por que não se deve passar senhas com --build-arg?

Resumo

  • EXPOSE 3000 é documentação: diz que o container ouve na 3000, aparece no docker inspect, e serve para o -P publicar tudo — mas sozinho não abre porta nenhuma. Publicar é com -p no docker run.
  • ENV CHAVE=valor grava a variável na imagem: visível no build (nos RUN) e no runtime; o -e do docker run sobrescreve.
  • ARG NOME=padrao é argumento de build, entregue por --build-arg; não fica na imagem (só no histórico). O truque ENV X=$ARG grava o valor de vez.
  • Regra de escolha: valor fixo da imagem → ENV; valor que muda por build → ARG; valor que muda por ambiente/senha → -e no run (nunca no Dockerfile).
  • Erros reais: achar que EXPOSE publica porta; ARG sem padrão virando variável vazia; senha em ARG (fica no docker history); valor com espaço sem aspas no ENV.
