Builds otimizados para CI

O pipeline da aula Docker no CI rodava verde, mas cada execução levava 8 minutos — e 6 deles eram só o npm install rodando do zero. Por quê? Porque no CI cada build começa numa máquina limpa, sem cache local, e se o Dockerfile estiver mal ordenado qualquer vírgula no código invalida todas as camadas seguintes. Nesta aula a Ana reorganiza o build dela e o pipeline cai para menos de 1 minuto. As técnicas servem tanto para o CI quanto para o notebook dela.

Você vai aprender
  • Como funciona o cache de camadas: por que a ordem das instruções decide se o build leva 8 minutos ou 40 segundos.
  • A regra de ouro: dependências antes do código (COPY package*.json → RUN npm install → COPY . .).
  • .dockerignore agressivo: o que tirar do contexto e o erro real de tirar demais.
  • Multi-stage: imagem final enxuta, sem ferramentas de build (com tabela de tamanhos).
  • Cache entre execuções no GitHub Actions: cache-from/cache-to com type=gha e type=registry.
  • Buildx: builds multi-plataforma (amd64 + arm64) e docker buildx build --load.
  • Como medir: time docker build e docker system df para o cache.

A ideia: cada instrução é uma gaveta com cadeado

Cada instrução do Dockerfile vira uma camada (gaveta) na imagem. O Docker guarda o cache de cada gaveta: se a entrada da instrução não mudou desde o último build, ele reaproveita a gaveta inteira e imprime CACHED; se mudou, ele abre a gaveta, refaz o conteúdo e invalida todas as gavetas abaixo dela.

Imagine o Dockerfile como uma pilha de gavetas. Se a gaveta do npm install está acima da gaveta do código (COPY . .), qualquer mudança no código passa por cima e invalida o install. Se a gaveta do install está acima do código (ordem correta), mudar o código só refaz a última gaveta. É só isso — ordem das instruções.

A regra de ouro: dependências antes do código

Compare os dois Dockerfiles da API da Ana:

# Dockerfile RUIM — qualquer mudança no código refaz o npm install
FROM node:22-alpine
WORKDIR /app
COPY . .                  # código + package.json juntos: muda toda hora
RUN npm install           # ← invalida a cada vírgula alterada
EXPOSE 3000
CMD ["node", "app.js"]
# Dockerfile BOM — o npm install fica em cache
FROM node:22-alpine
WORKDIR /app
COPY package*.json ./     # muda só quando as dependências mudam (raro)
RUN npm install           # ← fica CACHED na maioria dos builds
COPY . .                  # muda toda hora, mas é a ÚLTIMA gaveta de build
EXPOSE 3000
CMD ["node", "app.js"]

A diferença na prática, no terminal da ana@notebook:

$ # build 1: tudo novo
$ time docker build -t api:latest .
...
#7 [4/5] RUN npm install
#7 2.87 added 58 packages in 3s
#7 DONE 3.1s
...
real  0m4.21s

$ # Ana muda UMA vírgula no app.js e refaz o build:
$ time docker build -t api:latest .
#6 [3/5] COPY package*.json ./
#6 CACHED                 « não mudou → reaproveitado
#7 [4/5] RUN npm install
#7 CACHED                 « idem: 0s em vez de 3s!
#8 [5/5] COPY . .
#8 DONE 0.2s               « só o código é reempacotado
...
real  0m0.68s               « 6x mais rápido

Mesma regra para outras linguagens: COPY requirements.txt → RUN pip install → COPY . . (Python), COPY go.mod go.sum → RUN go mod download → COPY . . (Go), COPY pom.xml → RUN mvn dependency:go-offline → COPY . . (Java). Sempre: manifesto de dependências primeiro, código depois.

LinguagemOrdem correta no Dockerfile
NodeCOPY package*.json ./ → RUN npm install → COPY . .
PythonCOPY requirements.txt . → RUN pip install -r requirements.txt → COPY . .
GoCOPY go.mod go.sum . → RUN go mod download → COPY . .
Java (Maven)COPY pom.xml . → RUN mvn -B dependency:go-offline → COPY . .

.dockerignore agressivo

Antes do build, o Docker envia a pasta inteira — o contexto — para o daemon. Se a pasta tem node_modules (dezenas de milhares de arquivos), .git, logs e afins, o envio sozinho pode levar minutos e o COPY . . copia essa porcaria para dentro da imagem. Solução: um arquivo .dockerignore na raiz do contexto (aula .dockerignore):

node_modules
npm-debug.log
.git
.gitignore
Dockerfile
.dockerignore
docker-compose*.yml
*.md
.env
.env.*
tests
coverage
.vscode
.idea
__pycache__
*.pyc
.venv

Como saber se o contexto está gordo? O próprio build conta:

$ docker build -t api:latest .
#2 [internal] load build context
#2 transferring context: 2.45MB done    « com .dockerignore agressivo
#2 DONE 0.1s
# (sem .dockerignore, a mesma pasta dava: transferring context: 184MB)
Cuidado: se o seu build precisa de um arquivo que você listou no .dockerignore, a imagem quebra na hora com COPY failed: file not found in build context or excluded by .dockerignore. A mensagem já entrega o culpado: tire o arquivo da lista.

Multi-stage: imagem final enxuta

Com multi-stage (aula Multi-stage builds) você usa uma primeira imagem completa para compilar e uma segunda, mínima, só com o resultado. Compiladores e devDependencies não vão para a imagem final:

# ---- stage 1: builder (imagem grande, só para compilar) ----
FROM node:22-alpine AS builder
WORKDIR /app
COPY package*.json ./
RUN npm install              # instala TUDO, inclusive devDependencies
COPY . .
RUN npm run build            # gera dist/ (ou compila TypeScript)

# ---- stage 2: imagem final (limpa) ----
FROM node:22-alpine
ENV NODE_ENV=production
WORKDIR /app
COPY package*.json ./
RUN npm install --omit=dev   # só dependências de produção
COPY --from=builder /app/dist ./dist
EXPOSE 3000
CMD ["node", "dist/server.js"]

O COPY --from=builder /app/dist ./dist é a mágica: copia só a pasta dist/ do estágio anterior para a imagem final. O resto do stage 1 (o node_modules completo, ferramentas de build) é descartado.

Versão da imagemTamanho típico (app Node)O que carrega
Sem multi-stage (build na imagem final)~450MBNode + devDependencies + ferramentas de build + código fonte
Com multi-stage (--omit=dev + só dist/)~195MBNode + só dependências de produção + código compilado
Base node:22-alpine pura189MBSó o Node sobre Alpine
Multi-stage + distroless/scratch (estático)~20–60MBSó o binário compilado (Go/Rust) — aula Distroless e Alpine

Por que isso importa no CI: imagem menor = push mais rápido, pull mais rápido nos servidores de produção, menos disco gasto em todo lugar, superfície de ataque menor (sem shell, sem gerenciador de pacotes dentro).

Cache no GitHub Actions (type=gha e type=registry)

O problema do CI: cada run começa numa máquina limpa, então o cache local do Docker não existe. A solução é exportar o cache para fora do runner. O docker/build-push-action oferece dois jeitos:

# trecho do workflow .github/workflows/ci.yml
      - name: Build e push (com cache do GHA)
        uses: docker/build-push-action@v6
        with:
          push: true
          tags: ${{ secrets.DOCKERHUB_USERNAME }}/minhaapp:latest
          cache-from: type=gha
          cache-to: type=gha,mode=max
  • cache-from: type=gha — lê o cache salvo no cache do próprio GitHub Actions (limite de 10GB por repositório, expulsa o mais antigo quando enche).
  • cache-to: type=gha,mode=max — salva todas as camadas intermediárias, não só a final (mode=min é o padrão e é mais limitado).
  • Alternativa quando o limite do GHA estoura: cache-from: type=registry,ref=usuario/minhaapp:buildcache e cache-to: type=registry,ref=usuario/minhaapp:buildcache,mode=max — guarda o cache como uma imagem especial no próprio registry.
  • Também dá para cache local com type=local (pasta no runner) — útil em runners self-hosted que persistem.

Com o cache no lugar, o segundo build do pipeline (com a mesma ordem de instruções correta) fica quase instantâneo:

$ docker build -t ana/minhaapp:latest .   « no 2º run do pipeline
#6 [3/5] COPY package*.json ./
#6 CACHED
#7 [4/5] RUN npm install
#7 CACHED                 « cache veio do type=gha!
#8 [5/5] COPY . .
#8 DONE 0.3s
...
[+] Building 1.2s (8/8) FINISHED   « era 8 minutos no 1º run

Buildx: o motor por trás dos builds

Os runners do GitHub e o Docker Desktop usam o BuildKit por padrão — é ele que imprime #1 [internal] load… e faz o cache funcionar. Com o buildx você cria builders avançados: builds para várias arquiteturas de uma vez (amd64 + arm64, para rodar no notebook x86 e no Raspberry Pi da Ana) e cache remoto:

$ docker buildx ls
NAME/NODE          DRIVER/ENDPOINT             STATUS
default *          docker
  desktop-linux    docker-container            running

$ docker buildx create --name cibuilder --use   « cria um builder novo
cibuilder

$ docker buildx build --platform linux/amd64,linux/arm64 -t ana/minhaapp:latest --push .
#1 [internal] load build definition from Dockerfile
...
#20 exporting to image
#20 pushing layers 12.4s done
#20 naming to docker.io/ana/minhaapp:latest done

No GitHub Actions, o passo docker/setup-buildx-action@v3 cria esse builder para você antes do build (já está no workflow da aula anterior). No notebook, dá para criar um builder com driver docker-container para isolar o build — útil quando o build quebra o build padrão.

O Build Cache é exactly o que o CACHED usa — e ele cresce para sempre até você limpar. No CI não importa (a máquina é descartada), mas no notebook vale rodar de vez em quando:

$ docker builder prune        « limpa só o cache de build ocioso
$ docker system prune        « limpa tudo que não está em uso (aula docker-system-prune)

Erros comuns em build otimizado

RUN falhou: 
#7 ERROR: process "/bin/sh -c npm install" did not complete successfully: exit code: 1
#7 2.912 npm error code E404
#7 2.912 npm error 404 Not Found - GET https://registry.npmjs.org/pacote-que-nao-existe
Quando uma instrução RUN falha, o build para na hora. Olhe as linhas acima do ERROR: geralmente é dependência quebrada no manifesto, arquivo faltando no contexto (culpa do .dockerignore) ou variável ARG faltando. A partir do BuildKit, dá para montar secrets no build sem gravar na imagem: RUN --mount=type=secret,id=npmrc ….
Cache "mágico" demais: se o npm install ficou CACHED mas você mudou o package.json, a ordem das instruções está errada — o COPY package*.json ./ deve vir antes do RUN npm install. Para forçar um build sem cache (debug), use docker build --no-cache -t api ..
Plataforma errada: exec format error ao rodar a imagem — você buildou para arm64 num runner amd64 (ou vice-versa). Solução: --platform linux/amd64 explícito no build, ou o setup-qemu + platforms do buildx.

Checklist de build otimizado

  • ☐ O Dockerfile copia o manifesto de dependências antes do código (package*.json, requirements.txt…).
  • ☐ Existe .dockerignore com node_modules/.git/__pycache__/.env…
  • ☐ Apps compilados usam multi-stage (imagem final limpa, --omit=dev).
  • ☐ No CI, o build-push-action tem cache-from: type=gha e cache-to: type=gha,mode=max.
  • ☐ Medi com time docker build … antes e depois — a melhora é visível no número.
  • ☐ No notebook, rodei docker builder prune de vez em quando para liberar disco.
