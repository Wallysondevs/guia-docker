docker history e dive — o que tem dentro da imagem

A Ana buildou a minha-api:1.0 com multi-stage e achou que estava tudo enxuto. Aí rodou docker images e viu 195MB — para uma API pequena, parecia muito. Antes de tentar emagrecer uma imagem às cegas, você precisa enxergar o que cada camada carrega e quanto pesa. Toda imagem é um empilhamento de camadas (aulas docker pull e Camadas e cache): o docker history mostra isso no terminal; o dive mostra visualmente, arquivo por arquivo.

Você vai aprender
  • Ler a saída do docker history: IMAGE, CREATED BY, SIZE e <missing>.
  • O desperdício clássico: instalar numa camada e limpar na outra (o rm não tira o peso).
  • Instalar e usar o dive, a ferramenta interativa de análise de camadas.
  • Comparar docker history × dive e quando usar cada um.
  • Uma receita de emagrecimento passo a passo.

A ideia: a imagem é uma pilha de fôlegos

Cada instrução que gera conteúdo no Dockerfile (RUN, COPY, ADD) vira uma camada — um fô Lego em cima do outro. O que você vê no sistema de arquivos do container é a soma de todas as camadas. O detalhe importante: apagar um arquivo numa camada nova não apaga ele da camada velha — ele só ganha uma "marca de apagado" por cima. É por isso que limpar numa camada separada não emagrece nada (já já você vê).

docker history: o raio-x da imagem

O comando lista as camadas da imagem, da mais recente para a mais antiga, com o comando que a criou e o tamanho que ela adicionou:

$ docker history nginx:alpine
IMAGE          CREATED       CREATED BY                                      SIZE      COMMENT
b2c3d4e5f6a1   5 days ago    CMD ["nginx" "-g" "daemon off;"]                0B
<missing>      5 days ago    STOPSIGNAL SIGQUIT                              0B
<missing>      5 days ago    EXPOSE map[80/tcp:{}]                           0B
<missing>      5 days ago    ENV NGINX_VERSION=1.27.3                        0B
<missing>      5 days ago    RUN /bin/sh -c set -eux;  apk add --no-cache …   19.2MB    « a camada gorda
<missing>      5 days ago    COPY file:9f2c… in /etc/nginx/nginx.conf       1.8kB
<missing>      6 days ago    ADD file:a1b2… in /                              8.5MB     « a base alpine
<missing>      6 days ago    CMD ["/bin/sh"]                                 0B
ColunaSignificado
IMAGEID da camada. Camadas intermediárias aparecem como <missing> — elas não viram imagem sozinhas, só existem dentro da pilha.
CREATED BYA instrução do Dockerfile (RUN, COPY, ADD, ENV…) que gerou a camada.
SIZEQuanto aquela camada adicionou ao tamanho total. Comandos só de configuração (ENV, EXPOSE, CMD, USER) pesam 0B.
COMMENTComentário da instrução (quando existe).

Somando a coluna SIZE você chega ao tamanho da imagem. No exemplo, a camada de 19.2MB do apk add é a maior — e é exatamente onde se procura瘦za. Útil também: docker history --no-trunc nginx:alpine mostra os comandos completos (sem cortar com "…"), e docker history -q mostra só os IDs.

O desperdício clássico: instalar e limpar em camadas separadas

Um erro comum no Dockerfile da Ana, na primeira tentativa:

FROM python:3.12-slim
RUN apt-get update && apt-get install -y gcc       « camada 1: instala o compilador (+150MB)
COPY . .
RUN apt-get remove -y gcc && rm -rf /var/lib/apt/lists/*   « camada 2: "limpa"

O rm apaga os arquivos na segunda camada, mas eles continuam existindo na primeira — o tamanho não diminui. O docker history prova isso:

$ docker history minha-api:errada
…
<missing>   2 min ago   RUN apt-get remove -y gcc && rm -rf …   0B    « parece que limpou…
<missing>   2 min ago   RUN apt-get update && apt-get install …   152MB  « …mas o peso continua aqui

A forma certa é fazer tudo no mesmo RUN, ligado por &&:

FROM python:3.12-slim
RUN apt-get update && apt-get install -y gcc \
 && pip install -r requirements.txt \
 && apt-get remove -y gcc \
 && rm -rf /var/lib/apt/lists/*          « tudo numa camada só: o peso some de verdade

Regra de ouro: cada RUN vira uma camada; junte as operações relacionadas num RUN só, com &&. Isso também deixa o cache mais eficiente (aula Camadas e cache).

dive: a mesma análise, visual e interativa

O dive abre a imagem numa interface de terminal: camadas à esquerda, árvore de arquivos da camada selecionada à direita, e um indicador de wasted space (espaço desperdiçado por arquivos apagados em camadas seguintes) + a eficiência da imagem (percentual de bytes realmente usados):

$ dive nginx:alpine

Instalação no notebook da Ana (Ubuntu):

$ curl -OL https://github.com/wagoodman/dive/releases/download/v0.12.0/dive_0.12.0_linux_amd64.tar.gz   « Linux
$ tar xzf dive_0.12.0_linux_amd64.tar.gz && sudo mv dive /usr/local/bin/
$ dive --version
dive 0.12.0

(No macOS é brew install dive.) Navegação: ↑/↓ troca de camada, Tab alterna entre a árvore de camadas e a árvore de arquivos, Ctrl+C sai. O dive também funciona em CI: dive minha-api:1.0 -j saida.json exporta a análise em JSON, e --ci faz o comando falhar (exit 1) se a eficiência estiver abaixo de um limite — dá para colocar isso na pipeline para impedir imagem gorda de entrar.

Receita para emagrecer uma imagem

Quando a Ana achou a imagem de 195MB grande demais, seguiu este roteiro:

  1. Rode docker history minha-api:1.0 --no-trunc e ache a camada mais gorda (quase sempre um RUN apt/apk/npm install ou um COPY . . que trouxe node_modules/.git).
  2. Se for COPY . .: crie um .dockerignore com node_modules, .git, *.log — o contexto de build fica leve.
  3. Se for instalação de pacotes: junte tudo num RUN só com && e limpe no mesmo comando (rm -rf /var/lib/apt/lists/*, apk del, npm prune).
  4. Se forem dependências de build (compilador, headers): mude para multi-stage e copie só o artefato.
  5. Se a base for grande: troque para -alpine ou -slim, ou vá de distroless para binários estáticos.
  6. Rebuild e compare: docker images antes e depois, e dive para confirmar a eficiência subiu.

Missão: rode docker images e compare a coluna SIZE das imagens que você tem — qual é a mais pesada?

Imagem grande por causa de dependências de build? Se o docker history mostrar uma camada gigante de node_modules ou binários compilados, o problema pode ser o COPY . . copiando coisa demais — resolva com .dockerignore e, para binários, com multi-stage builds.
Cenário real: o .git que foi parar na imagem

A Ana fez COPY . . sem .dockerignore e a imagem ganhou 40MB de histórico do git — além de vazar o código inteiro (com direito a credenciais antigas que já avaient sido cometidas e apagadas depois, que continuam no histórico). O .dockerignore com .git resolve o peso e o vazamento de uma vez. Mesma coisa vale para node_modules local, arquivos .env e logs.

Camadas compartilhadas: por que 10 imagens não ocupam 10× o espaço

Se cada imagem tem suas camadas, por que o disco não enche? Porque as camadas são compartilhadas entre imagens: se nginx:alpine e minha-api:1.0 usam a mesma base Alpine, o arquivo da base é guardado uma vez só no disco e as duas imagens apenas apontam para ele. É por isso que no push vimos Mounted from library/nginx — o registry também compartilha camadas entre repositórios.

Para ver quanto cada imagem ocupa de verdade (e não somando camadas compartilhadas), use docker system df -v:

$ docker system df -v
Images Space Usage:
REPOSITORY      TAG       IMAGE ID       CREATED         SIZE      SHARED SIZE   UNIQUE SIZE   CONTAINERS
nginx           alpine    c3d4e5f6a1b2   5 days ago      48.2MB    8.5MB         39.7MB        1
minha-api       1.0       f6a1b2c3d4e5   2 hours ago     195MB     8.5MB         186.5MB       1
…
Containers Space Usage: …
Local Volumes Space Usage: …

As colunas importantes: SHARED SIZE (quanto é compartilhado com outras imagens) e UNIQUE SIZE (quanto só aquela imagem ocupa). É o UNIQUE que conta para o disco — e é nele que o multi-stage e o .dockerignore fazem diferença.

Resumo

  • Toda imagem é uma pilha de camadas; docker history lista cada uma com o comando que a criou (CREATED BY) e o tamanho que adicionou (SIZE).
  • <missing> = camada intermediária; instruções de metadado (ENV/CMD/USER/EXPOSE) pesam 0B.
  • Apagar arquivo numa camada nova não tira o peso da camada velha — junte install + limpeza num RUN só com &&.
  • dive mostra a árvore de arquivos por camada, o desperdício e a eficiência; no CI dá para exportar JSON (-j) e falhar com --ci.
  • Para emagrecer: .dockerignore (tira .git/node_modules do contexto), base alpine/slim/distroless, multi-stage para dependências de build.
