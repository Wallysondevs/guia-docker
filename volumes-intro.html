Volumes (-v) — dados que persistem

Tudo que um container grava na sua camada própria some quando o container é apagado (docker rm). Para dados que devem durar — banco de dados, uploads, configurações — você usa um volume: uma pasta que fica fora do container e é "encaixada" dentro dele com -v.

Você vai aprender
  • Por que os dados do container somem com docker rm (a camada gravável).
  • Os dois jeitos de usar -v: bind mount (pasta do seu computador) e volume nomeado (pasta gerenciada pelo Docker).
  • A anatomia: -v HOST:CONTAINER, -v NOME:CONTAINER e o sufixo :ro (somente leitura).
  • Exemplo clássico: Nginx servindo os arquivos do seu site local.
  • Volume nomeado para banco de dados (Postgres) e docker volume ls.

O problema: o container é descartável

A Ana gravou um arquivo dentro de um container e apagou o container. O arquivo sumiu:

$ docker run --rm alpine sh -c "echo oi > /tmp/arquivo.txt && cat /tmp/arquivo.txt"
oi
$ docker run --rm alpine cat /tmp/arquivo.txt   « container NOVO: camada gravável nova, vazia
docker: Error response from daemon: …
cat: can't open '/tmp/arquivo.txt': No such file or directory

Cada docker run cria um container novo, com uma camada gravável nova e vazia em cima da imagem. O que foi gravado no container anterior ficou para trás — e foi apagado com o --rm/rm. A imagem (receita) não muda; só a "camada de uso" some.

Montar uma pasta do host (bind mount)

O caso mais comum do dia a dia: o site da Ana está numa pasta do computador dela, e ela quer que o Nginx do container sirva esses arquivos:

$ mkdir ~/meusite
$ echo "<h1>Olá, sou o site da Ana</h1>" > ~/meusite/index.html
$ docker run -d -p 8080:80 -v /home/ana/meusite:/usr/share/nginx/html:ro --name meu-site nginx:alpine
$ curl -s http://localhost:8080
<h1>Olá, sou o site da Ana</h1>     « o arquivo da pasta dela, servido pelo container!
-v /home/ana/meusite:/usr/share/nginx/html:ro
A flag volume.
/home/ana/meusite
O caminho no host (sua máquina) — precisa ser absoluto (começa com /).
:
Separa host de container.
/usr/share/nginx/html
O caminho dentro do container onde a pasta vai aparecer (no Nginx oficial, é de onde ele serve os arquivos).
:ro
read-only: o container só lê a pasta, não consegue apagar/alterar seus arquivos — mais seguro. Sem o :ro, o container pode gravar na sua pasta.

Agora editar o arquivo na sua máquina reflete no container na hora (é a mesma pasta!):

$ echo "<h1>Versão 2 do site</h1>" > ~/meusite/index.html
$ curl -s http://localhost:8080
<h1>Versão 2 do site</h1>

Isso é ouro para desenvolvimento: você edita o código no seu editor e o container já vê a mudança (algumas imagens recarregam sozinhas; outras precisam de docker restart).

Missão: explore como o simulador trata volumes: rode docker run -v $(pwd):/dados --rm alpine cat /dados/arquivo.txt (no simulador a saída é simplificada; no Docker real, mostraria o conteúdo do arquivo da sua pasta atual dentro do container).

Volume nomeado (gerenciado pelo Docker)

Para dados que o próprio container gera e que devem durar — o banco de dados é o exemplo clássico. Você não aponta para uma pasta sua; dá um nome e o Docker cria a pasta gerenciada em /var/lib/docker/volumes/:

$ docker run -d --name banco \
    -e POSTGRES_PASSWORD=segredo123 \
    -v dados-postgres:/var/lib/postgresql/data \
    postgres:16-alpine
$ docker volume ls
DRIVER    VOLUME NAME
local     dados-postgres
-v dados-postgres:/var/lib/postgresql/data
Como o primeiro nome não começa com / (não é um caminho absoluto), o Docker entende que é um volume nomeado e cria/usa dados-postgres.
/var/lib/postgresql/data
Onde o Postgres grava os dados dentro do container — essa pasta passa a viver no volume.

Agora o banco sobrevive a tudo:

$ docker rm -f banco          « apagou o container…
$ docker run -d --name banco \
    -e POSTGRES_PASSWORD=segredo123 \
    -v dados-postgres:/var/lib/postgresql/data \
    postgres:16-alpine        « …e recriou: os dados continuaram no volume ✅
$ docker exec banco psql -U postgres -c "SELECT count(*) FROM produtos;"
 42

Caminho relativo não funciona no -v 
$ docker run -v meusite:/dados nginx:alpine
docker: Error response from daemon: create meusite: "meusite" includes invalid characters for a local volume name…
# na real, caminho relativo vira nome de volume sem querer — use SEMPRE caminho absoluto no host:
$ docker run -v ~/meusite:/dados nginx   « ~ também não expande aqui!
$ docker run -v "$PWD/meusite":/dados nginx   « certo: $PWD expande para o caminho absoluto
Permissões: o container roda como root (por padrão)

Se o container gravar numa pasta sua (sem :ro), os arquivos vão aparecer como dono root no seu computador — e aí você pode ter dificuldade para editar/apagar. Soluções: use :ro quando o container só precisa ler; ou rode o container com seu usuário (-u $(id -u):$(id -g)); ou ajuste o usuário na imagem (nível 3, aula usuário não-root).

Dados somem sem volume

Se você subiu um banco sem -v e deu docker rm, os dados foram junto — e não tem lixeira. Regra de ouro: todo container que guarda dados recebe um volume no mesmo run.

Em -v /home/ana/site:/usr/share/nginx/html:ro, o que é o :ro?

Qual a diferença entre -v /home/ana/dados:/dados e -v meusdados:/dados?

A Ana apagou o container do Postgres com docker rm e os dados sumiram. O que faltou?

Onde o volume mora de verdade?

Um volume nomeado é uma pasta no host (no Linux, em /var/lib/docker/volumes/<nome>/_data). Dá para inspecionar:

$ docker volume inspect dados-postgres
[
  {
    "Name": "dados-postgres",
    "Driver": "local",
    "Mountpoint": "/var/lib/docker/volumes/dados-postgres/_data",
    "Scope": "local"
  }
]
$ docker volume ls
DRIVER    VOLUME NAME
local     dados-postgres
$ docker volume rm dados-postgres     « apaga o volume (e os dados!) — só com o container parado
Error response from daemon: remove dados-postgres: volume is in use - container «…...

Apagar volume apaga os dados de vez — por isso o Docker só deixa apagar volume sem container usando. Para backup, monte o volume num container temporário e copie de lá (veja a linha de backup na tabela acima). A aula docker inspect em volumes detalha.

Exemplo completo: site + banco com persistência

$ docker run -d --name banco \
    -e POSTGRES_PASSWORD=segredo123 -e POSTGRES_DB=loja \
    -v dados-postgres:/var/lib/postgresql/data \
    postgres:16-alpine
$ docker run -d --name meu-site \
    -p 8080:80 \
    -v /home/ana/meusite:/usr/share/nginx/html:ro \
    nginx:alpine
$ docker ps
CONTAINER ID   IMAGE              STATUS         PORTS                   NAMES
f3a1…          nginx:alpine       Up 5 seconds   0.0.0.0:8080->80/tcp    meu-site
d4e5…          postgres:16-alpine Up 3 seconds   5432/tcp                banco
$ docker rm -f meu-site banco && docker system prune -f   « apagou tudo…
$ docker run -d --name banco -e POSTGRES_PASSWORD=segredo123 -e POSTGRES_DB=loja \
    -v dados-postgres:/var/lib/postgresql/data postgres:16-alpine   « …e o banco voltou COM os dados ✅

Volume anônimo e tmpfs (visión rápida)

Além de bind mount e volume nomeado, existem dois tipos que aparecem no nível 2 (volumes a fundo):

  • Volume anônimo: -v /dados (só o caminho do container). O Docker cria um volume sem nome na hora. Serve para dados que devem durar mais que o container, mas que você não precisa referenciar depois. Cuidado: volumes anônimos órfãos acumulam disco — limpe com docker volume prune.
  • tmpfs: --tmpfs /cache monta a pasta na memória RAM (rápido, mas some com o container e não ocupa disco). Ideal para cache e dados temporários sensíveis (não ficam gravados no disco).

Resumo dos três jeitos de persistir

Precisa de…Use
Editar o código no host e ver no container na horabind mount -v $PWD/site:/usr/share/nginx/html:ro
Dados do banco que sobrevivam a rm e recriaçõesvolume nomeado -v dados-db:/var/lib/postgresql/data

Resumo

  • O container é descartável: o que ele grava na camada própria some com docker rm. A imagem (receita) continua.
  • -v HOST:CONTAINER (caminho absoluto) = bind mount: monta uma pasta sua dentro do container (ótimo para código em dev; use :ro para só leitura).
  • -v NOME:CONTAINER (sem / inicial) = volume nomeado: pasta gerenciada pelo Docker, ideal para dados de banco. Veja com docker volume ls.
  • Regra de ouro: container que guarda dados recebe volume no próprio run.
  • Cuidados: caminho do host sempre absoluto ($PWD/…, não ~/…); sem :ro o container (root) pode gravar na sua pasta e criar arquivos como root.
  • Tipos a fundo (tmpfs, anonymous volumes, docker volume create/rm): aula volumes a fundo (nível 2).
