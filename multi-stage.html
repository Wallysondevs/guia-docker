Multi-stage builds — imagens enxutas

A Ana terminou o Dockerfile da API da Loja Aurora e, proud of herself, rodou docker images: a imagem tinha 1,1GB. Ela olhou a lista e viu o problema — o compilador, o npm inteiro, as dependências de teste e o node_modules completo tinham ido parar dentro da imagem final, junto com o app. Num Dockerfile comum, tudo que você instala para construir fica também na imagem de rodar. O multi-stage build resolve isso com vários FROM no mesmo Dockerfile: o estágio de build é descartado e o estágio final copia somente o artefato.

Você vai aprender
  • Por que ferramentas de build na imagem final são um problema (tamanho, start lento, superfície de ataque).
  • A sintaxe FROM … AS nome e COPY --from=nome ….
  • Exemplo completo em Node.js (build → runtime) e em Python.
  • Exemplo em Go terminando em FROM scratch (só o binário).
  • Ler a saída do BuildKit (Docker Engine 27) e usar --target.
  • Tamanhos antes e depois — e por que imagem menor é mais segura.

O problema: ferramentas de build na imagem final

No notebook da Ana, a comparação do antes e depois ficou assim:

$ docker images

node         22            a1b2c3d4e5f6   2 weeks ago     1.09GB

minha-api    multi-stage   f6a1b2c3d4e5   1 minute ago    195MB   « só o necessário

Imagem grande = pull lento no deploy, start lento, mais espaço em disco no servidor e superfície de ataque maior: cada ferramenta extra (compilador, npm, git) é uma porta de entrada a mais que pode ter um bug explorável. A ideia do multi-stage é simples: compile numa imagem grande, rode numa pequena.

EstágioPara que serveO que fica neleVai para a imagem final?

A sintaxe: vários FROM no mesmo Dockerfile

Um Dockerfile multi-stage tem dois ou mais FROM. Cada FROM começa um estágio novo, do zero — como se fosse um Dockerfile separado. O nome depois de AS serve para referenciar o estágio num COPY --from:

FROM node:22-alpine AS build
Inicia o estágio 1 e dá o nome build para ele (o AS é opcional, mas com nome dá para referenciar depois; sem nome, dá para referenciar por número: --from=0).
FROM node:22-alpine AS runtime
Inicia o estágio 2 — é o último estágio que vira a imagem final.
COPY --from=build /app/dist ./dist
Copia um arquivo de outro estágio (não do contexto de build): só o artefato sai do estágio de build para o final.

Os estágios intermediários são descartados depois do build — nunca aparecem na imagem final nem no docker images (só como cache de build, que pode ser limpo com docker system prune).

Exemplo completo: app Node.js

Este é o Dockerfile que a Ana usa na API da Loja Aurora (em ~/minha-api):

# ---- estágio 1: build (imagem grande, descartada depois) ----
FROM node:22-alpine AS build
WORKDIR /app
COPY package*.json ./
RUN npm install            # devDependencies entram aqui (precisam do compilador)
COPY . .
RUN npm run build          # gera a pasta dist/

# ---- estágio 2: imagem final só com o necessário ----
FROM node:22-alpine AS runtime
WORKDIR /app
ENV NODE_ENV=production
COPY --from=build /app/dist ./dist
COPY --from=build /app/node_modules ./node_modules
COPY package*.json ./
USER node                  # usuário não-root (aula de segurança)
EXPOSE 3000
CMD ["node", "dist/server.js"]

Repare na ordem: no estágio de build, o npm install (com devDependencies) acontece antes do COPY . . para aproveitar o cache de camadas (aula Camadas e cache) — como package.json muda pouco, essa camada fica em cache e o build voa. No estágio final, só dist/ e node_modules de produção são copiados de lá.

Detalhe que salva build: npm ci --omit=dev no lugar de npm install --omit=dev. Em vez de copiar tudo e instalar tudo no estágio final, dá para fazer o build completo no estágio 1 e no estágio 2 rodar só npm ci --omit=dev com o package*.json — assim o node_modules de produção é recriado limpo, sem ferramentas de build. As duas formas funcionam; a segunda deixa a imagem ainda mais enxuta.

Exemplo Python: build de wheels no estágio 1

Em Python, o truque clássico é compilar as dependências (wheels) num estágio e instalar no outro — porque algumas libs (ex.: psycopg2, pillow) precisam de compilador C, que não deve ir para a imagem final:

# ---- estágio 1: compila as wheels ----
FROM python:3.12-slim AS build
WORKDIR /wheels
COPY requirements.txt .
RUN pip wheel --no-cache-dir -r requirements.txt -w /wheels

# ---- estágio 2: instala as wheels e copia o app ----
FROM python:3.12-slim AS runtime
WORKDIR /app
RUN useradd -m appuser
COPY --from=build /wheels /wheels
COPY requirements.txt .
RUN pip install --no-cache-dir --no-index --find-links=/wheels -r requirements.txt \
 && rm -rf /wheels
COPY . .
USER appuser
EXPOSE 8000
CMD ["python", "-m", "uvicorn", "main:app", "--host", "0.0.0.0"]

O --no-index --find-links=/wheels instala só das wheels compiladas no estágio anterior — sem rede e sem compilador na imagem final. E o rm -rf /wheels no mesmo RUN garante que a pasta não pese na camada (lembre da aula docker history/dive: limpar numa camada separada não adianta).

Exemplo Go: FROM scratch (só o binário)

Em Go dá para ir ao extremo: compilar um binário estático (CGO_ENABLED=0) e copiar só ele para a imagem scratch — uma base vazia de 0MB, sem shell, sem nada:

# ---- estágio 1: compila ----
FROM golang:1.23-alpine AS build
WORKDIR /src
COPY go.mod go.sum ./
RUN go mod download
COPY . .
RUN CGO_ENABLED=0 go build -o /out/server .

# ---- estágio 2: imagem final mínima ----
FROM scratch
COPY --from=build /out/server /server
USER 65532:65532
EXPOSE 8080
ENTRYPOINT ["/server"]
Atenção aos detalhes do scratch: a imagem não tem shell (debugue com docker logs, nunca com docker exec … sh), nem certificados CA (se o app faz HTTPS para fora, copie /etc/ssl/certs/ca-certificates.crt do estágio de build com COPY --from=build) e nem /etc/passwd — por isso o usuário precisa ser numérico: USER 65532. Se precisar de shell só para debug, use FROM alpine no lugar do scratch e aceite os ~8MB a mais.

Lendo a saída do build (BuildKit, Engine 27)

O builder padrão desde o Docker 23 é o BuildKit — a saída mostra cada estágio com o nome que você deu, e dá para ver exatamente o que foi descartado:

Repare nos prefixos [build …] e [runtime …]: dá para ver o build rodando os dois estágios em paralelo quando dá. E o Successfully built no fim é a confirmação de que a imagem final foi gerada.

--target: buildar só até um estágio

Para debugar o estágio de build (entrar num container com todas as ferramentas, o código-fonte e o node_modules de dev), aponte o --target para ele:

$ docker build --target build -t minha-api:debug .
…
Successfully tagged minha-api:debug

$ docker run -it --rm minha-api:debug sh   « shell completo, só para investigar
/ #
Nunca publique a imagem :debug — ela carrega o compilador e todas as dependências de build. Multi-stage existe justamente para isso não ir para a imagem final. Se precisar publicar, publique só a tag final (minha-api:1.0).

Além de disco, imagem menor significa pull mais rápido no deploy (cada servidor baixa menos), start mais rápido, menos CVEs para se preocupar e — bônus — menos espaço para um atacante esconder ferramentas. Segurança e performance no mesmo truque. Quer saber exatamente quanto cada camada pesa? Aula docker history e dive.

Erros comuns

Nome de estágio errado quebra o build: se o COPY --from=build referencia um estágio que não existe (você esqueceu o AS build), o build falha na hora com failed to solve: … stage "build" not found. Dá para referenciar por número também: COPY --from=0 … (o primeiro estágio é o 0). E lembre: o contexto do build continua sendo a pasta inteira — use .dockerignore para não enviar node_modules e .git para o daemon (elespesam no envio e podem vazar segredos).
"COPY --from" copiando o contexto inteiro: um erro comum é fazer COPY --from=build /app /app no estágio final, o que traz node_modules de dev e código-fonte junto. Copie só o que o runtime precisa: /app/dist, não /app.
Esquecer o estágio final: se o Dockerfile termina no estágio de build (sem o segundo FROM), a imagem final é o estágio de build inteiro — exatamente o problema que o multi-stage veio resolver. Sempre termine com o estágio enxuto.

Missão: rode docker build --help no terminal abaixo e procure as flags -t, --target e --build-arg. No simulador o comando dispara um build de exemplo — repare no Successfully built no fim da saída.

Missão extra: depois do build, rode docker images e compare a coluna SIZE: a imagem que o simulador criou vs. as imagens oficiais. Qual é a mais pesada?

Resumo

  • Multi-stage = vários FROM no mesmo Dockerfile; só o último estágio vira a imagem final.
  • FROM imagem AS nome nomeia o estágio; COPY --from=nome caminho dest copia só o artefato dele (ou --from=0 pelo número).
  • Build em imagem grande (node:22, golang, python completo), runtime em imagem pequena (alpine, slim, scratch, distroless).
  • Imagem menor = pull/start mais rápidos, menos disco e menos superfície de ataque (menos ferramentas = menos CVEs).
  • --target build gera a imagem do estágio intermediário para debug — nunca publique essa tag.
  • Erros reais: stage "build" not found (esqueceu o AS) e copiar /app inteiro em vez de só /app/dist.
