Projeto 3: Fullstack com Compose

Chegou o projeto "de verdade". A Ana está montando um mini-app de tarefas para o trabalho da faculdade: um frontend em React que o navegador acessa, uma API em Node que processa as requisições e um banco PostgreSQL que guarda as tarefas. Em vez de subir um container por vez na mão, ela descreve os três num arquivo docker-compose.yml e sobe tudo com um comando só. Isso é Docker Compose em ação.

Você vai aprender
  • A arquitetura de uma aplicação fullstack em containers (quem fala com quem, e por qual porta).
  • Escrever um docker-compose.yml com vários serviços, comentado linha a linha.
  • Como os serviços se encontram pelo nome na rede interna que o Compose cria.
  • depends_on (ordem de subida), variáveis de ambiente, arquivo .env e volumes nomeados.
  • Dockerfile multi-stage para o frontend (build do React numa imagem, Nginx servindo o resultado na outra).
  • docker compose up -d --build, compose ps, compose logs, exec no banco e compose down.
  • Erros reais: banco ainda não aceitando conexão e variável de ambiente faltando.

A arquitetura: três ilhas que se conversam por nomes

Antes de escrever qualquer arquivo, a Ana desenhou no caderno como a aplicação funciona. O navegador fala só com o frontend; o frontend fala só com a API; a API fala só com o banco. Ninguém acessa o banco direto da internet — e no Compose isso acontece naturalmente, porque só o frontend e a API publicam portas:

navegador (sua máquina)
   │  http://localhost:5173
   ▼
┌─────────────┐   http://api:3000   ┌─────────┐   postgresql://db:5432   ┌────────────┐
│  frontend   │ ───────────────────► │   api   │ ───────────────────────► │     db     │
│  (nginx)    │                      │ (node)  │                          │ (postgres) │
│  porta 5173 │ ◄─────────────────── │ porta   │ ◄─────────────────────── │  sem porta │
└─────────────┘     JSON             │  3000   │       resultados SQL     │  publicada │
                                      └─────────┘                          └────────────┘
        ▲ todos na mesma rede interna "appnet" criada pelo Compose ▲

O detalhe poderoso: dentro da rede do Compose, cada serviço responde pelo próprio nome (api, db) — o Docker tem um DNS interno que traduz esses nomes para o IP de cada container. É por isso que a API usa DATABASE_URL=postgresql://postgres:segredo@db:5432/app: o db ali não é um IP, é o nome do serviço. A aula Containers se comunicando por nome mostra como isso funciona.

Passo 2: o docker-compose.yml, comentado

Este é o arquivo que orquestra tudo. Leia os comentários com calma — cada linha tem um motivo:

# docker-compose.yml — projeto fullstack da Ana
services:                 # cada serviço vira um container

  frontend:               # acessível no navegador: http://localhost:5173
    build: ./frontend     # constrói a imagem a partir do Dockerfile da pasta ./frontend
    ports:
      - "5173:80"         # host 5173 → container 80 (nginx serve o build do React lá)
    depends_on:
      - api               # sobe depois da api (só ordem — não espera "ficar pronto")
    networks:
      - appnet

  api:                    # a API do projeto 2, agora falando com o banco
    build: ./api
    environment:
      # "db" é o NOME do serviço do banco na rede interna do Compose (DNS interno)
      DATABASE_URL: ${DATABASE_URL}
      NODE_ENV: production
    ports:
      - "3000:3000"       # também publicada para testar direto com curl
    depends_on:
      - db
    networks:
      - appnet

  db:                     # banco de dados — SEM porta publicada (só a rede interna alcança)
    image: postgres:16-alpine
    environment:
      POSTGRES_USER: postgres
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD}
      POSTGRES_DB: app
    volumes:
      - pgdata:/var/lib/postgresql/data   # volume nomeado: os dados sobrevivem ao down
    networks:
      - appnet

networks:
  appnet:                 # declara a rede interna compartilhada pelos três

volumes:
  pgdata:                 # declara o volume nomeado usado pelo db

Pontos-chave para gravar:

  • build: ./api diz ao Compose para construir a imagem a partir do Dockerfile daquela pasta. Se fosse imagem pronta do Hub, seria image: postgres:16-alpine (como no serviço db). Dá para ter os dois: build + image nomeia a imagem construída.
  • ports segue o formato "HOST:CONTAINER", igual ao -p do run. O db não tem ports: ele só é alcançável pelos outros containers da appnet — banco não deve ficar exposto na internet.
  • volumes: pgdata:/var/lib/postgresql/data monta um volume nomeado no caminho onde o PostgreSQL grava os dados. Mesmo com docker compose down, o volume continua existindo — os dados não se perdem. Só down -v apaga volumes.
  • ${DATABASE_URL} e ${POSTGRES_PASSWORD} são lidos do arquivo .env na mesma pasta (veja o passo 4).
  • depends_on garante só a ordem de subida, não que o serviço esteja pronto para receber conexões. Para esperar "pronto de verdade", usa-se healthcheck + condition: service_healthy (nível 3, aula HEALTHCHECK).

Passo 3: os Dockerfiles (frontend multi-stage e api)

frontend/Dockerfile — build de React numa imagem, Nginx servindo na outra

O frontend usa multi-stage (aula Multi-stage builds): o primeiro estágio compila o React com Node; o segundo copia só os arquivos prontos (dist/) para uma imagem limpa de Nginx:

# ---- stage 1: build do React ----
FROM node:22-alpine AS build
WORKDIR /app
COPY package*.json ./
RUN npm install
COPY . .
RUN npm run build        # gera /app/dist

# ---- stage 2: imagem final, só nginx + arquivos prontos ----
FROM nginx:alpine
COPY --from=build /app/dist /usr/share/nginx/html
COPY nginx.conf /etc/nginx/conf.d/default.conf
EXPOSE 80
server {
    listen 80;
    root /usr/share/nginx/html;
    index index.html;

    # tenta o arquivo pedido; se não existir, devolve o index.html
    # (é o truque das SPA: rotas como /tarefas são servidas pelo React)
    location / {
        try_files $uri $uri/ /index.html;
    }

    # proxy: tudo que começa com /api/ vai para o serviço "api" na porta 3000
    location /api/ {
        proxy_pass http://api:3000/;
    }
}

O proxy_pass http://api:3000/ é o pulo do gato do frontend: o navegador chama /api/tarefas no próprio frontend, e o Nginx repassa a requisição para o container api — de novo, pelo nome do serviço, que o DNS interno resolve.

api/Dockerfile e api/app.js — a API com rota de banco

FROM node:22-alpine
WORKDIR /app
COPY package*.json ./
RUN npm install
COPY . .
EXPOSE 3000
CMD ["node", "app.js"]
const express = require('express');
const { Pool } = require('pg');
const app = express();

const pool = new Pool({ connectionString: process.env.DATABASE_URL });

app.get('/', (req, res) => {
  res.json({ mensagem: 'Olá do fullstack!', ambiente: process.env.NODE_ENV || 'development' });
});

app.get('/saude', (req, res) => res.json({ status: 'ok' }));

app.get('/tarefas', async (req, res) => {
  const resultado = await pool.query('SELECT * FROM tarefas ORDER BY id');
  res.json(resultado.rows);
});

app.listen(3000, '0.0.0.0', () => console.log('API rodando na porta 3000'));

O pacote pg é o driver do PostgreSQL para Node. A tabela tarefas é criada na primeira subida (a Ana rodou um CREATE TABLE via psql — passo 6).

Passo 4: o arquivo .env (senhas fora do YAML e do git)

Reparou nos ${DATABASE_URL} e ${POSTGRES_PASSWORD} no compose? Eles são preenchidos a partir de um arquivo .env na mesma pasta do docker-compose.yml — o Compose lê esse arquivo sozinho:

POSTGRES_PASSWORD=segredo
DATABASE_URL=postgresql://postgres:segredo@db:5432/app
$ echo ".env" >> .gitignore   « o .env NUNCA vai para o git
$ cat .gitignore
.env
node_modules
Erro real do Compose: se a variável não existir no .env nem no ambiente, o Compose avisa e segue com valor vazio: 
$ docker compose up -d
WARN: The "POSTGRES_PASSWORD" variable is not set. Defaulting to a blank string.
Nesse caso o PostgreSQL sobe sem senha (ou a API recebe uma URL errada e o /tarefas quebra). Sempre confira o .env antes do primeiro up.

Três detalhes na saída:

Isso é a diferença entre container e volume: o container é descartável, o volume persiste. Para apagar tudo, inclusive os dados, use docker compose down -v — mas pense duas vezes antes.

Erros comuns neste projeto

Banco ainda não aceitando conexões: 
$ docker compose logs api
fullstack-api-1  | Error: connect ECONNREFUSED 172.18.0.3:5432
    at TCPConnectWrap.afterConnect [as oncomplete] (node:events:515:16)
A API subiu antes do PostgreSQL terminar de inicializar — o depends_on só ordena a subida, não espera o banco ficar pronto. Soluções: (1) rode docker compose up -d de novo depois de alguns segundos (a API reinicia e conecta); (2) o jeito certo: declare um healthcheck no serviço db e no api use depends_on: db: condition: service_healthy.
Serviço não acha o outro pelo nome: getaddrinfo ENOTFOUND db — quase sempre o serviço que procurava não está na mesma rede. No nosso YAML, os três estão em appnet; se um serviço ficar sem o bloco networks:, ele cai na rede padrão e não enxerga os outros por nome.
Porta 5173 ocupada: Bind for 0.0.0.0:5173 failed: port is already allocated — mude o lado esquerdo do ports: no YAML (ex.: "5174:80") e acesse localhost:5174. O lado direito (80) não muda, porque é a porta do Nginx dentro do container.
O frontend carrega mas a chamada /api/… falha: confira o proxy_pass no nginx.conf — o nome api ali precisa ser exatamente o nome do serviço no compose, e o serviço precisa estar na mesma rede.

  • ☐ O compose declara os 3 serviços na mesma rede appnet, e só frontend/api têm ports.
  • ☐ docker compose up -d --build criou rede + volume + 3 containers Started.
  • ☐ docker compose ps mostrou os três; curl localhost:3000 respondeu JSON.
  • ☐ Entrei no banco com docker exec -it fullstack-db-1 psql …, criei a tabela e inseri linhas; /tarefas devolveu os dados.

Resumo

  • O Compose sobe vários containers de uma vez a partir de um YAML: rede e volumes são criados automaticamente, e cada serviço vira um hostname na rede interna.
  • Só publique portas dos serviços que o mundo externo precisa (frontend/api); o banco fica só na rede interna.
  • Variáveis vêm do .env (${VAR} no YAML) — nunca commite senhas; WARN: variable is not set é o aviso de que algo faltou.
  • Volumes nomeados persistem os dados entre down e up; down -v apaga tudo.
  • depends_on ordena a subida mas não espera "pronto" — para isso, healthcheck + condition: service_healthy.
  • Erros típicos: ECONNREFUSED (banco ainda subindo), ENOTFOUND db (serviço fora da mesma rede), porta ocupada no host.
