Docker no CI/CD (GitHub Actions)

A Ana terminou a API do projeto 2, subiu o código no GitHub e... o deploy quebrou. "Mas funcionava na minha máquina!" — a frase mais famosa da programação. A causa: o servidor de produção tinha uma versão diferente do Node, faltava variável de ambiente, o npm install rodou diferente... Com Docker, o ambiente do CI (a máquina que testa o código sozinha) é idêntico ao da máquina dela e ao da produção: tudo acontece dentro de imagens. Nesta aula você monta um pipeline completo no GitHub Actions, do zero.

Você vai aprender
  • O que é CI/CD e por que o runner do GitHub Actions já vem com Docker instalado.
  • A anatomia de um workflow YAML (on, jobs, steps, uses, run, if, secrets).
  • O workflow completo comentado: checkout → login → build → testes dentro do container → push com tags automáticas.
  • Como criar os secrets no repositório (DOCKERHUB_USERNAME e DOCKERHUB_TOKEN, com o passo a passo do token no Docker Hub).
  • Erros reais de CI: login interativo sem TTY, push negado, imagem não encontrada no passo de teste.

O que é CI/CD, em uma frase

CI (integração contínua) é a esteira que roda sozinha a cada push: ela baixa o código numa máquina limpa, compila, roda os testes e empacota o resultado. CD (entrega contínua) é o passo seguinte: se tudo passou, publica a imagem/deploy automaticamente. A gracia do Docker nesse processo: a esteira inteira acontece dentro de containers, então "funcionou no CI" passa a significar "vai funcionar em qualquer lugar".

A máquina que roda o job no GitHub Actions chama-se runner — é uma máquina virtual limpa (Linux Ubuntu por padrão) que o GitHub empresta por alguns minutos. E ela já vem com o Docker Engine instalado:

$ docker version   « dentro de um job rodando em ubuntu-latest
Client:
  Version:   27.3.1
  OS/Arch:   linux/amd64

Server: Docker Engine 27.3.1
  Storage Driver: overlay2
  Operating System: Ubuntu 24.04 LTS

Ou seja: no pipeline você usa os mesmos comandos docker build, docker run, docker push que usou no notebook — só que numa máquina que começa do zero a cada execução.

A anatomia de um workflow

Um workflow do GitHub Actions é um arquivo YAML dentro do seu repositório, no caminho .github/workflows/ (ex.: .github/workflows/ci.yml). Ele tem quatro níveis:

NívelChave YAMLO que declara
Workflowname:O nome que aparece na aba Actions do GitHub.
Gatilhoson:Quando roda: a cada push na main, em pull requests, por tag, por horário (cron)…
Jobsjobs:Blocos paralelos que rodam em runners diferentes (ex.: um job de teste, um de build). Cada job declara runs-on: (o tipo de máquina).
Passossteps:A lista ordenada dentro do job. Cada passo ou chama uma action (uses: …) ou roda um comando de shell (run: …).

YAML é chato com indentação: 2 espaços, nunca tab. Um nível a mais ou a menos e o workflow quebra com erro de sintaxe. Dica: o próprio GitHub valida o arquivo na aba Actions e mostra a linha do erro.

O workflow completo, comentado linha a linha

Este é o arquivo que a Ana criou para a API dela — copie, adapte os nomes e use no seu repositório:

# Nome que aparece na aba Actions
name: CI — build, teste e push

# GATILHOS: roda a cada push na main e em qualquer pull request para a main
on:
  push:
    branches: [main]
  pull_request:
    branches: [main]

jobs:
  build:                       # um único job chamado "build"
    runs-on: ubuntu-latest     # máquina virtual limpa; JÁ VEM COM DOCKER INSTALADO

    steps:
      # 1. Baixa o código do repositório para dentro do runner
      - name: Checkout do código
        uses: actions/checkout@v4

      # 2. Faz login no Docker Hub usando os secrets do repositório
      - name: Login no Docker Hub
        uses: docker/login-action@v3
        with:
          username: ${{ secrets.DOCKERHUB_USERNAME }}
          password: ${{ secrets.DOCKERHUB_TOKEN }}

      # 3. Configura o Buildx (builder avançado do Docker, com cache)
      - name: Setup do Buildx
        uses: docker/setup-buildx-action@v3

      # 4. Gera as tags da imagem automaticamente (latest, sha curta, etc.)
      - name: Metadados da imagem
        id: meta
        uses: docker/metadata-action@v5
        with:
          images: ${{ secrets.DOCKERHUB_USERNAME }}/minhaapp

      # 5. Faz o BUILD da imagem (sem push ainda) e roda os TESTES dentro dela
      - name: Build + testes
        uses: docker/build-push-action@v6
        with:
          push: false              # só constrói — o push acontece no passo 8
          tags: ${{ steps.meta.outputs.tags }}
          labels: ${{ steps.meta.outputs.labels }}
          cache-from: type=gha     # lê o cache de builds anteriores (rápido!)
          cache-to: type=gha,mode=max

      # 6. Roda a suíte de testes DENTRO do container acabado de construir
      - name: Testes
        run: docker run --rm ${{ secrets.DOCKERHUB_USERNAME }}/minhaapp:latest npm test

      # 7. (Opcional) Roda um "teste de fumaça": sobe o container e faz um curl
      - name: Teste de fumaça
        run: |
          docker run -d -p 3000:3000 --name api-teste ${{ secrets.DOCKERHUB_USERNAME }}/minhaapp:latest
          sleep 3
          curl -sf http://localhost:3000/saude
          docker rm -f api-teste

      # 8. Faz o PUSH para o Docker Hub — só quando o gatilho foi push na main
      - name: Push para o Docker Hub
        if: github.ref == 'refs/heads/main' && github.event_name == 'push'
        uses: docker/build-push-action@v6
        with:
          push: true
          tags: ${{ steps.meta.outputs.tags }}
          cache-from: type=gha
          cache-to: type=gha,mode=max

Pontos que valem atenção:

  • ${{ secrets.NOME }} referencia um secret configurado no repositório — o valor nunca aparece no log (o GitHub mascara automaticamente).
  • if: github.ref == 'refs/heads/main' faz o push acontecer só na branch principal — pull requests rodam build+testes mas não publicam nada.
  • O passo 7 é o "teste de fumaça": sobe o container de verdade, espera 3s, chama /saude com curl -sf (o -f faz o curl falhar se o HTTP não for 2xx) e limpa o container com rm -f. Se o app não responder, o passo falha e o pipeline fica vermelho.
  • cache-from/cache-to: type=gha guarda o cache das camadas entre execuções — a aula Builds otimizados detalha.

Build e testes dentro do container

Em vez de instalar Node e as dependências do projeto no runner, o pipeline constrói a imagem e roda os testes dentro dela — exatamente como a Ana faria no notebook:

docker
o CLI, já instalado no runner ubuntu-latest.
run
cria e inicia um container.
--rm
apaga o container ao terminar — no CI tudo é descartável, não deixamos lixo.
minhaapp:latest
a imagem que acabou de ser construída no passo anterior.
npm test

Se qualquer teste falhar, o comando sai com código diferente de zero e o job inteiro falha — o pipeline fica vermelho na aba Actions e ninguém consegue fazer merge (se a branch tiver a proteção ligada). É o CI funcionando como rede de segurança.

Login e push: criando os secrets passo a passo

Para enviar a imagem para o Docker Hub, o pipeline precisa se autenticar — e a senha/token nunca vai escrita no YAML. O caminho é criar secrets no repositório:

  1. No Docker Hub (hub.docker.com), a Ana entra em Account Settings → Security → New Access Token. Dá para dar um nome (ex.: "github-actions") e escolher a permissão: Read & Write (o pipeline precisa escrever para fazer push).
  2. Copia o token gerado na hora — o Docker Hub mostra ele uma vez só. Se perder, gera outro.
  3. No repositório do GitHub: Settings → Secrets and variables → Actions → New repository secret.
  4. Crie dois secrets: DOCKERHUB_USERNAME (seu usuário do Hub, ex.: ana) e DOCKERHUB_TOKEN (o token copiado).
  5. Pronto: no workflow, ${{ secrets.DOCKERHUB_USERNAME }} e ${{ secrets.DOCKERHUB_TOKEN }} preenchem o login.

Localmente, no notebook da Ana, o equivalente manual é:

$ docker login -u ana
Password:
Login Succeeded

$ docker tag minhaapp:latest ana/minhaapp:latest

$ docker push ana/minhaapp:latest
The push refers to repository [docker.io/ana/minhaapp]
9f8e7d6c5b4a: Layer already exists
...
latest: digest: sha256:9f8e7d6c5b4a3f2e... size: 1786
Nunca commite credenciais: se um token aparecer no YAML, no código ou no log, qualquer pessoa pode publicar imagens em seu nome (e minerar criptomoeda no seu runner, que é cobrado por minuto em repositórios privados). Se vazar, revogue o token no Docker Hub na hora (Account Settings → Security). No CI, o erro clássico de quem tenta login interativo é Error: Cannot perform an interactive login from a non TTY device — no runner não existe terminal interativo, por isso usamos a docker/login-action com secrets, nunca docker login pedindo senha.

Missão: simule o passo de build do CI: rode docker build -t minhaapp . e depois docker images para ver a imagem nova na lista.

Missão: simule o login no registry (no CI isso é feito pela action com os secrets): rode docker login -u ana.

Erros comuns no CI

Push negado: denied: requested access to the resource is denied — o token não tem permissão de escrita (Read & Write), o nome de usuário não bate com o do repositório (ana/minhaapp precisa começar com o usuário ana), ou o repositório não existe/no Hub ele é criado sozinho no primeiro push. Revise o token e o images: do metadata-action.
Login interativo: Error: Cannot perform an interactive login from a non TTY device — alguém colocou docker login num run:. Use docker/login-action com secrets.
Imagem não encontrada no passo de teste: Unable to find image 'minhaapp:latest' locally — o passo de teste rodou antes do build, ou o build usou outra tag. A ordem dos steps importa: build primeiro, teste depois. Se usar o metadata-action, a tag pode não ser latest — confira ${{ steps.meta.outputs.tags }}.
YAML inválido: YAMLException: bad indentation of a mapping entry — indentação errada (tab em vez de espaço, ou um nível a mais). O GitHub mostra a linha exata na aba Actions.
Cache do GHA encheu: o cache type=gha tem limite de 10GB por repositório; quando enche, o build continua mas o cache novo não é salvo (aparece um aviso). Alternativa: type=registry (guarda o cache como imagem no próprio Hub) — a aula Builds otimizados mostra.

As actions oficiais do Docker

ActionO que fazQuando usar
actions/checkout@v4Clona o repositório no runner.Sempre, primeiro passo.
docker/setup-buildx-action@v3Configura o builder Buildx (cache avançado, multi-plataforma).Antes do build-push-action.
docker/login-action@v3Login num registry (Docker Hub, GHCR, ECR…) usando secrets. Funciona com username/password ou só password como token.Antes de qualquer push/pull privado.
docker/metadata-action@v5Gera tags automáticas: latest, sha-abc1234, v1.2.3 (se a tag do git for semver), branch… e labels.Para nomear a imagem sem pensar.
docker/build-push-action@v6Build com BuildKit + push opcional, com cache-from/cache-to (type=gha, type=registry), platforms (amd64+arm64) e provenance.O coração do pipeline.
docker/setup-qemu-action@v3Emula outras arquiteturas (arm64) no runner x86.Para builds multi-plataforma.

Outros registries (GHCR, ECR…)

O GitHub tem o próprio registry, o GHCR (ghcr.io), que se autentica com o GITHUB_TOKEN automático do Actions — nem precisa de secret extra:

      - name: Login no GHCR
        uses: docker/login-action@v3
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}
      # imagem: ghcr.io/USUARIO/REPO:tag  (tudo em minúsculas!)

Regra do GHCR: o nome da imagem precisa ser minúsculas (ghcr.io/Ana/App é inválido; ghcr.io/ana/app é válido). No Docker Hub, o repositório também é sempre minúsculo.

Checklist do pipeline

  • ☐ O arquivo está em .github/workflows/ci.yml (indentação de 2 espaços, sem tab).
  • ☐ Gatilhos definidos (push na main + pull_request).
  • ☐ Secrets criados no repositório: DOCKERHUB_USERNAME e DOCKERHUB_TOKEN (Read & Write).
  • ☐ Passos na ordem: checkout → login → setup-buildx → metadata → build (push: false) → testes no container → push (só na main).
  • ☐ O push só acontece em github.ref == 'refs/heads/main'.
  • ☐ O primeiro run erschien verde na aba Actions; a imagem apareceu no Docker Hub com as tags do metadata-action.

Resumo

  • CI = esteira automática por push; com Docker, build e testes rodam dentro de containers no runner ubuntu-latest, que já tem Docker.
  • Workflow YAML: on (gatilhos) → jobs (runs-on) → steps (uses = action, run = shell).
  • Credenciais vão em secrets do repositório e entram no YAML como ${{ secrets.NOME }}
    • — nunca no texto.
  • Actions oficiais: checkout, setup-buildx, login-action, metadata-action (tags automáticas), build-push-action.
  • Fluxo recomendado: build (push: false) → testes dentro do container → push só na main.
  • Erros típicos: login sem TTY, push negado (token sem Read&Write), imagem não encontrada (ordem dos steps), YAML mal indentado.
