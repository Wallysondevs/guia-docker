Projeto 5: API Python Flask + PostgreSQL

O último projeto junta tudo o que a Ana aprendeu — e troca a linguagem: em vez de Node, uma API em Python com Flask que consulta um PostgreSQL de verdade dentro do Compose. A lição aqui é que a receita não muda com a linguagem: código + arquivo de dependências + Dockerfile + docker-compose.yml, e um comando sobe app e banco juntos, conversando pela rede interna.

Você vai aprender
  • Empacotar um app Python: requirements.txt + pip install no Dockerfile.
  • Por que usar psycopg2-binary e não psycopg2 (o erro real de compilação em imagens slim).
  • Conectar no PostgreSQL pela rede interna do Compose com DATABASE_URL (host db).
  • Um endpoint /banco que consulta o banco e devolve o resultado — prova de que app e banco estão conversando.
  • docker exec + psql para entrar no banco e criar tabela/inserir dados.
  • Desenvolvimento com bind mount: editar o app.py no host e ver a mudança com --reload, sem rebuild.
  • Erros reais: build do psycopg2 quebrando e KeyError: 'DATABASE_URL'.

app.py — a API com duas rotas

import os
import psycopg2
from flask import Flask, jsonify

app = Flask(__name__)

def consultar_banco():
    # DATABASE_URL vem do compose: postgresql://postgres:segredo@db:5432/app
    conn = psycopg2.connect(os.environ["DATABASE_URL"])
    cur = conn.cursor()
    cur.execute("SELECT version();")
    versao = cur.fetchone()[0]
    cur.close()
    conn.close()
    return versao

@app.route("/")
def home():
    return jsonify({"mensagem": "Olá do Flask no Docker!"})

@app.route("/banco")
def banco():
    return jsonify({"postgres": consultar_banco()})

if __name__ == "__main__":
    app.run(host="0.0.0.0", port=5000)

Mesma lição do projeto 2: host="0.0.0.0" é obrigatório em containers — com 127.0.0.1 a API ficaria presa dentro do container e o -p não alcançaria.

requirements.txt — as dependências, com versão travada

flask==3.0.3
psycopg2-binary==2.9.9
Por que psycopg2-binary e não psycopg2? O psycopg2 puro é um pacote em C que precisa compilar no build (precisa de gcc e dos headers do PostgreSQL). A imagem python:3.12-slim não tem compilador, e o build quebra com: 
#6 ERROR: Failed building wheel for psycopg2
#6 error: command 'gcc' failed with exit code 1
#6 ERROR: process "/bin/sh -c pip install ..." did not complete successfully: exit code: 1
O psycopg2-binary já traz o binário pré-compilado — instala na hora. (Em produção, dá para usar o puro numa imagem com ferramentas de build, num estágio multi-stage.)

docker-compose.yml — app + banco

services:
  app:                          # a API Flask
    build: .                    # constrói a imagem a partir do Dockerfile desta pasta
    ports:
      - "5000:5000"
    environment:
      # host "db" = nome do serviço abaixo, resolvido pelo DNS interno do Compose
      DATABASE_URL: postgresql://postgres:segredo@db:5432/app
    depends_on:
      - db

  db:                           # o PostgreSQL
    image: postgres:16-alpine
    environment:
      POSTGRES_USER: postgres
      POSTGRES_PASSWORD: segredo
      POSTGRES_DB: app
    volumes:
      - pgdata:/var/lib/postgresql/data   # dados persistem no volume

volumes:
  pgdata:

Passo 4: modo desenvolvimento com bind mount (sem rebuild)

O servidor do Flask tem um modo que recarrega sozinho quando o arquivo muda. Para usar no Compose durante o desenvolvimento, monte o código como bind mount e ligue o --reload:

# o Compose lê esse arquivo AUTOMATICAMENTE junto com o docker-compose.yml
services:
  app:
    volumes:
      - .:/app            # código do host montado dentro do container
    command: flask run --host=0.0.0.0 --reload
$ docker compose up -d
$ # edite o app.py no seu editor…
$ docker compose logs -f app
flask-api-app-1  |  * Detected change in '/app/app.py', reloading
flask-api-app-1  |  * Restarting with stat

Editou, salvou, e a API já recarregou — sem docker build. Esse arquivo docker-compose.override.yml é lido por padrão junto com o docker-compose.yml (dá para ter vários, com -f), e é o padrão para separar "produção" de "desenvolvimento". Não commite o override com mount de código se a equipe não usa.

Erros comuns neste projeto

Build do psycopg2 quebra: 
#6 ERROR: Failed building wheel for psycopg2
#6 error: command 'gcc' failed with exit code 1
#6 ERROR: process "/bin/sh -c pip install --no-cache-dir -r requirements.txt" did not complete successfully: exit code: 1
A imagem python:3.12-slim não tem compilador. Solução: use psycopg2-binary no requirements.txt (já está no exemplo) — ou, em projeto sério, um estágio multi-stage com gcc + libpq-dev para compilar e copiar só o resultado.
Variável faltando: se o DATABASE_URL não estiver definida no serviço app, a rota /banco devolve erro 500 e os logs mostram o erro real do Python: 
$ docker compose logs app
flask-api-app-1  | KeyError: 'DATABASE_URL'
Confira o bloco environment: do serviço app no compose — e o aviso do Compose na subida: WARN: The "DATABASE_URL" variable is not set.
Banco ainda não aceitando conexão: psycopg2.OperationalError: connection refused na primeira subida — o depends_on só ordena, não espera o PostgreSQL ficar pronto. Espere alguns segundos e reabra a página, ou adicione healthcheck no db com pg_isready e condition: service_healthy no app.
A porta 5000 já está em uso no host: Bind for 0.0.0.0:5000 failed: port is already allocated — ou o python app.py rodando local na máquina da Ana, ou outro container. Mude para "5001:5000" no compose e acesse localhost:5001.

Levando para produção: gunicorn e usuário não-root (bônus)

O flask run é o servidor de desenvolvimento — bom para testar, ruim para produção (single-thread, sem otimizações). Em produção, apps Python usam um servidor WSGI como o Gunicorn, e rodam como usuário sem privilégios (aulas Rodar como usuário não-root e Multi-stage):

# ---- stage 1: instala as dependências ----
FROM python:3.12-slim AS builder
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir --prefix=/install -r requirements.txt

# ---- stage 2: imagem final enxuta ----
FROM python:3.12-slim
WORKDIR /app
# copia só as bibliotecas instaladas no stage anterior
COPY --from=builder /install /usr/local
COPY . .
# cria um usuário sem privilégios e usa ele
RUN useradd -m appuser
USER appuser
ENV FLASK_APP=app.py
EXPOSE 5000
# gunicorn: 2 workers, bind em todas as interfaces
CMD ["gunicorn", "-w", "2", "-b", "0.0.0.0:5000", "app:app"]

Adicione gunicorn==22.0.0 ao requirements.txt, troque o serviço app do compose para build: { context: ., dockerfile: Dockerfile.prod }, e faça docker compose up -d --build. Pronto: API em produção dentro de um container, sem root, com imagem enxuta.

Por que o requirements.txt deste projeto usa psycopg2-binary em vez de psycopg2?

Na DATABASE_URL: postgresql://postgres:segredo@db:5432/app, por que o host é db e não localhost nem um IP?

Depurando dentro do container

Deu erro e você não sabe por quê? Entre no container e rode o Python na mão — a imagem python:3.12-slim tem o interpretador:

$ docker exec -it flask-api-app-1 python
Python 3.12.7 (main, ...) [GCC 12.2.0]
>>> import os
>>> os.environ.get("DATABASE_URL")
'postgresql://postgres:segredo@db:5432/app'
>>> import app   # importa a aplicação e já testa se o código carrega
>>> app.consultar_banco()[:40]
'PostgreSQL 16.4 on x86_64-pc-linux-'
>>> exit()

$ docker compose logs app | tail -5   « ou veja só os erros recentes

Esse trio — docker exec -it … python, teste manual da função, docker compose logs — resolve a maioria dos problemas de "a API não responde". E lembre: se o código mudou e você está no modo dev (override com --reload), o log avisa Detected change … reloading; se não avisou, você está rodando a imagem antiga e precisa de docker compose up -d --build.

Resumo

  • A receita independe da linguagem: requirements.txt + pip install no lugar de package.json + npm install; o resto do Dockerfile é igual.
  • Em imagens slim use sempre psycopg2-binary — o psycopg2 puro exige compilador e quebra o build.
  • O app fala com o banco pelo nome do serviço na DATABASE_URL (@db:5432), resolvido pelo DNS interno do Compose.
  • O volume pgdata guarda os dados do PostgreSQL para além do down.
  • Para desenvolver, o docker-compose.override.yml com bind mount + --reload tira o build do caminho.
  • Erros típicos: build do psycopg2 (gcc failed), KeyError: 'DATABASE_URL' (variável faltando) e connection refused (banco ainda subindo).
