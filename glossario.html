Glossário de Docker

Todo curso de Docker usa os mesmos termos o tempo inteiro — e eles voltam em todo canto: nos comandos, nos erros, nas conversas de trabalho. Este glossário reúne os termos essenciais em ordem alfabética, com definição em português claro e, quando faz sentido, um exemplo na máquina da Ana (ana@notebook). Consulte sempre que um termo aparecer pela primeira vez.

Você vai aprender
  • Os termos fundamentais: imagem, container, registry, Docker Hub, daemon, CLI, Dockerfile, build.
  • Estrutura interna: camada, volume, bind mount, tmpfs, rede bridge, contexto de build, .dockerignore.
  • Orquestração e afins: Compose, Swarm, Kubernetes, orquestração.
  • Técnicas avançadas: multi-stage, distroless, Alpine, OCI, runtime, BuildKit/buildx, cgroups, namespaces, healthcheck, tag/digest, exec, entrypoint.

Os termos, de A a Z

Alpine
Uma distribuição Linux mínima ( ~5MB ) usada como base de imagens leves como nginx:alpine e node:22-alpine. Vem só com o essencial — shell sh, apk (gerenciador de pacotes) — e por isso as imagens ficam pequenas e com menos superfície de ataque. Cuidado: não tem bash; dentro dela use docker exec … sh, não bash.
Bind mount
Montar uma pasta do seu computador dentro do container: docker run -v /home/ana/site:/usr/share/nginx/html:ro nginx:alpine. O caminho do host aparece direto no container — ótimo para desenvolvimento, porque editar o arquivo no host vale na hora (é o truque do projeto 1). Com :ro no final, o container só lê.
Build
O processo de criar uma imagem a partir de um Dockerfile, disparado por docker build -t nome:tag .. Cada instrução do Dockerfile vira uma camada; o build reaproveita camadas em cache (CACHED) quando nada mudou (aula Camadas e cache).
BuildKit / buildx
BuildKit é o motor moderno de build (o que imprime #1 [internal] load… e faz o cache avançado). buildx é a interface CLI dele (docker buildx …), que permite builds multi-plataforma (amd64 + arm64) e builders isolados. No CI, o docker/setup-buildx-action configura isso para você.
Camada (layer)
Cada instrução do Dockerfile que altera arquivos gera uma camada somente leitura, empilhada sobre a anterior. Camadas são imutáveis e compartilhadas entre imagens (duas imagens baseadas em node:22-alpine dividem as camadas da base) — é por isso que o cache existe e o disco não enche de cópias.
cgroups
Control groups — recurso do kernel Linux que limita e mede os recursos (CPU, memória, disco, rede) que cada container pode usar. É o que faz valer na prática o --memory 512m e o --cpus 1.5 (aula Limites de recursos).
CLI
Command Line Interface — o programa de linha de comando docker que você digita no terminal. Ele não faz o trabalho sozinho: manda pedidos para o daemon (via socket) e mostra a resposta.
Compose (Docker Compose)
Ferramenta para definir e subir vários containers de uma vez a partir de um arquivo docker-compose.yml. Com docker compose up você cria rede, volumes e todos os serviços juntos; os serviços se encuentran pelo nome na rede interna (projetos 3, 4 e 5).
Container
Uma instância criada a partir de uma imagem — rodando ou parada. Tem sistema de arquivos próprio (camadas da imagem + uma camada de escrita em cima), rede própria e processos próprios, isolados do host e dos outros containers, mas compartilhando o mesmo kernel do sistema (diferente de uma máquina virtual, que tem kernel próprio).
Contexto de build
A pasta que o docker build envia para o daemon antes de montar a imagem — no comando docker build -t app ., o contexto é o . (pasta atual). Tudo que o COPY/ADD pode usar precisa estar dentro do contexto; o .dockerignore tira itens dele.
.dockerignore
Arquivo na raiz do contexto de build com o que não deve ir para o build (ex.: node_modules, .git, .env). Deixa o envio do contexto rápido e a imagem limpa (aula .dockerignore).
Daemon
O servidor do Docker — o processo dockerd que roda em segundo plano na máquina e faz o trabalho pesado: criar containers, baixar imagens, montar volumes, publicar portas. A CLI só manda pedidos para ele pelo socket /var/run/docker.sock. Se o daemon está parado, todo comando dá "Cannot connect to the Docker daemon" (veja Erros comuns).
Digest
O identificador imutável de uma imagem: sha256:9f8e7d…. Enquanto a tag latest pode apontar para imagens diferentes com o tempo, o digest sempre aponta para a mesma imagem byte a byte — por isso produção séria usa digest (docker pull ana/app@sha256:…).
Distroless
Imagens mínimas do Google (gcr.io/distroless) que contêm só o aplicativo e suas dependências de runtime — sem shell, sem gerenciador de pacotes, sem nada. Resultam em imagens de poucos MB e quase sem vulnerabilidades (aula Distroless e Alpine).
Docker Hub
O registry público oficial (hub.docker.com): um catálogo gigante de imagens prontas (nginx, postgres, node, wordpress…). O docker pull baixa de lá por padrão, e o docker push publica lá (com seu usuário, ex.: ana/minhaapp).
Dockerfile
O arquivo de texto com a receita da imagem: uma instrução por linha (FROM, RUN, COPY, CMD…). O docker build transforma esse arquivo numa imagem. A cola completa está em ref-dockerfile.
ENTRYPOINT
Instrução do Dockerfile (e flag --entrypoint no run) que define o programa fixo do container. Diferente do CMD, os argumentos passados no docker run viram parâmetros do entrypoint em vez de trocar o comando inteiro.
exec
docker exec roda um comando dentro de um container que já está rodando — diferente do run, que cria um novo. Ex.: docker exec -it web sh abre um shell dentro do container web (aula docker exec).
EXPOSE
Instrução do Dockerfile que documenta a porta que o app usa dentro do container. Não publica nada para fora — para acessar de fora é preciso o -p no docker run (a pegadinha clássica).
Healthcheck
Teste periódico que o Docker roda dentro do container para saber se o app está saudável (HEALTHCHECK no Dockerfile ou --health-cmd no run). O status aparece como (healthy) no docker ps e pode comandar o depends_on: condition: service_healthy no Compose (aula HEALTHCHECK).
Imagem
Um modelo somente leitura, formado por camadas empilhadas, que serve de base para criar containers. Pense nela como a "classe" e no container como o "objeto" instanciado. Fica guardada localmente (docker images) ou num registry, e tem nome no formato repositório:tag (ex.: nginx:alpine).
Kubernetes (k8s)
O orquestrador de containers mais popular do mundo, criado pelo Google — para rodar milhares de containers em dezenas de máquinas com auto-cura, escalonamento automático e rolling updates. O Docker Swarm é a alternativa mais simples e nativa do Docker; para aprender k8s depois deste guia, veja E Kubernetes? Quando usar.
Multi-stage
Um Dockerfile com vários blocos FROM (estágios): o primeiro compila o app com todas as ferramentas de build; o último copia só o resultado para uma imagem limpa e pequena. É a técnica para imagens enxutas (aula Multi-stage builds).
Namespaces
Recurso do kernel Linux que isola a visão que o container tem do sistema: processos, rede, usuários, pontos de montagem, hostname. É o que faz o container achar que está sozinho na máquina — mesmo dividindo o kernel com o host e os outros containers.
OCI
Open Container Initiative — o padrão aberto que define o formato das imagens e dos runtimes de container (image spec + runtime spec). Graças a ele, uma imagem criada com Docker roda em qualquer runtime compatível (containerd, CRI-O, Podman) e vice-versa.
Orquestração
Gerenciar muitos containers em várias máquinas ao mesmo tempo: criar, distribuir, escalar, monitorar, substituir quando caem. Exemplos: Docker Swarm (nativo, mais simples — aula Swarm) e Kubernetes (mais completo, padrão da indústria).
Rede bridge
A rede padrão que o Docker cria em toda instalação (bridge): cada container ganha um IP interno (172.17.x.x), pode falar com os outros pelo nome (DNS interno) e publica portas no host com -p. Outras opções: host (sem isolamento de rede) e none (sem rede nenhuma) — aula Redes no Docker.
Registry
Um servidor que guarda e distribui imagens. O Docker Hub é o registry público mais famoso; dá para ter um registry privado na empresa (aula Registry privado). O fluxo é: docker login → docker tag → docker push para enviar; docker pull para baixar.
Runtime
O programa que realmente cria e roda o container a partir de uma imagem OCI — hoje o padrão é o runc (usado pelo Docker/containerd), mas existem outros (crun, Kata). O daemon conversa com o runtime por baixo dos panos; você quase nunca mexe nele direto.
Swarm
O orquestrador nativo do Docker: você transforma várias máquinas com Docker instalado num cluster (docker swarm init) e declara serviços com réplicas (docker service create --replicas 3 nginx) — o Swarm distribui, recria se cair e balanceia carga (aula Introdução ao Swarm).
Tag
O "sobrenome" da imagem em repositório:tag — ex.: nginx:alpine (tag alpine), node:22 (tag 22), meuapp:latest (tag latest, usada por padrão quando você não escreve nada). Tags são mutáveis (podem apontar para imagens diferentes ao longo do tempo); o digest é o que não muda.
tmpfs
Um tipo de montaje que guarda os arquivos na memória RAM do host, descartável: --tmpfs /tmp ou -v type=tmpfs,destination=/tmp. Ideal para dados temporários de um container --read-only.
Volume
Um espaço de armazenamento gerenciado pelo Docker (fica em /var/lib/docker/volumes/… no host) que sobrevive ao container. Criado com docker volume create dados e usado com -v dados:/caminho — ideal para bancos de dados (aula Tipos de volumes). Diferente do bind mount, o caminho do host é opaco (o Docker que gerencia).

Os pares que mais confundem

Estes pares soam parecidos mas não são a mesma coisa — é onde 90% das dúvidas mora:

ParA diferença em uma frase
Imagem × ContainerImagem é o modelo parado (somente leitura); container é a instância criada a partir dela, com uma camada de escrita em cima.
Volume nomeado × Bind mountVolume nomeado (-v dados:/…) é gerenciado pelo Docker e sobrevive ao container; bind mount (-v /home/ana/site:/…) é uma pasta sua do host montada direto — boa para desenvolver.
EXPOSE × -pEXPOSE 3000 no Dockerfile só documenta; -p 8080:3000 no run é que publica a porta para fora.
CMD × ENTRYPOINTCMD é o comando padrão, sobrescrevível no run; ENTRYPOINT é o programa fixo, e o que vem no run vira argumento dele.
bridge × host × nonebridge dá IP próprio e portas publicadas; host usa a rede do host direto (sem isolamento); none deixa o container sem rede.
build × rundocker build cria a imagem a partir do Dockerfile; docker run cria o container a partir da imagem.
Tag × DigestTag (:latest) é um apelido mutável; digest (@sha256:…) é o identificador imutável da imagem exata.
ENV × ARGARG vale só durante o build (--build-arg); ENV fica na imagem e vale em runtime (sobrescrevível com -e).
docker exec × docker runexec roda um comando num container já existente; run cria um container novo.
CLI × DaemonA CLI (docker) é o programa que você digita; o daemon (dockerd) é o servidor em segundo plano que executa de verdade.

Memorize esta frase

Resumo em uma linha: o Dockerfile gera a imagem (modelo), a imagem gera o container (instância rodando), e as imagens ficam guardadas num registry como o Docker Hub — o daemon faz tudo isso acontecer por baixo dos panos.

Missão: rode docker --version no terminal simulado e confira a versão do CLI e do Engine da máquina fictícia.

Resumo

  • Fluxo central: Dockerfile → build → imagem → run → container → registry.
  • Isolamento vem de namespaces (visão) + cgroups (recursos); o daemon orquestra tudo e o runtime (runc) executa.
  • Dados persistem em volumes; código em desenvolvimento entra por bind mount; temporários vão para tmpfs.
  • Vários containers = Compose (uma máquina) ou Swarm/Kubernetes (várias máquinas, orquestração).
  • Imagens têm tags (apelidos) e digests (imutáveis); o padrão aberto por trás de tudo é o OCI.
