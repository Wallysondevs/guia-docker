E Kubernetes? — quando usar

Depois do Swarm, a pergunta natural da Ana foi: "e o Kubernetes?". O K8s é o orquestrador que virou padrão da indústria — mais complexo, mas com um ecossistema enorme e suporte de todas as nuvens. Nesta aula: a comparação honesta entre os dois (sem torcida), quando cada um basta, as opções gerenciadas na nuvem e a verdade sobre o Docker dentro do K8s — porque ele não some.

Você vai aprender
  • Swarm vs Kubernetes: diferenças reais, não de torcida.
  • Quando o Swarm basta (e por que ele é subestimado).
  • Quando o Kubernetes passa a valer a pena.
  • Plataformas gerenciadas: EKS, GKE, AKS, ECS/Fargate — sem instalar nada.
  • O que muda no dia a dia: kubectl no lugar de docker service.
  • Que o Docker continua lá dentro: imagens, Dockerfile e containerd nos nós.

A ideia: Swarm é a Kombi, K8s é o caminhão

O Swarm é como uma Kombi: cabe no bolso, faz o serviço, dá para dirigir em qualquer lugar — serve para a loja inteira da Ana. O Kubernetes é como um caminhão de frota: precisa de estrada boa (infra), de motorista especializado (time de plataforma), mas carrega milhares de caixas com escala automática. Não existe "melhor" absoluto — existe o certo para o tamanho do problema.

Quando o Swarm basta

  • Você tem alguns poucos serviços (site + API + banco + redis, como nos projetos do guia).
  • A equipe é pequena e o docker-compose.yml já descreve tudo — com a seção deploy vira stack no Swarm sem reescrever nada.
  • Você quer alta disponibilidade simples (réplicas em 2-3 máquinas) sem aprender um ecossistema novo.
  • Simplicidade operacional pesa mais que sofisticação: menos peças = menos pane.

Muitas empresas rodam Swarm em produção por anos com zero drama. Não pule etapas: domine Compose e Swarm antes de encarar o K8s.

Quando ir para Kubernetes

  • Muitos microsserviços (dezenas ou mais) com donos diferentes e deploys independentes.
  • Precisa de autoscaling por métricas (HPA/VPA), filas, jobs batch e políticas de rede (NetworkPolicy).
  • Rolling updates sofisticados (canary, blue/green) e service mesh (Istio, Linkerd).
  • Multi-cloud ou hybrid cloud de verdade (o mesmo manifesto roda em AWS, GCP e Azure).
  • Existe time/orçamento para operar o cluster — ou você usa um gerenciado (abaixo).

Opções gerenciadas: K8s sem instalar nada

Quase ninguém hoje instala o K8s na mão em produção — usa o serviço gerenciado da nuvem, onde o "plano de controle" (os masters) é cuidado pelo provedor e você só gerencia os nós workers (e paga por eles):

ServiçoNuvemObservação
EKS (Elastic Kubernetes Service)AWSO mais usado; integra com Fargate (containers serverless, sem nós).

ECS + FargateAWSNão é K8s: é o orquestrador próprio da AWS, mais simples — um bom meio-termo entre Compose e K8s.

DOKS / OKE / outrosDigitalOcean / Oracle / outros provedoresOpções menores de K8s gerenciado.

Para aprender K8s no notebook sem gastar nada: kind (Kubernetes in Docker — roda um cluster K8s dentro de containers Docker) ou minikube. A Ana começou com kind: kind create cluster e já tinha um cluster de 1 nó para practicar.

E o Docker continua lá dentro

K8s não substitui o Docker: as imagens continuam sendo buildadas com Dockerfile e publicadas em registry (aulas multi-stage, tag/push, registry privado). Nos nós do cluster, quem roda os containers geralmente é o containerd (o mesmo runtime que o Docker usa por baixo) — o K8s conversa direto com ele via CRI. O que muda é a camada de cima: em vez de docker service, você aplica manifestos com kubectl:

$ kubectl get pods
NAME                    READY   STATUS    RESTARTS   AGE
web-6d5f4b8c7-x2abc    1/1     Running   0          3m
web-6d5f4b8c7-k9xyz    1/1     Running   0          3m

$ kubectl apply -f deployment.yaml
deployment.apps/web created

$ kubectl scale deployment web --replicas=5
deployment.apps/web scaled

$ kubectl rollout status deployment/web
deployment "web" successfully rolled out

Em dev, dá para continuar usando Compose normalmente — e ferramentas como o kompose convertem o docker-compose.yml em manifestos do K8s automaticamente (kompose convert -f docker-compose.yml), o que facilita a migração quando chegar a hora.

Não adote K8s por modismo: para a maioria dos projetos pequenos, Swarm (ou até um Compose bem escrito num servidor só, com backup e --restart) resolve. K8s cobra um preço real em complexidade — só vale quando essa complexidade se paga (escala automática, muitos serviços, multi-cloud). Comece simples e migre quando doer.

Missão: rode docker images no simulador e pense: quais dessas imagens você publicaria num Pod do Kubernetes? (No K8s você referencia a mesma imagem do registry — o Docker continua lá.)

Missão extra: suba um container com docker run -d --name web nginx:alpine e rode docker ps. Num cluster K8s, esse container seria um Pod gerenciado pelo K8s — aqui no simulador dá para treinar a inspeção.

Caminho de aprendizado sugerido

Se você está seguindo o guia do começo, a escada que faz sentido é:

  1. Fundamentos: containers e imagens no dia a dia (Nível 1: docker run, docker ps, docker logs…).
  2. Suas imagens: Dockerfile, build, camadas (Nível 2: Dockerfile, cache).
  3. Aplicações multi-container: Compose (projetos fullstack, WordPress).
  4. Produção numa máquina: segurança (USER, cap-drop, seccomp), limites, healthcheck, logs — as aulas deste nível.
  5. Mais de uma máquina: Swarm (esta seção) — réplicas, stacks, alta disponibilidade simples.
  6. Cluster grande: Kubernetes, de preferência num gerenciado (EKS/GKE/AKS) e praticando antes com kind/minikube.
  7. Automação: CI/CD com Docker (docker-ci, build-otimizado).

Não pule degraus: cada um usa o anterior. O K8s no fim da escada faz sentido porque você já sabe o que é uma imagem, um container, uma rede e um volume.

2. O que o Kubernetes tem que o Swarm não tem nativamente?

3. O K8s substitui o Docker?

4. Qual ferramenta converte um docker-compose.yml em manifestos do Kubernetes?

Resumo

  • Swarm = orquestrador nativo e simples (horas para aprender); K8s = padrão da indústria, poderoso e complexo (semanas/meses).
  • Swarm basta para até dezenas de serviços com compose + deploy; K8s vale para muitos microsserviços, autoscaling (HPA), canary e multi-cloud.
  • Gerenciados: EKS (AWS), GKE (Google), AKS (Azure), ECS+Fargate (AWS, não é K8s), Cloud Run (serverless).
  • No K8s a unidade é o Pod; no Swarm é o service. Comandos viram kubectl get/scale/apply/logs/rollout.
  • O Docker continua lá dentro: imagens com Dockerfile, registry privado, e o containerd (runtime do Docker) rodando os Pods nos nós.
  • kompose converte docker-compose.yml em manifestos K8s; para practicar local: kind ou minikube.
  • Regra prática: comece simples (Compose → Swarm) e migre para K8s quando a complexidade se pagar — não por modismo.
