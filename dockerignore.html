.dockerignore — o que não entra no build

Lembra que o docker build envia a pasta inteira (o contexto) para o daemon, toda vez? O arquivo .dockerignore é a lista do que não deve ser enviado — um porteiro na porta da cozinha. Ele fica na raiz do contexto, ao lado do Dockerfile, e a sintaxe é a mesma do .gitignore, que você já conhece.

Você vai aprender
  • Onde o .dockerignore fica e o formato (igual ao .gitignore: curingas, #, exceção com !).
  • Por que ignorar node_modules, .git, .env e arquivos de build local.
  • Os três motivos: contexto menor (build rápido), cache estável e segurança (segredo não entra na imagem).
  • Como medir o efeito: a linha Sending build context … antes e depois.
  • Erros reais: COPY de arquivo que o .dockerignore excluiu, e o arquivo na subpasta errada.
  • Um .dockerignore pronto para copiar para um projeto Node.

A cena: o antes e o depois na máquina da Ana

A Ana tem o projeto ~/meusite no notebook. Sem .dockerignore, o build dela envia tudo — incluindo a pasta .git e um node_modules enorme:

$ ls -a
.  ..  .git  Dockerfile  index.html  node_modules  package.json
$ du -sh .
482M    .   « a pasta pesa quase meio giga!
$ docker build -t site:1.0 .
Sending build context to Docker daemon  482.4MB   « tudo isso vai para o daemon, a cada build

Ela cria um .dockerignore na raiz e rebuilda:

$ cat > .dockerignore <<'EOF'
node_modules/
.git/
EOF
$ docker build -t site:1.0 .
Sending build context to Docker daemon  4.096kB   « de 482MB para 4kB!

Mesma imagem, build muito mais rápido — e o node_modules nem chega a ser observado pelo cache.

Como funciona

Tudo que você listar no .dockerignore não é enviado ao daemon no momento do build — logo não pode ser copiado para a imagem com COPY e não entra no cálculo do cache. A sintaxe é a do .gitignore:

  • pasta/ ou pasta — ignora a pasta inteira;
  • *.log — curingas funcionam (*, ?, ** para recursivo);
  • # comentário — linhas com # são comentários;
  • !excecao — o ! faz uma exceção (ex.: ignorar todos os *.md menos o README: *.md + !README.md);
  • **/temp — bate em qualquer nível de subpasta.
# exemplo de .dockerignore
node_modules/
.git/
*.log
!importante.log      # exceção: este log entra
**/tmp/
O .dockerignore vale para o COPY também: um arquivo ignorado não existe para o build — um COPY arquivo-ignorado.txt . falha com not found. Ou seja, o .dockerignore é a garantía de que o arquivo não entra na imagem nem por acidente.
Erro comum: .dockerignore na pasta errada. O arquivo só funciona na raiz do contexto (onde você deu o .). Se a Ana coloca o .dockerignore dentro de ~/meusite/src/ e builda de ~/meusite, ele é ignorado — e a linha Sending build context continua grande. O lugar certo é ao lado do Dockerfile, na raiz do contexto. (Com -f apontando para outro arquivo, o .dockerignore ainda é procurado na raiz do contexto, não ao lado do -f — detalhe que já confundiu muita gente.)

Por que isso importa (três motivos)

  1. Contexto menor = build mais rápido. Cada build envia o contexto inteiro ao daemon. Um node_modules com 400MB vai junto a cada docker build, deixando tudo lento — e em CI, cada segundo conta.
  2. Cache mais estável. Arquivos que mudam toda hora (logs, build local, banco local) nem chegam a ser observados pelo cache — eles não quebram a sequência de camadas.
  3. Segurança. Se um arquivo com senhas entra no contexto e um COPY . . o copia para a imagem, o segredo fica gravado numa camada para sempre — mesmo que um RUN rm depois o apague, a camada anterior continua lá, legível.
$ docker build -t site:1.0 .
Sending build context to Docker daemon  4.096kB    « com .dockerignore
$ docker build -t site:1.0 .
Sending build context to Docker daemon  482.4MB    « sem .dockerignore: node_modules e .git foram junto
Segredo na imagem: o vazamento real. Se o projeto da Ana tem um arquivo .env com DB_PASSWORD=… e o Dockerfile tem COPY . ., o .env entra na imagem. Qualquer pessoa com acesso à imagem consegue ler as camadas (basta docker history + inspeção, ou ferramentas como o dive — aula Analisando camadas). E publishar a imagem no registry publica o segredo junto. Regra de ouro: .env no .dockerignore, sempre. Passe segredos em runtime com -e ou --env-file, nunca no build.

Um .dockerignore pronto para projeto Node

# arquivo: .dockerignore  (fica na raiz do projeto, ao lado do Dockerfile)

# dependências e controle de versão — nunca vão para a imagem
node_modules/
.git/
.gitignore

# segredos — NUNCA enviar ao build
.env
.env.*
*.pem
*.key
id_rsa

# build local, logs e testes
coverage/
dist/
build/
*.log
npm-debug.log*
.DS_Store

# arquivos do próprio Docker (o Dockerfile ainda é lido; só não é copiado)
Dockerfile
.dockerignore
docker-compose.yml
.docker/
README.md

Depois de criar o arquivo, o próximo docker build já sente a diferença no tamanho do contexto. Dá para testar sem buildar nada: tar simulando o envio, ou simplesmente observe a linha Sending build context … no próximo build.

Por que o próprio Dockerfile entra na lista? Ele é lido pelo daemon (de fora do contexto), mas não precisa ser copiado para dentro da imagem — listar Dockerfile e .dockerignore evita que um COPY . . os ponha dentro da imagem sem querer.

Erros e pegadinhas reais

COPY de algo que o .dockerignore excluiu: se o .dockerignore tem config/ e o Dockerfile tem COPY config/ /app/config/, o build falha com failed to compute cache key: config/: not found. O arquivo simplesmente não existe para o build. Como consertar: tire a linha do .dockerignore (e use COPY config/producao.conf … específico, se for o caso) ou ajuste a exceção com !config/producao.conf.
Padrões que não batem: node_modules (sem barra) já ignora a pasta, mas /node_modules (com barra na frente) também funciona na raiz; o que não funciona é src/node_modules esperando pegar a raiz — os padrões são relativos à raiz do contexto. E node_modules/ não ignora um arquivo chamado node_modules — para isso, sem a barra.
.dockerignore não apaga nada do disco: ele só filtra o envio do build. Seus arquivos continuam na sua máquina, intactos. É filtro, não lixeira.
Build de contexto remoto (git/URL): nesse caso o .dockerignore é lido do próprio repositório remoto (raiz do contexto remoto). Se o repositório não tiver .dockerignore, tudo vai.

Resumo

  • O .dockerignore fica na raiz do contexto do build, ao lado do Dockerfile, e usa a sintaxe do .gitignore (pasta/, *.log, **/x, #, exceção com !).
  • O que está na lista não é enviado ao daemon no docker build — e portanto não pode ser copiado com COPY nem atrapalha o cache.
  • Três motivos: build rápido (veja a linha Sending build context …), cache estável e segurança — .env e chaves nunca devem entrar no contexto.
  • Ele é filtro de envio, não apaga nada do disco.
  • Erros reais: arquivo na subpasta errada (só a raiz vale), COPY de algo ignorado (dá not found), padrão que não bate com o caminho real.
  • Kit mínimo: node_modules/, .git/, .env*, *.pem/*.key, dist/, *.log, Dockerfile, .dockerignore, docker-compose.yml.
