Logs — drivers e rotação

Tudo que a sua aplicação imprime em stdout/stderr (o console.log, o print, o log do Nginx) vira log do container — o Docker captura e guarda isso para você, sem você configurar nada. Só que tem uma pegadinha que já derrubou servidor mundo afora: por padrão, o driver json-file grava em arquivo local sem limite de tamanho. Uma aplicação verbosa (ou um loop de erro) pode encher o disco inteiro — e disco cheio derruba todos os containers e serviços da máquina. Nesta aula: como ler os logs com docker logs, como trocar o driver e como configurar a rotação.

Você vai aprender
  • Ler logs com docker logs: --tail, --since, --until, -f, --timestamps.
  • Onde o log fica no disco e por que o padrão não tem limite.
  • Os drivers de log: json-file (padrão), syslog, journald, none e os externos (fluentd, gelf, awslogs…).
  • Rotação com --log-opt max-size=10m --log-opt max-file=3 e no /etc/docker/daemon.json (global).
  • Ver a configuração de log de um container com docker inspect.

A ideia: o Docker é o porteiro que anota tudo

Toda linha que o processo do container escreve na saída padrão vai para o log dele. O Docker não julga: log de acesso, erro, debug — tudo entra no mesmo arquivo. A sua aplicação só precisa imprimir no stdout/stderr (não gravar em arquivo próprio dentro do container, que é descartado). A boa notícia: docker logs lê esse arquivo para você, sem entrar no container.

docker logs: lendo o que o container imprimiu

$ docker run -d --name web -p 8080:80 nginx:alpine
a1b2c3d4e5f6…

$ docker logs web

$ docker logs --tail 2 web        « só as 2 últimas linhas
$ docker logs --since 10m web      « só as últimas 10 minutos
$ docker logs --until 1h web       « só até 1 hora atrás
$ docker logs -f web               « segue em tempo real (Ctrl+C sai, o container continua)
$ docker logs -t web               « com data/hora no início de cada linha
FlagO que fazExemplo

--since 10mMostra só a partir de 10 minutos atrás (aceita 1h, 2025-01-15, 2025-01-15T10:00:00…).docker logs --since 2025-01-15T10:00:00 web

Missão: suba um Nginx com docker run -d --name web nginx:alpine e depois leia a inicialização dele com docker logs web.

Onde o log fica no disco

Com o driver padrão json-file, cada container grava em:

$ ls /var/lib/docker/containers/
a1b2c3d4e5f6a1b2c3d4e5f6…/

$ ls -lh /var/lib/docker/containers/a1b2c3d4e5f6…/a1b2c3d4e5f6…-json.log
-rw-r--r-- 1 root root 148K jan 15 10:32 a1b2c3d4e5f6…-json.log   « cresce para sempre, sem limite

Cada linha do arquivo é um JSON (daí o nome): {"log":"…","stream":"stdout","time":"…"}. É por isso que docker logs consegue filtrar por tempo. Esse arquivo cresce sem limite — é a bomba-relógio da próxima seção.

Drivers de log: para onde vai o log

O driver decide quem recebe o que o container imprime. Você escolhe por container (--log-driver) ou para o host inteiro (daemon.json):

DriverPara onde vai o logQuando usar
json-fileArquivos JSON locais em /var/lib/docker/containers/… (padrão; docker logs funciona)Máquina única, quase tudo. Com max-size!
localArquivos locais otimizados (com rotação embutida via max-size)Alternativa moderna ao json-file em alguns casos
syslogServidor syslog da rede (--log-opt syslog-address=…)Centralizar logs de vários hosts num servidor só
journaldO journal do systemd do hostSistemas com systemd; depois lê com journalctl CONTAINER_NAME=web
fluentd / gelfColetores de log (Fluentd, Graylog, ELK/Loki)Pipeline de observabilidade (ELK, Loki, Datadog…)
awslogs / gcplogs / azurelogsCloudWatch / Cloud Logging / MonitorQuando o container roda na nuvem (precisa de credenciais)
noneEm lugar nenhum — o log é descartadoApps que já logam em volume próprio (evita duplicar); cuidado: docker logs fica vazio
$ docker run -d --name api --log-driver syslog \
>     --log-opt syslog-address=tcp://192.168.1.50:514 \
>     --log-opt tag="loja-api" \
>     ana/minha-api:1.0

Rotação: --log-opt max-size e max-file

Com o json-file, sem limite o arquivo cresce para sempre. A rotação resolve: quando o log chega no tamanho máximo, ele é renomeado (.1) e um novo é criado; passando do número máximo de arquivos, o mais antigo é apagado:

$ docker run -d --name site -p 8080:80 \
>     --log-driver json-file \
>     --log-opt max-size=10m \
>     --log-opt max-file=3 \
>     nginx:alpine
f3a1b2c3d4e5f6…
--log-driver json-file
Escolhe o driver de log do container (padrão já é esse; posto aqui para deixar explícito).
--log-opt max-size=10m
Quando o arquivo de log chega a 10MB, ele é rotacionado. Sem isso, sem limite.
--log-opt max-file=3
Guarda no máximo 3 arquivos rotacionados — no máximo ~30MB de log por container (10MB × 3).

Também dá para configurar o padrão global no /etc/docker/daemon.json (vale para todos os containers do host que não tiverem configuração própria):

{
  "log-driver": "json-file",
  "log-opts": {
    "max-size": "10m",
    "max-file": "3"
  }
}

Depois de mudar o daemon.json, reinicie o serviço: sudo systemctl restart docker. Atenção: a mudança vale para containers novos — containers já criados mantêm a configuração antiga (para trocar, recrie o container: docker compose up -d --force-recreate).

Conferindo a configuração de log de um container

$ docker inspect site --format '{{.HostConfig.LogConfig.Type}}'
json-file

$ docker inspect site --format '{{.HostConfig.LogConfig.Config}}'
map[max-size:10m max-file:3]

Esse inspect é a auditoria rápida: se max-size não aparecer, o log daquele container está sem limite.

Cenários e erros reais

O disco que encheu e derrubou tudo

Numa madrugada, a API da Loja Aurora entrou num loop de erro (um while logando exceção a cada requisição) e o arquivo de log cresceu 40GB em 3 horas — enchendo o disco do servidor. Resultado: o banco de dados não conseguia gravar, o Docker não conseguia criar camadas novas, docker ps começou a falhar. Tudo caiu. Depois disso, a equipe ligou max-size=10m, max-file=5 no daemon.json global e passou a monitorar docker system df (aula) — que mostra exatamente quanto cada imagem/container/log está ocupando.

Perigo real: json-file sem max-size + aplicação que loga demais = disco cheio no servidor, que derruba todos os containers e serviços da máquina (não só o culpado). Em produção, sempre configure rotação — por container ou no daemon.json global.
Cuidado com --log-driver none: nesse caso o docker logs não mostra nada. Só use se a app tiver log próprio (em volume/arquivo) — senão você fica cego em produção.
Driver errado para o ambiente: awslogs numa máquina local (sem credenciais AWS) faz o container não subir: Error response from daemon: failed to initialize logging driver: …. Cada driver de nuvem precisa das credenciais certas no ambiente (AWS_ACCESS_KEY_ID etc.) ou de um --log-opt apontando a região.

Log no docker-compose.yml

No Compose, o driver e a rotação vão na chave logging de cada serviço — é assim que a Ana configurou a loja inteira de uma vez:

services:
  web:
    image: nginx:alpine
    logging:
      driver: json-file
      options:
        max-size: "10m"
        max-file: "3"
  api:
    image: ana/minha-api:1.0
    logging:
      driver: json-file
      options:
        max-size: "50m"
        max-file: "5"
        labels: "servico=api"
  worker:
    image: ana/minha-api:1.0
    command: node worker.js
    logging:
      driver: none        « o worker já grava log próprio em volume
    volumes:
      - worker-logs:/app/logs

E para ler os logs de todos os serviços do projeto de uma vez: docker compose logs -f --tail 100 (aula compose up/down).

Resumo

  • Tudo que o container imprime em stdout/stderr vira log; o driver padrão json-file grava em /var/lib/docker/containers/<id>/-json.log sem limite.
  • docker logs: -f (segue), --tail N, --since/--until, -t (timestamps).
  • Drivers: json-file, local, syslog, journald, fluentd/gelf, awslogs/gcplogs/azurelogs, none.
  • Rotação: --log-opt max-size=10m --log-opt max-file=3 por container, ou global em /etc/docker/daemon.json + restart do serviço.
  • Conferindo: docker inspect … --format '{{.HostConfig.LogConfig}}'.
  • Perigo real: log sem limite + app verbosa = disco cheio = máquina inteira caída. Em produção, rotação sempre ligada.
