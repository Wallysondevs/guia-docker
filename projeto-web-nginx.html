Projeto 1: site estático com Nginx

O projeto mais rápido do guia, e o favorito da Ana: ela precisa entregar um trabalho da faculdade — uma página HTML sobre Docker — e quer mostrar para a turma como se fosse um site de verdade, acessível pelo navegador. Em vez de instalar Apache ou Nginx no notebook (e sujar a máquina), ela vai servir o arquivo com um container. Em menos de um minuto, o site estará no ar em http://localhost:8080.

Você vai aprender
  • Como a imagem nginx:alpine serve arquivos da pasta /usr/share/nginx/html.
  • O que é um bind mount: montar uma pasta da sua máquina dentro do container com -v.
  • Por que a flag :ro (somente leitura) protege seus arquivos.
  • Publicar a porta com -p 8080:80 e ler a coluna PORTS do docker ps.
  • Verificar o site no navegador, com curl e nos logs do container.
  • Editar o arquivo e ver a mudança na hora — sem rebuild.
  • Parar, remover e limpar tudo no final (e o erro real de tentar remover container rodando).

A ideia: o Nginx empresta o servidor, a pasta é sua

Pense no container como uma caixa de areia com um programa dentro. A imagem nginx:alpine traz o servidor web Nginx configurado para servir os arquivos que estiverem na pasta /usr/share/nginx/html dentro do container. Se essa pasta estiver vazia, o Nginx devolve o "Welcome to nginx!" padrão.

A mágica deste projeto é não copiar o site para dentro da imagem, e sim apontar uma pasta da máquina da Ana para dentro do container. Esse truque chama-se bind mount (montagem de pasta) e é a forma de um container "enxergar" um diretório do host — a aula Volumes nomeados, bind mounts e tmpfs detalha os três tipos de montagem:

TipoSintaxePara que serve
Volume nomeado-v dados:/var/lib/mysqlDados que o Docker gerencia e que sobrevivem ao container (bancos de dados).
Bind mount-v /home/ana/site:/usr/share/nginx/htmlUma pasta do seu computador aparece dentro do container — ideal para desenvolver (o que você edita no host aparece na hora).
tmpfs--tmpfs /tmpUma pasta na memória RAM, descartável — para arquivos temporários.

Neste projeto vamos usar o bind mount com a flag :ro (read-only, somente leitura): o container consegue ler seus arquivos, mas não consegue modificar nem apagar nada — uma proteção de graça.

Passo 1: crie o site

No terminal da ana@notebook, crie a pasta do projeto e o arquivo dentro dela:

$ mkdir -p ~/site
$ cd ~/site
$ ls -la   « pasta vazia por enquanto

A estrutura que vamos criar é minimale:

site/
└── index.html

Agora o arquivo em si. Crie index.html com o conteúdo abaixo (é um HTML simples, só para o trabalho da faculdade):

<!doctype html>
<html lang="pt-BR">
<head>
  <meta charset="utf-8">
  <meta name="viewport" content="width=device-width, initial-scale=1">
  <title>Meu site no Docker</title>
  <style>
    body { font-family: sans-serif; max-width: 640px; margin: 40px auto; padding: 0 16px; line-height: 1.6; }
    h1 { color: #0b5cad; }
    code { background: #eef3f8; padding: 2px 6px; border-radius: 4px; }
  </style>
</head>
<body>
  <h1>Olá! Este site está rodando dentro de um container Nginx 🐳</h1>
  <p>Este arquivo está na pasta ~/site do meu notebook, e o Nginx dentro do
     container está lendo ele direto de lá, gracias a um bind mount.</p>
  <p>Edite este arquivo e recarregue a página — a mudança aparece na hora,
     sem reconstruir imagem nenhuma.</p>
</body>
</html>

Confira que o arquivo foi criado:

$ ls -la
total 12
-rw-r--r-- 1 ana ana  612 Nov 24 12:00 index.html
$ head -3 index.html
<!doctype html>
<html lang="pt-BR">
<head>

Passo 2: suba o Nginx apontando para a sua pasta

Ainda na pasta ~/site, rode o comando abaixo. Leia a anatomia primeiro — cada peça tem um motivo:

docker run
cria e inicia um container novo.
-d
detach: roda em segundo plano e devolve o terminal na hora (senão o terminal ficaria preso no container).
-p 8080:80
publica a porta: HOST:CONTAINER. A porta 80 do container (onde o Nginx escuta) passa a responder na porta 8080 da máquina da Ana. Formato sempre -p host:container — a aula Publicando portas detalha.
-v $(pwd):/usr/share/nginx/html:ro
o bind mount: $(pwd) é a pasta atual (/home/ana/site), montada em /usr/share/nginx/html dentro do container, com :ro = somente leitura.
--name meu-site
dá um nome previsível ao container. Sem isso, o Docker inventa nomes como keen_blackwell — bons para diversão, ruins para Automação.
nginx:alpine
a imagem usada (Nginx sobre Alpine, ~48MB — a aula Imagens oficiais explica as tags).
$ docker run -d -p 8080:80 -v $(pwd):/usr/share/nginx/html:ro --name meu-site nginx:alpine
9f8e7d6c5b4a3f2e1d0c9b8a7f6e5d4c3b2a1908172a3b4c5d6e7f8a9b0c1d2e3f4

$ docker ps
CONTAINER ID   IMAGE          COMMAND                  CREATED          STATUS          PORTS                   NAMES
9f8e7d6c5b4a   nginx:alpine   "/docker-entrypoint.…"   8 seconds ago    Up 8 seconds    0.0.0.0:8080->80/tcp   meu-site

Três coisas para reparar na saída:

  • O docker run -d imprime o ID completo do container (64 caracteres hexadecimais). Dá para usar só os primeiros 12 dígitos nos próximos comandos.
  • Na coluna STATUS, Up 8 seconds diz que o container está rodando.
  • Na coluna PORTS, 0.0.0.0:8080->80/tcp confirma o redirecionamento: tudo que chegar na 8080 do host vai para a 80 do container. 0.0.0.0 significa "todas as interfaces" — ou seja, dá para acessar de outro dispositivo da rede também, se quiser restringir para só o seu computador, use -p 127.0.0.1:8080:80.

Missão: suba o container (adicione -v $(pwd):/usr/share/nginx/html:ro se quiser) e depois rode docker ps — o nome meu-site deve aparecer na lista.

Passo 3: veja no navegador e no terminal

Abra http://localhost:8080 no navegador da Ana. Você deve ver a página "Olá! Este site está rodando dentro de um container Nginx 🐳". Se aparecer "Welcome to nginx!", o bind mount não entrou (você rodou o comando fora da pasta site?) — confira com docker inspect meu-site e procure a parte de Mounts.

Pelo terminal, dá para provar que o servidor responde:

$ curl -s http://localhost:8080 | head -8
<!doctype html>
<html lang="pt-BR">
<head>
  <meta charset="utf-8">
  <meta name="viewport" content="width=device-width, initial-scale=1">
  <title>Meu site no Docker</title>

$ curl -sI http://localhost:8080 | head -1
HTTP/1.1 200 OK   « 200 OK = deu certo

E os logs do container mostram cada acesso que você fez — o Nginx registra todas as requisições:

$ docker logs meu-site
/docker-entrypoint.sh: Configuration complete; ready for start up
172.17.0.1 - - [24/Nov/2025:12:00:00 +0000] "GET / HTTP/1.1" 200 612 "-" "curl/8.5.0"
172.17.0.1 - - [24/Nov/2025:12:00:05 +0000] "GET / HTTP/1.1" 200 612 "-" "Mozilla/5.0"

O IP 172.17.0.1 é o endereço interno do próprio host na rede do Docker; "GET / HTTP/1.1" 200 é a requisição que chegou e foi atendida com sucesso.

Missão: confira os logs do Nginx: rode docker logs meu-site e procure a linha ready for start up.

Passo 4: edite e veja na hora (o pulo do gato)

Este é o momento "uau" do projeto. Abra o index.html no editor da Ana, mude o título para <h1>Agora com título novo! 🐳</h1>, salve, e recarregue o navegador. A mudança aparece na hora — porque o Nginx está lendo o arquivo direto da pasta do host, não de uma cópia dentro da imagem.

$ curl -s http://localhost:8080 | grep h1
  <h1>Agora com título novo! 🐳</h1>

É por isso que desenvolvedores usam bind mount durante o desenvolvimento: em vez de reconstruir a imagem a cada vírgula (docker build leva segundos a minutos), o arquivo é servido ao vivo. Em produção, o caminho inverso é mais comum: o site é copiado para dentro da imagem no build (COPY no Dockerfile), garantindo que o que foi testado é exatamente o que vai para o ar.

SituaçãoAbordagemComando
Desenvolvimento (editando toda hora)Bind mount: pasta do host dentro do container-v $(pwd):/usr/share/nginx/html:ro
Produção (site pronto, imagem imutável)Cópia dentro da imagem no buildCOPY . /usr/share/nginx/html no Dockerfile

Passo 5: pare e limpe tudo

Terminou de mostrar para a turma? Hora de devolver o notebook ao estado original. A ordem importa: primeiro para, depois remove:

$ docker stop meu-site
meu-site
$ docker rm meu-site
meu-site
$ docker ps -a
CONTAINER ID   IMAGE   COMMAND   CREATED   STATUS   PORTS   NAMES   « vazio: nada parado sobrando
$ docker ps
CONTAINER ID   IMAGE   COMMAND   CREATED   STATUS   PORTS   NAMES   « vazio: nada rodando

Repare que a imagem nginx:alpine continua na máquina (docker images) — só o container foi apagado. Imagens são reutilizáveis; containers são descartáveis. Esse é o modelo mental do Docker.

Erro real que a Ana cometeu: ela tentou dar docker rm meu-site antes do stop, e o Docker recusou: 
$ docker rm meu-site
Error response from daemon: cannot remove container "meu-site": container is running: stop the container before removing or force remove
A mensagem já diz a solução: pare antes (docker stop meu-site) ou force com docker rm -f meu-site. O -f manda um SIGKILL — útil para containers travados, mas perigoso para bancos de dados (pode corromper arquivos).
Outro erro real: se a porta 8080 já estiver ocupada (quem sabe outro container esquecido?), o run falha na hora: 
$ docker run -d -p 8080:80 --name meu-site nginx:alpine
docker: Error response from daemon: driver failed programming external connectivity on endpoint meu-site (...): Bind for 0.0.0.0:8080 failed: port is already allocated.
Solução: veja quem está usando a porta (docker ps ou sudo ss -ltnp | grep 8080) e ou apague esse container ou escolha outra porta do host: -p 8081:80 — o lado do container continua 80. A página Erros comuns lista esse e outros sustos.

Por baixo do capô: o que o Docker fez

Quando a Ana rodou aquele docker run longo, o Docker Engine trabalhou bastante nos bastidores. Dá para ver o resultado com docker inspect — ele devolve um JSON enorme com todos os detalhes do container:

$ docker inspect meu-site --format '{{json .Mounts}}' | python3 -m json.tool
[
    {
        "Type": "bind",
        "Source": "/home/ana/site",
        "Destination": "/usr/share/nginx/html",
        "Mode": "ro",
        "RW": false
    }
]

$ docker inspect meu-site --format '{{json .NetworkSettings.Ports}}'
{"80/tcp":[{"HostIp":"0.0.0.0","HostPort":"8080"}]}

Traduzindo: o inspect confirma que existe um mount do tipo bind, da pasta /home/ana/site do host para /usr/share/nginx/html do container, em modo somente leitura ("RW": false); e que a porta 80/tcp do container está publicada na 8080 do host em todas as interfaces. A aula docker inspect a fundo mostra outros usos do comando.

Também dá para entrar dentro do container e olhar a pasta montada por dentro — como se fosse um segundo computador:

$ docker exec meu-site ls -la /usr/share/nginx/html
total 16
-rw-r--r-- 1 ana ana  612 Nov 24 12:00 index.html

$ docker exec meu-site cat /usr/share/nginx/html/index.html | grep h1
  <h1>Agora com título novo! 🐳</h1>

$ docker exec meu-site sh -c 'echo "tentando escrever..." > /usr/share/nginx/html/teste.txt'
sh: can't create /usr/share/nginx/html/teste.txt: Read-only file system   « o :ro funcionando!

Repare na última linha: a escrita falhou com Read-only file system — é o :ro protegendo a pasta da Ana. Sem o :ro, o container conseguiria escrever (e apagar!) arquivos do host — por isso a flag é padrão em sites estáticos.

Variantes do comando (e quando usar cada uma)

SituaçãoComandoPor quê
Desenvolver o site (editar ao vivo)docker run -d -p 8080:80 -v $(pwd):/usr/share/nginx/html:ro --name meu-site nginx:alpineBind mount: cada edição no host aparece na hora.
Publicar só para o próprio computador… -p 127.0.0.1:8080:80 …Só o navegador da máquina acessa; ninguém da rede entra.

Resumo

  • A imagem nginx:alpine serve os arquivos de /usr/share/nginx/html dentro do container.
  • Com -v $(pwd):/usr/share/nginx/html:ro (bind mount), a pasta do host aparece dentro do container — e com :ro o container só lê.
  • -p 8080:80 publica a porta 80 do container na 8080 do host (formato HOST:CONTAINER); o docker ps mostra isso na coluna PORTS.
  • Graças ao bind mount, editar o arquivo no host reflete na hora no site — sem rebuild. Em produção, o caminho é copiar o site para dentro da imagem com COPY.
  • Limpeza: docker stop → docker rm (remover rodando dá erro; use -f só quando tiver certeza).
  • Porta ocupada dá port is already allocated — troque a porta do host ou apague o container que está usando ela.
