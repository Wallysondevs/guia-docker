build: no Compose — imagens próprias no projeto

Até agora os serviços usavam image: pronta, direto do Docker Hub. Mas quando a aplicação é a sua — o seu código, o seu Dockerfile — o Compose também constrói a imagem para você na hora da subida. É só trocar image: por build:. A Ana vai usar isso agora: a minhaloja dela tem uma API em Node.js, e ela quer que o up já deixe tudo no ar, imagem incluída.

Você vai aprender
  • build: . — usar o Dockerfile da pasta do projeto.
  • build na forma longa: context, dockerfile alternativo e args.
  • Quando o build acontece (primeira subida) e a pegadinha de mudar o código sem rebuildar.
  • docker compose build, up --build e --no-cache.
  • O nome que a imagem recebe (projeto-servico) e erros reais de build.

De image: para build:

Compare os dois serviços no mesmo arquivo: o banco usa imagem pronta do Hub; o api constrói a imagem local a partir do Dockerfile da pasta:

services:
  api:
    build: .              # usa o Dockerfile da pasta atual (onde está o docker-compose.yml)
    ports:
      - "3000:3000"
  banco:
    image: postgres:16-alpine

O Compose aceita misturar os dois no mesmo projeto sem problema — é exatamente o caso mais comum: imagens prontas para as dependências (banco, cache, fila) e build para o seu código.

build:
Em vez de image:, constrói a imagem na hora da subida.
.
O contexto do build: a pasta atual. O Compose procura o Dockerfile dentro dela e envia essa pasta inteira para o daemon fazer o build (é o mesmo . do docker build -t x ., aula docker build).
context:
Muda a pasta do contexto (ex.: context: ./api).
dockerfile:
Nome/caminho alternativo do Dockerfile dentro do contexto (ex.: dockerfile: Dockerfile.dev).
args:
Valores para os ARG do Dockerfile (ex.: NODE_ENV: production).
services:
  api:
    build:
      context: ./api            # pasta com o código-fonte (relativa ao YAML)
      dockerfile: Dockerfile    # arquivo dentro do contexto (esse já é o padrão)
      args:
        NODE_ENV: production    # vira ARG NODE_ENV no Dockerfile
      cache_from:               # imagens para aquecer o cache do build
        - app-api:latest

O Dockerfile do projeto

O build: . precisa de um Dockerfile na mesma pasta do docker-compose.yml. Para a API Node da Ana, algo assim (as instruções FROM, WORKDIR, COPY, RUN, EXPOSE e CMD têm aulas próprias: O que é um Dockerfile e RUN e CMD):

# syntax=docker/dockerfile:1
FROM node:22-alpine
WORKDIR /app
COPY package*.json ./
RUN npm install
COPY . .
EXPOSE 3000
CMD ["node", "server.js"]

E a estrutura da pasta, que o Compose vê assim:

app/
├── docker-compose.yml
├── Dockerfile
├── package.json
├── server.js
└── .dockerignore        # igual ao .gitignore, mas para o contexto do build (aula .dockerignore)

O .dockerignore evita que node_modules/ e .git sejam copiados para dentro da imagem — detalhe que economiza gigabytes (aula .dockerignore).

Exemplo completo: app Node + PostgreSQL

# docker-compose.yml — projeto "app"
services:
  api:                        # a sua aplicação: imagem construída do Dockerfile local
    build: .
    ports:
      - "3000:3000"
    environment:
      DATABASE_URL: postgres://ana:segredo@banco:5432/app   # @banco = nome do serviço na rede
    depends_on:
      - banco
    restart: unless-stopped

  banco:                      # imagem pronta do Docker Hub
    image: postgres:16-alpine
    environment:
      POSTGRES_USER: ana
      POSTGRES_PASSWORD: segredo
      POSTGRES_DB: app
    volumes:
      - dados:/var/lib/postgresql/data

volumes:
  dados:

Repare em @banco na DATABASE_URL: dentro da rede do projeto, o serviço é alcançado pelo próprio nome (DNS interno do Docker — aula Containers se comunicando por nome). A porta 5432 do banco nem precisa ser publicada no host: só os containers da rede chegam nela.

Quando o build acontece — e a pegadinha do código novo

Na primeira subida (ou quando a imagem ainda não existe na máquina), o Compose já faz o build sozinho. Se a imagem já existe, ele a reutiliza — e é aí que mora a pegadinha: depois de mudar o código, um up simples não refaz a imagem, e você testa a versão antiga achando que testou a nova. A Ana caiu nessa uma vez: mudou o server.js, rodou up -d, e o navegador continuava mostrando a página velha.

Para forçar o rebuild, use --build:

docker
o CLI.
compose
o plugin v2.
up
cria e inicia os serviços.
--build
reconstrói as imagens dos serviços com build: antes de subir.
-d
segundo plano.
$ docker compose up --build -d
[+] Building 14.2s (9/9) FINISHED
 => [internal] load build definition from Dockerfile
 => => transferring dockerfile: 212B
 => [1/5] FROM docker.io/library/node:22-alpine
 => [2/5] WORKDIR /app
 => [3/5] COPY package*.json ./
 => [4/5] RUN npm install
 => [5/5] COPY . .
 => exporting to image
 => => naming to docker.io/library/app-api
[+] Running 4/4
 ✔ Network app_default  Created                                    0.0s
 ✔ Volume app_dados     Created                                    0.0s
 ✔ Container app-banco-1  Started                                   0.5s
 ✔ Container app-api-1    Started                                   0.5s

Dois detalhes na saída: o build usa o cache de camadas (aula Camadas e cache do build) — se só o server.js mudou, as camadas de npm install são reaproveitadas e o build leva segundos; e a imagem recebeu o nome automático docker.io/library/app-api (nome do projeto + nome do serviço).

Também dá para buildar sem subir nada — só construir as imagens:

$ docker compose build
[+] Building 3.1s (9/9) FINISHED
 => => naming to docker.io/library/app-api
$ docker compose build --no-cache api   « ignora o cache: rebuild do zero (lento, útil para debugar build)

Erros reais de build

Dockerfile não existe na pasta do contexto (a Ana esqueceu de subir o arquivo pro notebook): 
$ docker compose up --build
failed to read dockerfile: open /home/ana/app/Dockerfile: no such file or directory
Conferira o context e se o arquivo se chama mesmo Dockerfile (com D maiúsculo, sem extensão).
COPY apontando para fora do contexto: 
COPY ../comum/config.json /app/
$ docker compose build
failed to compute cache key: failed to calculate checksum of ref ...: forbidden path outside the build context: ../comum/
O contexto é a "fronteira" do build: o Dockerfile só pode copiar o que está dentro da pasta do context (por segurança). Solução: ajuste o context para a pasta certa ou copie o arquivo para dentro do projeto.
Erro de sintaxe dentro do Dockerfile: 
$ docker compose build
#4 0.123 ERROR: failed to parse Dockerfile: unknown instruction: CPY
 => [2/5] CPY . .
CPY não existe — é COPY. O build para na instrução errada e mostra a linha. A lista completa está na aula Instruções do Dockerfile.

Para imagens enxutas em produção (multi-stage), a técnica é a mesma dentro do build: — veja Multi-stage builds.

Missão: construa só as imagens do projeto com docker compose build.

Missão: agora suba tudo rebuildando as imagens: docker compose up --build.

Missão: por fim, suba o projeto em segundo plano com docker compose up -d (sem rebuild — a imagem já existe).

O ciclo do dia a dia: editar, rebuildar, subir

Enquanto desenvolve, o ritual da Ana no ana@notebook virou um trio de comandos:

$ nano server.js            « editou o código
$ docker compose up -d --build   « rebuild da imagem + recria só o serviço que mudou
[+] Building 2.4s (9/9) FINISHED
[+] Running 3/3
 ✔ Container app-api-1    Recreated                                  0.4s
 ✔ Container app-banco-1  Running
$ docker compose logs -f api   « e acompanha os logs da API
app-api-1  | API rodando na porta 3000

Repare que só o api foi Recreated: o banco continuou Running, porque nada nele mudou — e os dados do volume nem foram tocados. O Compose compara o arquivo com o estado atual e muda só o necessário.

Se o build está lento demais, a primeira suspeita é o cache: se você mudou o package.json, a camada RUN npm install é refeita (e todas as seguintes). A ordem das instruções no Dockerfile importa — copie primeiro só o package*.json, rode o npm install, e só depois copie o resto do código (aula Camadas e cache do build).

ComandoQuando usar
docker compose buildConstruir/atualizar só as imagens, sem subir nada
docker compose up -dSubir o projeto reutilizando imagens existentes
docker compose up -d --buildRebuild das imagens com build: e recriar os serviços alterados
docker compose build --no-cacheBuild do zero, ignorando o cache (debug de build travado)
docker compose up -d --force-recreateRecriar os containers mesmo sem mudança no YAML (ex.: a aplicação leu variável de ambiente antiga)
docker compose downDerrubar tudo no fim do dia (volumes e dados ficam)

Resumo

  • build: . diz ao Compose para construir a imagem a partir do Dockerfile da pasta do projeto; dá para misturar com image: no mesmo arquivo.
  • Forma longa: context (pasta do código), dockerfile (arquivo alternativo), args (valores para ARG).
  • O build acontece na primeira subida; se a imagem já existe, ela é reutilizada — mude o código? rode docker compose up --build -d (ou compose build só para buildar).
  • A imagem recebe o nome automático <projeto>-<serviço> (ex.: app-api).
  • O build respeita o contexto (nada de COPY ../fora) e o cache de camadas; --no-cache força rebuild do zero.
  • Erros reais: failed to read dockerfile: ... no such file or directory, forbidden path outside the build context e instrução desconhecida no Dockerfile.
