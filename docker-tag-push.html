docker tag e push — publicar sua imagem

Até aqui as imagens da Ana vivent só no notebook dela (ana@notebook). Funcionam, mas têm dois problemas: se o notebook quebrar, as imagens somem; e ninguém da equipe consegue baixar. Para guardar, compartilhar e colocar em produção, você manda a imagem para um registry — um servidor que guarda imagens. O Docker Hub é o público e padrão (hub.docker.com). São dois passos: o docker tag dá um nome de publicação à imagem local e o docker push envia as camadas para o registry.

Você vai aprender
  • A anatomia completa do nome de uma imagem: [registry/][usuario/]repositório:tag.
  • Como autenticar no Docker Hub com docker login — e por que usar token no lugar da senha.
  • docker tag: renomear sem copiar nada (mesmo IMAGE ID).
  • docker push: enviar camadas ao registry (Pushed × Mounted from) e o digest sha256.
  • Os erros reais de permissão (denied, unauthorized, letra maiúscula).
  • Como isso vira pipeline de CI/CD (link para a aula de CI).

A ideia: o armário de imagens da internet

Pense no registry como um armário de imagens na internet: você guarda lá as suas ("ana/minha-api:1.0"), qualquer pessoa autorizada pode pegar uma cópia (docker pull), e o armário ainda guarda o histórico de cada versão. A máquina local continua guardando uma cópia em cache — o pull só baixa de novo o que mudou.

A anatomia do nome da imagem

Toda imagem tem um nome completo no formato:

[REGISTRY/] [USUÁRIO-OU-ORGANIZAÇÃO/] REPOSITÓRIO [:TAG]

Exemplos reais que a Ana usa:

NomeOnde moraQuem pode baixar
nginx:alpineBiblioteca oficial do Docker Hub: na verdade docker.io/library/nginx:alpineQualquer pessoa (público)
ana/minha-api:1.0Docker Hub, conta ana, repositório minha-api, tag 1.0Público (ou privado, se ela marcar)
registry.empresa.com/api:2.0Registry privado da empresa (próxima aula)Só quem tem login

Regras do nome: sem tag, o Docker assume :latest (a aula Tags e versões explica por que evitar depender dela em produção). O repositório só aceita letras minúsculas, números e os caracteres _ . - /. Se o primeiro elemento tiver ponto ou dois-pontos (ex.: registry.empresa.com), o Docker entende que é um host de registry; se não tiver, assume Docker Hub.

Passo 1: docker login

O push precisa de autenticação. Entre com a sua conta do Docker Hub (crie grátis em hub.docker.com):

$ docker login
Username: ana
Password:
WARNING! Your password will be stored unencrypted in /home/ana/.docker/config.json.
Configure a credential helper to remove this warning. See
https://docs.docker.com/engine/reference/commandline/login/#credentials-store

Login Succeeded

A credencial fica salva em ~/.docker/config.json — por isso o aviso. Em máquina compartilhada ou CI, prefira um token de acesso no lugar da senha: no Docker Hub, crie em Account Settings → Security → New Access Token, e use docker login -u ana -p dckr_pat_… (ou passe o token pelo stdin com --password-stdin, que é o jeito seguro em scripts: echo $TOKEN | docker login -u ana --password-stdin). Para sair: docker logout.

Nunca commite o ~/.docker/config.json no git. O aviso de "stored unencrypted" é sério: quem tem esse arquivo tem acesso às suas contas de registry. Coloque .docker/ no .gitignore e use tokens comescopo mínimo (só pull, ou só push) em vez da senha da conta.

Passo 2: docker tag (renomear localmente)

Você construiu a imagem minha-api:1.0 local (aula docker build). Para publicar na sua conta, crie um apelido com o nome completo:

$ docker build -t minha-api:1.0 .
…
Successfully tagged minha-api:1.0

$ docker tag minha-api:1.0 ana/minha-api:1.0   « não imprime nada: deu certo

$ docker images
REPOSITORY      TAG       IMAGE ID       CREATED          SIZE
minha-api       1.0       b2c3d4e5f6a1   2 minutes ago    189MB
ana/minha-api   1.0       b2c3d4e5f6a1   2 minutes ago    189MB
nginx           alpine    c3d4e5f6a1b2   5 days ago       48.2MB

Repare no IMAGE ID igual: o docker tag não copia nada — só aponta outro nome para a mesma imagem. Uma imagem pode ter vários nomes (várias tags), e apagar um nome com docker rmi não apaga a imagem enquanto existir outro nome (aula docker rmi).

Missão: crie o apelido ana/minha-api:1.0 para a imagem nginx:alpine com docker tag e confira a lista com docker images.

Passo 3: docker push (enviar ao registry)

Agora é a hora de subir. Só as camadas que o registry ainda não tem são enviadas de verdade — o resto é reutilizado:

$ docker push ana/minha-api:1.0
The push refers to repository [docker.io/ana/minha-api]
e5f6a1b2c3d4: Pushed
a1b2c3d4e5f6: Mounted from library/nginx      « o registry já tinha essa camada
1.0: digest: sha256:9f3ab2c1d4e5f60718… size: 2621

Cada linha é uma camada: Pushed (enviada agora) ou Mounted from … (já existia no registry, reutilizada — por isso o push da segunda versão é bem mais rápido). No fim, o digest (sha256:…) identifica a imagem de forma imutável: é esse digest que garante que o que você testou é exatamente o que vai rodar no servidor, não importa a tag. Em produção, dá para referenciar a imagem pelo digest: ana/minha-api@sha256:9f3ab2….

Missão: rode docker login (no simulador qualquer senha vale), depois docker push ana/minha-api:1.0 — o simulador avisa que o envio real acontece só num registry de verdade.

Baixando de volta: docker pull

Em qualquer máquina com Docker (um servidor de produção, o notebook de um colega), basta rodar o pull com o nome completo:

$ docker pull ana/minha-api:1.0
1.0: Pulling from ana/minha-api
e5f6a1b2c3d4: Pull complete
a1b2c3d4e5f6: Pull complete
Status: Downloaded newer image for ana/minha-api:1.0

$ docker run -d -p 3000:3000 ana/minha-api:1.0   « a mesma imagem, no servidor

Se a imagem for privada (repositório marcado como private no Hub), o pull sem login falha com denied — é a próxima aula, registry privado.

Fluxo completo: do código ao registry

No dia a dia da Ana, o fluxo é sempre o mesmo:

  1. Ela edita o código em ~/minha-api e testa local com docker compose up (projetos do guia).
  2. Quando dá certo, roda docker build -t minha-api:1.1 . (versão nova, tags).
  3. Cria o apelido público: docker tag minha-api:1.1 ana/minha-api:1.1 — e também ana/minha-api:latest, se quiser atualizar a tag padrão.
  4. Faz docker login (com token, via --password-stdin) e docker push ana/minha-api:1.1 (e o :latest).
  5. No servidor de produção, docker pull ana/minha-api:1.1 e reinicia o serviço apontando para a nova tag (ou melhor, para o digest).

Esse mesmo fluxo roda automaticamente numa pipeline de CI (GitHub Actions etc.) toda vez que ela dá push no git — é a aula Docker em pipelines de CI, e a otimização de builds para CI mostra como deixar esse build rápido.

Erros comuns

Push sem login: denied: requested access to the resource is denied ou unauthorized: authentication required. Solução: docker login antes do push — e, em CI, sempre --password-stdin com token.
Nome com letra maiúscula: docker tag nginx:alpine Ana/Minha-API:1.0 devolve invalid reference format: repository name must be lowercase. Repositório só aceita minúsculas (o ana do usuário também).
Permissão negada no repositório: se o repositório pertence a outra conta ou organização (ex.: docker push loja/minha-api:1.0 sem a Ana ter acesso), o push falha com denied — peça acesso de write na organização ou publique na sua própria conta.
Tag latest enganosa: dar push só em :latest faz todo mundo rodar "o que estiver hoje", sem saber o quê — a aula Tags mostra a convenção de usar versão semântica (:1.0, :1.1) e deixar :latest só como apelido móvel.

Várias tags, mesma imagem: a convenção da Loja Aurora

A Ana apelida cada build com duas tags: a versão exata e o latest móvel. Assim o servidor de produção pode apontar para a versão fixa (seguro) e o notebook dela pode seguir o latest (conveniente):

$ docker build -t minha-api:1.1 .
$ docker tag minha-api:1.1 ana/minha-api:1.1
$ docker tag minha-api:1.1 ana/minha-api:latest
$ docker push ana/minha-api:1.1
$ docker push ana/minha-api:latest

$ docker images ana/minha-api
REPOSITORY      TAG       IMAGE ID       CREATED          SIZE
ana/minha-api   1.1       b2c3d4e5f6a1   2 minutes ago    195MB
ana/minha-api   latest    b2c3d4e5f6a1   2 minutes ago    195MB   « mesmo ID: são apelidos

Regra de bolso da equipe: em producción, o deploy usa a tag de versão (:1.1) ou o digest; o :latest fica só para desenvolvimento. Assim ninguém é pego de surpresa por uma imagem que mudou debaixo do pé.

Resumo

ComandoO que faz
docker login [-u usuário] [--password-stdin]Autentica no Docker Hub (ou outro registry) e salva a credencial em ~/.docker/config.json. Em CI, use token + --password-stdin.
docker logoutRemove a credencial salva.
docker tag ORIGEM DESTINOCria um apelido local para a imagem — sem copiar, mesmo IMAGE ID.
docker push USUÁRIO/REPO:TAGEnvia as camadas da imagem ao registry (só as que o registry não tem). Devolve o digest sha256.
docker pull USUÁRIO/REPO:TAGBaixa uma imagem publicada por você ou por outra pessoa.
  • Nome completo: [registry/][usuário/]repositório:tag; sem registry, assume Docker Hub; sem tag, assume :latest.
  • Erros reais: denied/unauthorized (sem login), repository name must be lowercase (maiúscula no nome).
  • Em produção, prefira referenciar pelo digest (@sha256:…) — a tag pode mudar, o digest não.
