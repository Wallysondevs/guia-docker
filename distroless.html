Distroless e Alpine — imagens mínimas

Depois da aula de camadas, a Ana entendeu a matemática: imagem grande = pull lento, start lento e superfície de ataque maior (mais pacotes = mais CVEs possíveis = mais portas para um atacante). Duas famílias resolvem isso: o Alpine Linux (um sistema operacional mínimo de ~8MB, com shell e gerenciador de pacotes) e as imagens distroless do Google (só o seu binário + as bibliotecas que ele precisa — sem shell, sem nada, ~2MB). Nesta aula você vê as duas, as variantes distroless e quando usar cada uma.

Você vai aprender
  • Por que imagens menores são melhores em produção (pull, start, segurança).
  • Alpine: o que dá para fazer com o shell ash e o apk.
  • Distroless: todas as variantes (static, base, cc, nodejs, java, python3) e as tags :nonroot e :debug.
  • O trade-off de debug: o erro real de exec: "sh": executable file not found numa imagem distroless.
  • Um Dockerfile multi-stage de Go que termina numa imagem distroless.
  • Tabela comparativa: Alpine × distroless × Debian/Ubuntu comum.

Alpine: um Linux inteiro em ~8MB

O Alpine Linux é uma distribuição feita para ser mínima: usa o musl no lugar da glibc e o busybox no lugar de dezenas de utilitários. Resultado: ~8MB. No notebook da Ana:

$ docker pull alpine
latest: Pulling from library/alpine
8e402f132d08: Pull complete
Status: Downloaded newer image for alpine:latest

$ docker images
REPOSITORY   TAG      IMAGE ID       CREATED       SIZE
alpine       latest   a1b2c3d4e5f6   2 weeks ago   8.3MB

O Alpine tem shell (ash) e gerenciador de pacotes (apk), então dá para entrar e investigar na mão:

$ docker run -it --rm alpine sh
/ # apk add curl
fetch https://dl-cdn.alpinelinux.org/alpine/v3.20/main/x86_64/APKINDEX.tar.gz
(1/1) Installing curl (8.9.1-r0)
/ # exit

Por isso o nginx:alpine, node:22-alpine e postgres:16-alpine que usamos até agora são tão leves — são imagens sobre a base Alpine. O preço: às vezes um pacote compilado para glibc (Debian) não roda no Alpine (musl) — é o caso de alguns binários proprietary; a solução é usar a variante -slim (Debian) nesse caso.

Cuidado com o apk add em produção: se você instala pacotes no RUN do Dockerfile, junte com a limpeza no mesmo comando (apk add --no-cache curl já não deixa cache) — lembra da aula docker history: camadas separadas não emagrecem.

Distroless: só o binário e as bibliotecas

As imagens distroless (gcr.io/distroless/…) não têm sistema operacional, nem shell, nem apt/apk. Elas contêm somente o executável compilado e as bibliotecas que ele precisa, além de certificados CA e um usuário sem privilégios:

$ docker pull gcr.io/distroless/static-debian12
latest: Pulling from distroless/static-debian12
c3d4e5f6a1b2: Pull complete
Status: Downloaded newer image for gcr.io/distroless/static-debian12:latest

$ docker images
REPOSITORY                        TAG       IMAGE ID       CREATED       SIZE
gcr.io/distroless/static-debian12  latest   d4e5f6a1b2c3   3 weeks ago   2.1MB

As tags importantes: :nonroot (roda como usuário 65532, sem root — combine com a aula USER) e :debug (igual à normal, mas com um shell busybox dentro para depurar).

Sem shell, o exec de debug falha com erro real: docker exec -it meu-app sh numa imagem distroless devolve OCI runtime exec failed: exec failed: unable to start container process: exec: "sh": executable file not found in $PATH: unknown. Para depurar, use a tag :debug, o comando docker debug (Docker 27, que injeta ferramentas no container rodando) ou olhe os logs (docker logs continua funcionando sempre).

Dockerfile de Go terminando em distroless

A combinação clássica é o multi-stage build: compila num estágio grande (com o Go instalado) e copia só o binário para o estágio final, mínimo:

# ---- estágio 1: build (imagem grande, descartada depois) ----
FROM golang:1.23-alpine AS build
WORKDIR /src
COPY go.mod go.sum ./
RUN go mod download
COPY . .
RUN CGO_ENABLED=0 go build -o /out/server .

# ---- estágio 2: imagem final mínima ----
FROM gcr.io/distroless/static-debian12:nonroot
COPY --from=build /out/server /server
EXPOSE 8080
ENTRYPOINT ["/server"]

O resultado: uma imagem de poucos MB, sem shell, rodando como usuário sem privilégios (:nonroot) — ideal para produção. Para outras linguagens, o truque é o mesmo: copie só o artefato final (JAR para java21, pasta dist/ + node_modules para nodejs22, o venv para python3).

Regra prática da Ana: em produção, prefira distroless (ou alpine no mínimo); em desenvolvimento, pode usar a imagem completa (node:22, python:3.12) para ter shell e ferramentas à mão. E lembre: dá para ter os dois com multi-stage — build na imagem completa, runtime na mínima.

Cenário de produção: o ataque que não teve shell para usar

Numa auditoria, a empresa hipotética da Ana comparou duas imagens da mesma API: uma em debian (com bash, curl, apt) e outra em distroless. Depois de explorarem uma falha de RCE (execução remota) nas duas, no container Debian o atacante tinha shell, curl e apt à vontade — usou para baixar ferramentas e pivotar na rede. No container distroless, o comando injetado caía na hora com executable file not found: sem shell, sem curl, sem nada, a superfície de execução do atacante encolheu drasticamente. Não é bala de prata (se a própria app for maliciosa, ela roda do mesmo jeito), mas tira do atacante todo o "kit de ferramentas" que normalmente vem de brinde numa imagem completa.

Missão: baixe uma imagem distroless com docker pull gcr.io/distroless/static-debian12 e depois compare o tamanho dela com docker images.

Missão extra: rode docker images e ordene mentalmente da mais pesada para a mais leve — dá para ver na coluna SIZE quem é alpine e quem é distroless.

Como escolher a base certa: árvore de decisão

Na hora de escrever o FROM, a Ana segue este roteiro:

  1. A app é um binário estático (Go com CGO_ENABLED=0, Rust, C)? → estágio final em FROM scratch ou distroless/static:nonroot.
  2. A app precisa da glibc (binário dinâmico, lib C++)? → distroless/base ou distroless/cc.
  3. É Node/Python/Java e você não quer instalar nada em runtime? → distroless/nodejs22, distroless/python3, distroless/java21.
  4. Você precisa de shell/pacotes dentro do container (debug, instalar algo em runtime, scripts de entrypoint)? → base -alpine (ex.: node:22-alpine).
  5. Conveniência total em dev (bash, apt, ferramentas)? → imagem completa (node:22, python:3.12). Só em dev — em produção, troque pela versão slim/alpine.

E não esqueça: depois de escolher a base enxuta, aplique as proteções da aula USER (nas distroless, use :nonroot) e da multi-stage para o build não sujar a imagem final.

Resumo

  • Imagem mínima = pull/start rápidos + menos CVEs + menos ferramentas para um atacante usar.
  • Alpine (~8MB): Linux mínimo com shell (ash) e apk — bom quando você precisa entrar no container.
  • Distroless (~2–80MB): só o binário + bibliotecas + CA; sem shell nem gerenciador de pacotes — variants static, base, cc, nodejs, python3, java.
  • Tags distroless: :nonroot (roda como UID 65532) e :debug (com shell busybox, só para depurar).
  • Erro real de debug em distroless: exec: "sh": executable file not found in $PATH — use :debug ou docker debug.
  • Combine com multi-stage: build na imagem completa, runtime na mínima (Alpine ou distroless).
