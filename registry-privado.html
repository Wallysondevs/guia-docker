Registry privado e docker login

A Ana publicó ana/minha-api:1.0 no Docker Hub público na aula passada — ótimo para código aberto. Mas a API nova da Loja Aurora tem regras de negócio internas, e a imagem dela carrega o código-fonte: não pode ir para um lugar onde qualquer pessoa pode baixar. A solução é um registry privado — a mesma ideia do Hub, rodando dentro da sua infraestrutura (ou alugado na nuvem) — e o docker login funciona do mesmo jeito, só que apontando para outro endereço.

Você vai aprender
  • Por que empresas usam registry privado (segurança, compliance, velocidade de pull).
  • docker login registry.empresa.com — login é por host, não só para o Hub.
  • O nome completo da imagem muda: registry.empresa.com/projeto/api:2.0.
  • Pull e push de imagens privadas — e o erro real quando o servidor não está logado.
  • Subir um registry simples com a imagem oficial registry:2 e quando usar Harbor.
  • Os registries do mercado: Harbor, Nexus, ECR, Artifact Registry, ACR, GitLab.

Por que um registry privado?

O Docker Hub tem repositórios privados nos planos pagos, mas muitas empresas não quieren (ou não podem, por compliance) mandar o próprio código para um serviço de terceiro. Além de não vazar código proprietário, o registry privado costuma oferecer:

  • Controle de acesso: quem pode dar pull/push em cada projeto (times, papéis, service accounts).
  • Scan de vulnerabilidades na hora do push (o registry escaneia as camadas atrás de CVEs).
  • Proximidade: na mesma rede ou nuvem dos servidores, o pull é quase instantâneo (segundos em vez de minutos).
  • Replicação entre datacenters e quarentena de imagens não aprovadas.
  • Cache de camadas: como as bases (nginx:alpine etc.) já estão lá, só as camadas novas são enviadas.

docker login em outro registry

O docker login aceita o endereço do registry como argumento. A credencial fica salva por host no ~/.docker/config.json — dá para estar logado no Hub e no registry da empresa ao mesmo tempo:

$ docker login registry.empresa.com
Username: ana
Password:
WARNING! Your password will be stored unencrypted in /home/ana/.docker/config.json.
Configure a credential helper to remove this warning.

Login Succeeded

Para sair desse registry específico: docker logout registry.empresa.com. Para ver em quais registries você está logado: cat ~/.docker/config.json (as credenciais ficam em base64 — não é criptografia, é só ofuscação; por isso o aviso do login e a dica de usar credential helper ou token).

O nome completo da imagem muda

Quando o primeiro elemento do nome tem ponto ou dois-pontos (ex.: registry.empresa.com), o Docker entende que é um host de registry — e não um usuário do Hub. Sem o host na frente, o push vai para o lugar errado (o Hub):

$ docker build -t minha-api:2.0 .
$ docker tag minha-api:2.0 registry.empresa.com/projeto/minha-api:2.0

$ docker push registry.empresa.com/projeto/minha-api:2.0
The push refers to repository [registry.empresa.com/projeto/minha-api]
a1b2c3d4e5f6: Pushed
b2c3d4e5f6a1: Pushed
2.0: digest: sha256:1c8e4f2a9b3d… size: 3412
Erro clássico: esquecer o host no nome. docker push projeto/minha-api:2.0 manda a imagem para docker.io/projeto/minha-api (o Docker Hub público), não para o registry privado — e se o repositório lá for público, o código da empresa vaza. Sempre use o nome completo com o host na frente, e confira com docker images antes de dar push.

Baixando (pull) uma imagem privada

Em outra máquina (um servidor de produção, o notebook de um colega), basta estar logado nesse registry para baixar:

$ docker login registry.empresa.com
Login Succeeded

$ docker pull registry.empresa.com/projeto/minha-api:2.0
2.0: Pulling from projeto/minha-api
a1b2c3d4e5f6: Pull complete
e5f6a1b2c3d4: Pull complete
Status: Downloaded newer image for registry.empresa.com/projeto/minha-api:2.0

$ docker run -d -p 8080:8080 registry.empresa.com/projeto/minha-api:2.0
f3a1b2c3d4e5f6a1b2c3d4e5f6a1b2c3d4e5f6a1b2c3d4e5f6a1b2c3d4e5

Se o servidor não estiver logado, o pull/run falha na hora — essa é a mensagem real:

$ docker pull registry.empresa.com/projeto/minha-api:2.0
Error response from daemon: pull access denied for registry.empresa.com/projeto/minha-api,
repository does not exist or may require 'docker login': denied: requested access to the resource is denied

Em servidores de produção, o login não fica interactive: usa-se um service account (usuário de máquina) com token, injetado por gerenciador de segredos (Vault, AWS Secrets Manager, Kubernetes Secrets) na hora do deploy.

Missão: rode docker login registry.empresa.com e depois docker pull registry.empresa.com/projeto/minha-api:2.0 para baixar a "imagem privada" no simulador.

Subindo seu próprio registry (o jeito rápido)

Para testes ou uma equipe pequena, dá para subir um registry privado em um container — a própria projeto Docker mantém a imagem oficial registry:2:

$ docker run -d -p 5000:5000 --name registry registry:2

$ docker tag minha-api:2.0 localhost:5000/minha-api:2.0
$ docker push localhost:5000/minha-api:2.0
The push refers to repository [localhost:5000/minha-api]
…: Pushed

Esse registry de teste guarda as imagens numa pasta do host (monte um volume: -v registry-dados:/var/lib/registry) e não tem autenticação nem HTTPS — serve para a rede local, não para a internet. Para produção, use Harbor (abaixo) ou um serviço gerenciado.

Erros comuns

Token expirado: unauthorized: authentication required mesmo estando "logado". Tokens de CI expiram (ou são revogados) — refaça o docker login com um token novo. Em Kubernetes, o erro clássico é o ImagePullBackOff por credencial vencida no Secret.
Certificado autoassinado: x509: certificate signed by unknown authority ao dar pull de um registry interno com certificado próprio. Em produção, instale a CA da empresa nos hosts (ou no Docker: /etc/docker/certs.d/registry.empresa.com/ca.crt). Só em ambiente de teste, dá para marcar o registry como inseguro no /etc/docker/daemon.json ("insecure-registries": ["registry.empresa.com:5000"]) — nunca em produção, porque sem TLS o login e as imagens trafegam em texto claro.
Nome sem o host: dar docker push projeto/api:2.0 manda para o Docker Hub, não para o registry privado. Sempre use o nome completo com o host na frente.

Quem pode dar push? Papéis e projetos

Num registry de empresa (Harbor, ECR, GitLab…), o acesso é organizado em projetos e papéis. Na Loja Aurora, o projeto loja no registry tem essa cara:

PapelPode fazerQuem tem na Loja Aurora
GuestSó pull (baixar imagens)Estagiários, contas de leitura
DeveloperPull + pushDesenvolvedores (a Ana)
MaintainerPush + apagar tags + configurar o projetoTech lead
Project adminTudo no projeto, inclusive criar usuários e quotasEquipe de plataforma/DevOps

Boas práticas que a equipe adotou depois de um susto (alguém deu push numa tag :1.0 antiga por engano e sobrescreveu a versão boa):

  • Tags imutáveis: no Harbor dá para ligar "immutability" no projeto — depois do push, ninguém altera ou apaga aquela tag. O deploy passa a usar só digest.
  • Service accounts separadas para CI: a pipeline não usa o login pessoal da Ana; usa uma conta de robô com token próprio, que dá para revogar sem trocar a senha dela.
  • Quota de espaço: cada projeto tem um limite de GB — sem isso, um build descontrolado enche o registry e derruba os pulls de produção.
  • Scan no push: o registry escaneia as camadas e bloqueia (ou marca) imagens com CVE crítica — a Ana vê o resultado na interface web antes de liberar o deploy.

Resumo

  • Registry privado = mesma ideia do Docker Hub, na sua infraestrutura: código interno não vaza, pull é rápido na rede local e dá para ter controle de acesso e scan de CVE.
  • docker login HOST autentica por host; as credenciais ficam em ~/.docker/config.json (uma entrada por registry).
  • Nome completo com host: registry.empresa.com/projeto/api:2.0 — sem o host, o push vai para o Hub por engano.
  • Pull sem login em imagem privada falha com pull access denied … may require 'docker login'.
  • Para teste local: docker run -d -p 5000:5000 registry:2 (sem auth/HTTPS). Para produção: Harbor, ECR, Artifact Registry, ACR ou GitLab Registry.
  • Certificado autoassinado dá x509: certificate signed by unknown authority — instale a CA nos hosts; insecure-registries só em teste.
