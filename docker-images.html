docker images — as imagens locais

Enquanto docker ps lista containers (os "bolos prontos"), o docker images lista as imagens (as "receitas") guardadas na sua máquina. É o seu estoque de programas prontos para rodar.

Você vai aprender
  • A rodar docker images e ler a tabela inteira.
  • Cada coluna: REPOSITORY, TAG, IMAGE ID, CREATED, SIZE.
  • O que é REPOSITORY:TAG e por que o ID pode se repetir.
  • Imagens "penduradas" (dangling, <none>) e por que elas aparecem.
  • Variações: -a, -q, filtro por nome, --format.
  • Quanto espaço as imagens ocupam (docker system df).

As colunas, uma a uma

REPOSITORY
O nome da imagem (ex.: nginx = a oficial da biblioteca; ana/meuapp = publicada pela usuária ana). Sem barra, o Docker completa com library/ e docker.io.
TAG
A versão/variante (ex.: alpine, latest, 3.12-slim). Se você omite a tag no pull/run, o Docker usa :latest (aula Tags).
IMAGE ID
Os primeiros 12 caracteres do hash único da imagem. Duas tags podem apontar para o mesmo ID — acontece quando você dá docker tag (apelido novo para a mesma imagem) ou baixa a mesma versão com nomes diferentes.
CREATED
Quando a imagem foi criada (no registro, por quem a publicó) — não é quando você baixou. Repare: o hello-world diz "2 weeks ago" porque a imagem oficial foi publicada há 2 semanas, não porque a Ana baixou agora.
SIZE
O tamanho em disco: a soma das camadas que não são compartilhadas com outras imagens suas. Por isso duas imagens parecidas nem sempre somam o dobro.

REPOSITORY:TAG na prática

Cada linha é um "endereço + versão". Exemplos que a Ana vai encontrar:

Você vêSignificado
nginx:alpineNginx oficial, variante Alpine (leve, ~48MB)
postgres:16-alpinePostgreSQL versão 16, variante Alpine
python:3.12-slimPython 3.12, variante slim (Debian enxuto, sem compilador)
node:22-alpineNode.js 22, variante Alpine
hello-world:latestO teste de fumaça; latest = a tag padrão quando nenhuma é escrita

Imagens "penduradas" (dangling, <none>)

Quando você faz docker build de uma imagem com o mesmo nome/tag várias vezes, as versões velhas perdem a tag e aparecem como <none>:<none> — são as "imagens penduradas" (dangling):

$ docker images
REPOSITORY   TAG       IMAGE ID       CREATED          SIZE
meuapp       latest    f6a1b2c3d4e5   10 seconds ago   152MB
<none>     <none>    a1b2c3d4e5f6   5 minutes ago    148MB   « build antigo, sem tag
<none>     <none>    c3d4e5f6a1b2   1 hour ago       147MB   « outro build antigo

Elas ocupam espaço e não sirven para rodar por nome (só por ID). Para limpar: docker image prune (apaga só as dangling) ou docker system prune (apaga tudo que não está em uso) — aula docker system prune.

Por que docker rmi às vezes recusa?

Se um container (mesmo parado) estiver usando a imagem, o docker rmi responde conflict: unable to remove repository reference … container X is using its referenced image. Primeiro remova o container (docker rm) ou force com docker rmi -f. Detalhes na aula docker rmi.

Quanto espaço as imagens ocupam?

Imagens são a parte que mais enche o disco. Para ver o resumo:

$ docker system df
TYPE            TOTAL     ACTIVE    SIZE      RECLAIMABLE
Images          6         3         861MB     400MB (46%)
Containers      3         2         15MB      5MB (33%)
Local Volumes   2         1         120MB     120MB (100%)
Build Cache     12        0         340MB     340MB

ACTIVE = quantas estão em uso por algum container agora. RECLAIMABLE = o que dá para recuperar apagando o que não está em uso. A aula docker system df detalha; para limpar, docker system prune.

Apelidando imagem: docker tag

O comando docker tag cria uma nova linha na tabela apuntando para o mesmo IMAGE ID — é um apelido, não uma cópia:

$ docker tag nginx:alpine meu-nginx:dev
$ docker images
REPOSITORY   TAG       IMAGE ID       CREATED        SIZE
nginx        alpine    b2c3d4e5f6a1   5 days ago     48.2MB
meu-nginx    dev       b2c3d4e5f6a1   5 days ago     48.2MB   « mesmo ID!
$ docker run -d --name site meu-nginx:dev   « roda igualzinho

É assim que você marca uma imagem antes de mandar para o registry (ex.: docker tag meuapp:latest ana/meuapp:1.0) — aula docker tag e push.

"Baixei a imagem, mas o programa não está rodando"

Normal: docker images só mostra o que está guardado. Para o programa rodar de verdade, precisa de um container — docker run (e aí ele aparece no docker ps).

O que tem dentro de uma imagem? docker history

Cada imagem guarda o histórico das camadas (cada instrução do Dockerfile virou uma camada). Dá para ver:

$ docker history nginx:alpine
IMAGE          CREATED        CREATED BY                                      SIZE
b2c3d4e5f6a1   5 days ago     CMD ["nginx" "-g" "daemon off;"]                0B
<missing>      5 days ago     EXPOSE 80                                       0B
<missing>      5 days ago     COPY docker-entrypoint.sh … # buildkit           4.5kB
<missing>      5 days ago     …                                               44MB
<missing>      3 weeks ago    #(nop) ADD alpine base                          8MB

Cada linha é uma camada; a coluna SIZE mostra quanto aquela instrução adicionou. É assim que se entende por que uma imagem pesa o que pesa — e por que a ordem das instruções no Dockerfile muda o cache (aula camadas e cache). Para ver as camadas de verdade no disco: dive.

Filtros avançados

$ docker images --filter "dangling=true"      « só as <none> (sem tag)
$ docker images --filter "before=nginx:alpine"  « imagens criadas antes dessa
$ docker images --filter "since=python:3.12-slim" « criadas depois dessa
$ docker images --filter "reference=node:*"    « só o repositório node, qualquer tag

Resumo

  • docker images lista as receitas locais; cada linha é REPOSITORY:TAG + IMAGE ID + CREATED + SIZE.
  • CREATED é a idade da imagem no registro (não a data do seu pull).
  • Mesmo IMAGE ID em duas linhas = mesma imagem, tags diferentes (apelido).
  • Imagens <none> (dangling) são builds antigos sem tag — limpe com docker image prune / docker system prune.
  • Variações: -a (todas), -q (só IDs), docker images nginx (filtro), --format (saída própria).
  • Espaço em disco: docker system df. Remover imagem: docker rmi (próxima aula depois do pull).
