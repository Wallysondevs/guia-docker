Todos os campos do docker-compose.yml (cola)

O docker-compose.yml descreve um projeto inteiro com vários containers (web + banco + cache…) em um único arquivo YAML. O docker compose (v2, plugin que já vem com o Docker 27) lê esse arquivo e cria tudo sozinho: containers, rede interna e volumes. Esta cola lista todos os campos mais usados, com a sintaxe curta em YAML e um exemplo — guarde nos favoritos.

Você vai aprender
  • Os campos de serviço: image, build, ports, environment, env_file, volumes, depends_on, networks, restart, command, entrypoint, healthcheck.
  • Os campos de infraestrutura: services (raiz), volumes, networks, deploy, secrets, configs, profiles, extends.
  • Um docker-compose.yml completo e comentado, pronto para copiar.
  • Como subir e derrubar o projeto: up, down, ps, logs, exec, vários arquivos com -f e o override automático.
  • Os avisos/erros comuns (variável não set, arquivo com nome errado).

Regras de sintaxe do YAML que quebram iniciantes

  • Indentação de 2 espaços — nunca tab. Um espaço a mais muda o dono da chave.
  • Chaves terminam com : (services:, web:); valores simples não precisam de aspas, mas portas em formato "8080:80" precisam (senão o YAML interpreta como número/sexagesimal e dá erro).
  • Listas começam com - na linha de baixo, no mesmo nível de indentação do campo acima:
# certo:
ports:
  - "8080:80"
  - "8443:443"

# ERRADO (tab ou indentação errada quebra o parse):
ports:
     - "8080:80"

Valide o arquivo antes de subir com docker compose config — ele mostra o YAML resolvido (com variáveis expandidas) e avisa de erro de sintaxe na hora.

A tabela completa dos campos

CampoSintaxe (YAML)O que faz
services
services:
  nome-do-servico:
    …
Raiz do arquivo: declara cada serviço. Cada serviço vira um container chamado projeto-servico-1.
imageimage: nginx:alpineUsa uma imagem pronta do registry (não precisa de build).
buildbuild: . ou build: { context: ./api, dockerfile: Dockerfile.dev }Constrói a imagem a partir de um Dockerfile antes de subir o serviço. Pode ter image: junto para dar nome à imagem construída.
ports
ports:
  - "8080:80"
  - "127.0.0.1:9000:9000"
Publica portas no formato "HOST:CONTAINER" — igual ao -p do run. Com IP, restringe a interface (só localhost). Long syntax também existe (target/published/protocol).
environment
environment:
  - POSTGRES_PASSWORD=segredo
  # ou em mapa:
  # POSTGRES_PASSWORD: segredo
Variáveis de ambiente dentro do container — igual ao -e do run. Aceita ${VAR} do arquivo .env ou do ambiente.
env_file
env_file:
  - .env
Lê variáveis de um arquivo (um por linha, CHAVE=valor) — alternativa ao environment para muitos valores.
volumes
volumes:
  - ./site:/usr/share/nginx/html:ro   # bind mount
  - dados:/var/lib/postgresql/data     # volume nomeado
Monta pastas do host (bind mount, com :ro opcional) ou volumes nomeados — igual ao -v do run.
depends_on
depends_on:
  - db
# forma longa (espera ficar saudável):
depends_on:
  db:
    condition: service_healthy
Ordem de subida: o serviço sobe depois dos listados. Na forma curta só ordena; na longa pode esperar service_started, service_healthy (precisa de healthcheck no outro serviço) ou service_completed_successfully.
networks
networks:
  - minha-rede
Conecta o serviço a redes (declaradas na raiz networks: ou já existentes). Se omitir, o serviço entra na rede padrão do projeto. Dentro da rede, os serviços se acham pelo nome.
restartrestart: unless-stoppedPolítica de reinício automático do container: no (padrão), always, on-failure, unless-stopped.
commandcommand: node server.js ou lista ["node", "server.js"]Sobrescreve o CMD da imagem.
entrypointentrypoint: /docker-entrypoint.shSobrescreve o ENTRYPOINT da imagem.
healthcheck
healthcheck:
  test: ["CMD", "curl", "-f", "http://localhost"]
  interval: 30s
  timeout: 5s
  retries: 3
  start_period: 10s
Teste de saúde do serviço. O docker compose ps passa a mostrar (healthy), e o depends_on: condition: service_healthy de outro serviço passa a esperar por ele.
deploy.resources.limits
deploy:
  resources:
    limits:
      cpus: "0.50"
      memory: 512M
    reservations:
      memory: 128M
Limites e reservas de CPU/memória do serviço (aplicado pelo Compose v2; no Swarm vira docker service).
secrets
secrets:
  - minha_senha
# e na raiz:
secrets:
  minha_senha:
    file: ./senha.txt
Injeta segredos como arquivos dentro do container (geralmente montados em /run/secrets/) — melhor que variável de ambiente para senhas, porque não aparece no inspect.
configs
configs:
  - minha_config
# raiz:
configs:
  minha_config:
    file: ./nginx.conf
Injeta arquivos de configuração no container (ex.: um nginx.conf personalizado), também como arquivo em /run/secrets-style.
profiles
profiles: ["debug"]
# sobe só com:
# docker compose --profile debug up
Marca o serviço como opcional: só sobe se o profile for ativado (--profile ou COMPOSE_PROFILES). Ótimo para ferramentas de debug (phpMyAdmin, mailhog) que não devem subir sempre.
extends
extends:
  file: comum.yml
  service: base
Herda a configuração de outro serviço (de outro arquivo ou do mesmo) — evita repetir YAML.

Um docker-compose.yml completo, comentado

# version é opcional no Compose v2 (o formato novo não precisa mais)
services:
  web:                      # serviço "web" (vira o container meuapp-web-1)
    build: .                # constrói a imagem a partir do Dockerfile da pasta
    image: ana/meuapp:1.0   # …e dá esse nome à imagem construída
    ports:
      - "8080:80"           # host 8080 -> container 80
    environment:
      - NODE_ENV=production
      - DB_HOST=db          # fala com o serviço "db" pelo nome (DNS interno)
      - DB_PASSWORD=${DB_PASSWORD}   # vem do .env
    env_file:
      - .env                # também carrega tudo que estiver no .env
    volumes:
      - ./site:/usr/share/nginx/html:ro   # bind mount (pasta do host), somente leitura
    depends_on:
      db:
        condition: service_healthy      # espera o banco ficar saudável, não só subir
    networks:
      - minha-rede
    restart: unless-stopped             # reinicia sozinho se cair (a menos que pare na mão)
    healthcheck:
      test: ["CMD", "curl", "-f", "http://localhost"]
      interval: 30s
      retries: 3
      start_period: 10s
    deploy:
      resources:
        limits:
          cpus: "0.50"
          memory: 512M

  db:                       # serviço "db"
    image: postgres:16-alpine
    environment:
      - POSTGRES_PASSWORD=${DB_PASSWORD}
    volumes:
      - dados:/var/lib/postgresql/data    # volume nomeado (persiste os dados)
    networks:
      - minha-rede
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U postgres"]
      interval: 5s
      retries: 10

volumes:
  dados:                    # declara o volume nomeado usado acima

networks:
  minha-rede:               # declara a rede usada pelos serviços

$ docker compose up -d           « sobe tudo em segundo plano

Vários arquivos: -f e o override automático

Além do docker-compose.yml padrão, o Compose lê automaticamente o docker-compose.override.yml (se existir) e mescla os dois — é o padrão para separar dev de prod. Dá para passar vários arquivos na mão:

$ docker compose -f docker-compose.yml -f docker-compose.prod.yml up -d
$ docker compose -f docker-compose.yml -f docker-compose.override.yml config   « vê o merge

Ordem de prioridade: os arquivos passados depois sobrescrevem os anteriores (listas como ports são somadas; mapas como environment são mesclados por chave).

Atenção: o arquivo precisa se chamar exatamente docker-compose.yml (ou compose.yaml / compose.yml) e ficar na pasta de onde você roda o comando — ou use docker compose -f caminho/arquivo.yml up. Se o comando diz no configuration file provided: not found, o nome ou a pasta está errada.
Variável faltando: se o YAML usa ${DB_PASSWORD} e ela não existe no .env nem no ambiente, o Compose avisa na subida — WARN: The "DB_PASSWORD" variable is not set. Defaulting to a blank string. — e o serviço sobe com a variável vazia (o banco recusa, a app quebra). Sempre confira o .env (e ponha .env no .gitignore).

Missão: rode docker compose up no terminal simulado e veja os containers do projeto serem criados e iniciados.

Resumo

  • O Compose v2 lê docker-compose.yml (ou compose.yaml) da pasta atual e cria containers + rede + volumes de uma vez; docker-compose.override.yml é mesclado automaticamente.
  • Cada serviço declara image (pronta) ou build (Dockerfile), mais ports, environment/env_file, volumes, depends_on, networks, restart, healthcheck…
  • Dentro da rede do projeto, os serviços se alcançam pelo nome (db:5432, api:3000) — é o DNS interno do Docker.
  • Volumes nomeados persistem dados entre down e up; down -v apaga volumes também.
  • Valide com docker compose config; cuidado com WARN: variable is not set (variável vazia quebra banco/app).
  • Comandos do dia a dia: up -d, ps, logs -f, exec, down, -f para vários arquivos.
