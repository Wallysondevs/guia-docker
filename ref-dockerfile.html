Todas as instruções do Dockerfile (cola)

O Dockerfile é a receita da sua imagem: um arquivo de texto, uma instrução por linha, que o docker build lê de cima para baixo. Cada instrução que altera o sistema de arquivos vira uma camada (layer) na imagem — e é essa característica que faz o cache funcionar (aula Camadas e cache do build). Esta cola lista todas as instruções oficiais com sintaxe, exemplo e uma coluna extra: se ela vira camada (invalida o cache abaixo quando muda).

Você vai aprender
  • Todas as instruções do Dockerfile: FROM, RUN, CMD, ENTRYPOINT, COPY, ADD, WORKDIR, EXPOSE, ENV, ARG, LABEL, USER, VOLUME, HEALTHCHECK, ONBUILD e SHELL.
  • Quais instruções criam camada (e portanto entram no cache) e quais são só metadados.
  • Um Dockerfile completo comentado, pronto para adaptar.
  • As duas pegadinhas que mais confundem: EXPOSE não publica porta, e a diferença entre CMD e ENTRYPOINT.
  • A ordem recomendada das instruções para o cache funcionar no CI (build otimizado).

A ordem das instruções (para o cache voar)

Como cada instrução de cima invalida o cache das de baixo quando muda, a ordem certa é: coisas que mudam pouco em cima, coisas que mudam sempre embaixo:

FROM node:22-alpine          # muda raro (muda a base)
ARG VERSAO=22                # build-arg
LABEL …                      # metadados
WORKDIR /app                 # raro
COPY package*.json ./        # muda só quando muda dependência
RUN npm install              # ← fica CACHED na maioria dos builds
COPY . .                     # muda toda hora — fica por último
ENV NODE_ENV=production
EXPOSE 3000
USER node
CMD ["node", "server.js"]   # metadado final

Se o COPY . . viesse antes do RUN npm install, cada mudança no código invalidaria o install — o erro que a aula Builds otimizados corrige. Regra prática: manifesto de dependências → install → código.

Um Dockerfile completo, comentado

# Imagem base (leve, com Alpine) — ARG antes do FROM pode mudar a base no build
ARG VERSAO=22
FROM node:${VERSAO}-alpine

# Metadados (aparecem no docker inspect)
LABEL maintainer="ana@exemplo.com" versao="1.0" descricao="API do projeto 2"

# Diretório de trabalho dentro do container (cria se não existir)
WORKDIR /app

# Dependências primeiro: essa camada fica em cache enquanto o package.json não muda
COPY package*.json ./
RUN npm install --omit=dev

# Agora sim o código (muda toda hora, mas não invalida o install acima)
COPY . .

# Variável fixa em runtime (pode ser sobrescrita com -e no docker run)
ENV NODE_ENV=production

# Documenta a porta do app — NÃO publica! Para publicar use -p 3000:3000 no run
EXPOSE 3000

# Roda como usuário sem privilégios (o usuário "node" já existe na imagem oficial)
USER node

# Comando padrão ao iniciar o container (formato JSON = exec, sem shell)
CMD ["node", "app.js"]

As duas pegadinhas

Pegadinha 1: EXPOSE 3000 não publica a porta para fora do container. Ele só documenta (e alimenta o -P, que escolhe portas automáticas). Para acessar de fora, publique no docker run: docker run -p 8080:3000 minha-imagem. Se você fez o build, deu run sem -p e o navegador não abre: esse é o motivo.
Pegadinha 2: CMD vs ENTRYPOINT. Com ENTRYPOINT ["node"] e CMD ["server.js"], o container roda node server.js — e na hora do run você troca só a parte do CMD: docker run minha-imagem outro.js (vira node outro.js). Se a imagem tiver só CMD, o comando inteiro pode ser trocado no run: docker run minha-imagem echo oi. Pense no ENTRYPOINT como o programa fixo e no CMD como os argumentos padrão.
$ docker build -t meuapp:1.0 .
[+] Building 12.4s (8/8) FINISHED
 => [1/4] FROM docker.io/library/node:22-alpine
 => [2/4] WORKDIR /app
 => [3/4] COPY . .
 => [4/4] RUN npm install
 => exporting to image
 => => writing image sha256:c3d4e5f6a1b2…
 => => naming to meuapp:1.0
Successfully built c3d4e5f6a1b2
Successfully tagged meuapp:1.0
$ docker run -d --name api -p 3000:3000 meuapp:1.0
a1b2c3d4e5f6…
$ docker run --rm meuapp:1.0 echo "oi"   « sobrescreveu o CMD inteiro
oi

Missão: rode docker build -t meuapp:1.0 . no terminal simulado e veja o build criar a imagem camada por camada.

Erros comuns de Dockerfile

Instrução antes do FROM: só comentários e ARG podem vir antes da primeira FROM. Qualquer outra coisa dá Error: Dockerfile parse error line N: unknown instruction.
COPY não acha o arquivo: COPY failed: file not found in build context or excluded by .dockerignore — ou o caminho está errado (é relativo à raiz do contexto, não à pasta do Dockerfile), ou o arquivo está no .dockerignore.
RUN quebra porque a imagem não tem shell: imagens scratch/distroless não têm /bin/sh; nesse caso use o formato exec do RUN: RUN ["/app/binario", "--flag"].
Porta não abre mesmo com EXPOSE: lembre da pegadinha 1 — EXPOSE só documenta. Falta o -p no run.

FROM parametrizado com ARG (build-arg)

O ARG declarado antes do primeiro FROM pode ser usado dentro do próprio FROM — é o jeito de trocar a imagem base sem editar o arquivo:

ARG VERSAO=22
FROM node:${VERSAO}-alpine
WORKDIR /app
COPY . .
CMD ["node", "app.js"]
$ docker build -t api:22 --build-arg VERSAO=22 .
$ docker build -t api:23 --build-arg VERSAO=23 .   « mesma receita, base diferente
$ docker images | grep api
api   22   …   195MB
api   23   …   210MB

Uso clássica: testar a mesma aplicação em várias versões da linguagem no CI (uma matriz de build com VERSAO: [20, 22, 23]). Dentro do build (depois do FROM), o ARG continua valendo — dá para usar em qualquer instrução; só não confundir com ENV, que é a que fica na imagem e aparece no docker inspect e no -e do run.

Multi-stage na cola (dois FROM no mesmo arquivo)

# stage 1 — builder (descartado depois)
FROM node:22-alpine AS builder
WORKDIR /app
COPY package*.json ./
RUN npm install
COPY . .
RUN npm run build          # gera dist/

# stage 2 — imagem final limpa
FROM node:22-alpine
ENV NODE_ENV=production
WORKDIR /app
COPY package*.json ./
RUN npm install --omit=dev
COPY --from=builder /app/dist ./dist
USER node
EXPOSE 3000
CMD ["node", "dist/server.js"]

Pontos: o AS builder dá nome ao estágio; COPY --from=builder copia só o que interessa de lá; e a imagem final nem sabe que o estágio 1 existiu (por isso fica pequena). A aula Multi-stage builds mostra variações (distroless,阶段 com ferramentas de teste, etc.).
