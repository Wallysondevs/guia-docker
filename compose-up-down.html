docker compose up e down — subir e parar tudo

Com o docker-compose.yml pronto (aula O arquivo docker-compose.yml), o up cria e inicia rede, volumes e containers do projeto de uma vez. O down faz o caminho inverso: para e remove tudo. Estes são os dois comandos que você mais vai usar no dia a dia — e nesta aula vamos além deles: ps, logs, stop, start, restart e --scale.

Você vai aprender
  • docker compose up e up -d (segundo plano) — e o que cada linha da saída significa.
  • up --build para reconstruir imagens e up --scale web=3 para réplicas.
  • down e down -v (cuidado: apaga os dados dos volumes!).
  • compose ps, compose logs [-f] [--tail N] [serviço], stop, start e restart.
  • Por que o up é idempotente: rodar de novo não quebra nada.

O projeto de exemplo

Vamos usar este arquivo durante toda a aula — a Ana salvou como docker-compose.yml numa pasta ~/meuapp no ana@notebook:

# meuapp/docker-compose.yml
services:
  web:
    image: nginx:alpine
    ports:
      - "8080:80"
    depends_on:
      - banco
  banco:
    image: postgres:16-alpine
    environment:
      POSTGRES_PASSWORD: segredo
    volumes:
      - dados-db:/var/lib/postgresql/data
volumes:
  dados-db:

Dois serviços: um web (Nginx na porta 8080) e um banco (PostgreSQL com os dados num volume nomeado). É pouco, mas já mostra tudo: rede, volume, containers e ordem de subida.

up: criar e iniciar tudo

docker
o CLI.
compose
o plugin v2 (com espaço).
up
cria e inicia tudo que está no YAML: rede, volumes e containers — e reconecta o que já existe.
-d
detach: roda em segundo plano e devolve o terminal na hora.
$ docker compose up -d
[+] Running 4/4
 ✔ Network meuapp_default  Created                                    0.0s
 ✔ Volume meuapp_dados-db  Created                                    0.0s
 ✔ Container meuapp-banco-1  Started                                   0.5s
 ✔ Container meuapp-web-1    Started                                   0.5s

Lendo a saída, linha por linha:

  1. [+] Running 4/4 — o Compose enumerou 4 recursos para criar (1 rede + 1 volume + 2 containers).
  2. Network meuapp_default Created — a rede interna do projeto (todos os serviços se enxergam por ela).
  3. Volume meuapp_dados-db Created — o volume nomeado declarado no fim do YAML.
  4. Container meuapp-banco-1 Started — o banco subiu antes do web, por causa do depends_on.
  5. Container meuapp-web-1 Started — o site, já com a porta 8080 publicada.

O -1 no fim do nome é o número da réplica (cada serviço pode ter várias cópias — já já vemos como).

Sem o -d: o terminal vira os logs

Sem o -d, o up prende o terminal mostrando os logs de todos os serviços misturados, com o nome na frente — ótimo para debugar, péssimo para o dia a dia:

$ docker compose up
meuapp-banco-1  | database system is ready to accept connections
meuapp-web-1    | /docker-entrypoint.sh: Configuration complete; ready for start up
meuapp-web-1    | 172.17.0.1 - - [24/Nov/2025:12:00:01] "GET / HTTP/1.1" 200 612
^C                                                        « Ctrl+C para no logs; os containers continuam rodando

O up é idempotente

Rodar up -d de novo, sem mudar nada, não quebra nem duplica nada — o Compose vê que tudo já existe e só garante que está rodando:

$ docker compose up -d
[+] Running 2/2
 ✔ Container meuapp-banco-1  Started                                   0.2s
 ✔ Container meuapp-web-1    Started                                   0.2s

Mas se você editar o YAML (mudar a porta, a senha, a imagem), o up recria o serviço alterado:

$ docker compose up -d        « depois de trocar "8080:80" por "8081:80" no YAML
[+] Running 3/3
 ✔ Container meuapp-banco-1  Started
 ✔ Container meuapp-web-1    Recreated                                 0.3s
 ✔ Network meuapp_default   Created

Missão: suba o projeto inteiro com docker compose up -d.

up --build e up --scale

Duas variações muito usadas. O --build força a reconstrução das imagens que têm build: (detalhes na aula Build no Compose):

$ docker compose up -d --build
[+] Building 14.2s (9/9) FINISHED
 ✔ Container meuapp-api-1  Recreated                                  0.4s

E o --scale cria várias réplicas de um serviço — útil para testar balanceamento de carga:

$ docker compose up -d --scale web=3
[+] Running 4/4
 ✔ Container meuapp-web-1  Started
 ✔ Container meuapp-web-2  Started
 ✔ Container meuapp-web-3  Started
 ✔ Container meuapp-banco-1  Running

ps e logs: vendo o que subiu

Depois do up, o docker compose ps lista só os containers deste projeto (diferente do docker ps, que lista todos os containers da máquina):

$ docker compose ps
NAME            IMAGE              COMMAND                   SERVICE   CREATED          STATUS          PORTS
meuapp-web-1    nginx:alpine       "/docker-entrypoint.…"    web       30 seconds ago   Up 30 seconds   0.0.0.0:8080->80/tcp
meuapp-banco-1  postgres:16-alpine "docker-entrypoint.s…"   banco     30 seconds ago   Up 30 seconds   5432/tcp
$ docker compose ps -a        « inclui os containers parados do projeto também

E para ver a saída (logs) dos serviços — todos juntos, só um, só os últimos, ou em tempo real:

$ docker compose logs
meuapp-banco-1  | database system is ready to accept connections
meuapp-web-1    | /docker-entrypoint.sh: Configuration complete; ready for start up
$ docker compose logs web          « só do serviço "web"
$ docker compose logs --tail 20    « só as últimas 20 linhas
$ docker compose logs -f           « segue os logs em tempo real (Ctrl+C sai)

Missão: depois do up, liste os containers do projeto com docker compose ps.

Missão: veja os logs dos serviços com docker compose logs.

stop e start: pausa sem apagar

Para parar os containers do projeto sem removê-los (eles continuam existindo, parados — dá para ver com compose ps -a e voltar com start):

$ docker compose stop
[+] Running 2/2
 ✔ Container meuapp-web-1    Stopped                                    0.3s
 ✔ Container meuapp-banco-1  Stopped                                    0.4s
$ docker compose start
[+] Running 2/2
 ✔ Container meuapp-banco-1  Started                                    0.4s
 ✔ Container meuapp-web-1    Started                                    0.3s
$ docker compose restart web   « reinicia só o serviço web (útil depois de mudar configuração)

Na dúvida entre stop e down: stop pausa (os containers continuam na máquina, ocupando memória de disco); down remove. Para desenvolvimento, o down é o mais comum no fim do dia.

down: derrubar tudo

O down para e remove os containers e a rede criada para o projeto. Os volumes nomeados não são apagados por padrão — os dados do banco ficam guardados para o próximo up:

$ docker compose down
[+] Running 3/3
 ✔ Container meuapp-web-1    Removed                                    0.2s
 ✔ Container meuapp-banco-1  Removed                                    0.1s
 ✔ Network meuapp_default   Removed                                    0.1s
Cuidado com o -v: docker compose down -v apaga também os volumes nomeados do projeto — no nosso exemplo, todos os dados do PostgreSQL vão embora, sem lixeira. Use só quando quiser começar do zero de verdade (banco de desenvolvimento descartável, por exemplo). 
$ docker compose down -v
[+] Running 4/4
 ✔ Container meuapp-web-1    Removed                                    0.2s
 ✔ Container meuapp-banco-1  Removed                                    0.1s
 ✔ Network meuapp_default   Removed                                    0.1s
 ✔ Volume meuapp_dados-db   Removed                                    0.0s
Também existe o --rmi all (apaga junto as imagens usadas pelo projeto) — raramente precisa.

Missão: quando terminar, derrube o projeto com docker compose down.

Rodou o up numa pasta sem o arquivo?

Erro real quando não existe docker-compose.yml na pasta atual: 
$ cd ~
$ docker compose up
no configuration file provided: not found
Solução: entre na pasta do projeto (cd ~/meuapp) ou aponte o arquivo com -f: docker compose -f ~/meuapp/docker-compose.yml up -d.
Erro real de porta ocupada: se outra coisa na máquina (ou outro projeto seu) já estiver usando a 8080: 
$ docker compose up -d
Error response from daemon: driver failed programming external connectivity on endpoint meuapp-web-1 (a1b2c3d4e5f6…): Bind for 0.0.0.0:8080 failed: port is already allocated
Solução: troque a porta do host no YAML ("8081:80") ou derrube o que estiver usando a 8080. Veja também Erros Comuns e Soluções.

Resumo dos comandos

ComandoO que faz
docker compose upCria e inicia tudo, grudado nos logs.
docker compose up -dCria e inicia tudo em segundo plano. Idempotente: rodar de novo não quebra.
docker compose up -d --buildRebuild das imagens com build: antes de subir.
docker compose up -d --scale web=3Sobe 3 réplicas do serviço web.
docker compose ps [-a]Lista os containers do projeto (todos, se -a).
docker compose logs [-f] [--tail N] [serviço]Mostra os logs: de todos, só um serviço, últimas N linhas ou em tempo real.
docker compose stop / start / restart [serviço]Para / inicia / reinicia os containers sem apagá-los.
docker compose downPara e remove containers e a rede do projeto. Volumes ficam.
docker compose down -vComo o down, mas apaga também os volumes nomeados. Cuidado!

Quiz rápido

1. O que o docker compose down faz por padrão?

2. Qual flag sobe várias cópias de um serviço?

Resumo

  • docker compose up -d cria e inicia rede + volumes + containers do projeto em segundo plano; sem -d, o terminal vira os logs de todos os serviços.
  • O up é idempotente: reexecutar não duplica nada; se o YAML mudou, o serviço alterado é recriado (Recreated).
  • up -d --build reconstrói imagens com build:; up -d --scale web=3 sobe réplicas (meuapp-web-1, -2, -3).
  • compose ps lista só o projeto; compose logs [-f] [--tail N] [serviço] mostra as saídas.
  • stop/start pausa e retoma sem apagar; down remove containers e rede — e down -v apaga os volumes também (perigo com dados!).
  • Erros comuns: pasta sem YAML (no configuration file provided: not found) e porta do host já ocupada (port is already allocated).
