O que é Docker e Containers

Imagine que você vai se mudar. Em vez de colocar cada coisa solta no caminhão, você coloca tudo numa caixa padrão: louça numa caixa, livros noutra, roupa noutra. Qualquer caminhão carrega qualquer caixa, e na casa nova é só abrir. O Docker faz isso com programas: cada programa vai numa "caixa" chamada container, e essa caixa roda igual em qualquer computador.

Você vai aprender
  • O que é um container e o que é uma imagem.
  • A história real do problema "na minha máquina funciona" — com a Ana e o site dela.
  • A diferença entre container e máquina virtual (VM), linha por linha.
  • As peças do Docker: Engine (daemon), CLI, Registry e Docker Hub.
  • Um pouco de história: de 2013 (dotCloud) até a OCI de hoje.
  • Seu primeiro comando real: docker --version — e os erros de quem ainda não instalou.

O problema: "na minha máquina funciona"

A Ana é desenvolvedora web e fez um site novo no notebook dela. No computador da Ana, abre lindo no navegador: http://localhost:3000. Ela manda o endereço do servidor para o cliente e... nada. A página quebra. O servidor mostra um erro esquisito sobre uma biblioteca que "não existe".

O que aconteceu? O notebook da Ana tem Python 3.12 instalado, com um pacote chamado flask na versão 3. No servidor, tinha Python 3.9 e o flask nem estava instalado. Cada máquina é um ambiente levemente diferente — sistema operacional, versões, bibliotecas, variáveis de configuração, permissões — e essas diferenças minúsculas quebram programas que pareciam prontos.

Antes do Docker, a solução era: "instala aí no servidor a mesma coisa que eu tenho aqui" — e torcer. Deu tão errado que virou meme: "works on my machine" ("na minha máquina funciona").

O Docker resolve isso empacotando o programa junto com o ambiente inteiro: o sistema operacional base, as bibliotecas, as versões exatas, as variáveis de configuração. Tudo dentro de uma unidade que roda igual em qualquer lugar — no notebook da Ana, no servidor do cliente, no computador Windows do amiga dela, na nuvem. A frase vira outra: "roda em qualquer máquina".

Sem Docker (o drama da Ana)Com Docker
"Instala o Python 3.12 e o flask 3.0 no servidor, por favor"docker run meu-site — e pronto, é a mesma caixa em todo lugar
Funciona no notebook, quebra no servidorA caixa carrega o ambiente inteiro junto com o programa
"Qual versão você instalou?" — horas de debugA versão está escrita dentro da imagem, imutável
Um projeto atrapalha o outro (versões diferentes)Cada projeto roda isolado no seu próprio container

Container × Máquina Virtual

Muita gente confunde container com máquina virtual (VM, tipo VirtualBox). A diferença é o peso:

Máquina Virtual (VM)Container Docker
O que éUm computador inteiro simulado dentro do seuUm processo isolado que usa o sistema do hospedeiro
PesoGBs (tem um sistema operacional inteiro dentro)MBs (compartilha o kernel do Linux hospedeiro)
Tempo para ligarMinutosSegundos (ou menos)
IsolamentoTotal (hardware virtualizado)De processos e rede (namespaces + cgroups)
AnalogiaUma casa dentro do seu terrenoUm apartamento no seu prédio

Na analogia do prédio: a VM é uma casa própria — tem estrutura própria, demora para construir e ocupa terreno. O container é um apartamento — mora no mesmo prédio (sistema operacional hospedeiro), tem paredes próprias (isolamento de processos), mas divide o encanamento e a energia (o kernel do sistema). Por isso um servidor pequeno roda dezenas de containers, mas só 2 ou 3 VMs. Por isso containers viraram o padrão para rodar aplicações na nuvem.

Mas e a segurança?

O isolamento do container é de processos, não de hardware. Por isso container não substitui VM quando você precisa de isolamento máximo (por exemplo, rodar código de cliente desconhecido com privilégios altos). Para o uso normal — rodar aplicações, bancos, sites — o isolamento do Docker é o padrão da indústria e é o que todo serviço de nuvem usa por baixo dos panos.

Imagem: a receita. Container: o bolo pronto.

Os dois termos mais importantes do Docker:

Imagem (image)
É a receita: um arquivo somente leitura, em camadas, com o sistema base e tudo instalado. Você não muda a imagem depois de pronta; ela é o molde. Fica guardada no disco e pode ser compartilhada no Docker Hub (um "supermercado" de imagens prontas).
Container
É o bolo pronto: uma instância viva da imagem, com uma camada gravável em cima (onde o programa salva arquivos). Vários containers podem nascer da mesma imagem — como assar vários bolos da mesma receita. Você pode parar, apagar e recriar containers à vontade — a imagem continua lá.
$ docker images          « lista as receitas (imagens) na máquina
$ docker run nginx       « usa a receita nginx para assar um bolo (container)
$ docker ps              « lista os bolos (containers) rodando agora

Essa é a ideia central de todo o guia: quem manda é a imagem; o container é só uma cópia viva e descartável dela. Por isso dá para apagar um container sem medo — a receita continua guardada. E por isso dá para rodar 10 containers da mesma imagem: 10 cópias do mesmo bolo.

De onde vêm as imagens? O anatomy de um nome

Uma imagem tem um nome completo, como um endereço:

docker.io/library/nginx:alpine
│         │       │      └── tag (versão/variante)
│         │       └──────── repository (o nome da imagem)
│         └──────────────── namespace (quem publica; "library" = oficial)
└────────────────────────── registry (o depósito; docker.io = Docker Hub)
registry
O servidor que guarda e distribui imagens. O padrão é docker.io (o Docker Hub). Se você não escrever nada, o Docker completa com docker.io.
namespace
O "sobrenome" de quem publica. Imagens oficiais (nginx, postgres, node) moram em library. Usuários comuns usam o próprio nome de usuário: docker.io/ana/meuapp.
repository
O nome da imagem em si: nginx, meuapp.
tag
A versão ou variante: :alpine, :latest, :22. Se omitir, o Docker usa :latest. A aula Tags e versões detalha.

As peças do Docker

Quando você digita docker alguma-coisa, várias peças trabajan juntas:

  • Docker CLI (o comando docker): o programa de linha de comando que você digita; ele manda os pedidos para o Engine. É o controle remoto.
  • Docker Engine (o "daemon", dockerd): o serviço que roda em segundo plano na máquina e faz o trabalho pesado — criar, rodar, parar e gerenciar containers. É a cozinha.
  • Registry: um servidor que guarda e distribui imagens. O comando docker pull baixa de um registry; docker push envia para um.
  • Docker Hub (hub.docker.com): o registry público oficial. Tem imagens oficiais (nginx, postgres, node…) e as da comunidade. O comando docker pull nginx baixa de lá por padrão.
PeçaComando típicoAnalogia

Quando o Docker não está instalado ou o daemon está parado, a CLI avisa que não conseguiu falar com o Engine — é o erro Cannot connect to the Docker daemon, que você vai ver na aula Instalar o Docker.

Um pouco de história

Em 2013, a empresa dotCloud (que fazia uma plataforma de hospedagem chamada... dotCloud) liberou como código aberto a tecnologia interna que usava para isolar os apps dos clientes: o Docker. A ideia pegou rápido demais: em poucos meses, dezenas de milhares de pessoas já usavam. Em 2014 a empresa virou Docker Inc. e o projeto continuou crescendo.

Hoje o Docker é padrão da indústria, e existe até a OCI (Open Container Initiative), um padrão aberto de imagens e containers que o Docker segue — ou seja, uma imagem feita com Docker roda em outras ferramentas compatíveis (Podman, containerd, Kubernetes). Aprender Docker é aprender o idioma padrão dos containers.

Quando dá errado

Se aparecer command not found

O Docker não está instalado ou não está no PATH — volte para a aula de instalação e confira cada passo.

Se aparecer Cannot connect to the Docker daemon

A CLI está instalada, mas o serviço (o daemon dockerd) não está rodando. No Linux: sudo systemctl start docker (e sudo systemctl enable docker para ligar sozinho no boot). No Docker Desktop: abra o aplicativo. A aula Instalar o Docker cobre os dois casos.

Resumo

  • O problema clássico: "na minha máquina funciona" — cada máquina tem um ambiente levemente diferente e isso quebra programas.
  • O Docker empacota o programa com o ambiente inteiro numa caixa chamada container, que roda igual em qualquer máquina.
  • Imagem = receita (somente leitura, em camadas); container = bolo pronto (instância viva, descartável). Vários containers podem nascer da mesma imagem.
  • Container não é máquina virtual: VM tem sistema próprio (GBs, minutos); container compartilha o kernel do hospedeiro (MBs, segundos).
  • As peças: CLI (o que você digita), Engine/dockerd (o serviço que faz o trabalho), Registry (depósito de imagens) e Docker Hub (o registro público padrão).
  • O nome completo de uma imagem é registry/namespace/repository:tag — ex.: docker.io/library/nginx:alpine.
  • Primeiro comando: docker --version. Erros comuns: command not found (não instalou) e Cannot connect to the Docker daemon (daemon parado).
