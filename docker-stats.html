docker stats — recursos em tempo real

Quem está consumindo CPU? Quem está enchendo a memória? O docker stats mostra uma tabela viva, atualizada a cada segundo, com o uso de recursos de cada container rodando — é o top dos containers (pense no painel de um carro: velocímetro, marcador de combustível, temperatura do motor).

Você vai aprender
  • Ler as colunas: CPU %, MEM USAGE / LIMIT, MEM %, NET I/O, BLOCK I/O e PIDS.
  • --no-stream: imprimir uma única vez e sair (snapshot, ideal para scripts).
  • --format com templates Go ({{.CPUPerc}}, {{.MemPerc}}…).
  • Passar nomes/IDs para monitorar só alguns containers.
  • Diagnosticar container lento, com vazamento de memória (OOM kill, Exited 137) ou com disco travado.

A cena: a loja da Ana está lenta

Num sábado de pico, os clientes da minhaloja reclamaram que o site estava lento. A Ana abriu o ana@notebook, subiu os dois containers do projeto dela e abriu o painel:

$ docker run -d --name web -p 8080:80 nginx:alpine
$ docker run -d --name banco -e POSTGRES_PASSWORD=segredo postgres:16-alpine
$ docker stats
CONTAINER ID   NAME      CPU %     MEM USAGE / LIMIT     MEM %     NET I/O       BLOCK I/O     PIDS
a1b2c3d4e5f6   web       0.02%     8.5MiB / 7.79GiB      0.11%     1.2kB / 0B    648kB / 0B    5
b2c3d4e5f6a1   banco     1.34%     68.2MiB / 7.79GiB     0.86%     3.4kB / 0B    12MB / 4MB     28
^C

A tabela se atualiza sozinha a cada segundo; Ctrl+C sai (os containers continuam rodando — o stats só observa, não mata nada). Sem container rodando, a tabela aparece só com o cabeçalho.

As colunas, uma a uma

ColunaO que éDica de leitura
CONTAINER ID / NAMEO container daquela linha.O ID sai truncado (12 caracteres); o nome é o que você deu no --name.
CPU %Porcentagem da CPU da máquina usada pelo container.Pode passar de 100% em máquinas com vários núcleos (ex.: 250% = 2,5 núcleos inteiros).
MEM USAGE / LIMITMemória em uso agora / limite de memória disponível.O limite é o da máquina, a menos que você tenha imposto um com --memory (aula Limites de CPU e memória).
MEM %Percentual do limite de memória que está em uso.Perto de 100% = perigo de OOM kill (veremos abaixo).
NET I/OTráfego de rede acumulado: entrada / saída.Cresce sempre — é acumulado desde que o container subiu, não por segundo.
BLOCK I/OLeitura / escrita em disco acumuladas.Banco de dados costuma liderar aqui.
PIDSNúmero de processos/threads rodando dentro do container.Se cresce sem parar, há vazamento de processos.

Atenção: NET I/O e BLOCK I/O são acumulados (desde o início), não por segundo. Para ver a velocidade do momento, olhe a diferença entre duas atualizações da tabela.

Anatomia do comando

docker stats
abre a tabela viva de todos os containers rodando (parados não aparecem).
--no-stream
imprime a tabela uma única vez e já sai (snapshot) — perfeito para scripts e logs.
--format
saída personalizada com template Go (veremos já).
--no-trunc
mostra o ID completo do container (por padrão sai com 12 caracteres).
web banco
lista opcional de containers (nome ou ID) para monitorar só eles.

--no-stream: uma foto só (snapshot)

Por padrão o docker stats fica em tempo real (streaming), grudado no terminal. Com --no-stream, ele imprime a tabela uma única vez e devolve o terminal — ideal para registrar o uso de recursos num log ou numa variável de script:

$ docker stats --no-stream
CONTAINER ID   NAME   CPU %   MEM USAGE / LIMIT     MEM %   NET I/O       BLOCK I/O   PIDS
a1b2c3d4e5f6   web    0.05%   12.5MiB / 7.79GiB     0.16%   1.2kB / 0B    0B / 0B     5
b2c3d4e5f6a1   banco  1.20%   68.2MiB / 7.79GiB     0.86%   3.4kB / 0B    12MB / 4MB   28

Missão: suba um container (docker run -d --name web nginx:alpine) e rode docker stats --no-stream — a tabela deve mostrar a linha do container (com o uso de memória, ex.: 12.5MiB) e o comando deve voltar na hora.

Missão: sem nenhum container rodando, rode docker stats: a saída mostra só o cabeçalho (CONTAINER ID … PIDS), porque parados não entram na tabela.

Só alguns containers

Passe os nomes ou IDs no final para monitorar só quem interessa:

$ docker stats --no-stream web
CONTAINER ID   NAME   CPU %   MEM USAGE / LIMIT     MEM %   NET I/O       BLOCK I/O   PIDS
a1b2c3d4e5f6   web    0.05%   12.5MiB / 7.79GiB     0.16%   1.2kB / 0B    0B / 0B     5
$ docker stats web banco   « só esses dois, em tempo real

--format: saída sob medida com templates Go

Assim como no docker inspect --format (aula docker inspect), o stats aceita templates Go. Os campos mais usados: {{.Container}}, {{.Name}}, {{.CPUPerc}}, {{.MemUsage}}, {{.MemPerc}}, {{.NetIO}}, {{.BlockIO}}, {{.PIDs}}:

$ docker stats --no-stream --format "{{.Name}}: CPU {{.CPUPerc}} | MEM {{.MemUsage}} ({{.MemPerc}})"
web: CPU 0.05% | MEM 12.5MiB / 7.79GiB (0.16%)
banco: CPU 1.20% | MEM 68.2MiB / 7.79GiB (0.86%)
$ docker stats --no-stream --format "table {{.Name}}\t{{.CPUPerc}}\t{{.MemPerc}}"
NAME      CPU %     MEM %
web       0.05%     0.16%
banco     1.20%     0.86%

Útil para um alerta simples de monitoramento:

$ docker stats --no-stream --format "{{.Name}} {{.MemPerc}}" | awk '$2+0 > 80 {print "ALERTA: " $1 " com memoria acima de 80%: " $2}'

Lendo os sinais de alerta

Sinal no statsO que pode estar acontecendoO que fazer
CPU % alto e constanteUm processo dentro do container consumindo muito processamento (loop infinito, carga pesada, build dentro do container).docker exec <container> top para ver o processo; ajuste a aplicação ou imponha --cpus (aula Limites).
MEM % perto de 100%Risco de OOM Kill: o kernel mata o processo e o container sai com Exited (137).Veja docker ps -a; aumente o limite (--memory) ou corrija o vazamento de memória da aplicação.
BLOCK I/O crescendo rápidoMuito acesso a disco — banco em disco lento, muitos arquivos pequenos, log descontrolado.Verifique o driver de logs (aula Drivers de log) e se há volume/SSD adequado.
NET I/O altoMuito tráfego de rede (downloads, muitos acessos simultâneos, DDoS).Limite taxa no proxy reverso; confira se não há vazamento de conexões.
PIDS crescendo sem pararVazamento de processos (cada requisição abre um processo e não fecha).Reinicie o container como paliativo e corrija a aplicação.
Container morrendo "do nada"? Olhe o MEM % no docker stats: se a memória chega no limite, o kernel mata o processo (OOM Kill) e o container aparece como Exited (137) no docker ps -a: 
$ docker ps -a
CONTAINER ID   IMAGE     STATUS
f6a1b2c3d4e5   app-api   Exited (137) 5 minutes ago     « 137 = morto pelo kernel por falta de memória
$ docker inspect --format 'exit code: {{.State.ExitCode}}' f6a1b2c3d4e5
exit code: 137
Solução: aumentar o limite (flag --memory, aula Limites de CPU e memória) ou corrigir o vazamento de memória da aplicação. O docker inspect --format '{{.State.ExitCode}}' confirma o 137 (aula docker inspect).

stats × system df × top: quem vê o quê?

ComandoO que mostraQuando usar
docker statsUso agora de cada container rodando: CPU, memória, rede, disco, processos (tabela viva)."Meu container está lento/agindo estranho agora?"
docker system dfEspaço em disco acumulado do Docker (imagens, containers parados, volumes, cache)."O disco encheu — o Docker é o culpado?" (aula docker system df)
top / htop no hostProcessos da máquina inteira, incluindo o próprio daemon do Docker."A máquina inteira está lenta, não só um container"

Stats dos serviços do Compose

Os containers criados pelo docker compose up aparecem no docker stats como qualquer outro — com os nomes do projeto (meuapp-web-1, meuapp-banco-1):

$ docker compose up -d
$ docker stats --no-stream
CONTAINER ID   NAME             CPU %   MEM USAGE / LIMIT     MEM %   NET I/O       BLOCK I/O     PIDS
a1b2c3d4e5f6   meuapp-web-1     0.03%   9.1MiB / 7.79GiB      0.12%   1.5kB / 0B    648kB / 8kB   5
b2c3d4e5f6a1   meuapp-banco-1   2.10%   74.6MiB / 7.79GiB     0.94%   4.2kB / 0B    18MB / 4MB     30

Também existe o docker compose top, que mostra os processos dentro de cada serviço do projeto (é o top deles, sem precisar entrar com docker exec):

$ docker compose top banco
UID    PID     CPU %   MEM %   TIME
999    1201    1.8%    0.9%    0:01.23 postgres
999    1245    0.0%    0.1%    0:00.05 postgres: checkpointer

Registrando um snapshot num log

Como o --no-stream devolve o terminal na hora, dá para guardar a foto do uso de recursos num arquivo — útil para comparar antes e depois de uma mudança na aplicação:

$ docker stats --no-stream >> /var/log/meuapp-stats.log
$ tail -8 /var/log/meuapp-stats.log
CONTAINER ID   NAME   CPU %   MEM USAGE / LIMIT     MEM %   NET I/O       BLOCK I/O   PIDS
a1b2c3d4e5f6   web    0.05%   12.5MiB / 7.79GiB     0.16%   1.2kB / 0B    0B / 0B     5

O >> anexa ao fim do arquivo (em vez de apagar com >), então o log vira um histórico. Num servidor de verdade, esse tipo de coleta normalmente é feita por ferramentas de monitoramento (Prometheus + cAdvisor, Grafana…), mas para um notebook de estudo o stats --no-stream no crontab já resolve.

Quiz rápido

1. Para que serve o --no-stream no docker stats?

2. Um container aparece como Exited (137) no docker ps -a. O que aconteceu?

3. No docker stats, o que significa CPU % acima de 100%?

Resumo

  • docker stats é a tabela viva de recursos dos containers rodando: CPU %, MEM USAGE / LIMIT, MEM %, NET I/O, BLOCK I/O, PIDS. Ctrl+C sai sem parar nada.
  • --no-stream tira uma foto única e devolve o terminal (snapshot para scripts/logs); docker stats web banco filtra só alguns containers.
  • --format com templates Go: {{.Name}}, {{.CPUPerc}}, {{.MemUsage}}, {{.MemPerc}}, {{.NetIO}}, {{.BlockIO}}, {{.PIDs}}; prefixo table gera cabeçalho.
  • NET I/O e BLOCK I/O são acumulados desde a subida; CPU% pode passar de 100% (vários núcleos).
  • Tabela de alertas: CPU alto = processo consumindo; MEM% perto de 100% = OOM kill iminente (Exited (137), confirmado com docker inspect --format '{{.State.ExitCode}}'); BLOCK I/O crescendo = disco; PIDS crescendo = vazamento de processos.
  • Complementos: docker system df para espaço em disco acumulado e top no host para a máquina inteira.
