docker stop, start, restart

Um container rodando pode ser parado, religado e reiniciado sem ser recriado. O estado interno (arquivos gravados na camada do container) continua lá — parar não é apagar. Nesta aula a Ana controla the ciclo de vida do site dela no notebook.

Você vai aprender
  • docker stop: parar com educação (SIGTERM, espera, depois SIGKILL).
  • docker start: religar o mesmo container (nada se perde).
  • docker restart: stop + start num comando só.
  • docker kill: parar na marra (SIGKILL imediato) — quando usar.
  • A opção -t (tempo de espera) e o erro No such container.

A cena: o site da Ana no ar

Ela subiu o Nginx dela na aula de docker run:

$ docker run -d --name meu-site nginx:alpine
$ docker ps
CONTAINER ID   IMAGE          STATUS         PORTS     NAMES
f3a1b2c3d4e5   nginx:alpine   Up 5 seconds   80/tcp    meu-site

stop: parar com educação

Missão: suba um container com docker run -d --name meu-site nginx:alpine e depois pare com docker stop meu-site.

$ docker stop meu-site
meu-site
$ docker ps
CONTAINER ID   IMAGE   COMMAND   CREATED   STATUS   PORTS   NAMES   « sumiu dos rodando
$ docker ps -a
… STATUS                       NAMES
… Exited (0) 2 seconds ago     meu-site   « está parado, NÃO apagado

O comando imprime o nome do container parado (é a confirmação). Repare na diferença crucial: docker ps (só rodando) ficou vazio, mas docker ps -a mostra o container como Exited (0) — parado, guardado, pronto para religar.

docker stop meu-site
"Pare o container chamado meu-site" (dá para passar vários: docker stop a b c, ou IDs).
SIGTERM
O stop manda o sinal de término "gentil" para o processo principal: o Nginx fecha as conexões abiertas e sai limpando a casa.
espera 10 segundos
Se o processo não terminar nesse tempo, o Docker manda SIGKILL e mata na marra. Dá para mudar: docker stop -t 30 meu-site (30s) ou -t 0 (mata na hora).

start: religar o mesmo container

Religar usa o mesmo container — com os mesmos arquivos, mesma configuração, mesmo ID:

$ docker start meu-site
meu-site
$ docker ps
… STATUS          NAMES
… Up 2 seconds    meu-site   « voltou a rodar

É diferente de dar docker run de novo (que criaria um container novo). O start ressuscita o antigo — por isso o CREATED continua antigo no ps.

Missão: com o container parado, rode docker start meu-site e depois docker ps para vê-lo Up de novo.

restart: parar e ligar de novo

$ docker restart meu-site
meu-site

Equivalente a stop + start. Muito usado depois de trocar uma configuração montada por volume (ex.: editar o nginx.conf na sua pasta e mandar docker restart meu-site para o Nginx recarregar).

kill: parar na marra

$ docker kill meu-site    « SIGKILL imediato, sem esperar os 10s

O processo morre na hora, sem chance de limpar nada (arquivos abertos podem corromper). Use kill só quando o stop travar — container que não responde ao SIGTERM. No ps -a, um container morto por kill aparece como Exited (137) (128 + 9 = sinal 9, SIGKILL).

O ciclo de vida completo

$ docker run -d --name ciclo nginx:alpine    « nasce rodando
$ docker ps                → Up …            ciclo
$ docker stop ciclo        → Exited (0)       ciclo  (parado, existe)
$ docker start ciclo       → Up …            ciclo  (religou o MESMO)
$ docker stop ciclo
$ docker rm ciclo          → some da lista    (apagado de vez)

Os arquivos que o programa gravou dentro do container continuam na camada gravável enquanto o container existir (mesmo parado). Eles só somem com docker rm. Para dados que devem durar de qualquer jeito, use volumes.

Erro real: container que não existe

Missão: tente parar um container que não existe: docker stop nao-existe. Veja a mensagem de erro real.

$ docker stop nao-existe
Error response from daemon: No such container: nao-existe

Nome errado ou container já apagado. Confira os nomes certos com docker ps -a.

Erro real: start em container que já está rodando 
$ docker start meu-site     « já está Up
docker: Error response from daemon: container meu-site is already running

Vários containers de uma vez

Todos esses comandos aceitam vários nomes/IDs de uma vez, e dá para combinar com $(...):

$ docker run -d --name web nginx:alpine
$ docker run -d --name cache redis:7-alpine
$ docker stop web cache        « dois de uma vez
web
cache
$ docker start web cache
web
cache
$ docker restart $(docker ps -q)   « reinicia TODOS os que estão rodando
Cuidado com docker stop $(docker ps -q)

Isso para todos os containers rodando da máquina — inclusive de outros projetos. Sempre confira antes com docker ps.

Parar tudo de uma vez: a ordem certa

  1. docker ps — veja o que está rodando.
  2. docker stop $(docker ps -q) — para todos os rodando.
  3. docker ps -a — agora todos estão Exited.
  4. Quando quiser apagar: docker rm $(docker ps -aq) (próxima aula).

Relacionados: pause e restart policy

Dois parentes próximos que vale conhecer:

  • docker pause X / docker unpause X: congela o processo (ele continua existindo, mas não usa CPU) e descongela depois. Diferente do stop, que mata o processo. Útil para "dar um tempo" num container pesado sem perdê-lo.
  • --restart unless-stopped no docker run: se o container cair (ou a máquina reiniciar), o Docker religa sozinho — não precisa de start manual. É o que se usa em produção (aula HEALTHCHECK e restart policies aprofunda).
$ docker run -d --restart unless-stopped --name api node:22-alpine node server.js
$ docker ps
… STATUS                          NAMES
… Up 5 seconds (healthy)  ou simply Up 5 seconds   api

Parar na prática: o fluxo de debug da Ana

Quando um serviço cai sozinho, a sequência que a Ana usa:

  1. docker ps -a — o container está Exited (1)? (morreu com erro)
  2. docker logs NOME — qual foi a última linha antes de morrer? (aula logs)
  3. Corrige a causa (variável faltando, porta ocupada, arquivo errado…).
  4. docker start NOME — tenta religar o mesmo (se o comando padrão ainda vale).
  5. Se a imagem/config mudou: docker rm NOME + docker run … de novo (container novo).

Reinício automático: --restart

Em vez de religar na mão, dá para dizer pro Docker cuidar: a flag --restart no run define o que acontece quando o container cai ou a máquina reinicia:

ValorQuando religa
no (padrão)Nunca — se cair, fica parado até você dar start
alwaysSempre, mesmo se você deu stop na mão (só para de vez com docker rm)
on-failureSe saiu com código ≠ 0 (erro)
unless-stoppedSempre, exceto se você deu stop manualmente — o mais usado em produção
$ docker run -d --restart unless-stopped --name api node:22-alpine node server.js
$ docker ps
… STATUS                NAMES
… Up 5 seconds (healthy) ou Up 5 seconds   api

O status entre parênteses (ex.: (health)) aparece quando a imagem tem HEALTHCHECK definido — aula HEALTHCHECK e restart policies.

Quanto tempo o stop esperou?

Dá para ver no log do próprio container ou com docker inspect (campo State.FinishedAt menos StartedAt). E dá para mudar a espera: docker stop -t 30 meu-site (30 segundos) ou -t 0 (mata na hora, como kill).

Resumo

  • docker stop X para com educação (SIGTERM, espera até 10s com -t, depois SIGKILL) e imprime o nome.
  • docker start X religa o mesmo container — arquivos e config continuam lá; docker restart X = stop + start.
  • docker kill X mata na hora (SIGKILL, vira Exited (137)) — só quando o stop travar.
  • Parado ≠ apagado: o container parado só aparece no ps -a e só sai de vez com docker rm.
  • Erros reais: No such container: X (nome errado/apagado) e container X is already running (start em quem já está Up).
