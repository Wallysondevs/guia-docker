DNS interno — containers se comunicando por nome

Numa rede criada por você (docker network create), o Docker liga um servidor DNS interno (no endereço 127.0.0.11) que resolve o nome de cada container para o IP dele, na hora. É isso que permite a sua aplicação falar com o banco usando postgres://meu-banco:5432 — sem saber nenhum IP, e sem quebrar quando o IP mudar. Nesta aula a Ana monta o cenário completo dela: API + banco conversando por nome.

Você vai aprender
  • Como o DNS interno do Docker (127.0.0.11) resolve nomes de containers numa rede user-defined.
  • Um exemplo completo: app + banco na mesma rede, com --network.
  • Por que o IP pode mudar e o nome não — e como recriar o container não quebra a app.
  • --network-alias para dar apelidos a um container (vários nomes para o mesmo IP).
  • Por que -p só vai no serviço que precisa ser externo (o banco sem porta publicada fica protegido).
  • Por que na rede bridge padrão o nome não resolve (só o IP).
  • docker network inspect para ver os containers e IPs que o DNS está resolvendo.

A analogia: a lista telefônica do prédio

Na aula anterior vimos a rede como um prédio de apartamentos, onde cada container tem um interfone interno (um IP). O problema: IP muda — se o síndico troca o apartamento de lugar, o número do interfone muda. O DNS interno do Docker é a lista telefônica do prédio: você liga para o nome ("meu-banco") e a lista entrega o número atual. Se o container do banco for recriado e ganhar outro IP, a app nem percebe — ela continua ligando para o nome.

O cenário: app + banco na mesma rede

A Ana sobe a rede, o banco e a API no notebook dela, tudo na app-net:

$ docker network create app-net
7d6e5f4a3b2c1d0e9f8a7b6c5d4e3f2a1b0c9d8e7f6a5b4c3d2e1f0a9b8c7d6e
$ docker run -d --name meu-banco --network app-net \
>     -e POSTGRES_PASSWORD=segredo \
>     -v dados-postgres:/var/lib/postgresql/data \
>     postgres:16-alpine
a1b2c3d4e5f6a1b2c3d4e5f6a1b2c3d4e5f6a1b2c3d4e5f6a1b2c3d4e5f6a1b2c3d4e5f6a1b2c3d4e5f6a1b2c3d4e5
$ docker run -d --name minha-api --network app-net \
>     -p 3000:3000 \
>     -e DATABASE_URL=postgres://meu-banco:5432/guia \
>     node:22-alpine node server.js
b2c3d4e5f6a1b2c3d4e5f6a1b2c3d4e5f6a1b2c3d4e5f6a1b2c3d4e5f6a1b2c3d4e5f6a1b2c3d4e5f6a1b2c3d4e5f6a1b2c3d4e5

A mágica está na variável de ambiente: a API não sabe o IP do banco — ela só sabe o nome meu-banco.

postgres://
o protocolo do banco (Postgres no caso).
meu-banco
o nome do container — o DNS interno do Docker resolve isso para o IP na hora da conexão.
:5432
a porta padrão do Postgres, dentro da rede.
/guia
o nome do banco de dados dentro do Postgres.

O DNS interno na prática

De dentro da API, o nome meu-banco resolve sozinho. A Ana prova com um ping:

$ docker exec minha-api ping -c 2 meu-banco
PING meu-banco (172.18.0.2): 56 data bytes
64 bytes from 172.18.0.2: seq=0 ttl=64 time=0.089 ms
64 bytes from 172.18.0.2: seq=1 ttl=64 time=0.112 ms
--- meu-banco ping statistics ---
2 packets transmitted, 2 packets received, 0% packet loss

Repare no (172.18.0.2): era o nome que ela deu no --name, e o DNS interno devolveu o IP. E dá para ver para quem o container está perguntando: o arquivo /etc/resolv.conf dentro do container aponta para o DNS interno:

$ docker exec minha-api cat /etc/resolv.conf
nameserver 127.0.0.11   « o DNS interno do Docker mora nesse endereço dentro de toda rede user-defined
options ndots:0

Esse 127.0.0.11 é um endereço de loopback especial que o Docker intercepta e responde com os nomes dos containers da rede. É por isso que o nome resolve "magicamente".

O IP muda, o nome não

A Ana recria o container do banco (para testar) e o IP muda — a app nem sente:

$ docker rm -f meu-banco && docker run -d --name meu-banco --network app-net \
>     -e POSTGRES_PASSWORD=segredo -v dados-postgres:/var/lib/postgresql/data postgres:16-alpine
$ docker inspect meu-banco --format '{{range .NetworkSettings.Networks}}{{.IPAddress}}{{end}}'
172.18.0.5   « o IP mudou (antes era .2)!
$ docker exec minha-api ping -c 1 meu-banco | head -1
PING meu-banco (172.18.0.5): …   « mas o nome continua resolvendo para o IP novo

Apelidos: --network-alias

Além do --name, um container pode ter apelidos na rede com --network-alias — vários nomes apontando para o mesmo IP. Útil quando vários containers têm a mesma função (vários workers) e a app deve falar com "qualquer um deles":

$ docker run -d --name worker1 --network app-net --network-alias fila node:22-alpine node worker.js
$ docker run -d --name worker2 --network app-net --network-alias fila node:22-alpine node worker.js
$ docker exec minha-api ping -c 1 fila
PING fila (172.18.0.6): …   « "fila" resolve para um dos workers (round-robin)

O DNS interno faz balanceamento simples entre os apelidos iguais. No Compose, o nome do serviço já vira um alias automático (próximas aulas do nível 2).

-p só no serviço externo

Olhe de novo a lista de containers desse cenário:

$ docker ps
CONTAINER ID   IMAGE              STATUS         PORTS                     NAMES
a1b2c3d4e5f6   postgres:16-alpine Up 2 minutes   5432/tcp                  meu-banco
b2c3d4e5f6a1   node:22-alpine     Up 2 minutes   0.0.0.0:3000->3000/tcp    minha-api

A regra de ouro: só publique com -p quem o mundo de fora precisa acessar. A API precisa (é o serviço externo, na 3000). O banco, não — ele só existe para a API, dentro da app-net. Sem -p, a porta 5432 do banco não existe para a sua máquina nem para a internet: é um perímetro de segurança de graça. A Ana testa:

$ curl http://localhost:5432
curl: (7) Failed to connect to localhost port 5432   « o banco não está publicado no host
$ docker exec minha-api sh -c "node -e \"require('net').connect(5432,'meu-banco').on('connect',()=>console.log('conectou no banco pelo nome!'))\""
conectou no banco pelo nome!   « mas de dentro da rede, o nome resolve e a porta abre
Na rede bridge padrão o nome não resolve. Se você subir dois containers só com docker run -d (sem --network), eles se alcançam pelo IP (172.17.0.x), mas ping meu-banco falha com bad address 'meu-banco'. O DNS automático por nome só existe em redes criadas por você (ou no Compose, que cria uma rede para o projeto sozinho): 
$ docker run -d --name banco2 postgres:16-alpine   « bridge padrão
$ docker run --rm alpine ping -c 1 banco2
ping: bad address 'banco2'   « nome não resolve na bridge padrão!
Como consertar: crie uma rede e suba os dois nela com --network (ou use Compose).

Para ver os containers conectados e os IPs que o DNS está resolvendo:

            "Config": [

                    "Subnet": "172.18.0.0/16",
                    "Gateway": "172.18.0.1"

                "Name": "meu-banco",
                "MacAddress": "02:42:ac:12:00:02",

O bloco Containers é o "quem está na festa": nome, MAC e IP de cada um. É exatamente essa tabela que o DNS interno usa para responder meu-banco → 172.18.0.2. Dá para extrair só os nomes com --format '{{range .Containers}}{{.Name}}{{"\n"}}{{end}}'.

Erros comuns na conversa entre containers

bad address 'meu-banco': a app não achou o nome. Quase sempre é porque os dois containers estão em redes diferentes (um na bridge padrão, outro numa rede criada) — o DNS interno só enxerga a própria rede. Como consertar: confira com docker inspect se os dois estão na mesma rede (.NetworkSettings.Networks) e suba os dois com o mesmo --network.
Connection refused na porta certa: o nome resolveu (o DNS achou), mas a conexão foi recusada — o serviço dentro do container ainda não subiu, ou está ouvindo em outra porta/endereço. Ex.: o Postgres recusou porque a app tentou na 5432 mas o banco está na 5433, ou a app Node tentou conectar em localhost (dentro do próprio container!) em vez do nome do banco. Como consertar: dentro de um container, localhost é o próprio container — para falar com outro container, use o nome dele na rede.
Timed out / sem rota: firewall do host bloqueando a bridge (raro em instalação padrão), ou o container caiu entre o DNS e a conexão. Como consertar: docker ps para ver se o alvo está Up; docker logs nele para ver se o serviço iniciou de verdade.

Preview: isso tudo vira automático no Compose

Subir rede + banco + API na mão, um docker run por vez, dá trabalho (e a Ana já cansou). Na próxima aula o Compose faz tudo isso sozinho a partir de um YAML — este é o arquivo que ela vai escrever, comentado linha a linha:

# arquivo: docker-compose.yml (próxima aula — o Compose cria a rede sozinha)
services:
  banco:                          # um serviço = um container
    image: postgres:16-alpine
    environment:
      POSTGRES_PASSWORD: segredo
    volumes:
      - dados-postgres:/var/lib/postgresql/data   # volume nomeado (criado se não existir)
    # sem ports: o banco não precisa ser alcançado de fora

  api:                            # outro serviço, na MESMA rede do projeto
    image: node:22-alpine
    command: node server.js
    ports:
      - "3000:3000"               # só a API é publicada
    environment:
      DATABASE_URL: postgres://banco:5432/guia   # « repare: "banco" é o NOME do serviço
    depends_on:
      - banco

volumes:
  dados-postgres:                 # declara o volume nomeado usado acima

Com esse arquivo, docker compose up cria a rede, sobe os dois containers nela e o DNS interno já resolve banco — exatamente o cenário desta aula, sem nenhum comando manual. É o que vem a seguir.

Resumo

  • Numa rede criada por você, o Docker liga um DNS interno (127.0.0.11, visível no /etc/resolv.conf do container) que resolve o nome de cada container para o IP atual.
  • A aplicação fala com o banco pelo nome: postgres://meu-banco:5432/guia. Se o container for recriado e o IP mudar, o nome continua valendo — a app não quebra.
  • --network-alias dá apelidos extras a um container (vários nomes → mesmo IP, com balanceamento simples).
  • Na bridge padrão o nome não resolve — só IP. O DNS por nome existe em redes user-defined e no Compose.
  • Regra de segurança: só o serviço externo leva -p; banco e serviços internos ficam só na rede interna (5432/tcp sem -> no docker ps).
  • docker network inspect app-net mostra o mapa da rede: sub-rede, gateway e containers com IP/MAC — é a tabela que o DNS usa.
  • Erros reais: bad address (redes diferentes ou bridge padrão), connection refused (serviço não subiu ou porta errada; dentro do container, localhost é ele mesmo — use o nome do outro container).
