O arquivo docker-compose.yml

Todo projeto Compose vive num arquivo YAML na raiz da pasta do projeto — o docker-compose.yml (o Compose v2 também aceita compose.yaml, compose.yml, docker-compose.yaml, nessa ordem de preferência). É nesse arquivo que você declara os serviços, e cada serviço vira um container quando você dá o up.

Você vai aprender
  • O que é YAML e por que a indentação manda no arquivo (2 espaços, nunca tab).
  • Onde o arquivo fica, de onde vem o nome do projeto (nome da pasta) e a flag -f.
  • As chaves principais: services, image, build, ports, environment, volumes, depends_on e networks.
  • Por que portas como "8080:80" precisam de aspas.
  • Um exemplo completo e comentado, como validar com docker compose config e os erros reais de YAML.

O que é YAML (e por que ele existe)

YAML é um formato de arquivo feito para ser lido por pessoas — o slogan do projeto é "YAML Ain't Markup Language". Ele descreve dados com pares chave: valor e listas com traço, e a hierarquia vem do recuo das linhas. Pense numa lista de compras escrita assim:

frutas:
  - maçã
  - banana
legumes:
  - cenoura
  - batata

O recuo de dois espaços diz que maçã está dentro de frutas. Se você acertar o recuo errado, a lista muda de sentido — e no YAML do Compose, recuo errado quebra o arquivo inteiro. É por isso que a indentação é a primeira coisa que esta aula ensina.

Onde o arquivo fica e quem dá o nome do projeto

Por padrão, o docker compose procura o arquivo na pasta atual (onde você rodou o comando). O nome do projeto é o nome dessa pasta, normalizado para minúsculas e sem caracteres estranhos — e é ele que vira o prefixo de tudo que o Compose cria: numa pasta minhaloja, os containers viram minhaloja-web-1, minhaloja-banco-1, o volume minhaloja_dados-db e a rede minhaloja_default.

$ pwd
/home/ana/minhaloja
$ ls
docker-compose.yml  site/
$ docker compose ps
NAME              IMAGE         STATUS         PORTS
minhaloja-web-1   nginx:alpine  Up 2 minutes   0.0.0.0:8080->80/tcp

Para usar outro arquivo ou outra pasta, existe a flag -f (pode ser usada várias vezes) e a variável de ambiente COMPOSE_FILE:

$ docker compose -f ~/projetos/api/compose.yml ps     « arquivo em outro lugar
$ docker compose -p minhaapi up -d                      « ou outro nome de projeto (-p)

Se nada disso for dito, vale o padrão: arquivo na pasta atual, projeto = nome da pasta. Dica: mantenha o docker-compose.yml sempre na raiz do projeto, versionado no git junto com o código.

Anatomia das chaves

O arquivo é um mapa YAML. No primeiro nível quase sempre existirão services: (a única chave obrigatória) e, quando usados, volumes: e networks:. Dentro de cada serviço, as chaves mais comuns são estas — e quase todas têm um equivalente direto nas flags do docker run:

services:
Obrigatória. Cada entrada é um serviço — e cada serviço vira um container.
image:
A imagem pronta que o serviço usa (ex.: nginx:alpine, postgres:16-alpine). Equivale a não passar -t no build: é o docker run <imagem>.
build:
Em vez de image, constrói a imagem na hora a partir de um Dockerfile (aula Build no Compose).
ports:
Publica portas, no mesmo formato do -p: "8080:80" (host → container).
environment:
Variáveis de ambiente, em lista (- NOME=valor) ou em mapa (NOME: valor) — o mesmo do -e.
volumes:
Monta volumes nomeados ou pastas da máquina (bind), no mesmo formato do -v.
depends_on:
Ordem de subida: o serviço só inicia depois dos serviços listados.
networks:
Redes das quais o serviço participa. Se não declarar nada, todos os serviços entram numa rede default criada para o projeto.
restart:
Política de reinício (no, always, unless-stopped, on-failure) — como o --restart.
command:
Sobrescreve o comando padrão da imagem (o CMD).
Chave no YAMLFlag equivalente do docker run
image: nginx:alpinedocker run nginx:alpine
ports: - "8080:80"-p 8080:80 (aula Portas)
environment: - NOME=valor-e NOME=valor (aula Variáveis de ambiente)
volumes: - dados:/caminho-v dados:/caminho (aula Volumes)
build: .docker build + docker run juntos
restart: always--restart always
command: node app.jsdocker run imagem node app.js

Se você já sabe docker run, o YAML do Compose é só transcrever as flags para dentro do serviço — a aula Serviços, portas, variáveis e volumes no Compose mostra cada uma na prática.

Indentação: 2 espaços, nunca tab

YAML é sensível à indentação: a posição das linhas diz a hierarquia. A convenção no Compose (e no YAML em geral) é 2 espaços por nível — e a tecla Tab é proibida:

services:
  web:
    image: nginx:alpine
    ports:
→     - "8080:80"        « essa linha começou com TAB em vez de espaços
Erro real ao usar tab no YAML: 
$ docker compose config
minhaloja/docker-compose.yml: yaml: line 5: found character '\t' that cannot start any token
Um tab no começo da linha faz o parser inteiro desistir. Se o seu editor insere tab, configure-o para inserir espaços em arquivos .yml (VS Code, gedit e a maioria dos editores já fazem isso sozinhos ao detectar a extensão).
Outro erro clássico de recuo — o serviço "sumiu": se você recua um serviço um nível a menos, ele vira filho da chave errada e o Compose reclama: 
$ docker compose config
services.web must be a mapping     « "web:" ficou solto, sem o "image:" dentro dele
Ou, pior, o serviço é interpretado como texto e o comando lista um projeto vazio. Se o up disser que não há serviços, olhe o recuo.

Para validar o arquivo sem subir nada, use docker compose config: ele lê o YAML, imprime a configuração normalizada (já com valores padrão preenchidos e variáveis resolvidas) e avisa se algo está errado:

$ docker compose config
services:
  web:
    image: nginx:alpine
    ports:
    - mode: ingress
      target: 80
      published: "8080"
      protocol: tcp
    depends_on:
      banco:
        condition: service_started
  banco:
    image: postgres:16-alpine
    environment:
      POSTGRES_PASSWORD: segredo
    volumes:
    - type: volume
      source: dados-db
      target: /var/lib/postgresql/data
volumes:
  dados-db: {}

Repare como o "8080:80" virou um objeto estruturado (published: "8080", target: 80) — o Compose já interpretou a string. É essa a prova de que o arquivo está válido.

Por que as portas vão entre aspas: "8080:80"

O par 8080:80 tem um : no meio. Em YAML 1.1 (que muita gente ainda associa a arquivos de configuração), 8080:80 pode ser lido como um número na base 60 (sexagesimal) — igual horas e minutos: 8080:80 viraria o número 484880. Resultado:

Erro real de porta sem aspas: 
$ docker compose up -d
services.web.ports must be a string     « ou o YAML quebra na hora de ler a linha
Regra de ouro: sempre coloque aspas em portas no Compose — "8080:80", nunca 8080:80. O mesmo vale para qualquer valor com : (horários, URLs).

Exemplo completo e comentado

Este é o arquivo que a Ana usa na ~/minhaloja — cada linha comentada:

# docker-compose.yml — projeto "minhaloja"
# Rode nesta pasta: docker compose up -d

services:                     # cada entrada aqui vira UM container

  web:                        # nome do serviço (vai parar no nome do container: minhaloja-web-1)
    image: nginx:alpine       # imagem pronta do Docker Hub
    ports:
      - "8080:80"             # host 8080 -> container 80 (as aspas são obrigatórias!)
    volumes:
      - ./site:/usr/share/nginx/html:ro   # pasta da máquina dentro do container (ro = somente leitura)
    depends_on:
      - banco                 # o web só sobe depois do banco
    restart: unless-stopped   # se o container cair, o Docker reinicia sozinho

  banco:
    image: postgres:16-alpine
    environment:              # variáveis de ambiente (formato mapa)
      POSTGRES_USER: ana
      POSTGRES_PASSWORD: segredo
    volumes:
      - dados-db:/var/lib/postgresql/data   # volume nomeado: os dados persistem ao "down"

volumes:                      # declara os volumes nomeados usados acima
  dados-db:

Três detalhes para notar: ./site é um bind mount — a pasta do projeto entra no container (ótimo para desenvolvimento: editou o HTML na máquina, recarregou a página); :ro deixa o container só ler; e o serviço banco não tem porta publicada — só os outros containers alcançam ele pela rede interna, o que deixa o banco mais seguro.

Erros reais de YAML que todo mundo comete uma vez

Faltou os dois pontos depois da chave: 
services
  web:
    image: nginx:alpine
$ docker compose config
yaml: line 1: mapping values are not allowed in this context
Todo chave: precisa do dois pontos. Sem ele, o parser acha que você está escrevendo uma frase no meio de um mapa.
Chave duplicada (copiou o serviço e esqueceu de trocar o nome): 
$ docker compose config
yaml: mapping key "web" already defined at line 4
Cada serviço aparece uma vez só. Para rodar várias réplicas do mesmo serviço, não duplique a chave — use docker compose up -d --scale web=3 (aula up e down).
Lista onde devia ser mapa (ou o contrário): escrever 
services:
  - web
  - banco
faz o Compose reclamar que services precisa ser um mapa de nomes para configurações, não uma lista. A lista (- item) aparece dentro das chaves: ports:, environment: (forma lista), volumes:, depends_on:.

Resumo

  • O projeto Compose é um arquivo YAML na raiz da pasta (por padrão docker-compose.yml); services: é a única chave obrigatória e cada serviço vira um container.
  • YAML é sensível à indentação: 2 espaços por nível, tab nunca — tab dá found character '\t' that cannot start any token.
  • O nome do projeto vem do nome da pasta e vira o prefixo dos containers, volumes e rede (minhaloja-web-1).
  • Chaves ↔ flags do docker run: ports=-p, environment=-e, volumes=-v, build=build+run, restart=--restart.
  • Portas sempre entre aspas ("8080:80") — sem aspas o YAML pode interpretar como número base 60.
  • Valide o arquivo sem subir nada com docker compose config — ele imprime a configuração normalizada e acusa erros de sintaxe.
