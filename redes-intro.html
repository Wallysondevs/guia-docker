Redes no Docker — bridge, host e none

Assim como o sistema de arquivos, a rede também é isolada por container: cada container nasce com um IP próprio numa rede interna virtual e só fala com o mundo de fora pelas portas que você publicar com -p. O Docker já vem com três redes prontas para usar: bridge, host e none. Nesta aula a Ana vai ver o isolamento funcionando no notebook dela.

Você vai aprender
  • O que é o isolamento de rede e por que cada container tem um IP próprio.
  • A rede bridge padrão: NAT para a internet, IPs internos (172.17.x.x) e publicação de portas com -p.
  • As redes host (sem isolamento: o container usa a rede da máquina) e none (sem rede nenhuma).
  • Quando usar cada uma — e por que -p é descartado no modo host (com o aviso real).
  • Como descobrir o IP de um container com docker inspect --format.
  • Erros reais: porta não publicada, conflito de porta no host.

A analogia: um prédio de apartamentos

Pense na sua máquina (o host) como um prédio. Cada container é um apartamento com a sua própria rede interna: ele tem um interfone interno (o IP próprio, tipo 172.17.0.2), conversa com os outros apartamentos pelo interfone, e só fala com a rua (a internet) pela portaria — que é controlada: só o que o síndico (você, com -p) abrir passa.

O Docker cria essa "rede do prédio" automaticamente: a rede bridge (bridge = ponte, porque faz a ponte entre os containers e o mundo de fora, com NAT).

O diagrama da bridge padrão

Resumindo a topologia que o Docker cria sozinho na máquina da Ana (dá para desenhar num papel — ajuda muito):

# diagrama da rede bridge padrão (criada sozinha pelo Docker)

sua máquina (host) ......... 192.168.1.10 na rede de casa
  └── interface docker0 .... 172.17.0.1  (é o GATEWAY dos containers)
        ├── container "web" ........ 172.17.0.2   porta 80 → publicada na 8080 do host (-p 8080:80)
        └── container "meu-banco" .. 172.17.0.3   porta 5432 → só interna (sem -p)

internet ← NAT pela máquina (os containers saem para fora pelo IP do host)

Todo container novo na bridge ganha o próximo IP da faixa (172.17.0.4, .5, …). O docker0 é a "ponte" que liga os containers ao host — e o host faz NAT para a internet.

O isolamento na prática

A Ana sobe dois containers no notebook dela e pergunta o IP de cada um:

$ docker run -d --name web nginx:alpine
$ docker run -d --name meu-banco -e POSTGRES_PASSWORD=segredo postgres:16-alpine
$ docker inspect web --format '{{range .NetworkSettings.Networks}}{{.IPAddress}}{{end}}'
172.17.0.2
$ docker inspect meu-banco --format '{{range .NetworkSettings.Networks}}{{.IPAddress}}{{end}}'
172.17.0.3

Cada container está num mundo separado: o web é o 172.17.0.2 e o meu-banco é o 172.17.0.3. Eles conseguem se falar dentro dessa rede interna (pelo IP), e o mundo de fora só alcança o que você liberar com -p. É por isso que o banco pode ficar sem porta publicada e mesmo assim ser usado pela aplicação — a aula Containers se comunicando por nome mostra como.

O truque do --format: o docker inspect cuspe um JSONzão; o --format '{{…}}' extrai só o campo que você quer. O comando acima é o canivete suíço para pegar IP de container em scripts.

Todo container nasce na rede bridge, a menos que você diga o contrário com --network:

a padrão. O container ganha um IP próprio (172.17.x.x), com NAT para a internet, e as portas só aparecem do lado de fora com -p. É a rede dos seus apps.
host
o container usa a rede da máquina diretamente — mesmo IP, mesmas portas. Não existe isolamento de rede nem precisa de -p.
none
sem rede nenhuma: só o loopback (127.0.0.1). Para jobs que não precisam falar com ninguém.

bridge (a padrão): NAT e portas publicadas

Na bridge, o container fala com a internet passando por um NAT (o Docker reescreve os endereços, como um roteador de casa faz). E o caminho inverso — da internet para o container — só existe nas portas que você publica com -p (aula Publicando portas). A Ana testa dos dois lados:

$ docker run -d --name site -p 8080:80 nginx:alpine
$ curl http://localhost:8080 | head -1
<!DOCTYPE html>   « de fora, pela porta publicada 8080 do host
$ docker exec site sh -c "wget -qO- http://ifconfig.me" 2>/dev/null || true
189.x.x.x   « de dentro, o container alcança a internet pelo NAT (IP público do host)
Erro comum: subir sem -p e tentar acessar. O container está no ar, mas sem porta publicada ele é invisível para o host: 
$ docker run -d --name site2 nginx:alpine   « sem -p!
$ curl http://localhost
curl: (7) Failed to connect to localhost port 80   « nada publicado
$ docker ps
…  site2  nginx:alpine  Up 5 seconds  80/tcp   « repare: 80/tcp sem "0.0.0.0:…->" — não tem porta no host
Na coluna PORTS do docker ps, 80/tcp sozinho significa "só dentro da rede do Docker"; 0.0.0.0:8080->80/tcp significa "publicada na 8080 do host".

host: sem isolamento de rede

Com --network host, o container divide a rede com a sua máquina. Um Nginx assim responde direto na porta 80 do host — sem -p:

$ docker run -d --network host --name site-rapido nginx:alpine
$ curl http://localhost | head -1
<!DOCTYPE html>   « o Nginx está na porta 80 da máquina inteira
$ docker inspect site-rapido --format '{{range .NetworkSettings.Networks}}{{.IPAddress}}{{end}}'
« vazio — no modo host não existe IP próprio de container

É mais rápido (sem NAT) e útil para ferramentas de rede e portas baixas (80, 443), mas qualquer porta que o container abrir está aberta na máquina — e pode conflitar com um serviço que já esteja na máquina. Use com cuidado, só quando confiar na imagem.

Portas descartadas no modo host: se você passar -p junto com --network host, o Docker avisa e ignora: 
$ docker run -d --network host -p 8080:80 --name site3 nginx:alpine
WARNING: Published ports are discarded when using host network mode
Nesse modo, a porta do container já é a porta do host — não existe tradução. O aviso é barulhento de propósito: se você não esperava por ele, o -p provavelmente estava errado.
Conflito de porta no host: se a máquina já tem algo na porta 8080 e a Ana tenta publicar -p 8080:80, o run falha: 
$ docker run -d -p 8080:80 --name site4 nginx:alpine
docker: Error response from daemon: driver failed programming external connectivity on endpoint site4: Bind for 0.0.0.0:8080 failed: port is already allocated.
Como consertar: escolha outra porta do host (-p 8081:80) ou mate o processo que está usando a 8080.

none: container sem rede

Com --network none, o container fica isolado total: só o loopback (127.0.0.1) funciona dentro dele. A Ana testa:

$ docker run -d --network none --name processamento alpine sleep 1d
$ docker exec processamento ping -c 1 8.8.8.8
ping: bad address '8.8.8.8'   « não alcança ninguém: nem a internet, nem outros containers

Perfeito para jobs de processamento que só precisam de CPU e disco (converter vídeo, rodar modelo de ML, backup local), e para aumentar a segurança de containers que não devem ter acesso à rede (um worker que processa dados sensíveis, por exemplo).

Resumo

Quase sempre você vai usar a bridge (é o padrão) ou uma rede criada por você (próxima aula). Guarde host e none para casos específicos: host quando precisar de performance máxima de rede e confiar na imagem; none quando o container não deve falar com rede nenhuma.

Resumo

  • A rede é isolada por container: cada um ganha um IP próprio na rede virtual interna (172.17.x.x na bridge) e só fala com o mundo de fora pelas portas publicadas com -p.
  • O Docker vem com três redes prontas: bridge (padrão, com NAT), host (usa a rede da máquina, sem isolamento) e none (sem rede).
  • Na bridge, sem -p o container é invisível para o host (curl: (7) Failed to connect; no docker ps, 80/tcp sem ->).
  • No modo host, o -p é descartado com warning — a porta do container já é a do host. Conflito de porta dá port is already allocated.
  • docker inspect web --format '{{range .NetworkSettings.Networks}}{{.IPAddress}}{{end}}' mostra o IP interno do container.
  • Use none para jobs que não precisam de rede; use host só com imagem de confiança e necessidade real de performance.
