docker system df — onde o Docker gasta espaço

Imagens, containers parados, volumes e cache de build vão se acumulando no disco. O docker system df mostra, numa tabela só, quanto o Docker está ocupando e quanto dá para recuperar — diferente do df -h, que mostra o disco inteiro. É o primeiro comando que se roda quando o notebook da Ana começa a dizer "disco cheio".

Você vai aprender
  • Onde o Docker guarda os dados (/var/lib/docker).
  • Ler a tabela do docker system df: TYPE, TOTAL, ACTIVE, SIZE e RECLAIMABLE.
  • O modo detalhado docker system df -v (objeto por objeto) e imagens dangling.
  • --format com templates Go para imprimir só o que interessa.
  • A diferença entre docker system df e df -h — e quando limpar.

A história: o disco da Ana encheu

Numa segunda-feira, o ana@notebook começou a reclamar: o editor de texto decía "espaço insuficiente para salvar" e o navegador mostrava páginas pela metade. A Ana abriu o terminal e olhou o disco inteiro:

$ df -h
Filesystem      Size  Used Avail Use% Mounted on
/dev/nvme0n1p2  98G   91G  2,1G  98% /

O disco está quase cheio — mas quem encheu? O sistema operacional? As fotos? O Docker? É aí que entra o docker system df, que olha só para dentro da gaveta do Docker:

$ docker system df
TYPE            TOTAL     ACTIVE    SIZE      RECLAIMABLE
Images          6         2         874MB     512MB (58%)
Containers      3         2         12.4MB    6.2MB (50%)
Local Volumes   2         1         245MB     120MB (48%)
Build Cache     41        0         1.84GB    1.84GB

Olhando as duas saídas juntas, a culpa é clara: de 91GB usados no disco, quase 3GB são do Docker (874MB de imagens + 1,84GB de cache de build + volumes) — e a coluna RECLAIMABLE diz que dá para recuperar boa parte disso com segurança. A próxima aula (docker system prune) mostra a faxina.

Onde o Docker guarda as coisas

Por padrão (no Linux), tudo fica em /var/lib/docker:

/var/lib/docker/
├── image/       ← as imagens e suas camadas (overlay2)
├── containers/  ← a camada gravável de cada container
├── volumes/     ← os volumes nomeados (dados de banco, por exemplo)
├── buildkit/    ← o cache do docker build
├── network/     ← as redes
└── overlay2/    ← as camadas das imagens e dos containers

Cada pasta dessa vira uma linha (TYPE) na tabela do docker system df. Dá para confirmar com o du (disk usage):

$ sudo du -sh /var/lib/docker
2.9G    /var/lib/docker
$ sudo du -sh /var/lib/docker/* | sort -h
12M     /var/lib/docker/containers
245M    /var/lib/docker/volumes
874M    /var/lib/docker/image
1.8G    /var/lib/docker/buildkit

No macOS e no Windows (Docker Desktop), esses arquivos não ficam soltos no sistema: ficam dentro de uma VM/arquivo de disco virtual do próprio Docker Desktop — mas o docker system df continua valendo do mesmo jeito, porque ele pergunta para o daemon, não para o filesystem.

O comando

Missão: rode docker system df no terminal e encontre a coluna RECLAIMABLE — o quanto dá para recuperar.

$ docker system df
TYPE            TOTAL     ACTIVE    SIZE      RECLAIMABLE
Images          6         2         874MB     512MB (58%)
Containers      3         2         12.4MB    6.2MB (50%)
Local Volumes   2         1         245MB     120MB (48%)
Build Cache     41        0         1.84GB    1.84GB
docker system
a família de comandos de administração do Docker (ver docker system --help).
df
disk free: mostra o uso de espaço — aqui, só do Docker, não do disco inteiro.
-v
verbose: lista cada objeto individualmente (veremos já).
--format
imprime a saída com um template Go (veremos já também).

As colunas, uma a uma

TYPE
O tipo de objeto: Images, Containers, Local Volumes ou Build Cache.
TOTAL
Quantos objetos existem desse tipo (6 imagens, 3 containers, 2 volumes, 41 itens de cache).
ACTIVE
Quantos estão em uso agora: imagem usada por algum container, container existente (rodando ou parado), volume anexado a algum container. No exemplo: 2 imagens em uso (as outras 4 estão órfãs), 2 containers ativos.
SIZE
Espaço total ocupado por esse tipo, contando camadas compartilhadas uma vez só por objeto.
RECLAIMABLE
Quanto dá para apagar com segurança — a coluna que interessa na hora da limpeza. Se está em 100%, tudo daquele tipo pode ir embora sem afetar nada que esteja rodando.

Um detalhe importante: imagens compartilham camadas. Se nginx:alpine e a imagem da Ana usam as mesmas camadas base, o espaço delas não é contado duas vezes na hora de apagar — é por isso que RECLAIMABLE de imagens pode ser menor que SIZE.

Repare na imagem <none>: <none>: ela é uma imagem dangling ("órfã", sem tag) — sobrou de um build antigo cuja tag foi sobrescrita e que nenhum container usa (repare na coluna CONTAINERS = 0). É candidata certa à limpeza. O mesmo vale para o container wizardly_curie (parado há 2 horas) e para o cache de build inteiro (100% recuperável).

--format: filtrar a saída com templates Go

Assim como o docker inspect --format (aula docker inspect), o docker system df aceita --format com templates Go. Os campos disponíveis são {{.Type}}, {{.TotalCount}}, {{.Active}}, {{.Size}} e {{.Reclaimable}}:

$ docker system df --format "{{.Type}}: ocupa {{.Size}}, libera {{.Reclaimable}}"
Images: ocupa 874MB, libera 512MB (58%)
Containers: ocupa 12.4MB, libera 6.2MB (50%)
Local Volumes: ocupa 245MB, libera 120MB (48%)
Build Cache: ocupa 1.84GB, libera 1.84GB
$ docker system df --format "table {{.Type}}\t{{.Active}}/{{.TotalCount}}\t{{.Reclaimable}}"
TYPE            ACTIVE/TOTAL   RECLAIMABLE
Images          2/6            512MB (58%)
Containers      2/3            6.2MB (50%)

O prefixo table imprime com cabeçalho e colunas alinhadas; sem ele, cada linha sai como você mandou. Útil em scripts — por exemplo, um alerta simples:

$ docker system df --format "{{.Type}} {{.Reclaimable}}" | grep -i "100%" && echo "ALERTA: há 100% recuperável — rode docker system prune"

Se o df -h mostra o disco cheio, rode docker system df em seguida: se a coluna RECLAIMABLE estiver grande, o Docker é o responsável — e a próxima aula, docker system prune, mostra como limpar.

Erro real quando o disco enche durante um build ou pull: 
$ docker build -t minhaapp .
…
error: failed to register layer: write /var/lib/docker/overlay2/…: no space left on device
O build não termina porque o disco lotou — e o vilão quase sempre é o Build Cache ou imagens antigas. Veja a coluna RECLAIMABLE do docker system df, rode docker system prune -f e tente o build de novo. Se precisar, mude a pasta do Docker (data-root no /etc/docker/daemon.json) para outro disco. Quando faz sentido limpar

Olhe sempre a coluna RECLAIMABLE: é o espaço que o Docker pode devolver sem machucar nada que esteja em uso. Regra prática:

  • Containers recuperável → há containers parados que podem ser removidos.
  • Images parcialmente recuperável → há imagens sem nenhum container usando (dangling ou não).
  • Build Cache grande e 100% → builds antigos acumulando espaço; em máquina de desenvolvimento, é comum ver vários GB aqui.
  • Local Volumes recuperável → há volumes órfãos. Cuidado redobrado: volume apagado não tem lixeira — só limpe volume se tiver certeza de que não há dados importantes (banco de teste, por exemplo).

Resumo

  • O Docker guarda tudo em /var/lib/docker (Linux): image/, containers/, volumes/, buildkit/ (cache) etc.
  • docker system df resume isso em 4 linhas: Images, Containers, Local Volumes, Build Cache.
  • Colunas: TOTAL (quantos existem), ACTIVE (quantos em uso), SIZE (espaço total), RECLAIMABLE (quanto dá para recuperar com segurança).
  • -v detalha objeto por objeto e revela as imagens <none> (dangling) e os containers parados.
  • --format "{{.Type}}: {{.Reclaimable}}" usa templates Go para imprimir só o campo desejado (bom para scripts).
  • df -h vê o disco inteiro; docker system df responde "o Docker é o culpado? quanto dá para limpar?".
