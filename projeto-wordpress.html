Projeto 4: WordPress + MySQL

A Ana quer um blog para publicar os resumos da faculdade, mas não quer sujar o notebook instalando PHP, Apache e MySQL na mão (e depois descobrir que a versão do PHP quebrou o WordPress). Com Docker Compose ela descreve dois serviços — wordpress e mysql — e em minutos tem um WordPress completo rodando em http://localhost:8080, com os dados guardados em volumes que sobrevivem a qualquer down.

Você vai aprender
  • Por que WordPress + banco é o exemplo clássico de Compose: dois containers que precisam um do outro.
  • Subir serviços com imagens oficiais grandes (wordpress:latest, mysql:8.0) sem escrever Dockerfile.
  • Configurar os dois containers só com variáveis de ambiente (WORDPRESS_DB_* e MYSQL_*).
  • Volumes nomeados para persistência: down e up de novo sem perder nada.
  • O assistente de instalação do WordPress no navegador, passo a passo.
  • Como fazer backup do volume do banco com um container auxiliar (tar).
  • Erros reais: porta ocupada e "Error establishing a database connection".

A ideia: dois containers, uma conversa só deles

O WordPress precisa de duas coisas para funcionar: um servidor web com PHP (a imagem oficial wordpress já traz Apache + PHP configurados) e um banco MySQL. A imagem do WordPress, na primeira subida, lê variáveis de ambiente e configura a conexão com o banco sozinho — a Ana só precisa dizer onde está o banco e quais são as credenciais.

navegador
   │  http://localhost:8080
   ▼
┌──────────────────┐  WORDPRESS_DB_HOST=db:3306   ┌──────────────┐
│  wordpress:80    │ ───────────────────────────► │  mysql:3306  │
│  (Apache + PHP)  │     usuário/senha/banco      │  (MySQL 8)   │
│  volume wp-…    │                              │  volume dbdata│
└──────────────────┘                              └──────────────┘
        ▲ os dois na rede "wordpress_default" criada pelo Compose ▲

O db:3306 no meio é o nome do serviço do banco + a porta padrão do MySQL — de novo, o DNS interno do Compose resolve db para o IP do container do MySQL. A aula Containers se comunicando por nome explica essa mágica.

Passo 1: a pasta e o docker-compose.yml

$ mkdir -p ~/wordpress
$ cd ~/wordpress

Crie o arquivo abaixo. Cada bloco está comentado:

# wordpress/docker-compose.yml
services:

  wordpress:                      # o site em si
    image: wordpress:latest       # imagem oficial: Apache + PHP + WordPress
    ports:
      - "8080:80"                 # host 8080 → container 80 (Apache)
    environment:
      WORDPRESS_DB_HOST: db:3306  # onde está o MySQL: serviço "db", porta 3306
      WORDPRESS_DB_USER: wordpress
      WORDPRESS_DB_PASSWORD: senha_do_wp
      WORDPRESS_DB_NAME: wordpress
    volumes:
      - wp-content:/var/www/html/wp-content   # temas, plugins e uploads persistem
    depends_on:
      - db                        # sobe depois do banco (só ordem de subida)

  db:                             # o banco de dados
    image: mysql:8.0
    environment:
      MYSQL_ROOT_PASSWORD: senha_do_root   # senha do root (1ª subida)
      MYSQL_DATABASE: wordpress            # cria esse banco vazio
      MYSQL_USER: wordpress                # cria esse usuário…
      MYSQL_PASSWORD: senha_do_wp          # …com essa senha (a mesma do WordPress!)
    volumes:
      - dbdata:/var/lib/mysql     # dados do MySQL persistem aqui

volumes:
  wp-content:                     # declara os volumes nomeados usados acima
  dbdata:

Repare no detalhe que faz as credenciais "baterem": o serviço db cria o usuário wordpress com a senha senha_do_wp, e o serviço wordpress usa exatamente essas mesmas credenciais nas variáveis WORDPRESS_DB_*. Se uma letra differser entre os dois lados, o WordPress não conecta no banco.

Essas senhas são de exemplo. Em algo sério, use senhas fortes e ponha tudo no .env (como no projeto 3): WORDPRESS_DB_PASSWORD: ${WP_DB_PASSWORD} e MYSQL_PASSWORD: ${WP_DB_PASSWORD}, com o .env no .gitignore. Aqui usamos texto puro porque é um WordPress local de estudo.

Passo 2: suba os dois containers

$ docker compose up -d
[+] Running 5/5
 ✔ Network wordpress_default          Created   0.1s
 ✔ Volume "wordpress_wp-content"      Created   0.0s
 ✔ Volume "wordpress_dbdata"          Created   0.0s
 ✔ Container wordpress-db-1           Started   8.4s
 ✔ Container wordpress-wordpress-1    Started   6.1s

$ docker compose ps
NAME                    IMAGE            COMMAND                  SERVICE     CREATED         STATUS         PORTS
wordpress-wordpress-1   wordpress:latest "docker-entrypoint.s…"   wordpress   30 seconds ago  Up 29 seconds  0.0.0.0:8080->80/tcp
wordpress-db-1          mysql:8.0        "docker-entrypoint.s…"   db          30 seconds ago  Up 29 seconds  3306/tcp, 33060/tcp

Observe: o db mostra 3306/tcp sem 0.0.0.0:… — a porta existe só dentro da rede interna do Compose, não está publicada no host. Mais uma vez: banco não deve ficar exposto.

Os logs mostram o MySQL criando o banco na primeira subida:

$ docker compose logs db | tail -3
... [Note] [MY] - ready for connections. Version: '8.0.40'  socket: '/var/run/mysqld/mysqld.sock' port: 3306

Passo 3: instale o WordPress no navegador (o famoso "5 minutos")

Abra http://localhost:8080. Como o banco está vazio, o WordPress mostra o assistente de instalação. No navegador da Ana:

  1. A tela de idioma aparece → escolha Português do Brasil → Continuar.
  2. O WordPress avisa que precisa dos dados do banco → clique em Vamos lá!
  3. Ele já preencheu tudo sozinho (graças às variáveis WORDPRESS_DB_*) → Enviar. Se aparecer "Isso significa que a conexão com o banco de dados foi estabelecida"… na verdade a mensagem é "Tudo certo! Já podemos instalar…" → Instalar agora.
  4. Preencha: Título do site (ex.: "Blog da Ana"), nome de usuário, senha, seu e-mail → Instalar WordPress.
  5. "Sucesso!" → clique em Acessar e faça login com o usuário e senha que acabou de criar.

Pelo terminal dá para confirmar que o site responde (na primeira vez ele redireciona para a instalação):

$ curl -sI http://localhost:8080 | head -1
HTTP/1.1 302 Found   « redireciona para /wp-admin/install.php na primeira vez
$ curl -sI http://localhost:8080/wp-admin/ | head -1
HTTP/1.1 302 Found   « depois de instalado, /wp-admin/ pede login

Depois de instalar, a home responde 200 OK e o curl -s http://localhost:8080 mostra o HTML do tema.

Passo 4: seus dados estão nos volumes (teste de persistência)

A Ana publica um post, instala um tema e faz upload de uma imagem. Onde isso ficou? Nos volumes wp-content (arquivos do site) e dbdata (banco). Agora o teste de fogo — derrube tudo e suba de novo:

$ docker compose down
[+] Running 3/3
 ✔ Container wordpress-wordpress-1   Removed
 ✔ Container wordpress-db-1          Removed
 ✔ Network wordpress_default         Removed

$ docker volume ls
DRIVER    VOLUME NAME
local     wordpress_dbdata
local     wordpress_wp-content     « os volumes continuam aqui

$ docker compose up -d
...
 ✔ Container wordpress-db-1           Started
 ✔ Container wordpress-wordpress-1    Started

$ curl -sI http://localhost:8080 | head -1
HTTP/1.1 200 OK   « site no ar, JÁ INSTALADO — não pede mais o assistente

O post, o tema e a imagem continuam lá, porque não estavam dentro dos containers (que foram apagados), e sim nos volumes. Container é descartável; volume é permanente.

Para apagar de verdade (dados incluídos): use docker compose down -v. O -v remove também os volumes nomeados declarados no YAML. Sem o -v, os volumes ficam. Pense duas vezes antes de usar -v num banco de dados.

Missão: crie um volume nomeado como os do projeto: rode docker volume create dbdata e depois docker volume ls para vê-lo na lista.

Passo 5: backup dos dados (bônus prático)

Volumes são pastas no host (em /var/lib/docker/volumes/…), então dá para fazer backup deles como qualquer pasta — o truque é usar um container auxiliar com a pasta montada:

$ docker run --rm -v wordpress_dbdata:/dados -v $(pwd):/backup alpine tar czf /backup/dbdata.tar.gz -C /dados .
$ ls -lh dbdata.tar.gz
-rw-r--r-- 1 ana ana 12M Nov 24 13:00 dbdata.tar.gz

Para restaurar, é o caminho inverso: suba um container com o volume vazio montado e o backup montado, e rode o tar xzf. E para inspecionar um volume sem saber o nome exato, docker volume inspect wordpress_dbdata mostra o Mountpoint no host (precisa de sudo para ler direto lá).

As variáveis usadas, resumidas

VariávelServiçoPara que serve
WORDPRESS_DB_HOSTwordpressOnde o WordPress encontra o MySQL: db:3306 = serviço db, porta 3306.
WORDPRESS_DB_USER / WORDPRESS_DB_PASSWORD / WORDPRESS_DB_NAMEwordpressCredenciais e nome do banco que o WordPress vai usar na conexão.
MYSQL_ROOT_PASSWORDdbSenha do usuário root do MySQL — obrigatória na primeira subida.
MYSQL_DATABASEdbCria esse banco vazio na primeira subida.
MYSQL_USER / MYSQL_PASSWORDdbCria o usuário que o WordPress vai usar (tem que bater com WORDPRESS_DB_USER/PASSWORD).

Essas variáveis são lidas pelos scripts de entrada das imagens oficiais na primeira inicialização — é o padrão de configuração de imagens no Docker: em vez de editar arquivos de configuração na mão, você passa variáveis de ambiente (a aula Variáveis de ambiente generaliza).

Erros comuns neste projeto

Porta 8080 ocupada: 
$ docker compose up -d
docker: Error response from daemon: Bind for 0.0.0.0:8080 failed: port is already allocated
Outro processo (quem sabe o projeto 1 esquecido?) está usando a 8080. Solução rápida: mude o ports: do serviço wordpress para "8081:80" e acesse localhost:8081. Para descobrir quem usa a porta: sudo ss -ltnp | grep 8080.
"Error establishing a database connection": na primeira subida o MySQL demora alguns segundos para criar o banco e o usuário; se o container do WordPress tenta conectar antes, ele mostra essa tela de erro. Solução: espere ~10 segundos e recarregue a página, ou rode docker compose restart wordpress. Se continuar, confira se WORDPRESS_DB_PASSWORD é exatamente igual ao MYSQL_PASSWORD.
O container do banco fica "restarting": geralmente a senha do root está vazia (MYSQL_ROOT_PASSWORD faltando gera o aviso WARN: The "MYSQL_ROOT_PASSWORD" variable is not set e o MySQL recusa subir sem senha de root). Preencha a variável e rode docker compose up -d de novo.

Resumo

  • WordPress + MySQL é o exemplo clássico de Compose: dois containers oficiais, configurados só por variáveis de ambiente, na mesma rede interna.
  • As variáveis MYSQL_* criam banco/usuário na 1ª subida; as WORDPRESS_DB_* dizem ao WordPress onde conectar (db:3306, pelo nome do serviço).
  • Os dados ficam nos volumes nomeados (dbdata, wp-content): down não apaga; só down -v apaga.
  • Banco sem ports: não é alcançável de fora da rede do Compose — proteção de graça.
  • Erros comuns: porta do host ocupada (mude o lado esquerdo do ports:) e "Error establishing a database connection" (espere o MySQL subir / confira as senhas).
  • Backup de volume = montar o volume num container auxiliar e rodar tar.
