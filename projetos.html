Como usar os Projetos

Chegou a hora de sair do hello-world e montar aplicações de verdade. A Ana chegou até aqui no notebook dela depois de passar pelos três níveis do guia — e agora ela mesma vai montar um site, uma API, um blog e uma aplicação fullstack, tudo rodando em containers. Cada projeto desta seção é um passo a passo completo: os arquivos para criar, os comandos para rodar na ordem certa, a saída esperada no terminal e uma missão no simulador para praticar sem medo de quebrar nada.

Você vai aprender
  • O que você precisa ter instalado e testado antes de começar (leva 2 minutos).
  • O ritual de cada projeto: criar arquivos → rodar comandos → conferir a saída → fazer a missão → limpar tudo.
  • Quais são os 5 projetos, o que cada um monta e o que ele ensina de novo.
  • Em que ordem fazer os projetos para o aprendizado encaixar um no outro.
  • O checklist geral que vale para qualquer projeto Docker.

O cenário: a Ana e o notebook dela

Toda esta seção acontece na máquina fictícia ana@notebook — um notebook comum, com Ubuntu 24.04 e o Docker Engine 27 instalado (a aula Instalar o Docker mostra como ela fez). A Ana não é especialista em Linux: ela usa o terminal para o básico e o navegador para ver os sites. Se você está acompanhando no seu próprio computador, rode os mesmos comandos aí — o resultado é o mesmo.

Uma regra de ouro antes de começar: nesta seção, tudo termina do jeito que começou. Cada projeto ensina a desmontar o que montou (docker compose down, docker stop + docker rm), porque container esquecido é porta ocupada e disco cheio — e a página Erros comuns vive disso.

Como ler os blocos de cada página de projeto

Antes de entrar no projeto 1, vale entender os quatro tipos de bloco que vão aparecer em todas as páginas desta seção — eles são sempre os mesmos:

BlocoAspectoO que significa
pre.file (caixa clara, botão "copiar")arquivo de textoUm arquivo para você criar no seu computador, exatamente como está escrito. O nome do arquivo aparece no título da caixa.
pre.term (caixa escura, tipo terminal)terminal da ana@notebookComandos e saídas de verdade: as linhas que começam com $ são comandos para digitar; as outras são a resposta da máquina. O texto depois de « é uma anotação nossa.
dl.anatomyanatomiaO comando "desmontado" peça por peça, com uma explicação de cada parte embaixo — para você entender antes de decorar.
div.try (caixa com terminal embutido)simuladorUm terminal fictício que roda no navegador e entende os comandos Docker principais. Tem botão Reiniciar e, nas missões, botão Ver comando. A faixa ✔ Missão cumprida! aparece quando a saída bate com o objetivo.

Os blocos warn (borda vermelha) são os erros reais que a Ana já cometeu — com a mensagem exata que apareceu no terminal dela e a solução. Não pule: é neles que mora metade do aprendizado prático.

Pré-requisitos (2 minutos)

Antes do primeiro projeto, confirme que o Docker está instalado e répondendo na sua máquina:

$ docker version
Client:
  Version:   27.3.1
  OS/Arch:   linux/amd64

Server: Docker Engine 27.3.1
  Storage Driver: overlay2
  Operating System: Ubuntu 24.04 LTS

Se aparecer Cannot connect to the Docker daemon, volte na aula Instalar o Docker — provavelmente o serviço não está no ar ou seu usuário ainda não está no grupo docker.

Você também vai precisar de:

  • Um terminal (no Windows, use o WSL2; no Mac, o Terminal mesmo).
  • Um navegador, para abrir as páginas que os projetos publicam (localhost:8080, localhost:3000…).
  • Um editor de texto qualquer (VS Code, gedit, nano) para criar os arquivos dos projetos.
  • curl instalado, para testar as APIs pelo terminal (no Ubuntu: sudo apt install curl).

Missão: antes de qualquer projeto, confirme que o Docker responde na sua máquina (neste simulador, na máquina fictícia ana@notebook): rode docker --version e veja a linha Docker version 27.3.1.

O ritual de cada projeto

Todos os projetos seguem a mesma ordem, como uma receita de bolo. Memorize esse fluxo — ele vale para qualquer aplicação Docker que você for montar no futuro:

  1. Crie a pasta do projeto e os arquivos mostrados nos blocos pre.file (cada bloco tem botão de "copiar"). São arquivos pequenos — dá para digitar na mão.
  2. Entre na pasta certa com cd e confira com ls que os arquivos estão lá. atenção para a pasta: rodar o comando na pasta errada é um dos erros mais comuns.
  3. Rode os comandos na ordem em que aparecem, no terminal real da sua máquina, e compare com a saída esperada mostrada no bloco pre.term.
  4. Abra o navegador na porta publicada (localhost:8080 etc.) ou teste com curl — ver funcionando é metade do aprendizado.
  5. Faça as missões nos terminais simulados da própria página (eles imitam os comandos Docker e muestran ✔ quando você acerta). Errar no simulador não quebra nada.
  6. Desmonte tudo no final: docker compose down nos projetos com Compose, ou docker stop + docker rm nos projetos de container único — para não deixar portas ocupadas nem disco sujo.
Se algo der errado no meio: não entre em pânico e não saia apagando tudo. O ritual de diagnóstico é sempre o mesmo: docker ps -a (quem está parado?), docker logs NOME (o que o app disse por último?), docker images (a imagem existe?). A página Erros comuns e soluções tem a lista completa dos sustos mais frequentes.

Ordem sugerida

Faça do 1 ao 5. Cada projeto usa o que o anterior ensinou:

  1. O projeto 1 é o "hello-world com serventia": você aprende que um container pode servir uma pasta da sua máquina e que tudo começa com um docker run bem montado.
  2. O projeto 2 troca a imagem pronta por uma imagem : entra o Dockerfile e o docker build.
  3. O projeto 3 mostra por que um container sozinho não basta: vários serviços precisam conversar — entra o Compose.
  4. O projeto 4 prova que dá para rodar software complexo (WordPress + MySQL) sem instalar nada além do Docker — só declarando um YAML.
  5. O projeto 5 troca a linguagem (Python em vez de Node) para mostrar que a receita é a mesma: código + Dockerfile + Compose + banco.

Se travar em algum passo, volte na aula correspondente do Nível 1 ou do Nível 2 linkada na página — e use o simulador da página para testar o comando antes de rodar na máquina real.

Checklist geral de qualquer projeto Docker

Antes de começar e antes de terminar, passe por esta lista — ela resume a seção inteira:

QuandoVerifique
Antes de começardocker version responde; você está na pasta certa do projeto (ls confirma os arquivos).
DuranteCada comando rodou na ordem; a saída bateu com a esperada; docker ps mostra o que deveria mostrar.
Depois (navegador/curl)A página abre em localhost:PORTA; a API responde curl; os logs fazem sentido (docker logs).
Antes de fecharTudo desmontado (compose down ou stop+rm); docker ps -a não mostra containers parados esquecidos; os dados que precisavam persistir estão em volume.

Perguntas rápidas

“Posso pular o projeto 1 e ir direto para o Compose?” Pode, mas não é recomendado: o projeto 1 ensina bind mount e portas, que o Compose só esconde — e na hora do erro você vai precisar saber o que está por trás.
“E se eu não tiver Node/Python instalados na máquina?” Não precisa: é exatamente por isso que usamos containers. O projeto 2 precisa de Node só dentro do build (a imagem node:22-alpine traz o Node); a sua máquina só precisa do Docker.
“O simulador da página é igual ao Docker de verdade?” Ele imita os comandos principais e as saídas (versão 27.3.1), mas é um modelo: na máquina real, os IDs, tempos e mensagens são diferentes — a estrutura, não.

Resumo desta página

  • Os projetos são passo a passo completos: arquivos em blocos copiáveis, comandos em ordem, saída esperada e missões no simulador.
  • O ritual é sempre: criar arquivos → cd na pasta certa → rodar → conferir no navegador/curl → fazer a missão → limpar tudo no final.
  • Ordem sugerida: Nginx (1) → API Node (2) → Fullstack (3) → WordPress (4) → Flask (5).
  • Se travar, o diagnóstico começa em docker ps -a + docker logs — e a página Erros comuns lista os sustos mais frequentes.
