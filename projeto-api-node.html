Projeto 2: API Node.js com Dockerfile

No projeto 1 o container servia um arquivo pronto. Agora a Ana vai dar um passo maior: ela tem um aplicativo de verdade — uma API em Node.js que responde JSON — e quer empacotá-lo numa imagem Docker, do tipo que daria para mandar para um servidor de produção. Para isso ela escreve um Dockerfile (a "receita" da imagem), constrói com docker build e sobe o container publicando a porta 3000.

Você vai aprender
  • O cenário real: por que empacotar a API numa imagem (funciona igual em qualquer máquina).
  • Escrever um Dockerfile do zero: FROM, WORKDIR, COPY, RUN, EXPOSE, CMD — linha por linha.
  • Por que COPY package*.json vem antes do COPY . . (cache de camadas).
  • docker build -t api . e como ler a saída do BuildKit (CACHED, DONE).
  • Rodar com -p 3000:3000 e -e NODE_ENV=production, testar com curl e ler os logs.
  • O ciclo build → run → test → rebuild, que é o dia a dia de quem trabalha com Docker.
  • Erros reais: porta ocupada, imagem não encontrada e o clássico listen em 127.0.0.1.

A ideia: a receita vira imagem, a imagem vira container

Até agora usamos imagens prontas (nginx:alpine). Desta vez a Ana cria a própria imagem. O fluxo tem três degraus, e vale decorar:

Dockerfile  --(docker build)-->  imagem  --(docker run)-->  container
  • O Dockerfile é um arquivo de texto com instruções, uma por linha. Cada instrução vira uma camada da imagem (a aula Camadas e cache do build explica).
  • A imagem é o resultado pronto, somente leitura, guardada na máquina.
  • O container é a imagem posta para rodar, com uma camada de escrita em cima.

A analogia da cozinha: o Dockerfile é a receita do bolo, a imagem é o bolo pronto na forma, e o container é a fatia servida no prato — com a cereja que cada um coloca na hora.

Passo 1: os arquivos do projeto

No notebook da Ana, crie a pasta do projeto e entre nela:

$ mkdir -p ~/api
$ cd ~/api

Crie a estrutura abaixo (quatro arquivos — o .dockerignore já já faz sentido):

api/
├── app.js
├── package.json
├── .dockerignore
└── Dockerfile

app.js — a API

Uma API mínima com duas rotas: / devolve uma mensagem e o ambiente, e /saude devolve um status (útil para healthchecks):

const express = require('express');
const app = express();
const PORT = process.env.PORT || 3000;

app.get('/', (req, res) => {
  res.json({
    mensagem: 'Olá do container!',
    ambiente: process.env.NODE_ENV || 'development'
  });
});

app.get('/saude', (req, res) => {
  res.json({ status: 'ok' });
});

app.listen(PORT, '0.0.0.0', () => {
  console.log(`API rodando na porta ${PORT}`);
});

Repare no app.listen(PORT, '0.0.0.0', …): dentro de um container, escutar em 127.0.0.1 (localhost) deixaria a API invisível para fora do container — o 0.0.0.0 diz "aceito conexões em todas as interfaces", e é o -p que controla o que chega de fora. Esse é um dos erros mais comuns de quem começa (veja a seção de erros lá embaixo).

package.json — o manifesto do projeto

{
  "name": "api",
  "version": "1.0.0",
  "main": "app.js",
  "scripts": {
    "start": "node app.js",
    "test": "node --test"
  },
  "dependencies": {
    "express": "^4.19.2"
  }
}

Só uma dependência: o Express. O package-lock.json será gerado pelo npm install dentro do build.

.dockerignore — o que NÃO vai para dentro da imagem

node_modules
.git
npm-debug.log
Dockerfile
.dockerignore
*.md
.env

Antes do build, o Docker envia a pasta inteira (o "contexto") para o daemon. Sem o .dockerignore, o seu node_modules local (que pode ter zilhões de arquivos) seria enviado e copiado para dentro da imagem — lentidão e sujeira. A aula .dockerignore detalha a sintaxe.

Dockerfile — a receita da imagem

FROM node:22-alpine
WORKDIR /app
COPY package*.json ./
RUN npm install
COPY . .
EXPOSE 3000
CMD ["node", "app.js"]

Anatomia, instrução por instrução (a cola completa está em Instruções do Dockerfile):

FROM node:22-alpine
a imagem base: Node 22 sobre Alpine Linux, ~189MB, já com node e npm (a aula FROM explica como escolher a base).
WORKDIR /app
cria a pasta /app dentro do container e define como diretório de trabalho — os próximos comandos rodam a partir dela.
COPY package*.json ./
copia só os manifestos de dependências (package.json e package-lock.json, se existir) para /app. Fica antes do código de propósito: como quase nunca mudam, a camada fica em cache e o npm install não refaz tudo a cada build (veremos isso na saída).
RUN npm install
roda durante o build e instala as dependências dentro da imagem. Cada RUN vira uma camada.
COPY . .
copia todo o resto do contexto (respeitando o .dockerignore) para /app.
EXPOSE 3000
documenta a porta que a app usa. Não publica nada sozinha — para acessar de fora, ainda precisamos do -p no run (pegadinha clássica).
CMD ["node", "app.js"]
o comando padrão que o container executa ao iniciar, em formato JSON (obrigatório nesse formato para não ser interpretado pelo shell).

Passo 2: construa a imagem

Na pasta ~/api, rode o build. O . no final é o contexto do build (a pasta atual — tudo que o Docker pode usar no COPY):

docker build
lê o Dockerfile e monta a imagem camada por camada.
-t api:latest
dá o nome api e a tag latest à imagem criada (formato repositório:tag).
.
o contexto: a pasta atual.
$ docker build -t api:latest .

Como ler a saída do BuildKit (o motor de build):

  • #N [k/total] INSTRUÇÃO — cada instrução do Dockerfile, numerada.
  • CACHED — a entrada dessa instrução não mudou desde o último build, então a camada foi reaproveitada (0s).
  • DONE x.xs — a instrução rodou de verdade agora e levou esse tempo.
  • No fim, writing image sha256:… é o ID real da imagem criada.

Agora a imagem está na lista local:

$ docker images
REPOSITORY   TAG         IMAGE ID       CREATED           SIZE
api          latest      9f8e7d6c5b4a   25 seconds ago    195MB
node         22-alpine   c3d4e5f6a1b2   1 week ago        189MB
nginx        alpine      b2c3d4e5f6a1   5 days ago        48.2MB

Repare: a imagem api tem 195MB — os 189MB da base Node mais o Express e o node_modules (~6MB).

Missão: faça o build como no CI: rode docker build -t api . e depois docker images para confirmar que a imagem api foi criada.

Passo 3: rode o container

Com a imagem pronta, é hora do run:

docker run
cria e inicia o container.
-d
segundo plano: devolve o ID e libera o terminal.
-p 3000:3000
publica a porta 3000 do container na 3000 do host (dava para usar outra, tipo -p 8081:3000).
--name api
nome previsível para os próximos comandos.
-e NODE_ENV=production
define a variável de ambiente NODE_ENV dentro do container — a app lê ela no process.env (e o Express muda de comportamento: menos logs, sem stack trace de erro, etc.).
api:latest
a imagem usada.
$ docker run -d -p 3000:3000 --name api -e NODE_ENV=production api:latest
b1c2d3e4f5a6071829304a5b6c7d8e9f0a1b2c3d4e5f6a7b8c9d0e1f2a3b4c5d6

$ docker ps
CONTAINER ID   IMAGE         COMMAND        CREATED          STATUS          PORTS                    NAMES
b1c2d3e4f5a6   api:latest    "node app.js"  5 seconds ago    Up 5 seconds    0.0.0.0:3000->3000/tcp   api

Missão: suba a API: rode docker run -d -p 3000:3000 --name api api:latest (a imagem api já existe se você fez o build antes nesta página) e depois docker ps — a coluna PORTS deve mostrar 3000:3000.

Passo 4: teste a API

$ curl -s http://localhost:3000
{"mensagem":"Olá do container!","ambiente":"production"}

$ curl -s http://localhost:3000/saude
{"status":"ok"}

$ curl -sI http://localhost:3000/saude | head -1
HTTP/1.1 200 OK

$ docker logs api
API rodando na porta 3000

O valor "ambiente":"production" veio da variável -e NODE_ENV=production: dá para mudar o comportamento do container sem trocar a imagem — só passando variáveis na hora do run (a aula Variáveis de ambiente mostra outras formas, como --env-file).

Também dá para entrar no container e ver o código por dentro:

$ docker exec api ls /app
app.js  node_modules  package.json  package-lock.json
$ docker exec api node -e "console.log(process.env.NODE_ENV)"
production

Passo 5: o ciclo build → run → test (mude e repita)

Agora a parte que vira rotina: a Ana quer adicionar uma rota nova, /hora, que devolve a hora do container. Ela edita o app.js no host:

app.get('/hora', (req, res) => {
  res.json({ agora: new Date().toISOString() });
});

E repete o ciclo:

$ docker build -t api:latest .
#6 [3/5] COPY package*.json ./
#6 CACHED                    « não mudou → cache
#7 [4/5] RUN npm install
#7 CACHED                    « idem: 0s em vez de 3s!
#8 [5/5] COPY . .
#8 DONE 0.2s                 « só o código foi reempacotado
...

$ docker stop api && docker rm api
api
api
$ docker run -d -p 3000:3000 --name api -e NODE_ENV=production api:latest
b1c2d3e4f5a6…

$ curl -s http://localhost:3000/hora
{"agora":"2025-11-24T12:05:31.442Z"}

Esse é o fluxo do dia a dia: edita o código → build → stop/rm do container antigo → run de novo → testa com curl. A ordem COPY package*.json antes de COPY . . fez o npm install ficar CACHED — o build inteiro levou menos de 1 segundo em vez de 4. A aula Builds otimizados aprofunda essa economia.

Erros comuns neste projeto

Porta ocupada: 
$ docker run -d -p 3000:3000 --name api api:latest
docker: Error response from daemon: driver failed programming external connectivity on endpoint api (b1c2d3e4f5a6...): Bind for 0.0.0.0:3000 failed: port is already allocated
Já existe outro processo usando a 3000 do host — quem sabe um container api esquecido? Pare o antigo (docker stop api) ou publique outra porta no host: -p 3001:3000 (e acesse localhost:3001).
Imagem não encontrada: 
$ docker run -d -p 3000:3000 --name api api:latest
Unable to find image 'api:latest' locally
docker: pull access denied for api, repository does not exist or may require 'docker login'.
A Ana rodou o docker run antes do docker build. Build primeiro, run depois. (Se a imagem não existisse nem no Docker Hub, o pull automático falha com essa mensagem — é o mesmo erro quando o nome está errado.)
Nome já em uso: 
$ docker run -d --name api api:latest
docker: Error response from daemon: Conflict. The container name "/api" is already in use by container "b1c2d3e4f5a6…". You have to remove (or rename) that container to be able to reuse that name.
Nomes são únicos, mesmo para containers parados. Solução: docker rm api antes, ou outro --name.
A API responde no navegador mas não dá curl / dá "connection refused" de fora: a causa clássica é o app.listen(PORT) sem o '0.0.0.0'. Dentro do container, localhost é o próprio container — a app fica presa lá dentro e o -p não consegue alcançá-la. Sempre escute em 0.0.0.0 em apps containerizadas.
O build quebra no RUN npm install: 
#7 ERROR: process "/bin/sh -c npm install" did not complete successfully: exit code: 1
Geralmente é dependência quebrada no package.json ou arquivo faltando no contexto (você listou demais no .dockerignore e o COPY não achou o arquivo: COPY failed: file not found in build context). Leia as linhas acima do erro no log do build.

Levando a imagem para outro lugar (tag e push)

Uma imagem só na máquina da Ana não serve para o trabalho de faculdade entregar no servidor da turma. Para mandar a imagem para o Docker Hub (ou qualquer registry), o nome precisa ter o seu usuário na frente — é assim que o registry sabe de quem é o repositório:

$ docker login -u ana
Password:
Login Succeeded

$ docker tag api:latest ana/api-hello:1.0
$ docker images | grep ana
REPOSITORY     TAG       IMAGE ID       CREATED          SIZE
ana/api-hello  1.0       9f8e7d6c5b4a   2 minutes ago    195MB

$ docker push ana/api-hello:1.0
The push refers to repository [docker.io/ana/api-hello]
9f8e7d6c5b4a: Layer already exists
...
1.0: digest: sha256:9f8e7d6c5b4a3f2e... size: 1786

Depois disso, qualquer pessoa (ou servidor) com Docker pode baixar a imagem com docker pull ana/api-hello:1.0 e rodar com o mesmo docker run — é exatamente por isso que "funciona na minha máquina" deixa de ser desculpa. A aula docker tag e push detalha tags, digests e o login.

Nunca suba imagem com senha dentro: se o projeto usa variáveis sensibles (senhas de banco, chaves de API), elas não devem estar no código nem na imagem. Use variáveis de ambiente no run (-e) ou um arquivo .env (com --env-file), e mantenha o .env fora do git e fora do contexto do build (está no nosso .dockerignore).

Resumo

  • O fluxo é: Dockerfile (receita) → docker build → imagem → docker run → container.
  • Ordem do Dockerfile importa: COPY package*.json + RUN npm install antes do COPY . ., para o cache não invalidar a cada mudança de código.
  • EXPOSE só documenta a porta; quem publica é o -p no run.
  • -e CHAVE=valor muda a configuração do container sem rebuild; apps em containers devem escutar em 0.0.0.0.
  • O ciclo do dia a dia: edita → build → stop/rm → run → curl.
  • Erros clássico: porta ocupada (port is already allocated), run antes do build (Unable to find image), nome repetido (already in use).
