--read-only — sistema de arquivos somente leitura

A Ana já deixou a API da Loja Aurora rodando como usuário comum (aula USER). Ótimo. Mas ela reparou numa coisa: mesmo como usuário comum, o processo dentro do container ainda consegue escrever em qualquer lugar do sistema de arquivos — inclusive em cima de binários importantes, como o /usr/bin/node. Se um atacante entrar no container, ele pode trocar esse binário por uma versão adulterada e, da próxima vez que a app reiniciar, o código malicioso roda no lugar do dela. Com --read-only, o sistema de arquivos inteiro do container é montado como somente leitura, e o que a app precisar gravar vai para lugares explícitos que você libera.

Você vai aprender
  • O que muda na prática com docker run --read-only.
  • --tmpfs /tmp: uma pasta na memória RAM para arquivos temporários, com opções size, noexec, nosuid.
  • Apps stateless: dados persistentes vão para volumes, não para dentro do container.
  • O erro real Read-only file system (Errno 30) quando a app tenta gravar — e como ler o caminho que ela tentou gravar.
  • Exemplo completo com Nginx, liberando exatamente as pastas que ele precisa.
  • Tabela resumo: o que fica gravável e o que fica bloqueado.

A ideia: o apartamento vira museu

Sem --read-only, o container ganha uma camada gravável no topo da imagem: o processo pode escrever em qualquer lugar, como se o apartamento fosse dele para reformar. Com --read-only, o sistema de arquivos inteiro vira somente leitura — como um museu: dá para olhar, não dá para riscar a parede.

E onde a app vai gravar o que precisa? Em dois lugares, que você controla:

  • Volumes (-v): pastas persistentes, o lugar certo para dados de verdade (banco, uploads, logs em arquivo).
  • tmpfs (--tmpfs): pastas temporárias que vivem na memória RAM — rápidas, graváveis e descartáveis quando o container para.

A regra de ouro fica sendo: container é descartável, dado não é.

--read-only na prática

No notebook da Ana, o site estático da loja sobe assim:

$ docker run -d --name site --read-only --tmpfs /tmp -p 8080:80 nginx:alpine
f3a1b2c3d4e5…

$ docker ps
CONTAINER ID   IMAGE          STATUS         PORTS                  NAMES
f3a1b2c3d4e5   nginx:alpine   Up 3 seconds   0.0.0.0:8080->80/tcp   site

O Nginx sobe normal porque o pouco que ele precisa gravar vai para /tmp — que liberamos com --tmpfs.

--read-only
Monta o sistema de arquivos inteiro do container (a imagem + a camada gravável) como somente leitura.
--tmpfs /tmp
Cria /tmp como tmpfs: gravável, rápido (RAM) e descartável — o conteúdo some quando o container para ou é apagado.
-p 8080:80
Publica a porta 80 do container na 8080 da máquina. Portas de rede não envolvem o sistema de arquivos, então seguem funcionando.
-d --name site
Roda em segundo plano com nome fixo, para o docker ps e o docker logs ficarem fáceis (aula docker run).

O erro quando a app tenta gravar

Sem tmpfs em lugar nenhum, qualquer tentativa de escrita falha na hora com o erro que vem lá do kernel:

$ docker run --rm --read-only python:3.12-slim python -c "open('/tmp/x','w')"
Traceback (most recent call last):
  File "<string>", line 1, in <module>
OSError: [Errno 30] Read-only file system: '/tmp/x'

E dá para confirmar de fora, entrando no container:

$ docker exec site touch /novo-arquivo
touch: /novo-arquivo: Read-only file system
Se a sua aplicação quebrar com Errno 30 depois de ligar --read-only, é sinal de que ela grava em algum lugar do sistema de arquivos. A cura não é desligar o --read-only: é ler o caminho no próprio erro (no exemplo, /tmp/x) e liberar exatamente essa pasta com --tmpfs — ou, se o dado precisa persistir, jogá-lo num volume (-v). Cada pasta liberada é uma porta a mais; libere só o necessário.
Cenário real: a API que gravava em /tmp e "funcionava"

A Ana ligou --read-only na API da Loja Aurora e, na primeira subida, o container caía na hora com OSError: [Errno 30] Read-only file system: '/app/cache/sessao-123'. Acontece que a biblioteca de sessões gravava arquivos numa pasta cache/ dentro do próprio app — um cache que nem precisava persistir. A solução foi apontar o cache para /tmp (variável de ambiente SESSION_DIR=/tmp/sess) e adicionar --tmpfs /tmp no docker run. Em dez minutos a API subiu travada contra escrita. Se o dado fosse importante (um upload de cliente, por exemplo), aí sim teria ido para um volume nomeado.

--tmpfs: pastas temporárias na RAM

O --tmpfs cria uma pasta que vive na memória RAM: é gravável, muito rápida e não persiste — quando o container para ou é apagado, o conteúdo some. Use para /tmp, /run, caches e qualquer coisa descartável:

$ docker run -d --name api --read-only \
>     --tmpfs /tmp \
>     --tmpfs /run \
>     --tmpfs /var/cache:size=64m,noexec \
>     -p 3000:3000 minha-api:segura
b2c3d4e5f6a1…

Depois dos dois pontos dá para passar opções, separadas por vírgula:

Opção do --tmpfsO que fazExemplo
size=64mLimita o tamanho da pasta na RAM (padrão: metade da RAM do host).--tmpfs /var/cache:size=64m
noexecNão deixa executar binários dali — um atacante não consegue rodar um programa que ele tenha conseguido gravar.--tmpfs /tmp:noexec
nosuidBinários dali não ganham privilégios (bloqueia executáveis setuid).--tmpfs /run:nosuid
rw / roForça gravável ou somente leitura (padrão é rw).--tmpfs /tmp:rw,noexec,nosuid

Combine as três proteções nos lugares de escrita temporária: size=… para não estourar a RAM, noexec e nosuid para o que for gravado lá não virar executável privilegiado.

Apps stateless: dados persistentes vão para volumes

Com o sistema de arquivos fechado, a regra é: tudo que precisa sobreviver vai para um volume, que é montado depois do --read-only e continua gravável normalmente:

$ docker volume create api-dados
api-dados

$ docker run -d --name api --read-only \
>     --tmpfs /tmp \
>     -v api-dados:/app/dados \
>     -p 3000:3000 minha-api:segura
c3d4e5f6a1b2…

Assim a app grava em /app/dados (o volume, que sobrevive ao container) normalmente, mas não consegue tocar em mais nada — nem sobrescrever o próprio código. Volumes nomeados são criados com docker volume create (aula docker volume); bind mounts (-v ~/pasta:/caminho) também funcionam e seguem graváveis.

Exemplo completo: Nginx só de leitura

A imagem oficial do Nginx grava em algumas pastas na inicialização (cache, pid, templates de configuração). A receita é liberar exatamente essas pastas com tmpfs, nada mais:

$ docker run -d --name site --read-only \
>     --tmpfs /tmp \
>     --tmpfs /var/cache/nginx \
>     --tmpfs /var/run \
>     --tmpfs /etc/nginx/conf.d \
>     -p 8080:80 nginx:alpine
d4e5f6a1b2c3…

$ docker logs site
/docker-entrypoint.sh: Configuration complete; ready for start up   « subiu normal

Repare no padrão: cada pasta que a imagem precisa escrever vira um --tmpfs explícito. Nada de "liberar tudo" — cada exceção é um lugar a mais onde um atacante poderia gravar.

Resumo: onde dá para gravar com --read-only

LocalGravável?Como
Sistema de arquivos da imagem (/, /usr, /etc, /app…)NãoBloqueado pelo --read-only — nem o próprio código da app pode ser alterado.
/tmp e outras pastas com --tmpfsSimVivem na RAM; somem ao parar o container. Use noexec,nosuid para endurecer.
Volumes montados (-v nome:/caminho)SimPersistem no host; o lugar certo para dados de verdade.
Portas de rede (-p) e variáveis (-e)SimNão envolvem o sistema de arquivos.
Erro comum: app que grava no próprio diretório e "funcionava no teste". Em desenvolvimento a Ana rodava o container sem --read-only e a app gravava relatórios em /app/relatorios/ sem ninguém notar. Em produção, com --read-only, o primeiro pedido que gera relatório derruba a requisição com Errno 30. Regra: teste sempre com --read-only antes de subir em produção, e procure no código por caminhos de escrita (grep por writeFile, open(...,'w'), fs.createWriteStream).

Missão: suba um Nginx somente leitura com tmpfs em /tmp: docker run -d --name site --read-only --tmpfs /tmp -p 8080:80 nginx:alpine (no simulador, use --tmpfs=/tmp) — e depois confira com docker ps.

Missão extra: com o container site no ar, rode docker logs site e encontre a linha Configuration complete — prova de que o Nginx inicializou mesmo com o sistema de arquivos fechado.

2. A app quebrou com OSError: [Errno 30] Read-only file system: '/tmp/x'. Qual é a cura certa?

3. Onde ficam os arquivos de um --tmpfs /tmp?

Resumo

  • --read-only monta o sistema de arquivos inteiro do container como somente leitura: o código da app não pode ser alterado por dentro.
  • O que a app precisa gravar vai para lugares explícitos: --tmpfs (RAM, descartável) ou volumes -v (persistentes).
  • Opções do tmpfs: size=64m, noexec, nosuid — use as três nos diretórios temporários.
  • Erro real de app gravando no lugar errado: OSError: [Errno 30] Read-only file system: '/caminho' — o caminho no erro diz o que liberar.
  • Regra de produção: container descartável, dado em volume; teste com --read-only antes de subir.
  • Combina com a aula anterior: USER não-root + --read-only = mesmo se o atacante entrar, ele não é root e não consegue alterar nada.
