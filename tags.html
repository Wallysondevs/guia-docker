Tags e versões

Uma imagem pode ter várias tags — pense nelas como apelidos para versões diferentes da mesma receita. Sem tag, o Docker usa :latest. Nesta aula você aprende a ler uma tag, escolher a certa e evitar a armadilha do :latest.

Você vai aprender
  • A anatomia de repositório:tag e a regra do :latest.
  • Os tipos de tag: versão maior (:22), versão+variante (:22-alpine), variante só (:alpine), codinome do Debian (:bookworm).
  • Por que :latest é perigoso em produção.
  • Como fixar a versão de verdade com o digest @sha256:….
  • Como descobrir todas as tags disponíveis de uma imagem (no Hub).

A anatomia de uma tag

node : 22 - alpine
 │      └────────── a tag (versão/variante), depois dos dois pontos
 └───────────────── o repositório (nome da imagem)
node
O repositório: a imagem oficial do Node.js (namespace library implícito).
:22-alpine
A tag: versão 22 do Node, variante Alpine (Linux minúsculo).
sem tag
docker pull node = node:latest — a tag padrão, que aponta para "a mais recente".
$ docker pull node          « é exatamente isto:
Using default tag: latest
… docker.io/library/node:latest

Como escolher a variante?

  • alpine: menor imagem, menos ferramentas dentro (bom para produção enxuta). Atenção: usa musl em vez de glibc — raríssimas bibliotecas nativas quebram; teste antes.
  • slim: Debian enxuto, com glibc — compatibilidade quase total, tamanho médio.
  • bookworm / padrão (sem sufixo): Debian/Ubuntu completo, com compilador e ferramentas — bom para desenvolvimento e para imagens que precisam instalar pacotes (apt install).

Por que evitar :latest em produção

O :latest muda sem avisar — hoje pode ser a versão 22, amanhã a 23, e seu app pode quebrar com a mudança. A cena clássica da Ana: o app dela rodava com node:latest; numa madrugada o Hub atualizou a tag para o Node 23, o servidor fez pull automático e o deploy novo quebrou. O fix foi trocar para node:22-alpine.

AmbienteTag recomendadaPor quê
Estudo / teste local:latest ou só o nomeConveniente; você quer ver o que tem de novo
Desenvolvimento em equipenode:22-alpine (versão fixa)Todo mundo usa a mesma versão — adeus "na minha máquina"
Produçãoversão fixa, de preferência por digestNada muda sem você mandar
Even com versão fixa, a tag ainda pode mudar

node:22 não é 100% imutável: quem publica pode (por engano ou arquitetura nova) trocar o conteúdo da tag 22. A trava de verdade é o digest: node:22-alpine@sha256:abc123…. O digest é o hash do conteúdo — se mudar uma vírgula, muda o hash. Para achar o digest: na página da tag no Docker Hub, ou no resultado do seu docker pull (linha Digest: sha256:…).

Ver todas as tags de uma imagem

No Docker Hub (hub.docker.com), na página da imagem oficial, a aba Tags lista todas as versões disponíveis, com o sistema de cada uma e a data de atualização. Exemplos reais:

  • hub.docker.com/_/node/tags — dezenas: 22, 22-alpine, 22-bookworm, 22-slim, 20…
  • hub.docker.com/_/python/tags — 3.12, 3.12-slim, 3.12-alpine, 3.13…
  • hub.docker.com/_/nginx/tags — alpine, 1.27, 1.27-alpine, stable…

No terminal, dá para listar as suas locais com docker images nginx (todas as tags que você tem daquele repositório).

Erro comum: escrever a tag no lugar errado 
$ docker pull alpine:latest:3.18        « errado: duas tags?
docker: invalid reference format.
$ docker pull alpine 3.18              « errado: espaço = outro argumento
Usage:  docker pull [OPTIONS] NAME[:TAG|@DIGEST]

A forma certa é tudo junto, depois dos dois pontos: alpine:3.18. E se quiser o digest no lugar da tag, é com @: alpine@sha256:….

Como escolher a tag certa (checklist da Ana)

  1. Entre na página da imagem no Hub → aba Tags.
  2. Prefira a versão maior fixa da linguagem que seu projeto usa (ex.: se o projeto é Node 22, use 22-…, não latest nem 23-…).
  3. Escolha a variante: alpine/slim para produção enxuta; padrão (bookworm) se precisar instalar pacotes ou debugar.
  4. Se o projeto já tem Dockerfile/Compose, copie a tag de lá — consistência entre máquinas é o ponto do Docker.
  5. Em produção, considere travar pelo digest (@sha256:…).

Ver a tag padrão de verdade: docker image inspect

Quer saber para qual imagem uma tag está apontando agora? O docker image inspect mostra os metadados, incluindo o digest:

$ docker image inspect nginx:alpine --format '{{.RepoDigests}}'
[nginx@sha256:b2c3d4e5f6a1…]
$ docker image inspect nginx:alpine --format '{{.Os}}/{{.Architecture}}'
linux/amd64

Útil também para saber se a imagem serve para o seu chip (amd64 = Intel/AMD; arm64 = Apple Silicon/Mac M1-M3 e Raspberry Pi — se a tag não tiver variante para arm64, o Docker baixa a amd64 e roda com emulação, mais lento).

Erro de tag: "manifest unknown" 
$ docker pull nginx:nao-existe
docker: manifest for nginx:nao-existe not found: manifest unknown: manifest unknown

A tag não existe (nome errado ou a versão não foi publicada). Veja as tags válidas na aba Tags do Hub ou com docker images nginx (as que você já tem).

Resumo

  • Toda imagem é repositório:tag; sem tag, vale :latest (a mais recente).
  • Tipos de tag: versão (:22, :1.27.3), variante (:alpine, :slim), versão+variante (:22-alpine), codinome Debian/Ubuntu (:bookworm, :jammy).
  • Variantes: alpine (mínima, musl), slim (Debian enxuta), padrão/bookworm (completa, com ferramentas).
  • :latest em produção é roleta: a tag pode mudar de conteúdo. Prefira versão fixa e, no limite, o digest @sha256:… (imutável).
  • Todas as tags disponíveis de uma imagem: aba Tags da página dela no Docker Hub; as que você tem local: docker images NOME.
