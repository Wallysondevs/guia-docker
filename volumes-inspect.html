docker volume inspect — onde o volume mora no host

Todo volume nomeado tem uma pasta real no sistema de arquivos do host. O docker volume inspect mostra o JSON completo do volume, incluindo esse caminho — o Mountpoint. É o comando para responder a pergunta que todo mundo faz uma hora: "onde diabos está esse dado?". A Ana vai usar isso para achar os dados do Postgres dela no notebook.

Você vai aprender
  • Ler o JSON do docker volume inspect: Mountpoint, Driver, Scope, Labels, Options, CreatedAt.
  • Extrair só um campo com --format (ex.: só o Mountpoint) — ouro em scripts.
  • Marcar volumes com --label no create e filtrar com --filter label=….
  • A ligação direta entre -v nome:/caminho e o Mountpoint no host (prova com docker exec + cat).
  • O docker inspect genérico: funciona com qualquer objeto (container, imagem, rede, volume).
  • O cuidado de não editar os arquivos do volume direto no host.

A cena: "onde está o banco da Ana?"

A Ana criou o volume dados-postgres na aula passada e agora quer saber onde os arquivos foram parar no disco do notebook dela. Ela pergunta ao Docker:

$ docker volume create dados
dados
$ docker volume inspect dados
[
    {
        "CreatedAt": "2025-06-10T14:02:11+02:00",
        "Driver": "local",
        "Labels": null,
        "Mountpoint": "/var/lib/docker/volumes/dados/_data",
        "Name": "dados",
        "Options": null,
        "Scope": "local"
    }
]

O comando aceita vários volumes de uma vez: docker volume inspect dados dados-postgres devolve um array JSON com os dois.

Anatomia do JSON

Mountpoint
o caminho real da pasta no host (no Linux, /var/lib/docker/volumes/<nome>/_data). É para lá que o -v dados:/algum/lugar aponta. No Windows/Mac (Docker Desktop), fica dentro da VM do Docker, não acessível direto.
Driver
quem guarda os dados. O padrão é local (disco da máquina); dá para plugar outros (NFS, volumes de nuvem, plugins) com --driver no create.
Scope
local = o volume vive nessa máquina. Existe global para drivers de cluster (Swarm).
Labels
etiquetas chave=valor que você prende no volume com --label (veja abaixo).
Options
opções específicas do driver (ex.: em NFS, o servidor e o caminho). Vem null no driver local.
CreatedAt
quando o volume foi criado.
Só um campo, por favor: o --format extrai só o que você quer do JSON — perfeito para scripts: 
$ docker volume inspect dados --format '{{.Mountpoint}}'
/var/lib/docker/volumes/dados/_data
$ docker volume inspect dados --format '{{.Name}} criado em {{.CreatedAt}}'
dados criado em 2025-06-10T14:02:11+02:00
O --format usa templates Go (entre {{ }}). Esse mesmo truque funciona no docker inspect de containers e imagens — a aula docker inspect a fundo mostra mais.

Labels: etiquetando volumes

Volumes órfãos são o terror de toda máquina com Docker. Para saber para que serve cada volume, prenda etiquetas na criação e filtre depois:

$ docker volume create --label projeto=guia --label ambiente=dev dados-app
dados-app
$ docker volume inspect dados-app
[
    {
        "CreatedAt": "2025-06-10T14:05:47+02:00",
        "Driver": "local",
        "Labels": {
            "ambiente": "dev",
            "projeto": "guia"
        },
        "Mountpoint": "/var/lib/docker/volumes/dados-app/_data",
        "Name": "dados-app",
        "Options": null,
        "Scope": "local"
    }
]
$ docker volume ls -q --filter label=projeto=guia
dados-app

A ligação com o -v: o DESTINO do volume é o Mountpoint

Quando você monta -v dados:/app/dados, o /app/dados dentro do container é exatamente a pasta do Mountpoint no host — o mesmo arquivo, visto dos dois lados. A Ana prova isso escrevendo dentro do container e lendo no host:

$ docker run -d --name web -v dados:/app/dados nginx:alpine
e5f6a1b2c3d4a1b2c3d4e5f6a1b2c3d4e5f6a1b2c3d4e5f6a1b2c3d4e5f6a1b2c3d4e5f6a1b2c3d4
$ docker exec web sh -c "echo teste > /app/dados/arquivo.txt"
$ sudo cat /var/lib/docker/volumes/dados/_data/arquivo.txt
teste   « mesmo arquivo, visto do host pelo Mountpoint

É por isso que o volume persiste: o que o container escribe em /app/dados cai direto na pasta do host. E é por isso que dá para fazer backup só empacotando essa pasta (com o banco parado, como vimos na aula anterior).

Não edite os arquivos direto no Mountpoint. O Docker não sabe que você mexeu ali por fora — e bancos de dados (Postgres principalmente) podem corromper os dados se os arquivos forem alterados sem eles saberem. Para copiar arquivos para dentro ou fora de um volume, prefira docker cp ou um container auxiliar (aula docker volume mostrou as duas formas).

E o docker inspect genérico?

O docker inspect funciona com qualquer objeto do Docker — container, imagem, rede, volume. Para volumes, a forma longa é a mesma coisa que o docker volume inspect:

$ docker inspect dados
[
    {
        "CreatedAt": "2025-06-10T14:02:11+02:00",
        "Driver": "local",
        ...
        "Mountpoint": "/var/lib/docker/volumes/dados/_data",
        ...
    }
]

Em vez de decorar, use docker volume inspect para volumes e docker inspect para containers, imagens e redes — mas saiba que os dois chegam no mesmo lugar. O docker inspect aceita vários objetos de tipos diferentes de uma vez: docker inspect web dados app-net devolve os três JSONs.

Quero inspecionar…Comando
Um volumedocker volume inspect dados (ou docker inspect dados)
Um containerdocker inspect web
Uma imagemdocker inspect nginx:alpine
Uma rededocker network inspect app-net (ou docker inspect app-net)
Um campo específico de qualquer um… --format '{{.CAMPO}}'

Script: listar volumes com Mountpoint numa linha

Juntando ls -q com inspect --format, a Ana fez um script que imprime cada volume e onde ele mora no host — útil num servidor que não é o seu notebook:

#!/bin/bash
# arquivo: volumes-resumo.sh — para cada volume, imprime "nome -> mountpoint (driver)"
for v in $(docker volume ls -q); do
    mp=$(docker volume inspect "$v" --format '{{.Mountpoint}}')
    drv=$(docker volume inspect "$v" --format '{{.Driver}}')
    echo "$v -> $mp ($drv)"
done

Saída típica no notebook dela:

$ ./volumes-resumo.sh
dados -> /var/lib/docker/volumes/dados/_data (local)
dados-postgres -> /var/lib/docker/volumes/dados-postgres/_data (local)
dados-app -> /var/lib/docker/volumes/dados-app/_data (local)

Ver os volumes montados pelo lado do container

O caminho inverso também existe: o docker inspect de um container lista todos os volumes que ele montou, no bloco Mounts — com Source (o Mountpoint no host, para volumes nomeados) e Destination (o caminho dentro do container):

$ docker inspect web --format '{{json .Mounts}}' | python3 -m json.tool
[
    {
        "Type": "volume",
        "Name": "dados",
        "Source": "/var/lib/docker/volumes/dados/_data",
        "Destination": "/app/dados",
        "Driver": "local",
        "Mode": "rw",
        "RW": true
    }
]
$ docker inspect web --format '{{range .Mounts}}{{.Destination}} ← {{.Source}} ({{.Type}}){{"\n"}}{{end}}'
/app/dados ← /var/lib/docker/volumes/dados/_data (volume)

É a prova de que o Destination do container é o Source (Mountpoint) no host. Esse mesmo bloco mostra bind mounts (Type: "bind") e tmpfs (Type: "tmpfs"). A aula docker inspect a fundo explora o resto do JSON do container.

Erros comuns

Inspecionar volume que não existe: docker volume inspect dados-postgre (nome errado) devolve [] — um array vazio, sem erro. Repare: o comando não falha, ele só não acha nada. Se o seu script usa o retorno, cheque se não veio vazio antes de usar.
Procurar o Mountpoint no Mac/Windows e não achar: no Docker Desktop (Mac/Windows), o Docker roda dentro de uma VM Linux; o caminho /var/lib/docker/volumes/… existe dentro da VM, não no seu Mac/Windows. Para ver os arquivos, use docker run --rm -v dados:/dados alpine ls /dados (um container auxiliar) ou docker cp.
Editar direto no Mountpoint corrompe banco: se a Ana abrir /var/lib/docker/volumes/dados-postgres/_data e apagar um arquivo "para limpar espaço" enquanto o Postgres roda, o banco quebra de formas estranhas. Regra: no Mountpoint, só o Docker mexe; você usa docker cp ou container auxiliar.

Missão: inspecione um objeto com o docker inspect: rode docker inspect hello-world (a imagem já existe na máquina) e encontre o campo Created no JSON. Depois rode docker volume inspect dados — no Docker real ele mostra o Mountpoint do volume.

Missão extra: crie um volume e liste: rode docker volume create dados e depois docker volume ls — o nome dados deve aparecer depois do cabeçalho DRIVER VOLUME NAME.

Resumo

  • Todo volume nomeado tem uma pasta real no host: o Mountpoint (/var/lib/docker/volumes/<nome>/_data no Linux), revelado pelo docker volume inspect.
  • O JSON traz Driver (local por padrão), Scope, Labels, Options e CreatedAt. Com --format '{{.Campo}}' você extrai só um campo — ouro em scripts.
  • -v dados:/app/dados faz o /app/dados do container ser exatamente o Mountpoint — por isso os dados persistem e dá para backupear a pasta.
  • Etiquete volumes com --label na criação e filtre com docker volume ls --filter label=….
  • docker inspect serve para qualquer objeto (container, imagem, rede, volume).
  • Nunca edite o Mountpoint direto no host com o banco rodando — use docker cp ou container auxiliar. E no Mac/Windows o Mountpoint fica dentro da VM do Docker Desktop.
