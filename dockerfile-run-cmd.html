RUN e CMD — duas horas diferentes

Essas são as duas instruções que mais confundem quem está começando no Dockerfile. A diferença é quando cada uma executa: o RUN roda agora, durante o build (é o preparo do bolo, que fica gravado para sempre), e o CMD roda depois, toda vez que um container inicia (é o modo de servir a fatia). Nesta aula a Ana vai montar a API dela passo a passo no notebook e ver essa diferença na prática.

Você vai aprender
  • A linha do tempo: docker build (build time) vs. docker run (runtime) — o que acontece em cada um.
  • RUN: executar comandos no build (instalar pacotes) e virar camada da imagem; encadear com && para gerar uma camada só.
  • CMD: definir o comando padrão do container.
  • Forma shell vs. forma exec (JSON) — e por que na exec o processo vira PID 1 e recebe sinais na hora certa.
  • Como sobrescrever o CMD na linha de comando do docker run (útil para debug).
  • O que é o ENTRYPOINT (o programa fixo) e como ele se combina com o CMD (os argumentos).
  • Erros reais: instalação no CMD, aspas no JSON, vários CMD no mesmo arquivo.

A linha do tempo: build vs. runtime

Antes de olhar para as instruções, imagine a linha do tempo do seu projeto. Existe um momento em que a imagem é construída (uma vez, ou a cada mudança de código) e um momento em que o container roda (toda vez que alguém dá docker run, possivelmente em outra máquina):

Build time (agora, no docker build)Runtime (depois, no docker run)
Quem executaO Docker daemon, lendo o Dockerfile linha a linhaO próprio container, ao iniciar
Instruções típicasFROM, RUN, COPY, ENV, WORKDIRCMD, ENTRYPOINT
O resultadoCamadas gravadas na imagem (só leitura)Um processo rodando num container
Quanto tempo duraSegundos a minutos, uma vez por buildEnquanto o container estiver no ar
Exemplo da AnaRUN npm install — instala as dependências e grava na imagemCMD ["node", "server.js"] — sobe o servidor toda vez

Regra de bolso: se a instrução prepara a imagem, ela roda no build (RUN); se define o que o container faz quando nasce, ela é de runtime (CMD).

RUN: o preparo, que fica gravado na imagem

Cada RUN executa um comando durante o build, dentro de um container temporário, e o resultado vira uma camada permanente da imagem. É com ele que você instala pacotes. A Ana, na base Alpine, usa o apk:

FROM node:22-alpine
RUN apk add --no-cache curl

Na base Alpine o gerenciador de pacotes é o apk (em imagens Debian/Ubuntu seria apt; em imagens completas tipo ubuntu, apt também). O --no-cache evita guardar o índice de pacotes na camada, deixando a imagem menor.

Você pode encadear vários comandos com && para gerar uma única camada — cada RUN vira uma camada, então juntar os comandos economiza camadas (aula Camadas e cache):

RUN apk add --no-cache curl git \
 && npm install -g serve

A barra invertida \ no fim da linha continua o comando na linha de baixo — o Dockerfile aceita isso para deixar o RUN comprido legível.

RUN
"rode isso durante o build". O comando é executado com /bin/sh -c por padrão.
apk add --no-cache curl
no Alpine, instala o pacote curl sem guardar o cache do índice.
&&
"e também": só roda o próximo comando se o anterior deu certo. Se o apk falhar, o build inteiro falha — o que é bom: você não gera imagem quebrada.
\
continuação de linha: o Docker junta as linhas antes de executar.
Por que o && importa: sem ele, cada comando vira parte de uma mesma linha de shell, mas se um falhar no meio, o RUN ainda pode terminar com sucesso (dependendo do último comando). Com &&, qualquer falha para o build na hora — imagem quebrada não passa despercebida.

CMD: o comando padrão na hora de rodar

O CMD não executa nada no build — ele só registra qual comando o container deve rodar quando iniciar. A Ana termina o Dockerfile da API dela assim:

FROM node:22-alpine
WORKDIR /app
COPY server.js .
CMD ["node", "server.js"]

Quando alguém rodar docker run minha-api:1.0, o container nasce executando node server.js. O CMD é um padrão, não uma ordem fixa — dá para trocar na hora (veja abaixo).

Forma shell vs. forma exec

Toda instrução que roda comando (RUN, CMD, ENTRYPOINT) aceita duas sintaxes:

CMD node server.js          # forma shell
CMD ["node", "server.js"]   # forma exec (JSON)
CMD node server.js
forma shell: o Docker roda /bin/sh -c "node server.js". O processo principal do container vira o shell, e o Node fica como filho dele. Sinais como Ctrl+C (SIGINT) nem sempre chegam no Node na hora certa.
CMD ["node", "server.js"]
forma exec (JSON): o node vira o processo principal (PID 1) direto, sem shell no meio. Sinais chegam na hora, e o docker stop mata o processo certo.

Regra prática: use a forma exec (entre colchetes, com aspas duplas em cada elemento) no CMD e no ENTRYPOINT. A forma shell é aceitável dentro do RUN, onde o shell já vai existir de qualquer jeito (o RUN sempre roda via shell).

Forma shellForma exec (JSON)
EscritaCMD node server.jsCMD ["node", "server.js"]
Comando real executado/bin/sh -c "node server.js"node server.js direto
PID 1 do containero shello próprio programa
Variáveis de ambiente no comandoexpansadas pelo shell ($HOME funciona)não são expansadas (vá direto ao ponto)
Usa noRUN (OK) e CMD/ENTRYPOINT (evite)CMD e ENTRYPOINT (recomendado)
Erro real: aspas simples no JSON. A forma exec exige aspas duplas: CMD ['node', 'server.js'] dá erro de parse no build (invalid character — JSON não aceita aspas simples). E CMD [node, server.js] (sem aspas nenhuma) também quebra. Sempre: ["node", "server.js"].

O CMD é sobrescrevível na linha de comando

Como o CMD só vale como padrão, você pode trocá-lo na hora de rodar, colocando outro comando depois do nome da imagem no docker run. A Ana testa a imagem ola:1.0 dela assim:

$ docker run --rm ola:1.0 echo "rodei outro comando!"
rodei outro comando!

O echo "Olá! Eu fui assado por um Dockerfile." do Dockerfile foi substituído pelo echo novo. Isso é útil demais para debug: docker run -it minha-api:1.0 sh abre um shell dentro do container no lugar de subir o servidor — você entra na "cozinha" para fuçar.

Truque de debug da Ana: se a API não sobe, ela roda docker run -it --rm minha-api:1.0 sh e testa dentro do container: node --version, ls /app, node server.js na mão para ver o erro. O CMD padrão é só um atalho.

Missão: rode docker run hello-world no terminal abaixo. A mensagem que aparece é o CMD padrão da imagem hello-world executando.

Missão extra: sobrescreva o CMD na hora do run: rode docker run --rm hello-world echo "rodei outro comando" e veja que o texto do Dockerfile foi trocado pelo seu.

ENTRYPOINT: o programa fixo

Se o CMD é fácil de trocar, o ENTRYPOINT é o programa fixo do container — e o CMD passa a ser os argumentos dele:

FROM node:22-alpine
WORKDIR /app
COPY . .
ENTRYPOINT ["node"]
CMD ["server.js"]

Nesse exemplo, docker run minha-api:1.0 roda node server.js, e docker run minha-api:1.0 outro.js roda node outro.js — só os argumentos mudam, o programa não. É a combinação clássica para CLIs empacotadas em imagem (tipo docker run minha-cli --help).

Só CMDENTRYPOINT + CMD
DockerfileCMD ["node", "server.js"]ENTRYPOINT ["node"] + CMD ["server.js"]
docker run imagemroda node server.jsroda node server.js
docker run imagem outro.jsroda outro.js (trocou tudo)roda node outro.js (só os argumentos)
Uso típicoServiço único (API, banco)Ferramenta/CLI com subcomandos

Também dá para trocar o ENTRYPOINT inteiro no run com --entrypoint: docker run --entrypoint sh minha-api:1.0.

# 2. Pasta de trabalho dentro da imagem

# 3. Copia só os manifests primeiro (cache amigo — aula de camadas)

# 4. Instala as dependências NO BUILD (RUN, não CMD!)

Quando dá errado

Erro clássico: colocar instalação de dependências no CMD. 
# ERRADO — o CMD não roda no build!
FROM node:22-alpine
CMD npm install && node server.js
O build gera a imagem "magra" e o npm install só tenta rodar quando o container inicia — cada container repetiria a instalação, nada ficaria gravado na imagem, e o processo principal seria o shell. Como consertar: instalação é RUN: RUN npm install, e o CMD fica só com ["node", "server.js"].
Vários CMD: só o último vale. Se o Dockerfile tem dois CMD, o build não reclama — ele usa o último e ignora o primeiro. É fonte de confusão ("por que meu comando não rodou?"). Como consertar: um CMD por etapa; se quiser mudar o padrão, edite o Dockerfile e rebuild.
Forma exec sem aspas duplas: CMD ["node", 'server.js'] (aspas simples no segundo) quebra o parse do JSON no build. Em forma exec, sempre aspas duplas em todos os elementos.
Esquecer que o CMD roda em toda réplica: se você usa CMD ["npm", "start"] e sobe 10 containers da mesma imagem, os 10 rodam npm start. Se o que você queria era rodar algo uma vez só no build, de novo: era caso para RUN.

Resumo

  • Há dois momentos: o build (docker build, instruções RUN/COPY/ENV) e o runtime (docker run, instruções CMD/ENTRYPOINT).
  • RUN executa no build e cada um vira uma camada; encadeie com && para uma camada só e para o build falhar se algo der errado.
  • CMD só registra o comando padrão do container; na hora do docker run dá para sobrescrever passando outro comando depois da imagem.
  • Prefira a forma exec CMD ["node", "server.js"]: o programa vira PID 1, sem shell no meio, e recebe sinais (Ctrl+C, docker stop) na hora certa. No JSON só valem aspas duplas.
  • ENTRYPOINT é o programa fixo; CMD vira os argumentos dele — combinação clássica para CLIs.
  • Erro clássico: por instalação no CMD — o lugar é o RUN. E vários CMD no arquivo: só o último vale, sem aviso.
