--cap-drop — remover capabilities

Na aula USER a Ana aprendeu a não rodar o processo como root. Só que tem um detalhe: root dentro do container ainda tem poderes demais. No Linux moderno, o poder do root foi quebrado em capabilities — cerca de 40 "pedaços" de privilégio (abrir porta baixa, mudar a rede, montar discos…). O container padrão recebe um conjunto dessas capabilities mesmo sem ser root de verdade. Nesta aula você aprende a tirar todas com --cap-drop ALL e devolver só o que a app precisa com --cap-add — o princípio do menor privilégio.

Você vai aprender
  • O que são Linux capabilities e por que "root de container" ainda é perigoso.
  • A combinação clássica de produção: --cap-drop ALL + --cap-add NET_BIND_SERVICE.
  • Tabela das capabilities mais comuns e quando cada uma é necessária.
  • Como inspecionar as capabilities de um container (docker inspect, /proc/self/status).
  • Por que --privileged é o último recurso — e quais alternativas usar.

A ideia: o molho de chaves do root

Antigamente, no Linux, root era "tudo ou nada": ou você tinha todos os poderes, ou nenhum. Hoje o poder foi dividido em capabilities — pense num molho de chaves: cada chave abre uma porta diferente. CAP_NET_BIND_SERVICE abre a porta de "usar portas abaixo de 1024" (80, 443). CAP_SYS_ADMIN é a chave mestra — abre mount, namespaces e muita coisa perigosa.

Um processo comum (usuário sem privilégios) não tem chave nenhuma. O root tem o molho inteiro. E o container padrão do Docker? Ele não é root de verdade, mas ganha um molho parcial — dá para ver na prática. No notebook da Ana, um usuário comum tentando abrir a porta 80 dentro de um container falha:

$ docker run --rm --user 1000 python:3.12-slim python -c "import socket; s=socket.socket(); s.bind(('0.0.0.0', 80))"
Traceback (most recent call last):
  …
PermissionError: [Errno 13] Permission denied

Mas o container padrão (como root, com o molho parcial) consegue. Com a capability CAP_NET_BIND_SERVICE, até um usuário comum consegue abrir a porta 80 — é por isso que dá para rodar um servidor web na porta baixa sem ser root. É exatamente essa a jogada de produção: usuário comum + só a chave de que precisa.

--cap-drop ALL + --cap-add só o necessário

A combinação clássica: remove todas as capabilities e devolve somente a que a app usa:

$ docker run -d --name api -p 80:8080 \
>     --user 1000:1000 \
>     --cap-drop ALL \
>     --cap-add NET_BIND_SERVICE \
>     minha-api:segura
c3d4e5f6a1b2…
--cap-drop ALL
Remove todas as capabilities do conjunto padrão — o container fica "desarmado", sem nenhuma chave.
--cap-add NET_BIND_SERVICE
Devolve uma só chave: permite abrir portas abaixo de 1024 (80, 443).
--user 1000:1000
Roda como usuário comum (aula USER) — com as duas coisas juntas, nem root nem portas baixas são problema.
-p 80:8080
Publica a porta 8080 do container na 80 do host. Repare: quem precisa da porta baixa é o daemon do Docker (lá fora), não o processo de dentro — mas a app também pode querer abrir a 80 direto.

Se a app não precisa de nenhuma capability (a maioria não precisa), basta --cap-drop ALL sozinho — e se a app usa porta alta (8080, 3000), nem isso precisa.

Missão: rode um container sem nenhuma capability e devolvendo só NET_BIND_SERVICE: docker run --rm --cap-drop ALL --cap-add NET_BIND_SERVICE -p 8080:80 nginx:alpine (no simulador, use = nas flags).

Missão extra: suba um container qualquer com docker run -d --name web nginx:alpine e rode docker ps para ver o cabeçalho CONTAINER ID — depois use docker inspect web para ver os detalhes dele.

Tabela: capabilities comuns

CapabilityO que permiteUso típico em container
NET_BIND_SERVICEAbrir portas abaixo de 1024 (80, 443).Servidor web rodando como usuário comum.
NET_RAWUsar sockets raw (ex.: ping).Ferramentas de diagnóstico de rede.
NET_ADMINMudar IPs, rotas e regras de firewall do container.Quase nunca em app; sidecars de rede (VPN, mesh).
SYS_ADMINA "chave mestra": mount, namespaces e mais.Evite — é a capability que mais ajuda em escapes de container.
SYS_CHROOTMudar a raiz com chroot.Algumas apps legadas.
SYS_PTRACEDebugar outros processos (strace, gdb).Só em imagens de debug, nunca em produção.
MKNODCriar device nodes em /dev.Raro; geralmente desnecessário.
SETUID / SETGIDTrocar de usuário (o que o sudo faz).Evite — combine com no-new-privileges (aula seccomp).
DAC_OVERRIDEPassar por cima de permissões de arquivos.Perigosa; remova com --cap-drop.
CHOWN / FOWNERMudar o dono de arquivos.Às vezes necessário em apps que gerenciam próprios arquivos.

O conjunto padrão do Docker inclui ainda FSETID, KILL, SETPCAP, SETFCAP, AUDIT_WRITE e NET_RAW, além das citadas acima. Dá para remover uma a uma com --cap-drop NOME (sem o prefixo CAP_) — por exemplo, --cap-drop SYS_PTRACE --cap-drop NET_RAW tira só essas duas e deixa o resto.

Como ver as capabilities de um container

Dentro do próprio container, o arquivo /proc/self/status mostra as máscaras de capabilities em hexadecimal. Depois de subir o container com só NET_BIND_SERVICE:

$ docker exec api grep Cap /proc/self/status
CapInh: 0000000000000000
CapPrm: 0000000000000400
CapEff: 0000000000000400
CapBnd: 00000000a80425fb

O valor 0000000000000400 (bit 10 ligado) é exatamente a NET_BIND_SERVICE. Compare com um container padrão, que mostra bem mais bits ligados. Pelo lado de fora, sem entrar no container:

$ docker inspect api --format '{{json .HostConfig.CapDrop}} {{json .HostConfig.CapAdd}}'
["ALL"] ["NET_BIND_SERVICE"]

Esse docker inspect é a forma rápida de auditar: se a coluna CapDrop não tiver ALL (ou a lista de permissões esperadas), o container está mais poderoso do que deveria. O docker inspect tem aula própria: docker inspect a fundo.

--privileged: o último recurso

Existe uma flag que devolve tudo: todas as capabilities, acesso a todos os dispositivos em /dev e as proteções de seccomp/AppArmor desativadas:

$ docker run -d --privileged …   « equivalente a --cap-add ALL + /dev liberado + sem seccomp
Nunca use --privileged em produção. Com ela, um escape de container vira root no host na hora — é como deixar a chave mestra no capacho. Use só em casos muito específicos e temporários — Docker-in-Docker num CI, mexer em módulos do kernel, acesso a hardware dedicado — e, mesmo assim, restrito à máquina de teste. Prefira alternativas pontuais: em vez de --privileged, tente --device /dev/x (libera só um dispositivo), --cap-add NOME (só uma chave) ou -v do que precisar.
Cenário real: "precisa de privileged para funcionar"

Um colega da Ana disse que a app dele "só sobe com --privileged". Investigando, descobriram que a app só precisava de NET_ADMIN para configurar uma interface de rede virtual — e de um dispositivo específico em /dev. Trocaram --privileged por --cap-add NET_ADMIN --device /dev/net/tun e a app continuou funcionando, só que agora com o resto do molho de chaves trancado. Quase sempre dá para ser específico: o --privileged é a desculpa preguiçosa, não a necessidade real.

Montando o comando seguro completo

Juntando as três aulas de segurança até aqui, o comando de produção da API da Loja Aurora fica assim:

$ docker run -d --name api \
>     --user 1000:1000 \
>     --read-only \
>     --tmpfs /tmp:size=32m,noexec,nosuid \
>     --cap-drop ALL \
>     --cap-add NET_BIND_SERVICE \
>     --security-opt no-new-privileges \
>     -v api-dados:/app/dados \
>     -p 3000:3000 \
>     ana/minha-api:1.0
f3a1b2c3d4e5…

Cada flag cobre um tipo de ataque diferente: usuário comum (aula USER), sistema de arquivos fechado (--read-only), sem capabilities (--cap-drop ALL), sem ganhar privilégios novos (no-new-privileges, aula seccomp). Em produção, use as camadas juntas.

As mesmas flags no docker-compose.yml

Em produção a Ana não usa docker run solto: ela descreve tudo no docker-compose.yml (aula O arquivo docker-compose.yml). Lá, as capabilities entram em cap_drop / cap_add, como read_only e security_opt:

services:
  api:
    image: ana/minha-api:1.0
    user: "1000:1000"
    read_only: true
    cap_drop:
      - ALL
    cap_add:
      - NET_BIND_SERVICE
    security_opt:
      - no-new-privileges
    tmpfs:
      - /tmp:size=32m,noexec,nosuid
    volumes:
      - api-dados:/app/dados
    ports:
      - "3000:3000"

volumes:
  api-dados:

Com docker compose up -d, o Docker aplica exatamente as mesmas proteções do docker run — e o arquivo fica versionado no repositório, então a configuração de segurança não depende da memória de ninguém.

Resumo

  • Capabilities são os ~40 "pedaços" em que o poder do root foi dividido; o container padrão recebe um molho parcial mesmo sem ser root.
  • --cap-drop ALL remove todas; --cap-add NOME devolve só uma (sem o prefixo CAP_).
  • Caso clássico: usuário comum + --cap-drop ALL --cap-add NET_BIND_SERVICE para servidor web na porta 80/443.
  • Veja as caps em /proc/self/status (dentro) ou docker inspect --format '{{json .HostConfig.CapDrop}}' (fora).
  • --privileged devolve tudo (caps + /dev + sem seccomp) — nunca em produção; prefira --cap-add e --device pontuais.
  • SYS_ADMIN, SYS_PTRACE e DAC_OVERRIDE são as mais perigosas: mantenha fora do conjunto do container.
