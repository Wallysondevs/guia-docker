docker volume — criar, listar e remover

Volumes nomeados são objetos gerenciados pelo Docker, como imagens, containers e redes — e têm um subgrupo próprio de comandos: docker volume. Aqui você cria volumes antes de usar (bom para scripts e para documentar a infraestrutura), lista o que existe na máquina, inspeciona e remove o que não precisa mais. A Ana vai organizar os dados do projeto dela assim.

Você vai aprender
  • docker volume create para criar um volume nomeado — e o --label para etiquetar.
  • docker volume ls para listar, com -q (só nomes) e --filter (ex.: dangling=true).
  • Um exemplo completo: volume dedicado para o Postgres, com os dados sobrevivendo à troca de container.
  • docker volume rm e o erro real de "volume is in use".
  • docker volume prune para apagar todos os volumes não usados — e por que é destrutivo.
  • Como fazer backup de um volume (tar pelo Mountpoint ou via container auxiliar).

O básico: create e ls

$ docker volume create dados
dados
$ docker volume ls
DRIVER    VOLUME NAME
local     dados

O create devolve o nome do volume — essa linha é a confirmação de que deu certo. O ls lista todos os volumes locais: repare que o driver padrão é sempre local (os dados ficam no disco da máquina, em /var/lib/docker/volumes/).

docker volume
o subgrupo de comandos que gerencia volumes.
create
cria um volume nomeado (driver local por padrão).
dados
o nome do volume — precisa ser único na máquina e é esse nome que você usa no -v dados:/caminho.
Nome descritivo salva vidas: em vez de vol1, use dados-postgres, uploads-site, cache-redis. Daqui a seis meses, docker volume ls vai mostrar uma lista e você vai saber para que serve cada um sem abrir o projeto.

Etiquetando volumes com --label

Volumes órfãos (criados e esquecidos) são o terror de toda máquina com Docker. Para saber para que serve cada volume, prenda etiquetas na criação:

$ docker volume create --label projeto=minha-api --label ambiente=dev dados-api
dados-api
$ docker volume ls --filter label=projeto=minha-api
DRIVER    VOLUME NAME
local     dados-api
$ docker volume ls -q --filter dangling=true   « só os volumes sem container usando (órfãos)

O -q imprime só os nomes, um por linha — perfeito para scripts (for v in $(docker volume ls -q --filter dangling=true); do …).

Exemplo completo: volume dedicado para o Postgres

Em vez de deixar o Docker criar o volume implicitamente no docker run, a Ana cria antes — bom para scripts e para deixar claro na máquina o que é o quê:

$ docker volume create dados-postgres
dados-postgres
$ docker run -d --name meu-banco \
>     -e POSTGRES_PASSWORD=segredo \
>     -e POSTGRES_USER=ana \
>     -p 5432:5432 \
>     -v dados-postgres:/var/lib/postgresql/data \
>     postgres:16-alpine
c3d4e5f6a1b2c3d4e5f6a1b2c3d4e5f6a1b2c3d4e5f6a1b2c3d4e5f6a1b2c3d4e5f6a1b2c3d4e5f6a1b2c3d4e5f6a1
$ docker ps
CONTAINER ID   IMAGE              STATUS         PORTS                     NAMES
c3d4e5f6a1b2   postgres:16-alpine Up 4 seconds   0.0.0.0:5432->5432/tcp    meu-banco
$ docker volume ls
DRIVER    VOLUME NAME
local     dados
local     dados-postgres

Agora os dados do banco sobrevivem ao container. A Ana testa: cria uma tabela, apaga o container, sobe outro com o mesmo volume:

$ docker exec meu-banco psql -U ana -d postgres -c "CREATE TABLE teste (id int);"
CREATE TABLE
$ docker rm -f meu-banco
meu-banco
$ docker run -d --name meu-banco -e POSTGRES_PASSWORD=segredo -e POSTGRES_USER=ana \
>     -p 5432:5432 -v dados-postgres:/var/lib/postgresql/data postgres:16-alpine
$ docker exec meu-banco psql -U ana -d postgres -c "\dt"
 teste   « a tabela continua lá, no volume

docker volume rm: remover um volume

$ docker volume rm dados
dados

Sem erro, o comando devolve o nome do volume removido. Mas se algum container estiver usando o volume, o Docker recusa:

$ docker volume rm dados-postgres
Error response from daemon: remove dados-postgres: volume is in use - [c3d4e5f6a1b2]
Volume em uso não pode ser removido: Error response from daemon: remove dados-postgres: volume is in use - [c3d4e5f6a1b2]. Pare e remova o container primeiro (docker rm -f meu-banco) e só depois rode o docker volume rm. E lembre: apagar o volume apaga os dados de vez — não tem lixeira. Se quiser guardar, faça backup antes (veja abaixo).
Erro de digitação no nome: docker volume rm dados-postgre (faltando o s) dá Error response from daemon: volume dados-postgre does not exist — o Docker não adivinha nem sugere. O docker volume ls antes ajuda a acertar o nome.

Backup de um volume (duas formas)

Como o volume é uma pasta no host (/var/lib/docker/volumes/dados-postgres/_data), dá para empacotar com tar. A forma mais segura é usar um container auxiliar que monta o volume e o destino do backup — assim você não mexe no Mountpoint direto (o que pode corromper bancos rodando):

$ docker run --rm \
>     -v dados-postgres:/dados:ro \
>     -v /home/ana/backups:/backup \
>     alpine tar czf /backup/dados-postgres.tar.gz -C /dados .
$ ls -lh /home/ana/backups
dados-postgres.tar.gz   187MB   « backup pronto no host

Para restaurar, é o inverso: monte o volume (vazio ou não) e descompacte dentro dele. Em produção, prefira o backup nativo do banco (pg_dump) — o tar do volume só vale com o banco parado ou em modo consistente.

docker volume prune: limpar volumes não usados

Com o tempo, volumes de containers antigos vão sobrando. O prune apaga todos os volumes que nenhum container está usando:

$ docker volume prune
WARNING! This will remove all local volumes not used by at least one container.
Are you sure you want to continue? [y/N] y
Deleted Volumes:
dados-antigos
uploads-teste

Total reclaimed space: 1.24GB

Para só listar os volumes "órfãos" sem apagar nada, use docker volume ls -q --filter dangling=true (vimos acima).

Cuidado: o prune é destrutivo e não pergunta volume por volume — só mostra o aviso inicial. Ele pula os volumes em uso, mas "em uso" significa "referenciado por algum container existente" — um container parado também conta como uso. Só rode quando tiver certeza de que os volumes órfãos realmente não prestam. E nunca rode docker system prune -a --volumes sem ler antes — isso apaga também imagens (aula docker system prune).

Copiar arquivos para dentro e fora de um volume: docker cp

Às vezes você precisa jogar um arquivo para dentro de um volume (um dump de banco para restaurar, um certificado novo) ou puxar algo de dentro dele, sem entrar no container. O docker cp faz essa ponte entre o host e o container — e funciona com volumes porque o caminho do volume existe dentro do container:

$ docker cp /home/ana/backup.sql meu-banco:/tmp/backup.sql
Successfully copied 2.56kB to meu-banco:/tmp/backup.sql
$ docker exec meu-banco psql -U ana -d postgres -f /tmp/backup.sql   « restaurou o dump
$ docker cp meu-banco:/var/lib/postgresql/data/postgresql.conf /home/ana/postgresql.conf.bak
Successfully copied 4.12kB to /home/ana/postgresql.conf.bak   « puxou a config para o host

O primeiro copia do host para o container (e cai no volume, se o destino estiver nele); o segundo copia do container para o host. Útil também para inspecionar: docker cp meu-banco:/var/lib/postgresql/data/PG_VERSION /tmp/.

docker cp vs. editar direto no Mountpoint: evite editar arquivos direto em /var/lib/docker/volumes/…/_data no host — o Docker não sabe que você mexeu ali, e bancos como o Postgres podem corromper os dados. Use docker cp (ou um container auxiliar) para entrar e sair de volumes.

Um volume em vários containers (compartilhamento)

Nada impede dois containers de montarem o mesmo volume — é um jeito comum de compartilhar arquivos entre eles (ex.: um container gera relatórios, outro serve eles por HTTP):

$ docker run -d --name gerador -v dados-compartilhados:/dados alpine sh -c "while true; do date > /dados/hora.txt; sleep 5; done"
$ docker run -d --name web -p 8080:80 -v dados-compartilhados:/usr/share/nginx/html:ro nginx:alpine
$ curl http://localhost:8080/hora.txt
qui 24 nov 13:45:12 -03 2025   « o arquivo que o gerador escreveu, servido pelo nginx

Os dois containers enxergam a mesma pasta ao mesmo tempo. Cuidado com bancos de dados nesse modo: dois Postgres apontando para o mesmo volume corrompem os dados — banco não se compartilha assim (a não ser em modo cluster, que é outra história).

Script de backup reutilizável

Com o que vimos, dá para guardar o backup num scriptzinho. A Ana salva isso como backup-volume.sh na home dela:

#!/bin/bash
# arquivo: backup-volume.sh — empacota um volume nomeado em tar.gz na pasta ~/backups
VOLUME="$1"                       # nome do volume (ex.: dados-postgres)
DESTINO="$HOME/backups"           # pasta dos backups no host
mkdir -p "$DESTINO"
docker run --rm \
    -v "$VOLUME":/dados:ro \
    -v "$DESTINO":/backup \
    alpine tar czf "/backup/$VOLUME-$(date +%F).tar.gz" -C /dados .
echo "Backup de $VOLUME salvo em $DESTINO"

Uso: ./backup-volume.sh dados-postgres. Repare no :ro: o container auxiliar lê o volume mas não consegue alterá-lo — o backup não corrompe o original.

Resumo dos subcomandos

ComandoO que faz
docker volume create dadosCria o volume nomeado dados; aceita --label chave=valor e --driver.
docker volume lsLista todos os volumes. -q = só os nomes; --filter label=… ou --filter dangling=true = filtra.
docker volume inspect dadosMostra o JSON completo do volume, com Mountpoint, Driver e Labels (próxima aula).
docker volume rm dadosRemove o volume — só se nenhum container estiver usando.
docker volume pruneRemove todos os volumes locais não usados por nenhum container (destrutivo!).
SintomaCausa
volume is in use - […]Tem container (até parado) usando o volume: docker rm ele antes
volume … does not existNome errado (confira com docker volume ls)
Volume aparece vazio no ls mas tem dadosOs dados estão no Mountpoint do host — docker volume inspect mostra onde

Missão: crie um volume chamado dados com docker volume create dados e depois confirme com docker volume ls — o nome dados deve aparecer na lista.

Missão extra: liste os volumes com docker volume ls e olhe a coluna DRIVER — o driver padrão é local.

Resumo

  • Volumes nomeados são objetos do Docker gerenciados pelo subgrupo docker volume; o driver padrão é o local (pasta em /var/lib/docker/volumes/<nome>/_data).
  • docker volume create dados cria e devolve o nome; aceita --label para etiquetar (e filtrar depois). O docker run -v dados:… cria o volume sozinho se não existir.
  • docker volume ls lista tudo; -q dá só os nomes; --filter dangling=true mostra os órfãos; --filter label=… filtra por etiqueta.
  • docker volume rm remove só se nenhum container usar — senão volume is in use. Apagar volume apaga os dados de vez (faça backup antes: tar via container auxiliar).
  • docker volume prune apaga todos os volumes não usados de uma vez — destrutivo, use com dangling=true na cabeça.
  • Nomes descritivos (dados-postgres) e labels salvam a sua vida daqui a meses.
