docker logs

Todo container guarda o que imprime no stdout/stderr (o que apareceria no terminal se ele estivesse grudado na sua tela). O docker logs mostra isso — mesmo depois que o container parou. É a primeira coisa que se olha quando "o serviço não subiu".

Você vai aprender
  • docker logs NOME: a saída inteira do container.
  • -f: acompanhar em tempo real (igual tail -f; Ctrl+C sai).
  • --tail N, --since 10m, --timestamps.
  • Logs de container parado (hello-world) e a diferença entre logs e exec.
  • Que os logs somem quando o container é apagado (docker rm).

A cena: o site da Ana não abre

Ela subiu o Nginx com -d (segundo plano), então não viu nada na tela. O primeiro passo de qualquer debug: olhar os logs.

$ docker run -d --name meu-site nginx:alpine
$ docker ps
… Up 3 seconds   meu-site

Missão: com um nginx rodando (docker run -d --name meu-site nginx:alpine), rode docker logs meu-site.

$ docker logs meu-site
/docker-entrypoint.sh: /docker-entrypoint.d/ is not empty, will attempt to perform configuration
/docker-entrypoint.sh: Looking for shell scripts in /docker-entrypoint.d/
/docker-entrypoint.sh: Launching /docker-entrypoint.d/10-listen-on-ipv6-by-default.sh
10-listen-on-ipv6-by-default.sh: info: Enabled listen on IPv6 in /etc/nginx/conf.d/default.conf
/docker-entrypoint.sh: Launching /docker-entrypoint.d/20-envsubst-on-templates.sh
/docker-entrypoint.sh: Launching /docker-entrypoint.d/30-tune-worker-processes.sh
/docker-entrypoint.sh: Configuration complete; ready for start up

Repare na última linha: Configuration complete; ready for start up — o Nginx está no ar. Se aqui aparecesse um erro (ex.: nginx: [emerg] invalid number of arguments…), era esse o problema.

docker logs meu-site
"Mostre tudo o que o container meu-site já imprimiu" (dá para passar ID curto também, e vários nomes).
/docker-entrypoint.sh: …
Linhas do script de inicialização da imagem oficial do Nginx — cada imagem imprime o que quiser aqui.

-f: acompanhar em tempo real

Com -f (de follow), o comando fica grudado mostrando as linhas novas, como o tail -f de um arquivo:

$ docker logs -f meu-site
… (linhas antigas)
172.17.0.1 - - [24/Nov/2025:13:40:01] "GET / HTTP/1.1" 200 615   « cada acesso ao site aparece aqui na hora
^C                                          « Ctrl+C sai do modo follow (o container CONTINUA rodando)

Cada requisição que chega no Nginx vira uma linha de log (é o "access log"). Ctrl+C só solta a sua tela do log — o container segue vivo (confira com docker ps).

--tail: só o final

$ docker logs --tail 20 meu-site    « só as últimas 20 linhas
$ docker logs --tail 50 -f meu-site « últimas 50 + continua seguindo

--since: só as recentes

$ docker logs --since 10m meu-site   « só o que foi impresso nos últimos 10 minutos
$ docker logs --since "2025-11-24T13:00:00" meu-site   « ou uma data/hora exata

--timestamps: com hora em cada linha

$ docker logs --timestamps meu-site
2025-11-24T13:40:01.123456789Z /docker-entrypoint.sh: Configuration complete; ready for start up
2025-11-24T13:41:10.987654321Z 172.17.0.1 - - "GET / HTTP/1.1" 200 615
ComandoQuando usar
docker logs XVer tudo o que o container já imprimiu (debug geral).
docker logs -f XAcompanhar ao vivo (ver requisições chegando, erros na hora).
docker logs --tail 100 XSó o final (logs grandes).
docker logs --since 30m X"O que aconteceu só agora há pouco?"
docker logs --timestamps XCorrelacionar horário dos logs com outros eventos.

Logs de container parado (hello-world)

O logs funciona também em container parado — é justamente quando você mais precisa (o processo morreu e você quer saber por quê):

Missão: rode docker run --name meu-hello hello-world (o container imprime e sai) e depois docker logs meu-hello para ver a mensagem de novo, mesmo parado.

$ docker run --name meu-hello hello-world
… Hello from Docker! …
$ docker ps -a
… Exited (0) 5 seconds ago   meu-hello
$ docker logs meu-hello

Hello from Docker!
This message shows that your installation appears to be working correctly.
…

Erros e avisos

Logs somem com docker rm

Os logs ficam grudados no container. Se você apagar o container (docker rm), os logs vão junto. Se precisar guardar, redirecione para um arquivo: docker logs meu-site > logs.txt. Em produção, o certo é configurar um driver de log (ex.: json-file com rotação, ou enviar para um sistema central) — aula Drivers de log.

Erro real: container que não existe 
$ docker logs nao-existe
Error response from daemon: No such container: nao-existe

Nome errado ou container já apagado — confira com docker ps -a.

Logs de uma aplicação real (ex.: API Node)

Um programa seu imprime o que quiser — e vira log. Veja uma API mínima em Node dentro de um container:

$ docker run -d --name api -p 3000:3000 node:22-alpine node -e "require('http').createServer((q,s)=>{console.log(new Date().toISOString()+' '+q.method+' '+q.url);s.end('ok')}).listen(3000)"
$ curl -s http://localhost:3000/ola
ok
$ docker logs api
2025-11-24T13:40:01.123Z GET /ola
$ docker logs -f api     « e cada chamada nova aparece na hora:
2025-11-24T13:41:55.456Z GET /ola
2025-11-24T13:41:58.789Z GET /outra

É assim que se debuga um serviço rodando em segundo plano: console.log no código vira linha de log, e docker logs -f mostra na hora.

Onde os logs ficam no host?

Por padrão (driver json-file), o Docker guarda os logs em um arquivo JSON por container, em /var/lib/docker/containers/<ID>/<ID>-json.log (no Linux). Dá para ler direto, mas o certo é usar docker logs. Se os logs estão enchendo o disco, configure a rotação na hora do run:

$ docker run -d --log-opt max-size=10m --log-opt max-file=3 --name api node:22-alpine …
« guarda no máximo 3 arquivos de 10MB (30MB no total) por container — quando enche, apaga o mais antigo

Isso e outros drivers (syslog, journald, enviar para um servidor central) têm aula própria: Drivers de log e rotação.

Container que imprime demais pode encher o disco

Sem limite (--log-opt max-size), um container que imprime em loop (um erro que se repete) pode gravar gigabytes no -json.log e encher o disco da máquina. Em produção, sempre configure rotação ou um driver externo.

Filtrando os logs (grep) e contando erros

O docker logs joga tudo na tela; no terminal dá para filtrar com grep:

$ docker logs api | grep -i error          « só linhas com "error"
$ docker logs api | grep -c "GET /ola"     « quantas vezes acessaram /ola
12
$ docker logs --since 1h api | tail -50    « última hora, só as últimas 50 linhas

Logs no Compose (vários containers de uma vez)

Quando o projeto sobe com Compose (nível 2), dá para ver os logs de todos os serviços juntos ou de um só:

$ docker compose logs            « tudo, misturado (cada linha ganha o nome do serviço na frente)
web-1  | 172.17.0.1 - "GET / HTTP/1.1" 200
api-1  | 2025-11-24T13:40:01 GET /ola
$ docker compose logs -f api       « só do serviço "api", ao vivo
$ docker compose logs --tail 20 db
"Não aparece nada no logs"

Se o docker logs está vazio, o programa provavelmente não imprime nada no stdout (ou imprime em arquivo). programa que loga em arquivo dentro do container precisa de volume nesse arquivo — ou você lê com docker exec X cat /var/log/app.log. Outro caso clássico: o processo escribe para o stderr e você está vendo só stdout — o docker logs mostra os dois juntos, então se estiver vazio de verdade, o programa não está logando.

Salvando os logs antes de apagar o container

Se o container vai ser apagado e você quer guardar o histórico:

$ docker logs meu-site > logs-meu-site.txt 2>&1    « stdout E stderr no arquivo
$ docker logs --since 2025-11-24 meu-site >> log-dia.txt   « só o do dia, anexando
$ wc -l logs-meu-site.txt
1284

O 2>&1 manda o stderr (erros) para o mesmo lugar do stdout — no Docker ambos já aparecem juntos no logs, mas o redirecionamento vale para qualquer comando.

Resumo

  • docker logs X mostra tudo o que o container imprimiu no stdout/stderr — funciona rodando ou parado.
  • -f acompanha em tempo real (Ctrl+C solta a tela, o container continua); --tail N pega só o final; --since 10m filtra por tempo; --timestamps põe hora em cada linha.
  • É a primeira ferramenta de debug: "o serviço não subiu? olha os logs".
  • Logs ficam grudados no container: docker rm apaga eles junto. Para guardar: redirecione para arquivo ou configure driver de log.
  • Erro real: No such container: X. Não confunda com docker exec (roda comando novo dentro do container).
