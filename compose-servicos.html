Serviços, portas, variáveis e volumes no Compose

Cada entrada em services: é um serviço — e cada serviço vira um container. As chaves dentro dele fazem o mesmo papel das flags do docker run: ports é o -p, environment é o -e, volumes é o -v. Se você já entendeu o docker run, aqui é só transcrever — desta vez num arquivo que dá para versionar e compartilhar.

Você vai aprender
  • Como o nome do serviço vira o nome do container (projeto-servico-1) e vira hostname na rede interna.
  • ports nos formatos "8080:80", "127.0.0.1:8080:80", "8080" e "53:53/udp" — sempre com aspas.
  • environment em lista e em mapa, env_file e interpolação ${VAR} com arquivo .env.
  • volumes: nomeados (persistem) e bind (pasta da máquina), com :ro.
  • depends_on (ordem de subida), networks, restart e command.

Cada serviço vira um container — e um hostname

Numa pasta meuapp, o serviço web vira o container meuapp-web-1 (nome do projeto + nome do serviço + número da réplica):

$ docker compose up -d
$ docker compose ps
NAME            IMAGE              STATUS          PORTS
meuapp-web-1    nginx:alpine       Up 20 seconds   0.0.0.0:8080->80/tcp
meuapp-banco-1  postgres:16-alpine Up 20 seconds   5432/tcp

A mágica acontece na rede: o Compose cria uma rede interna para o projeto e coloca cada serviço nela com um DNS automático. Dentro do container web, o banco responde simplesmente pelo nome banco — sem IP, sem porta publicada:

$ docker exec meuapp-web-1 ping -c 1 banco
PING banco (172.18.0.3): 56 data bytes
64 bytes from 172.18.0.3: seq=0 ttl=64 time=0.123 ms

É o mesmo mecanismo da aula Containers se comunicando por nome, agora criado automaticamente pelo Compose. Por isso a aplicação da Ana configura a conexão com o banco como postgres://ana:segredo@banco:5432/app — @banco é o nome do serviço.

ports: o -p escrito no YAML

ports:
Lista de portas publicadas — equivalente ao -p do docker run (aula Publicando portas).
"8080:80"
Porta 8080 da sua máquina → porta 80 do container. Sempre com aspas: sem elas o YAML pode ler 8080:80 como número (base 60) e o Compose quebra (aula docker-compose.yml).
services:
  web:
    image: nginx:alpine
    ports:
      - "8080:80"              # http://localhost:8080 abre o container
      - "127.0.0.1:443:443"    # só o localhost da máquina alcança (mais seguro que 0.0.0.0)
      - "9000"                 # porta aleatória do host -> 9000 do container
      - "53:53/udp"            # também dá para publicar UDP
FormatoSignificado
"8080:80"Host 8080 → container 80, em todas as interfaces da máquina
"127.0.0.1:8080:80"Só o localhost da máquina alcança (nada de rede externa)
"8080:80/udp"Publica UDP em vez de TCP
"9000"Só o container; o Docker escolhe uma porta livre no host
Erro real quando a porta do host já está ocupada (outro programa usando a 8080, ou outro projeto Compose seu): 
$ docker compose up -d
Error response from daemon: driver failed programming external connectivity on endpoint meuapp-web-1 (a1b2c3d4e5f6…): Bind for 0.0.0.0:8080 failed: port is already allocated
Solução: troque a porta do host no YAML (ex.: "8081:80"), ache o culpado com sudo ss -ltnp | grep 8080, ou derrube o outro projeto com docker compose down nele.

environment: lista ou mapa — e o arquivo .env

As variáveis de ambiente aceitam dois formatos — o resultado é o mesmo (mesmo -e do docker run, aula Variáveis de ambiente):

services:
  banco:
    image: postgres:16-alpine
    environment:
      # formato lista:
      - POSTGRES_USER=ana
      - POSTGRES_PASSWORD=segredo
  # ...ou formato mapa (equivalente, mais comum em Compose):
  # environment:
  #   POSTGRES_USER: ana
  #   POSTGRES_PASSWORD: segredo

E para não deixar senhas no YAML (que vai para o git), o Compose lê um arquivo .env na mesma pasta e interpola ${VAR}:

POSTGRES_PASSWORD=segredo
POSTGRES_USER=ana
services:
  banco:
    image: postgres:16-alpine
    environment:
      POSTGRES_USER: ${POSTGRES_USER}
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD}
Aviso real quando a variável não existe: 
$ docker compose up -d
WARN[0000] The "POSTGRES_PASSWORD" variable is not set. Defaulting to a blank string.
O Compose avisa e segue com a string vazia — no caso do PostgreSQL, o banco sobe sem senha. Sempre confira o .env (e coloque .env no .gitignore!).

Também dá para carregar um arquivo inteiro de variáveis com env_file: ./config.env dentro do serviço.

volumes: nomeado (persiste) e bind (pasta da máquina)

services:
  banco:
    image: postgres:16-alpine
    volumes:
      - dados-db:/var/lib/postgresql/data   # volume NOMEADO: o Docker gerencia e os dados persistem ao "down"
  web:
    image: nginx:alpine
    volumes:
      - ./site:/usr/share/nginx/html:ro     # BIND: monta a pasta ./site da máquina (ro = somente leitura)

volumes:
  dados-db:                                 # declara o volume nomeado usado acima

A regra é a mesma do -v (aula Volumes nomeados, bind mounts e tmpfs):

  • dados-db:/var/lib/postgresql/data — volume nomeado: o Docker cria e gerencia; sobrevive ao docker compose down (só some com down -v). Use para dados (banco, uploads).
  • ./site:/usr/share/nginx/html:ro — bind mount: um atalho para uma pasta da sua máquina. Use para código em desenvolvimento (editou o arquivo, o container já vê). O :ro no fim deixa o container somente ler.
Armadilha real do bind mount: se a pasta do host não existe, o Docker cria uma pasta vazia no lugar (no Linux) — e o site parece "vazio" dentro do container: 
$ ls
Dockerfile  docker-compose.yml        « esqueci a pasta site/
$ docker compose up -d
$ docker compose exec web ls /usr/share/nginx/html
                                          « vazio! a pasta ./site foi criada vazia pela engine
Conferira o caminho relativo (sempre relativo à pasta do docker-compose.yml) antes de subir.

depends_on: a ordem de subida

O depends_on diz ao Compose para criar e iniciar o serviço depois dos que estão listados — útil para o banco subir antes da aplicação:

services:
  web:
    image: nginx:alpine
    depends_on:
      - banco

Forma longa, com condição de saúde (o serviço só sobe quando o banco estiver saudável, não apenas iniciado):

services:
  web:
    depends_on:
      banco:
        condition: service_healthy   # espera o HEALTHCHECK do banco passar
  banco:
    image: postgres:16-alpine
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U ana"]
      interval: 5s
      retries: 5
Atenção: o depends_on simples só garante a ordem, não que o banco já esteja pronto para receber conexões. Sem service_healthy, é comum ver Error: connect ECONNREFUSED 172.18.0.3:5432 na primeira subida — a API tentou conectar antes de o PostgreSQL terminar de inicializar. Solução: healthcheck + condition: service_healthy (aula HEALTHCHECK e restart policies) ou simplesmente rode o up -d de novo depois de alguns segundos.

networks, restart e command

services:
  web:
    image: nginx:alpine
    restart: unless-stopped     # se cair, o Docker reinicia (aula de políticas de restart)
    command: nginx -g "daemon off;"   # sobrescreve o CMD da imagem
    networks:
      - frontend                # este serviço entra na rede "frontend"
  banco:
    image: postgres:16-alpine
    networks:
      - frontend
      - backend

networks:                       # declara as redes nomeadas usadas acima
  frontend:
  backend:

Se não declarar networks:, todos os serviços entram na rede <projeto>_default criada automaticamente. Com redes próprias, dá para isolar: o web fala com o banco, mas o banco não é alcançável de fora (sem porta publicada).

Exemplo completo: web + banco

# docker-compose.yml — web + banco com tudo que vimos nesta aula
services:
  web:
    image: nginx:alpine
    ports:
      - "8080:80"
    volumes:
      - ./site:/usr/share/nginx/html:ro   # os arquivos do site ficam na sua máquina
    environment:
      - NGINX_HOST=localhost
    depends_on:
      - banco
    restart: unless-stopped

  banco:
    image: postgres:16-alpine
    environment:
      POSTGRES_USER: ${POSTGRES_USER}          # vem do .env
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD}  # vem do .env
    volumes:
      - dados-db:/var/lib/postgresql/data      # dados persistem no volume
    # sem ports: só os outros containers alcançam o banco pela rede interna

volumes:
  dados-db:

Resumo

  • Cada serviço vira um container projeto-servico-1 e um hostname na rede interna do projeto — os serviços se alcançam pelo nome (@banco).
  • ports: "8080:80" (host→container), "127.0.0.1:443:443" (só localhost), "9000" (porta aleatória no host), "53:53/udp"; sempre com aspas. Porta ocupada dá port is already allocated.
  • environment em lista (- NOME=valor) ou mapa; senhas vão no .env e entram com ${VAR} — variável faltando gera WARN ... Defaulting to a blank string.
  • volumes: nomeado (persiste ao down) vs bind ./pasta:/caminho:ro (pasta da máquina; se não existe, o Docker cria vazia — conferira o caminho).
  • depends_on só ordena a subida; para esperar o banco de verdade, use condition: service_healthy com healthcheck.
  • Também dá para declarar networks: próprias, restart: e command: (sobrescreve o CMD da imagem).
