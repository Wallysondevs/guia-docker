Os 3 tipos de volume — nomeado, bind e tmpfs

Tudo que um container grava na camada dele some quando o container é apagado — lembra da camada gravável do topo? O -v resolve isso apontando um lugar fora do container para dentro dele. E esse lugar pode ser de três tipos: um volume nomeado (uma caixinha gerenciada pelo Docker), uma pasta sua do computador (bind mount) ou a memória RAM (tmpfs). Nesta aula a Ana vai ver os dados do banco dela sobreviverem à troca de container.

Você vai aprender
  • Por que os dados somem sem volume (a camada gravável do container).
  • A sintaxe -v ORIGEM:DESTINO:OPÇÕES e a forma longa --mount type=….
  • Volume nomeado: para dados de aplicação e banco (o Docker cria sozinho se não existir).
  • Bind mount: para código em desenvolvimento e arquivos de config versionados.
  • tmpfs: para segredos que não podem tocar o disco.
  • Quando usar cada um (tabela de decisão) e a armadilha do -v com caminho inexistente no host.

O problema: a gaveta que some

Analogia: o container é um quarto alugado. Tudo que você guarda lá dentro (a camada gravável) vai junto quando o quarto é desalugado (docker rm). Se a Ana guarda o banco de dados dentro do container do Postgres e apaga o container, os dados vão embora — todos. O volume é como um móvel seu que fica no depósito e entra no quarto: apaga o quarto, o móvel continua.

$ docker run --rm postgres:16-alpine sh -c "echo dado > /var/lib/postgresql/data/teste.txt"
$ docker run --rm postgres:16-alpine sh -c "cat /var/lib/postgresql/data/teste.txt"
cat: can't open '/var/lib/postgresql/data/teste.txt': No such file or directory   « sumiu com o container

A sintaxe do -v

O formato geral é -v ORIGEM:DESTINO:OPÇÕES:

-v
a flag de volume do docker run.
ORIGEM
o que vai ser montado: o nome de um volume (dados) ou um caminho do host (/home/ana/site).
DESTINO
o caminho dentro do container (/var/lib/postgresql/data).
:ro
opcional: monta como somente leitura (read-only).
-v dados-postgres:/var/lib/postgresql/data        « volume nomeado
-v /home/ana/meusite:/usr/share/nginx/html:ro    « bind mount (pasta do host), somente leitura
--mount type=tmpfs,target=/segredos              « tmpfs (só memória)
ElementoExemploSignificado
-v-v dados:/app/dadosflag de volume
ORIGEMdados ou /home/ana/sitenome de volume (sem barra) ou caminho absoluto do host (com barra)
DESTINO/app/dadossempre caminho absoluto dentro do container
OPÇÕES:ro, :rw, :zro = somente leitura; z/Z = SELinux (volumes compartilhados)

Volume nomeado: banco de dados

É o caso clássico: o Postgres grava tudo em /var/lib/postgresql/data. Sem volume, cada container novo começa com o banco vazio. Com volume nomeado, os dados sobrevivem. A Ana sobe o banco dela no notebook:

$ docker run -d --name meu-banco \
>     -e POSTGRES_PASSWORD=segredo \
>     -v dados-postgres:/var/lib/postgresql/data \
>     postgres:16-alpine
f3a1b2c3d4e5f6a1b2c3d4e5f6a1b2c3d4e5f6a1b2c3d4e5f6a1b2c3d4e5f6a1b2c3d4e5f6a1b2c3d4e5f6a1b2c3d4
$ docker volume ls
DRIVER    VOLUME NAME
local     dados-postgres

Repare: ela não criou o volume antes — o Docker criou dados-postgres sozinho na primeira vez que viu esse nome. Agora o teste de fogo: apaga o container e sobe outro com o mesmo volume:

$ docker rm -f meu-banco
meu-banco
$ docker run -d --name meu-banco \
>     -e POSTGRES_PASSWORD=segredo \
>     -v dados-postgres:/var/lib/postgresql/data \
>     postgres:16-alpine
e5f6a1b2c3d4…
$ docker exec meu-banco psql -U postgres -c "\dt"   « as tabelas continuam lá!

Volume nomeado é a escolha certa para dados de aplicação, porque o Docker gerencia esses volumes com comandos próprios (docker volume …, próximas aulas): dá para listar, inspecionar, fazer backup e remover. Eles moram em /var/lib/docker/volumes/<nome>/_data no host (aula docker volume inspect mostra exatamente isso).

Bind mount: seu código em desenvolvimento

Num projeto em desenvolvimento, você quer editar o código no seu editor e ver a mudança no container na hora, sem recriar nada. É só montar a pasta do projeto dentro do container. A Ana faz isso com o site dela:

$ docker run -d -p 8080:80 \
>     -v /home/ana/meusite:/usr/share/nginx/html:ro \
>     --name meu-site \
>     nginx:alpine
a1b2c3d4e5f6a1b2c3d4e5f6a1b2c3d4e5f6a1b2c3d4e5f6a1b2c3d4e5f6a1b2c3d4e5f6a1b2c3d4e5f6a1b2c3d4e5
$ echo "<h1>Nova versão</h1>" > /home/ana/meusite/index.html
$ curl http://localhost:8080
<h1>Nova versão</h1>   « a página já mudou, sem recriar o container

O :ro no final deixa o container somente leitura — ideal para servir arquivos estáticos com segurança (o container não consegue alterar seus arquivos, mesmo se for invadido).

Outro uso comum de bind mount: um arquivo de configuração que você versiona no Git, montado no lugar certo dentro do container:

$ docker run -d -p 8080:80 \
>     -v /home/ana/nginx.conf:/etc/nginx/nginx.conf:ro \
>     --name meu-site nginx:alpine
Bind mount é caminho absoluto do host: -v meusite:/html (sem barra no início) é interpretado como nome de volume, não como pasta! O Docker criaria um volume chamado meusite vazio e montaria ele — o código não apareceria. Regra: caminho do host começa com / (ou ~/ em alguns shells — no docker run o ~ não é expandido pelo Docker; deixe o shell expandir: -v ~/meusite:/html funciona porque o Bash expande antes de passar pro Docker).

tmpfs: segredos só em memória

Alguns dados não devem nunca tocar o disco — uma chave de API, um token temporário. O tmpfs monta uma pasta na memória RAM do host: é rápida, não deixa rastro no disco e some quando o container para:

$ docker run -d --name minha-api \
>     --tmpfs /segredos:rw,noexec,nosuid,size=16m \
>     node:22-alpine node server.js
b2c3d4e5f6a1b2c3d4e5f6a1b2c3d4e5f6a1b2c3d4e5f6a1b2c3d4e5f6a1b2c3d4e5f6a1b2c3d4e5f6a1b2c3d4e5
$ docker exec minha-api sh -c "ls /segredos; mount | grep segredos"
tmpfs on /segredos type tmpfs (rw,noexec,nosuid,size=16m)   « está na RAM, não no disco

Também dá com a sintaxe longa: --mount type=tmpfs,target=/segredos. Repare que o tmpfs não existe na forma curta com -v — exige --tmpfs ou --mount type=tmpfs. As opções noexec,nosuid endurecem: o que estiver ali não pode ser executado nem trocar de usuário — bom para arquivos de senha.

-v ou --mount?

As duas formas fazem a mesma coisa. O --mount é mais explícito e legível — e é o recomendado em produção e no Compose (onde a forma curta de tmpfs nem existe):

# forma curta
-v dados-postgres:/var/lib/postgresql/data
-v /home/ana/meusite:/usr/share/nginx/html:ro

# forma explícita (type=volume | type=bind | type=tmpfs)
--mount type=volume,source=dados-postgres,target=/var/lib/postgresql/data
--mount type=bind,source=/home/ana/meusite,target=/usr/share/nginx/html,readonly
--mount type=tmpfs,target=/segredos
-v (curta)--mount (longa)
Sintaxe-v origem:destino:opcoes--mount type=…,source=…,target=…,readonly
LegibilidadeCompacta, mas crípticaAutoexplicativa — mostra o tipo

tmpfsNão aceitatype=tmpfs aceita

Armadilha do -v: se o caminho do host não existe, o Docker cria uma pasta vazia nesse caminho (com o dono root) em vez de avisar. A Ana digitou -v /home/ana/meusit:/html (erro de digitação) e o Docker criou a pasta /home/ana/meusit vazia — o site não carregou e não veio erro nenhum. Com --mount type=bind,source=/home/ana/meusit,…, o comando dá erro na hora se a origem não existir. Por isso, prefira --mount quando o caminho precisa existir de verdade.

Erros comuns na prática

Esquecer que o container vê o DESTINO, não a ORIGEM: dentro do container, o caminho é /var/lib/postgresql/data — a pasta dados-postgres (o nome do volume) não existe dentro do container. Se a app grava em /dados e você montou em /app/dados, os dados vão para a camada gravável e somem. Sempre monte no caminho que a aplicação usa de verdade (cada software tem o seu: Postgres = /var/lib/postgresql/data, Nginx = /usr/share/nginx/html, MySQL = /var/lib/mysql).
Montar volume em cima de dados existentes da imagem: quando você monta um volume vazio em cima de uma pasta que já tem arquivos na imagem (ex.: montar volume vazio em /var/lib/postgresql/data), o Docker copia o conteúdo inicial da imagem para o volume na primeira vez — então os dados não somem. Mas se montar um bind de pasta vazia do host, a pasta do host (vazia) "tampa" a da imagem. Cuidado com bind mounts em pastas populadas da imagem.
Permissões: arquivos escritos pelo container num bind mount ficam com o dono do processo dentro do container (muitas vezes root). Depois, apagar do host pode exigir sudo. Solução: rode o container com usuário não-root (-u) ou ajuste o --chown — nível 3.

Resumo

  • Sem volume, o que o container grava na camada gravável some com o docker rm. O -v monta um lugar persistente dentro do container.
  • Três tipos: volume nomeado (-v dados:/caminho, gerenciado pelo Docker, ideal para banco de dados), bind mount (-v /caminho/do/host:/caminho, ideal para código em dev e configs), tmpfs (--tmpfs /caminho, só na RAM, ideal para segredos).
  • Forma curta -v origem:destino:opções vs. longa --mount type=volume|bind|tmpfs,… — em produção e no Compose, prefira --mount.
  • Armadilhas reais: -v com caminho do host inexistente cria pasta vazia (use --mount para falhar na hora); montar no caminho errado da app (dados vão para a camada gravável); bind em cima de pasta populada da imagem "tampa" o conteúdo.
  • :ro monta somente leitura — ótimo para servir arquivos e configs com segurança.
