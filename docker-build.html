docker build — criando a imagem

O docker build é o comando que lê o seu Dockerfile e monta a imagem, instrução por instrução. Você vai rodar ele toda vez que o código ou o Dockerfile mudar — então vale a pena entender cada pedacinho: a sintaxe, o tal do "contexto", como ler a saída passo a passo e as opções que salvam tempo (e dor de cabeça). A Ana roda esse comando o dia inteiro no notebook dela; vamos acompanhar.

Você vai aprender
  • A sintaxe completa: docker build -t nome:tag ., parte por parte.
  • O que é o contexto do build, por que ele é enviado ao daemon e como medir o tamanho do envio.
  • Ler a saída passo a passo: Step N/M, ---> hash, Using cache, Successfully built/tagged — e a cara nova do BuildKit ([+] Building … FINISHED).
  • As opções que mais usamos: -f, --build-arg, --no-cache, --pull, --target, -q, --progress=plain.
  • Build a partir de uma URL ou repositório git (contexto remoto).
  • Erros reais: Dockerfile não encontrado, contexto gigante, build sem permissão.

A sintaxe, parte por parte

docker build
o comando que monta a imagem a partir de um Dockerfile.
-t minha-api:1.0
--tag: dá nome e tag à imagem (nome:tag). Você pode repetir o -t para dar várias tags à mesma imagem. Sem -t, a imagem fica sem nome (<none>).
.
o contexto do build: a pasta cujo conteúdo é enviado ao Docker. O . é "a pasta atual" — e é dentro dela que o comando procura o arquivo Dockerfile.
$ docker build -t minha-api:1.0 .

O Dockerfile que esse build lê

Para o comando fazer sentido, lembre do arquivo que ele lê — comentado linha a linha:

# arquivo: Dockerfile (na raiz do contexto)
FROM node:22-alpine            # 1. base: Node 22 enxuto (build começa aqui)
WORKDIR /app                  # 2. cria /app e passa a trabalhar nela
COPY package*.json ./         # 3. copia só os manifests (cache amigo)
RUN npm install --omit=dev    # 4. instala dependências NO build (vira camada)
COPY . .                      # 5. copia o código por último (muda toda hora)
EXPOSE 3000                   # 6. documenta a porta (não publica; isso é -p no run)
CMD ["node", "server.js"]     # 7. comando padrão quando o container inicia

Cada linha desse arquivo vira um Step N/M na saída do build — e a ordem 3→4→5 é a que deixa o cache voando (aula Camadas e cache).

O contexto do build: a pasta que viaja inteira

O Docker não manda o Dockerfile sozinho: ele compacta e envia a pasta inteira (o contexto) para o daemon, que é quem executa o build de verdade. Por isso a primeira linha da saída é sempre essa:

$ docker build -t minha-api:1.0 .
Sending build context to Docker daemon  58.37kB

Consequências práticas:

  • Só o que está no contexto pode ser copiado para a imagem com COPY. Se o seu projeto está em ~/minha-api, rode o build de dentro dela (cd ~/minha-api) ou aponte o contexto: docker build -t minha-api:1.0 ~/minha-api.
  • Quanto maior o contexto, mais lento o envio — e o envio acontece a cada build, mesmo que nada tenha mudado. Pastas grandes demais deixam tudo lento; é aí que entra o .dockerignore.
  • Segredos no contexto são perigo: se um .env está na pasta e o Dockerfile tem COPY . ., o segredo vai para dentro da imagem (aula .dockerignore).
Contexto gigante sem querer: sem .dockerignore, um node_modules de 400MB e a pasta .git são enviados ao daemon a cada build: 
$ docker build -t minha-api:1.0 .
Sending build context to Docker daemon  480.5MB   « lento e desnecessário
Com um .dockerignore listando essas pastas, o mesmo build envia míseros kilobytes. A primeira linha da saída entrega o tamanho — fique de olho nela.

Lendo a saída passo a passo (saída clássica)

Cada instrução do Dockerfile vira um Step N/M na saída. No fim, o Docker imprime o ID da imagem criada e confirma a tag:

$ docker build -t minha-api:1.0 .
Sending build context to Docker daemon  58.37kB
Step 1/5 : FROM node:22-alpine
 ---> c3d4e5f6a1b2
Step 2/5 : WORKDIR /app
 ---> Running in a1b2c3d4e5f6
Removing intermediate container a1b2c3d4e5f6
 ---> b2c3d4e5f6a1
Step 3/5 : COPY package*.json ./
 ---> d4e5f6a1b2c3
Step 4/5 : RUN npm install
 ---> Running in e5f6a1b2c3d4
Removing intermediate container e5f6a1b2c3d4
 ---> f6a1b2c3d4e5
Step 5/5 : CMD ["node", "server.js"]
 ---> Running in 1a2b3c4d5e6f
Removing intermediate container 1a2b3c4d5e6f
 ---> 2b3c4d5e6f7a
Successfully built 2b3c4d5e6f7a
Successfully tagged minha-api:1.0
Step N/M
a instrução N de M do Dockerfile sendo executada.
Running in …
o comando RUN rodou num container temporário (que será apagado já já).
Removing intermediate container …
o container temporário foi descartado; o resultado virou camada da imagem.
---> hash
o ID da camada criada naquele passo. Using cache no lugar significa que o passo foi reutilizado.
Successfully built / tagged
a imagem final foi montada e etiquetada com a tag pedida.

A cara nova: BuildKit

Nas versões recentes do Docker (Engine 23+), o build roda por padrão no BuildKit, que imprime uma saída mais bonita e paralela:

$ docker build -t minha-api:1.0 .
#1 [internal] load build definition from Dockerfile
#1 transferring dockerfile: 234B done
#2 [internal] load .dockerignore
#3 [1/4] FROM docker.io/library/node:22-alpine
#4 [2/4] WORKDIR /app
#5 [3/4] COPY package*.json ./
#6 [4/4] RUN npm install
#6 exporting layers
#7 writing image sha256:2b3c4d5e6f7a…
#7 naming to docker.io/library/minha-api:1.0
[+] Building 12.4s (8/8) FINISHED

O que muda para você: as etapas aparecem como #N [i/j], o resumo final vem como [+] Building … FINISHED, e dá para ver o cache claramente (CACHED). Para ver a saída clássica antiga, use DOCKER_BUILDKIT=0 docker build … (só para teste — o BuildKit é mais rápido).

Depois do build, a imagem aparece no docker images e pode rodar com docker run:

$ docker images minha-api
REPOSITORY   TAG   IMAGE ID       CREATED          SIZE
minha-api    1.0   2b3c4d5e6f7a   30 seconds ago   195MB
$ docker run -d -p 3000:3000 --name api minha-api:1.0
9f8e7d6c5b4a

-f: Dockerfile com outro nome ou lugar

Por padrão o comando procura o arquivo Dockerfile dentro do contexto. Com -f você escolhe outro arquivo — clássico para ter um Dockerfile.dev com hot reload ao lado do de produção:

$ ls
Dockerfile  Dockerfile.dev  src  package.json
$ docker build -f Dockerfile.dev -t minha-api:dev .
…
Successfully tagged minha-api:dev

O -f pode apontar para um arquivo fora do contexto (ex.: docker build -f docker/Dockerfile.prod -t minha-api:1.0 .) — desde que o arquivo exista, o contexto continua sendo o ..

Erro real: -f apontando para arquivo que não existe. docker build -f Dockerfile.prod . numa pasta sem esse arquivo dá failed to read dockerfile: open Dockerfile.prod: no such file or directory — mesmo erro de quando o Dockerfile padrão falta. Confira o nome e o caminho.

O cache: rebuilds que voam

Se nada mudou desde o último build, cada passo imprime Using cache (ou CACHED no BuildKit) e o build termina em segundos — o Docker reutiliza as camadas prontas (aula Camadas e cache do build):

$ docker build -t minha-api:1.0 .
Sending build context to Docker daemon  58.37kB
Step 1/5 : FROM node:22-alpine
 ---> Using cache
Step 2/5 : WORKDIR /app
 ---> Using cache
Step 3/5 : COPY package*.json ./
 ---> Using cache
Step 4/5 : RUN npm install
 ---> Using cache
Step 5/5 : COPY . .
 ---> 3c4d5e6f7a8b
Successfully built 3c4d5e6f7a8b

Para forçar o build do zero, ignorando o cache: docker build --no-cache -t minha-api:1.0 . — útil quando você desconfia que uma camada antiga está envenenando o build.

Build a partir de URL ou git: contexto remoto

O contexto não precisa ser uma pasta local: pode ser um repositório git ou uma URL que contenha um Dockerfile na raiz (ou num subdiretório, com #branch/:subdir):

$ docker build -t meu-app:git https://github.com/meu-org/meu-app.git
$ docker build -t meu-app:git https://github.com/meu-org/meu-app.git#main:docker

O Docker clona o repositório (raso) e builda a partir dele. Útil para CI: builda direto do código no GitHub, sem precisar baixar nada antes. A segunda forma aponta para a subpasta docker/ do branch main.

Quando dá errado

Dockerfile não encontrado: rodar o build na pasta errada (sem cd) dá ERROR: failed to solve: failed to read dockerfile: open Dockerfile: no such file or directory. Como consertar: cd para a pasta do projeto ou passe o contexto: docker build -t app ~/projeto.
Permissão negada ao enviar o contexto: se a pasta tem arquivos que o usuário do Docker não pode ler, o envio falha com permission denied ao montar o contexto. Como consertar: ajuste as permissões da pasta ou rode com o usuário que tem acesso (o Docker no Linux normalmente exige que o usuário esteja no grupo docker — aula Instalar o Docker).
Espaço em disco cheio no meio do build: o daemon guarda as camadas em /var/lib/docker; se o disco enche, o build morre com no space left on device. Como consertar: docker system df para ver o uso e docker system prune para limpar (aulas de espaço em disco e limpeza).
Comando inválido dentro do RUN: se o RUN chama um comando que não existe na imagem base, o build falha naquele passo e mostra a saída do erro: 
$ docker build -t app .
…
Step 4/5 : RUN apt install vim
 ---> Running in e5f6a1b2c3d4
/bin/sh: apt: not found        « o Alpine não tem apt (é apk)!
error: failed to solve: process … did not complete successfully
Como consertar: use o gerenciador certo da base (apk no Alpine, apt no Debian) — trocar de base no meio do build não adianta.

Resumo

  • docker build -t nome:tag .: o . é o contexto (pasta enviada ao daemon, com o Dockerfile dentro); o -t etiqueta a imagem.
  • A primeira linha da saída (Sending build context …) mostra o tamanho do envio — se estiver em MB/GB, crie um .dockerignore.
  • Cada instrução vira um Step N/M; passos inalterados aparecem como Using cache e o build voa. No BuildKit moderno, a saída vem como #N [i/j] e termina com [+] Building … FINISHED.
  • Opções do dia a dia: -f (outro Dockerfile), --build-arg (valor para ARG), --no-cache (build do zero), --pull (base atualizada), --target (etapa do multi-stage), -q (só o ID), --progress=plain (logs de CI).
  • O contexto pode ser remoto: docker build https://github.com/org/repo.git builda direto do git.
  • Erros reais: Dockerfile não achado (pasta errada), contexto gigante sem .dockerignore, no space left on device, comando inexistente no RUN (gerenciador errado da base).
