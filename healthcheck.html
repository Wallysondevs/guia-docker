HEALTHCHECK e políticas de restart

A Ana subiu a API da Loja Aurora com --restart unless-stopped e achou que estava tudo resolvido. Na primeira madrugada, o banco de dados caiu por um instante, a API travou esperando a conexão — e continuou com status Up no docker ps, porque o processo dela não tinha morrido; só estava travado. O site ficou fora do ar até de manhã. Nesta aula você aprende a diferença entre "o processo está vivo" e "a aplicação responde": o HEALTHCHECK testa a saúde de dentro do container, e a política de restart faz o Docker reagir quando o processo morre. Juntos, são a primeira linha de auto-recuperação.

Você vai aprender
  • Por que Up no docker ps não basta (processo vivo ≠ app respondendo).
  • HEALTHCHECK no Dockerfile: CMD curl -f http://localhost/ || exit 1 e as flags de tempo.
  • Healthcheck direto no docker run: --health-cmd, --health-interval, etc.
  • Ver a saúde no docker ps (healthy/unhealthy) e no docker inspect.
  • Políticas de restart: no, always, on-failure, unless-stopped — tabela comparativa.
  • O limite do Docker puro: unhealthy não reinicia sozinho (quem faz isso é o orquestrador).

A ideia: termômetro vs. pessoa viva

O status Up do container é como dizer "a pessoa está viva": o coração bate, mas ela pode estar desmaiada. O healthcheck é o termômetro: de tempos em tempos, o Docker pergunta de dentro do container "você está bem?" e anota a resposta. Se a resposta vier errada várias vezes seguidas, o status muda para unhealthy — e quem olha esse status (um load balancer, um orquestrador, um script seu) pode agir.

HEALTHCHECK no Dockerfile

A instrução diz ao Docker como testar o container de tempos em tempos. A regra: o comando deve devolver código de saída 0 (saudável) ou diferente de 0 (doente):

FROM nginx:alpine
COPY site/ /usr/share/nginx/html/

HEALTHCHECK --interval=30s --timeout=5s --start-period=10s --retries=3 \
  CMD curl -f http://localhost/ || exit 1
HEALTHCHECK
Inicia a definição do teste de saúde da imagem.
--interval=30s
De quanto em quanto tempo o teste roda (padrão 30s).
--timeout=5s
Se o teste passar desse tempo, conta como falha (padrão 30s).
--start-period=10s
Janela inicial em que falhas não contam — dá tempo da app subir (padrão 0s). Essencial para apps que demoram para iniciar.
--retries=3
Quantas falhas seguidas mudam o status para unhealthy (padrão 3).
CMD curl -f http://localhost/ || exit 1
O comando de teste. curl -f devolve erro se o HTTP não for 2xx/3xx; || exit 1 garante saída 1 nesse caso. Dá para usar HEALTHCHECK NONE para desligar um healthcheck herdado da imagem base.

Imagens sem curl (como as distroless) podem usar wget -q -O /dev/null http://localhost/ ou um binário de healthcheck próprio compilado junto com a app (em Go é comum embutir um /healthz no próprio servidor e testar com o binário estático).

Healthcheck direto no docker run

Para imagens de terceiros que não têm HEALTHCHECK, dá para definir na hora de subir o container:

$ docker run -d --name web -p 8080:80 \
>     --health-cmd "curl -f http://localhost/ || exit 1" \
>     --health-interval 30s \
>     --health-timeout 5s \
>     --health-start-period 10s \
>     --health-retries 3 \
>     nginx:alpine
f3a1b2c3d4e5f6a1b2c3d4e5f6a1b2c3d4e5f6a1b2c3d4e5f6a1b2c3d4e5

As flags equivalentes no docker run são --health-*; no Compose, os campos são healthcheck: com test, interval, timeout, retries e start_period.

Vendo a saúde: docker ps e docker inspect

Depois de alguns segundos, a coluna STATUS ganha o estado de saúde entre parênteses:

$ docker ps
CONTAINER ID   IMAGE          STATUS                          PORTS                   NAMES
f3a1b2c3d4e5   nginx:alpine   Up 45 seconds (healthy)         0.0.0.0:8080->80/tcp    web
c3d4e5f6a1b2   minha-api:1.0  Up 2 minutes (unhealthy)        3000/tcp                api
b5e6f7a8b9c0   redis:7-alpine Up 3 minutes (health: starting)                    cache

Os três estados: starting (ainda na janela de --start-period), healthy e unhealthy. O detalhe dos últimos testes fica no inspect:

$ docker inspect web --format '{{.State.Health.Status}}'
healthy

$ docker inspect api --format '{{range .State.Health.Log}}{{.Start}} → exit {{.ExitCode}}: {{.Output}}{{"\n"}}{{end}}'
2025-01-15T10:00:00Z → exit 1: curl: (7) Failed to connect to localhost port 3000

Esse log de health é ouro para debugar: diz quando começou a falhar e o que o teste viu (o output do comando).

Importante: no Docker puro, unhealthy não reinicia o container sozinho — ele só muda o status (e aparece como erro em load balancers que respeitam health, que param de mandar tráfego para ele). Quem recria o container quando fica unhealthy é o orquestrador (Swarm/Kubernetes). Numa máquina só, dá para fazer um script simples que lê o status e dá docker restart — ou usar o restart policy abaixo para o caso de o processo morrer.

Políticas de restart: o container volta sozinho

O --restart diz o que acontece quando o processo do container morre (crash, exit, OOM kill) ou quando o daemon reinicia:

PolíticaComportamentoQuando usar
noPadrão. Nunca reinicia sozinho.Jobs pontuais, containers de teste (ex.: --rm).
alwaysSempre reinicia — mesmo se você deu docker stop manual; volta quando o daemon subir.Serviços críticos que devem estar sempre no ar, mesmo depois de stop acidental.
on-failureReinicia só se o processo sair com código de erro (ex.: Exited (1)). Aceita limite: on-failure:5 (tenta 5 vezes, depois desiste).Workers/jobs que podem falhar e devem tentar de novo.
unless-stoppedComo o always, mas respeita o stop manual — se você parou de propósito, ele não volta.Recomendada para produção na máquina única.
$ docker run -d --name web --restart unless-stopped -p 8080:80 nginx:alpine
f3a1b2c3d4e5f6…

$ docker ps -a
CONTAINER ID   IMAGE          STATUS           PORTS                   NAMES
f3a1b2c3d4e5   nginx:alpine   Up 5 seconds     0.0.0.0:8080->80/tcp    web
… depois de um crash …
CONTAINER ID   IMAGE          STATUS                        PORTS                   NAMES
f3a1b2c3d4e5   nginx:alpine   Up 2 seconds (health: starting)  0.0.0.0:8080->80/tcp   web   « voltou sozinho

A política atual aparece no inspect: docker inspect web --format '{{.HostConfig.RestartPolicy.Name}}' → unless-stopped. E dá para mudar depois: docker update --restart always web.

Missão: suba um container com a política --restart=unless-stopped (no simulador, use = na flag) e depois confira com docker ps e docker inspect web.

HEALTHCHECK + restart: exemplo completo

A combinação que a Ana usa na API da Loja Aurora em produção (máquina única, sem orquestrador ainda):

$ docker run -d --name api \
>     --restart unless-stopped \
>     --health-cmd "curl -f http://localhost:3000/health || exit 1" \
>     --health-interval 20s \
>     --health-timeout 5s \
>     --health-start-period 15s \
>     --health-retries 3 \
>     -p 3000:3000 \
>     ana/minha-api:1.0
f3a1b2c3d4e5f6…

Agora o container (1) é testado a cada 20s (e fica unhealthy se o /health falhar 3 vezes) e (2) se o processo morrer, o Docker o reinicia sozinho. Sem esses dois, a pane é descoberta pelo cliente — como aconteceu naquela madrugada.

Cenário real: o healthcheck que salvou o Black Friday

Numa loja online, a API principal tinha um vazamento de memória: a cada pico de acesso, ela travava (processo vivo, sem responder). O docker ps mostrava Up o dia todo — ninguém percebia. Depois de adicionar HEALTHCHECK CMD curl -f http://localhost/health, o load balancer passou a ver unhealthy nos picos e tirou a réplica do ar; o Swarm recriou a réplica sadia na hora. O cliente nem notou. Sem o healthcheck, o travamento só era descoberto pelos erros 502 no site.

Erros comuns

Healthcheck que usa ferramenta que a imagem não tem: HEALTHCHECK CMD curl … numa imagem distroless (sem curl) marca tudo como unhealthy mesmo com a app perfeita. Teste o comando dentro da imagem antes: docker run --rm IMAGEM curl -f http://localhost/. Em distroless, use o binário de health da própria app ou wget (também não tem… o jeito é embutir o check na app, ex.: um endpoint /healthz testado por um binário estático compilado junto).
--start-period esquecido em app lenta: banco de dados e apps Java demoram 30-60s para subir; sem --start-period, as falhas do início contam para o unhealthy e o container fica marcado como doente forever. Sempre configure --start-period (ou start_period no Compose) maior que o tempo de subida.
Healthcheck que testa a porta errada: testar http://localhost/ quando a app sobe na porta 3000 dá connection refused e status unhealthy — confira a porta real no dockerfile-expose-env.html (EXPOSE/ENV) da imagem.

Resumo

  • Up = processo vivo, não = app respondendo. O HEALTHCHECK testa de dentro: exit 0 = saudável, outro código = doente.
  • No Dockerfile: HEALTHCHECK --interval --timeout --start-period --retries CMD …; no run: --health-cmd e amigos.
  • Status no docker ps: (health: starting), (healthy), (unhealthy); log dos testes no docker inspect.
  • Restart policies: no (padrão), always, on-failure[:N], unless-stopped (recomendada em produção).
  • No Docker puro, unhealthy não reinicia sozinho — é o orquestrador (Swarm/K8s) que recria a réplica.
  • Erros comuns: testar com ferramenta que a imagem não tem (curl em distroless), esquecer --start-period em app lenta, porta errada no teste.
