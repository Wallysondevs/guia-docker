Camadas e cache do build

Uma imagem não é um bloco único: ela é uma pilha de camadas (layers), uma para cada instrução do Dockerfile. E é essa pilha que dá ao docker build o seu superpoder: o cache. Entender isso muda a ordem que você escreve o Dockerfile — e transforma builds de minutos em builds de segundos. A Ana sentiu essa diferença na pele; vamos ver por quê.

Você vai aprender
  • Que cada instrução do Dockerfile vira uma camada só de leitura, e que o container ganha uma camada gravável no topo.
  • Como o cache funciona: passo reutilizado aparece como Using cache (ou CACHED no BuildKit).
  • A regra do cache: se um passo muda, ele e todos os seguintes são refeitos.
  • Por que a ordem importa: dependências antes, COPY . . sempre por último.
  • docker history para ver as camadas da imagem e quanto cada uma pesa.
  • Como invalidar o cache de propósito: --no-cache, --pull e o truque do ARG CACHEBUST.

A analogia: o bolo de camadas

Pense na imagem como um bolo de camadas (daí vem o nome layer). Cada instrução do Dockerfile despeja uma nova camada em cima da anterior: a base (FROM) é a primeira camada; o WORKDIR adiciona uma quase vazia; cada RUN e cada COPY adicionam a sua, com o resultado do comando ou os arquivos copiados. Nenhuma camada pode ser alterada depois de pronta — só dá para empilhar em cima.

E o container? Quando ele roda, o Docker coloca uma camada gravável no topo da pilha. É nessa camada que o container escreve (arquivos de log, banco de dados local, arquivos temporários). Apagar o container apaga só essa camada do topo — as camadas da imagem, embaixo, continuam intactas. É por isso que um container não "estraga" a imagem de origem.

CamadaÉ gravável?Some quando?
Camadas da imagem (FROM, RUN, COPY…)Não — só leituraSó quando a imagem é apagada (docker rmi)
Camada do container (a do topo)Sim — é onde o container escreveQuando o container é removido (docker rm)

Cada instrução vira uma camada

Quando o build executa um RUN, COPY, ENV etc., o resultado vira uma camada só de leitura, empilhada em cima da anterior. Veja o Dockerfile da Ana e as camadas que ele gera:

$ docker build -t minha-api:1.0 .
Step 1/5 : FROM node:22-alpine      ← camada da imagem base (189MB)
Step 2/5 : WORKDIR /app              ← camada (quase vazia, só muda o metadado)
Step 3/5 : COPY package*.json ./     ← camada com os manifests (2kB)
Step 4/5 : RUN npm install           ← camada com o node_modules (~45MB)
Step 5/5 : COPY . .                  ← camada com o código-fonte (12kB)

Repare nos tamanhos: a camada do npm install é de longe a mais pesada. É por isso que você não quer refazê-la a cada mudancinha de código — e o cache existe justamente para isso.

Camadas são compartilhadas: se duas imagens usam a mesma base (node:22-alpine), elas compartilham as camadas da base no disco — você não baixa 189MB duas vezes. É outro motivo para escolher bases oficiais populares.

O cache: cada passo é reutilizado se nada mudou

O build guarda o resultado de cada instrução. No próximo build, para cada passo ele compara: a instrução mudou? os arquivos que ela usou mudaram? Se não, ele pula o passo e imprime Using cache. A Ana muda uma linha do server.js e rebuilda:

$ docker build -t minha-api:1.0 .   « mudei só um arquivo de código
Sending build context to Docker daemon  58.37kB
Step 1/5 : FROM node:22-alpine
 ---> Using cache
Step 2/5 : WORKDIR /app
 ---> Using cache
Step 3/5 : COPY package*.json ./
 ---> Using cache
Step 4/5 : RUN npm install
 ---> Using cache            « node_modules não foi recriado!
Step 5/5 : COPY . .
 ---> 3c4d5e6f7a8b            « só o código foi recopiado
Successfully built 3c4d5e6f7a8b

Build em segundos, porque só o último passo foi refeito. No BuildKit moderno, o passo reutilizado aparece como CACHED:

$ docker build -t minha-api:1.0 .
#1 [internal] load build definition from Dockerfile
#2 [1/4] FROM docker.io/library/node:22-alpine
#3 [2/4] WORKDIR /app  CACHED
#4 [3/4] COPY package*.json ./  CACHED
#5 [4/4] RUN npm install  CACHED
#6 [5/5] COPY . .                  « esse refez
[+] Building 1.2s (5/5) FINISHED
A regra do cache: se um passo muda, ele é refeito — e todos os passos depois dele também, porque cada camada depende da anterior. Mudar o FROM refaz tudo; mudar só o último COPY refaz só ele.

Ordem errada vs. ordem certa

O erro que mais atrasa build de iniciante: copiar o código antes de instalar as dependências.

Ordem errada invalida tudo: se o COPY . . vem antes do RUN npm install, qualquer mudança no código invalida o cache do npm install — e ele roda de novo do zero (minutos a cada build): 
# RUIM: código antes das dependências
FROM node:22-alpine
WORKDIR /app
COPY . .                 ← muda toda hora (inclui o código)
RUN npm install          ← cache quebrado a cada mudança de código
CMD ["node", "server.js"]
O COPY . . muda a cada edição, e tudo depois dele é refeito — o npm install de 45MB vai pro ralo a cada build.

A ordem certa separa o que muda sempre do que muda pouco:

# BOM: dependências primeiro, código por último
FROM node:22-alpine
WORKDIR /app
COPY package*.json ./   ← muda só quando as dependências mudam
RUN npm install         ← fica em cache na maioria dos builds
COPY . .                ← o código muda toda hora, mas está no fim
EXPOSE 3000
CMD ["node", "server.js"]

Com essa ordem, trocar uma linha do server.js e rebuildar refaz só o último COPY — o npm install continua em cache. A aula COPY, ADD e WORKDIR mostrou essa mesma ordem no exemplo completo.

O que mudaCom a ordem certa, o que é refeito
Um arquivo de código (server.js)Só o COPY . . final — build em segundos
Uma dependência nova (package.json)O COPY package*.json, o RUN npm install e o COPY . .
O Dockerfile inteiro (ex.: trocar a base)Tudo, do FROM em diante
NadaNada — tudo Using cache

Dependências de outras linguagens

A mesma lógica vale para qualquer linguagem — mude só o gerenciador e o arquivo de manifesto:

# Python (pip)
FROM python:3.12-slim
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY . .
CMD ["python", "app.py"]
# Go (módulos)
FROM golang:1.23-alpine AS build
WORKDIR /app
COPY go.mod go.sum ./     # manifesto primeiro!
RUN go mod download
COPY . .
RUN go build -o app .

Vendo as camadas: docker history

O comando docker history lista as camadas da imagem, da mais nova para a mais antiga, com o comando que gerou cada uma e o tamanho:

$ docker history minha-api:1.0
IMAGE          CREATED          CREATED BY                                      SIZE      COMMENT
3c4d5e6f7a8b   2 minutes ago    COPY . .                                        12.4kB
f6a1b2c3d4e5   2 minutes ago    RUN npm install                                 45.2MB
b2c3d4e5f6a1   3 minutes ago    WORKDIR /app                                    0B
d4e5f6a1b2c3   3 minutes ago    COPY package*.json ./                           2.1kB
c3d4e5f6a1b2   3 minutes ago    node:22-alpine                                  189MB

Dá para ver claramente: a camada do npm install pesa 45MB, a do código só 12kB. Com --no-trunc, os IDs aparecem completos; com -q, só os IDs (útil em scripts). A aula Analisando camadas (dive, docker history) aprofunda a inspeção visual com a ferramenta dive.

Invalidando o cache de propósito

Às vezes você quer que um passo rode de novo — por exemplo, para baixar a imagem base atualizada ou refazer um apt upgrade de segurança:

SituaçãoO que faz o cache
Nada mudou no Dockerfile nem nos arquivos copiadosTodos os passos com Using cache — build em segundos.
Você mudou uma instrução do DockerfileEssa instrução e todas as seguintes são refeitas.
Você mudou um arquivo que um COPY usaAquele COPY e tudo depois dele são refeitos.
docker build --no-cache …Ignora o cache inteiro: todos os passos rodam de novo.
docker build --pull …Baixa a imagem base (FROM) atualizada antes de começar.
Truque do ARG CACHEBUST=1Mudar o valor do ARG quebra o cache daquele ponto em diante (útil para forçar apk upgrade): ARG CACHEBUST=1 + RUN apk upgrade, e no build: --build-arg CACHEBUST=$(date +%s).

O cache mora em disco na máquina do Docker — dá para ver o quanto ele ocupa:

$ docker system df
TYPE            TOTAL     ACTIVE    SIZE      RECLAIMABLE
Images          6         2         900MB     450MB (50%)
Containers      3         1         15MB      10MB (66%)
Local Volumes   2         1         1.2GB     600MB (50%)
Build Cache     24        0         3.4GB     3.4GB

Missão: rode docker system df no terminal abaixo e encontre a linha Build Cache — é o espaço que o cache dos builds ocupa em disco.

Missão extra: force um build ignorando o cache: rode docker build --no-cache -t minha-api:1.0 . e veja o FINISHED no fim (no simulador, o --no-cache é aceito e o build roda inteiro).

Erros e pegadinhas reais

ADD de URL quebra o cache sempre que a URL muda: ADD https://…/arquivo.tar.gz /tmp/ faz o Docker baixar de novo se o conteúdo mudou — e como o conteúdo muda sem mudar a instrução, o cache daquele passo (e de tudo depois) cai. Se a URL não tem versão no nome, cada build baixa de novo. Prefira URLs com versão/tague no nome, ou RUN curl com arquitetura explícita.
Mudar a ordem das instruções "só para organizar" refaz o build inteiro: reordenar linhas do Dockerfile muda as instruções de cada passo, e o cache só bate de passo em passo na mesma ordem. Mantenha a ordem estável; organize com comentários.
O contexto inteiro é rehashado: mesmo com COPY package.json específico, o Docker calcula o hash de todo o contexto para o passo — por isso o .dockerignore (aula .dockerignore) é o que deixa o cálculo rápido, não o COPY estreito.
Variáveis de ambiente mudam o hash: se um RUN usa $VERSAO e o ENV/ARG mudou, aquele RUN (e tudo depois) é refeito — mesmo que o comando seja igual. É o comportamento esperado; só surprises quando a variável muda sem você perceber (ex.: ARG sem padrão recebendo valor do CI).

Resumo

  • A imagem é uma pilha de camadas só de leitura, uma por instrução do Dockerfile; o container ganha uma camada gravável no topo, que some com o docker rm.
  • O cache compara cada passo: instrução igual + arquivos iguais → Using cache e o passo pula. Se um passo muda, ele e todos os seguintes são refeitos.
  • Ordem certa para cache: FROM → WORKDIR → COPY manifests → RUN install → COPY . . (código por último) → EXPOSE/CMD.
  • docker history mostra as camadas e o peso de cada uma (a do install costuma ser a maior).
  • Para invalidar: --no-cache (tudo), --pull (só a base), ou ARG CACHEBUST (um ponto). O cache ocupa disco — veja em docker system df na linha Build Cache.
  • O contexto inteiro é rehashado a cada build — por isso o .dockerignore também deixa o cache mais rápido.
