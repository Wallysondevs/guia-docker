USER — rodar como usuário não-root

A Ana finalmente colocou a API da Loja Aurora num container para testar em produção. Funcionou de primeira — até ela rodar um comando inocente para inspecionar o container e reparar que o processo lá dentro respondia root. "Ué", pensou ela, "eu criei o container, por que ele é root?". Acontece que, por padrão, todo processo dentro de um container roda como root (UID 0) — o mesmo número que o kernel da máquina enxerga. Nesta aula você vai entender por que isso é perigoso e como trocar o usuário padrão da sua imagem com a instrução USER do Dockerfile.

Você vai aprender
  • Por que root dentro do container não é "faz de conta" — e o que acontece num escape de container.
  • O atalho perigoso: montar /var/run/docker.sock dentro do container.
  • Criar usuário no Dockerfile: adduser -D (Alpine) e useradd -m (Debian/Ubuntu).
  • A instrução USER ana — e USER 1000:1000 com UID/GID explícito para volumes.
  • Auditar qualquer imagem com docker exec … whoami.
  • Quem é o usuário padrão de cada imagem oficial (tabela).
  • Um Dockerfile seguro completo, de cabo a rabo.

A ideia: quem manda no processo manda na máquina

Pense no container como um apartamento no térreo de um prédio. O porteiro (o kernel do Linux, lá fora) não deixa o morador mexer na estrutura do prédio — paredes, encanamento, quadro de luz. Essa é a barreira dos namespaces: o processo dentro do container acha que é dono de tudo, mas só enxerga o próprio apartamento.

O problema é a identidade do morador. Se o processo roda como root (UID 0), ele carrega um "crachá mestre" dentro do apartamento. Normalmente a barreira contém o estrago. Mas se algum dia a barreira tiver uma fresta — um bug no kernel, um escape de container — quem tem o crachá mestre atravessa e vira root no prédio inteiro, ou seja, na máquina real (o host).

É a mesma lógica de não deixar a chave reserva debaixo do capacho: mesmo que a porta esteja trancada, você não deixa a chave no lado de fora. Rodar como usuário comum é tirar o crachá mestre: se o atacante entrar, ele entra como "visitante", com pouquíssimos poderes.

Dentro do containerSe houver escape de container
Processo roda como root (UID 0)Atacante vira root no host — troca binários, lê senhas, abre backdoor.
Processo roda como usuário comum (UID 1000)Atacante fica preso como usuário comum — quase sem poder mexer em nada do host.

O perigo do root no container

Toda imagem que não define USER inicia como root. No notebook da Ana (ana@notebook, Ubuntu 24.04 com Docker Engine 27.3.1), a imagem oficial do Nginx responde assim:

$ docker run --rm nginx:alpine whoami
root

Repare: o comando whoami ("quem sou eu?") foi executado dentro do container e a resposta foi root. A barreira entre o container e a máquina existe (namespaces, capabilities, seccomp — próximas aulas), mas se ela falhar, o atacante já está com o crachá mestre na mão.

O atalho ainda pior: o socket do Docker

Existe um arquivo especial, /var/run/docker.sock, que é o "telefone direto" com o daemon do Docker. Quem consegue falar com ele consegue criar containers — inclusive um container privilegiado que monta a raiz do host inteiro. Montar esse socket dentro de um container é entregar a chave do prédio:

$ docker run -v /var/run/docker.sock:/var/run/docker.sock nginx:alpine …   « NÃO faça isso em produção
Nunca monte /var/run/docker.sock num container de produção. Quem controla o socket controla o daemon — e com o daemon dá para subir um container privilegiado que monta / do host: root na máquina inteira, sem precisar de nenhum bug. Ferramentas de CI às vezes usam esse socket, mas em produção a regra é outra: nada de socket. A primeira linha de defesa continua sendo não ser root: rode seus apps como usuário comum.
Cenário real: o ataque que começa num container esquecido

Numa empresa hipotética, um estagiário subiu um container de debug com -v /var/run/docker.sock:/var/run/docker.sock "só para testar". Semanas depois, um atacante explorou uma vulnerabilidade antiga nesse container de debug (que ninguém atualizava porque "era só teste"). Como o socket estava montado, ele criou um container privilegiado com -v /:/host e leu o arquivo /host/etc/shadow — as senhas de todos os usuários da máquina. O estrago não foi o bug antigo; foi a combinação bug + root + socket. Tirar qualquer uma dessas três pernas derruba a ataque.

Criando um usuário no Dockerfile

A instrução RUN roda como root durante o build — é a hora certa de criar o usuário e entregar a posse dos arquivos para ele. Depois, a instrução USER troca o usuário padrão da imagem: tudo que vier depois (e o processo final do container) roda como esse usuário. Veja o Dockerfile da API da Loja Aurora, que a Ana escreveu em ~/minha-api:

FROM node:22-alpine
WORKDIR /app

COPY package*.json ./
RUN npm install --omit=dev

COPY . .

# cria a usuária "ana" (Alpine) e entrega a pasta do app para ela
RUN adduser -D -s /bin/sh ana \
 && chown -R ana:ana /app

# tudo abaixo roda como ana, não como root
USER ana

EXPOSE 3000
CMD ["node", "server.js"]
RUN adduser -D -s /bin/sh ana
Cria a usuária ana durante o build. O RUN roda como root, por isso pode criar usuários. No Alpine, adduser -D cria usuário sem senha e sem pasta home (-D = "don't assign a password"); o -s /bin/sh define o shell dela.
chown -R ana:ana /app
Entrega a pasta da aplicação para ela ("change owner" recursivo). Sem isso, a ana não conseguiria nem ler os arquivos do app, quanto menos gravar logs ou caches.
USER ana
Define o usuário padrão da imagem: o CMD e qualquer docker run dessa imagem passam a rodar como ana. É a instrução mais importante desta aula — e a mais esquecida.
EXPOSE 3000
Documenta a porta que a app usa (não publica nada sozinha; a aula EXPOSE, ENV e ARG detalha).
CMD ["node", "server.js"]
O processo final — agora rodando como ana, não como root.

Em imagens Debian/Ubuntu

O comando equivalente é o useradd. A Ana testou a mesma API numa base node:22-slim (Debian) e usou:

$ grep -n "useradd\|USER" Dockerfile
8:RUN useradd -m -s /bin/bash ana && chown -R ana:ana /app
10:USER ana

O -m cria a pasta home (/home/ana) — no Alpine o adduser -D não cria home por padrão, e algumas aplicações precisam dela (é só tirar o -D ou usar adduser -D -H… na prática, se a app reclamar de home faltando, crie com mkdir -p /home/ana && chown ana:ana /home/ana).

Verificando com docker exec whoami

Depois de buildar a imagem segura, a Ana subiu o container e perguntou para ele quem estava no comando:

$ docker build -t minha-api:segura .
…
Successfully tagged minha-api:segura

$ docker run -d --name api -p 3000:3000 minha-api:segura
9f8e7d6c5b4a…

$ docker exec api whoami
ana

Agora a resposta é ana. Compare com a imagem oficial, que continua respondendo root:

$ docker run --rm nginx:alpine whoami
root

Esse docker exec … whoami é o truque para auditar qualquer imagem — inclusive imagens de terceiros que você vai usar: suba um container dela com --rm e pergunte quem está rodando. A regra de bolso para produção: só use imagens que não sejam root, ou imagens suas terminando com USER no Dockerfile. (O docker exec em si tem aula própria: Entrando num container rodando.)

Missão: rode docker run --rm nginx:alpine whoami no terminal abaixo e confirme que a imagem oficial do Nginx responde root. Depois imagine a sua imagem própria, com USER ana no Dockerfile, respondendo ana.

Missão extra: suba um container em segundo plano com docker run -d --name api nginx:alpine, depois rode docker ps e veja a coluna CONTAINER ID — é esse ID que você usaria num docker exec api whoami.

USER com UID/GID explícito: o truque dos volumes

Quando você monta um volume (-v, aula Volumes), as permissões valem pelo UID numérico, não pelo nome. O notebook da Ana usa UID 1000 (o primeiro usuário criado numa distro Linux comum). Se o container roda com USER 1000:1000, os arquivos que ele gravar no volume ficam no nome da própria Ana na máquina — sem "arquivo fantasma" pertencente a um número que não existe:

$ docker run --rm -v ~/dados:/app/dados --user 1000:1000 minha-api:segura whoami
ana
$ ls -l ~/dados
-rw-r--r-- 1 ana ana 4096 jan 15 10:00 pedido-123.json   « dueño certo: ana, não "1000"
--user 1000:1000
Roda o container com UID 1000 e GID 1000 — vale o mesmo que USER 1000:1000 no Dockerfile, mas na hora do docker run (útil para imagens de terceiros que você não quer rebuildar).
-v ~/dados:/app/dados
O volume continua gravável para o usuário comum, desde que o UID tenha permissão na pasta do host.

Por que isso importa: se o container rodasse como UID 65532 (um número alto, comum em imagens nonroot) e gravasse no volume, o arquivo ficaria 65532:65532 no host — e a Ana não conseguiria apagar o próprio arquivo sem sudo. Casar o UID do container com o UID do dono do volume evita essa dor de cabeça. Esse detalhe combina direto com a próxima aula: com --read-only o sistema de arquivos fecha para escrita e o volume vira o único lugar gravável.

Erro comum: esqueceu o chown e a app não sobe. Se o seu Dockerfile cria o usuário mas não entrega a pasta do app (chown -R), a aplicação quebra na inicialização com Error: EACCES: permission denied ao tentar escrever em /app — e como o processo já é o usuário comum, o erro aparece na hora, não depois. A ordem certa no Dockerfile é sempre: COPY os arquivos → RUN criar usuário + chown → USER.

Quem é o usuário padrão das imagens oficiais?

Antes de confiar numa imagem de terceiro, rode o whoami nela. Estas são as respostas mais comuns hoje:

Repare no padrão: imagens de aplicação (nginx, node, python) costumam vir como root porque o build pode precisar instalar pacotes; imagens de banco de dados (postgres, redis, mysql) já vêm com usuário dedicado, porque o próprio software exige não ser root. Para as de aplicação, o USER final é responsabilidade sua.

Dockerfile seguro completo: a API da Loja Aurora

Juntando tudo desta aula (e um pouco da aula de multi-stage, para a imagem ficar enxuta), este é o Dockerfile que a Ana usa de verdade para a API da loja:

# ---- estágio de build ----
FROM node:22-alpine AS build
WORKDIR /app
COPY package*.json ./
RUN npm install
COPY . .
RUN npm run build

# ---- estágio final (runtime) ----
FROM node:22-alpine AS runtime
WORKDIR /app
ENV NODE_ENV=production

# usuário dedicado, sem privilégios
RUN adduser -D -s /bin/sh appuser \
 && mkdir -p /app/logs \
 && chown -R appuser:appuser /app
USER appuser

COPY --from=build /app/dist ./dist
COPY --from=build /app/node_modules ./node_modules
COPY package*.json ./

EXPOSE 3000
# o processo roda como appuser: mesmo se o código tiver uma falha,
# o atacante não vira root dentro do container
CMD ["node", "dist/server.js"]

Três camadas de proteção só nesse arquivo: imagem Alpine (pequena), usuário não-root (esta aula) e build separado (multi-stage). Some ainda --cap-drop e --read-only na hora de subir — próximas aulas.

Erros comuns

Esqueci o USER no fim — e o build "limpou" depois

Um erro clássico de iniciante: colocar USER ana no meio do Dockerfile e depois um RUN que precisa de root (instalar pacote, por exemplo) — o build quebra com permission denied. Outro clássico oposto: criar o usuário, dar chown, mas esquecer o USER no fim, e o container continua root mesmo com usuário criado. A regra visual: o USER deve ser uma das últimas instruções do Dockerfile, depois de todos os RUN.

USER não existe na imagem → o container nem sobe. Se você escreve USER ana numa imagem que não tem a usuária ana (esqueceu o RUN adduser), o docker run falha na hora com Error response from daemon: unable to find user ana: no matching entries in passwd file. Crie primeiro, troque depois.
--user com nome errado dá a mesma mensagem. docker run --user anaa … (com erro de digitação) devolve o mesmo erro de "no matching entries in passwd file". Para imagens de terceiro, prefira o número: --user 1000:1000 sempre funciona, porque UID não precisa existir no /etc/passwd.

Quiz rápido

1. Por que rodar o processo do container como usuário comum é mais seguro?

2. Numa imagem node:22-alpine, qual destas linhas deixa o container rodando como usuário comum?

3. A Ana rodou docker run --rm nginx:alpine whoami e recebeu root. O que isso significa?

4. Por que faz sentido usar USER 1000:1000 (números) em vez de USER ana quando o container grava num volume?

Resumo

  • Por padrão, o processo do container roda como root (UID 0) — o mesmo UID que o kernel do host enxerga. Num escape de container, root dentro vira root fora.
  • Nunca monte /var/run/docker.sock num container de produção: quem fala com o socket controla o daemon e vira root no host.
  • Crie o usuário no build (RUN adduser -D … no Alpine, RUN useradd -m … no Debian), entregue a pasta com chown -R e finalize com USER.
  • Verifique qualquer imagem com docker run --rm IMAGEM whoami ou docker exec … whoami.
  • Para volumes, prefira UID/GID explícitos (USER 1000:1000 / --user 1000:1000) casando com o dono da pasta no host.
  • Imagens de banco (postgres, redis, mysql) já vêm não-root; imagens de app (nginx, node, python) geralmente vêm root e pedem USER seu.
  • Erros reais: unable to find user …: no matching entries in passwd file (USER antes de criar) e EACCES: permission denied (esqueceu o chown).
