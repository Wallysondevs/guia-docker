seccomp e AppArmor — perfis de segurança

A Ana já blindou o container da API da Loja Aurora por dois lados: usuário comum (aula USER) e capabilities mínimas (aula --cap-drop). Só que ainda falta uma porta: mesmo como usuário comum e sem capabilities, o processo do container ainda pode chamar qualquer uma das ~300 syscalls do kernel — abrir arquivos, criar processos, ler memória de outros processos. O seccomp é o filtro que diz quais syscalls são permitidas. O AppArmor (e o SELinux) confinam o container por outro ângulo: o que ele pode acessar no sistema de arquivos. Nesta aula você vê como as duas camadas funcionam e como aplicá-las.

Você vai aprender
  • O que é uma syscall e por que filtrá-las.
  • O perfil seccomp padrão do Docker e as syscalls que ele bloqueia.
  • Perfil seccomp próprio em JSON: --security-opt seccomp=perfil.json.
  • AppArmor: perfil docker-default e --security-opt apparmor=…; SELinux com label=….
  • A flag extra no-new-privileges (bloqueia o sudo dentro do container).
  • Tabela resumo: todas as camadas de segurança do container.

A ideia: a lista de pedidos permitidos no kernel

Toda vez que um programa quer algo do kernel — abrir um arquivo, criar um processo, falar na rede — ele faz um pedido formal chamado syscall (system call, "chamada de sistema"). O kernel tem aproximadamente 300 dessas portas de atendimento. O seccomp (de secure computing mode) é um filtro colocado na frente dessas portas: cada pedido é conferido numa lista e, se não estiver permitido, o kernel devolve erro na hora (EPERM ou ENOSYS), sem nem executar.

É como a lista de visitantes autorizados na portaria do prédio: o pedido chega, o porteiro confere a lista, e se não tiver nome lá, não entra — não importa quem seja.

O perfil seccomp padrão (já vem ligado)

Desde o Docker 10, todo container já nasce com um perfil seccomp que bloqueia cerca de 44 syscalls perigosas — incluindo mount, umount2, ptrace, bpf, init_module/finit_module/delete_module (carregar módulos do kernel), kexec_load, reboot, swapon/swapoff, sethostname, clock_settime e perf_event_open. A Ana confirma no notebook dela:

$ docker info
…
Security Options:
  apparmor
  cgroupns
  seccomp
   Profile: builtin
…

Uma syscall bloqueada não quebra o container: ela simplesmente devolve erro para o processo. É por isso que mount dentro de um container comum falha mesmo o processo sendo root:

$ docker run --rm nginx:alpine mount -t tmpfs tmpfs /mnt
mount: /mnt: permission denied.   « a syscall mount foi bloqueada pelo seccomp
Syscall bloqueada no perfil padrãoPor que é perigosa
mount / umount2Montar sistemas de arquivos do host dentro do container = caminho clássico de escape.
ptraceLer/escrever a memória de outros processos (roubar credenciais).
bpfProgramar o kernel em baixo nível — usado em vários exploits recentes.
init_module / delete_moduleCarregar/descarregar módulos do kernel do host.
kexec_load, rebootReiniciar ou trocar o kernel da máquina.
perf_event_openMedir o kernel de perto — usado para ataques de side-channel.

Perfil seccomp próprio (JSON)

Se o perfil padrão bloqueia algo que a sua app precisa — ou se você quer ser ainda mais restritivo — crie um perfil próprio em JSON e aplique com --security-opt:

{
  "defaultAction": "SCMP_ACT_ERRNO",
  "architectures": ["SCMP_ARCH_X86_64", "SCMP_ARCH_X86", "SCMP_ARCH_X32"],
  "syscalls": [
    {
      "names": ["accept", "accept4", "access", "brk", "chmod", "chown",
                "close", "connect", "dup", "epoll_wait", "exit", "exit_group",
                "fstat", "gettid", "listen", "mmap", "open", "read", "recv",
                "send", "socket", "write"],
      "action": "SCMP_ACT_ALLOW"
    }
  ]
}

A regra "defaultAction": "SCMP_ACT_ERRNO" bloqueia tudo que não estiver na lista de SCMP_ACT_ALLOW — por isso o perfil precisa listar as syscalls que o seu app usa (o exemplo acima é didático e enxuto; um app real precisa de mais).

$ docker run -d --name api --security-opt seccomp=perfil-seccomp.json -p 3000:3000 minha-api:segura
b2c3d4e5f6a1…
defaultAction
A ação padrão para qualquer syscall não listada: SCMP_ACT_ERRNO (bloqueia com erro), SCMP_ACT_ALLOW (permite) ou SCMP_ACT_KILL (mata o processo).
syscalls[].names
A lista de syscalls que fogem à regra padrão.
syscalls[].action
A ação para essas syscalls — aqui, SCMP_ACT_ALLOW.
Perfil errado = container nem sobe. Se o arquivo não existir ou o JSON estiver inválido, o daemon recusa na hora: Error response from daemon: open perfil-seccomp.json: no such file or directory (ou erro de sintaxe JSON). Dica para descobrir as syscalls do seu app: em desenvolvimento, rode com --security-opt seccomp=unconfined --cap-add SYS_PTRACE e faça um strace -c -f dentro do container; aí monte a lista de allow e volte para o perfil restritivo em produção.

AppArmor (e SELinux)

Enquanto o seccomp filtra syscalls (o que o processo pode pedir ao kernel), o AppArmor confina por perfil de aplicação (o que o processo pode acessar): regras como "esse processo não pode ler /proc/*/mem" ou "não pode escrever em /sys". No Ubuntu (o sistema da Ana), o Docker já aplica o perfil docker-default automaticamente em todo container. Confirme de dentro:

$ docker exec api cat /proc/self/attr/current
docker-default (enforce)

"enforce" quer dizer que as regras estão valendo (existe também o modo complain, que só loga). Para usar um perfil próprio, registre-o no host e aplique no container:

$ sudo apparmor_parser -r /etc/apparmor.d/meu-perfil
$ docker run -d --security-opt apparmor=meu-perfil …

Em distros com SELinux (Fedora, RHEL, Rocky), o mecanismo é análogo: use --security-opt label=… e lembre dos sufixos :z/:Z nos volumes para o container poder gravar neles (ex.: -v api-dados:/app/dados:Z).

no-new-privileges: bloqueia o sudo dentro do container

Uma flag extra muito usada em produção: --security-opt no-new-privileges diz ao kernel que o processo nunca pode ganhar privilégios novos — ou seja, um sudo ou um binário setuid dentro do container não consegue elevar para root, mesmo que exista. Combina perfeitamente com a aula USER:

$ docker run -d --name api \
>     --user 1000:1000 \
>     --security-opt no-new-privileges \
>     --cap-drop ALL \
>     -p 3000:3000 minha-api:segura
c3d4e5f6a1b2…

Com isso, mesmo que o atacante ache um binário setuid esquecido dentro da imagem, ele não consegue usar para virar root. É barato de ligar e não atrapalha apps normais.

Missão: rode um container com no-new-privileges: docker run --rm --security-opt no-new-privileges nginx:alpine (no simulador, use = na flag). Lembre: por baixo, o perfil seccomp padrão já está ativo nesse container.

As camadas na prática: um ataque passo a passo

Imagine que um atacante explorou uma falha na API da Loja Aurora e conseguiu executar comandos dentro do container. Veja o que cada camada faz com ele:

  1. Ele tenta virar root com sudo → bloqueado pelo no-new-privileges e por não haver usuário root útil (aula USER).
  2. Ele tenta mount do disco do host → syscall bloqueada pelo perfil seccomp padrão.
  3. Ele tenta ler /proc/1/mem do host → bloqueado pelo AppArmor (docker-default).
  4. Ele tenta alterar o binário da app para persistir o acesso → sistema de arquivos somente leitura (aula --read-only).
  5. Ele tenta abrir portas privilegiadas ou mudar rotas → sem capabilities (aula --cap-drop).

Nenhuma camada é perfeita sozinha — mas cada uma fecha uma porta, e o atacante precisa passar por todas.

Resumo: as camadas de segurança do container

CamadaOpção / instruçãoO que bloqueia
UsuárioUSER / --userProcesso não roda como root.
Capabilities--cap-drop / --cap-addTira os "pedaços" de poder do root.
Syscallsseccomp (perfil padrão ou --security-opt seccomp=…)Filtra as chamadas de sistema permitidas (~44 bloqueadas por padrão).
AppArmor / SELinux--security-opt apparmor=… / label=…Confina o acesso a arquivos e recursos do host.
Sistema de arquivos--read-only + --tmpfsNinguém altera o conteúdo do container.
Privilégios novos--security-opt no-new-privilegessetuid/sudo não consegue elevar privilégios.

Em produção, use as camadas juntas: usuário comum + caps mínimas + seccomp padrão + read-only + no-new-privileges. Cada uma cobre um tipo de ataque diferente.

Erros comuns

Perfil seccomp apontando para caminho errado: --security-opt seccomp=perfil.json procura o arquivo relativo ao diretório onde você rodou o comando. Se você rodou de ~/ e o arquivo está em ~/minha-api/, o erro é Error response from daemon: open perfil.json: no such file or directory. Use o caminho completo: --security-opt seccomp=$PWD/perfil.json.
App que precisa de uma syscall bloqueada: se a app usa perf_event_open ou ptrace (raro, mas acontece em ferramentas de monitoreo), o perfil padrão bloqueia e a app quebra com Operation not permitted. A solução não é desligar o seccomp (seccomp=unconfined) em produção: é fazer um perfil próprio que permita só essa syscall.
no-new-privileges quebrando sudo legítimo: se a sua imagem depende de um script que faz sudo na inicialização, com no-new-privileges o sudo falha silenciosamente (exit code 1). Em imagens modernas você nem precisa de sudo — rode direto como o usuário certo com USER.

Resumo

  • Seccomp filtra syscalls: o Docker já aplica um perfil padrão que bloqueia ~44 chamadas perigosas (mount, ptrace, bpf, módulos do kernel…).
  • Perfil próprio em JSON com --security-opt seccomp=arquivo.json; defaultAction: SCMP_ACT_ERRNO bloqueia tudo que não estiver na lista de allow.
  • AppArmor/SELinux confinam por perfil de aplicação (acesso a arquivos); no Ubuntu o perfil docker-default já vem ativo.
  • --security-opt no-new-privileges impede o processo de ganhar privilégios novos — sudo/setuid não funciona dentro do container.
  • As camadas se somam: usuário não-root + cap-drop + seccomp + AppArmor + read-only + no-new-privileges.
  • Erros reais: caminho errado do perfil JSON (no such file or directory) e app que depende de syscall bloqueada (Operation not permitted).
